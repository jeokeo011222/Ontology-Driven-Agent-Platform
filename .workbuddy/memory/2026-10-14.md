## 第八轮：核查「一份文档 → 本体/工具/Agent/工作流 → 前端自动化使用」可行性

用户设想：提交一份文档，让 AI 自动生成本体 + Agent + 相关工具，前端即可自动化使用。
核查结论：**生成段已实现且可用，断点在「绑定 → 制品 → 执行」**。以下为可复用的事实。

### 四个生成端点（已实现，同构）

- `POST /api/v1/ontologies/generate`、`/agents/generate`、`/tools/generate`、`/workflows/generate`。
- 共用 `prepareGenContext` / `readCorpus` / `llmJSON`：输入是 `source_path`（相对 `docs/资料`）或 `instructions`，
  单次同步 LLM 调用 + JSON Schema 强约束，产出全部落 **DRAFT**。
- Agent 产物含 `prompt{system,user}`、`input/output_schema`、`tools[]`（存 `dependency_manifest`）、temperature/max_output_tokens。
- 工具产物含 `input/output_schema`、`capabilities[]`、`effect_class`（READ/EXTERNAL_WRITE/INTERNAL_WRITE）。
- 工作流产物含 `definition{nodes,edges}`（节点类型 start/end/task/agent/tool/approval/condition，可带 agent_key/tool_key）。

### 断点（带证据，全部实测）

1. **工具没有执行绑定**：`registry.tool_versions` 只有 input_schema/output_schema/capabilities/
   effect_class/content_digest/status，**无 endpoint / handler / artifact 列** → 生成的工具"只有名片没有身体"。
2. **工具调用恒 503**：`POST /api/v1/tools/{id}/invoke` 校验完参数后返回
   "工具执行需经 Agent 执行器与授权/ERP 网关（未接入本进程）"。
3. **没有步进执行器**：`cmd/worker/main.go` 自述"真实调度骨架"，只做 ClaimNext/Machine.Apply/Publisher；
   `internal/agent` 与 `internal/registry` 在**生产代码里 import = 0**（仅测试引用）。
4. **四类资产互不校验**：本体生成会校验 `relations.from_class/to_class` ∈ `classes`；
   但 Agent 的 `tools[]` **不校验 tool_key 是否存在**，Agent 也不绑定 ontology 版本；工作流节点的 agent_key/tool_key 同理。
   → 一份文档产出的四类资产可能互相悬空。
5. **发布门禁四类不一致**：本体必须 VALID/APPROVED（DRAFT 直发 409）；Agent 允许 DRAFT→PUBLISHED；
   工具**没有 publish 端点**（只有 invoke）；工作流有 publish。
6. **DRAFT 已对业务用户可见**：`Store.Apps` 查 `registry.agents` **不过滤 status**（LIMIT 200），
   而 `/apps`（BusinessAppsPage，DOMAIN_ICON 已含 contract）是业务用户入口 → 生成即曝光。
7. 机制缺陷（上一轮已确认，此处同样适用）：生成**无 HTTP 幂等表**（同 source_path 重提 = 白烧 token 后 409）；
   后端**不按路由校验功能权限**（只校验会话）。

### 建议的落地设计（尚未实现）

资产包（AssetBundle）做成一等对象：`ontology.asset_bundles` + `asset_bundle_items`；
`POST /api/v1/asset-bundles/generate` 返回 202 + 任务号（不要同步串 4 次模型调用）；
生成顺序 本体 → 工具 → Agent → 工作流；生成后做**闭包校验**（所有跨资产引用必须解析，不过则整包 422 + JSON Pointer）；
工具补实现绑定（HTTP / ERP_QUERY / INTERNAL + ref + 授权策略），默认只生成 READ 类；
worker 补步进执行器（先 LLM + READ 工具）；Run 落版本锁；
统一发布门禁 + `/apps` 只列 PUBLISHED；bundle 用 **Saga + 补偿**（ADR-005：跨库无原子事务），不假装原子。

| 5 驱动流程 | 无。工作流 `definition{nodes,edges}` 与 `Report` 之间无任何接线 | ❌ |

### 关键洞察（决定实现代价）

**「产 RDF/OWL/SHACL 文件」不是必须的中间态。**
`shacl.Validate` 的输入是 Go 结构 `[]Shape`，**不是 SHACL Turtle**。所以有两条路：

- **路 A（代价小，可立即打通）**：让 AI 生成本体时**直接产出 `[]Shape` 的 JSON**，
  落成 `ontology_artifacts(artifact_type='SHACL', media_type='application/vnd.odap.shacl+json')`
  或直接进 `ontology_versions`。**绕开 Turtle 解析器这个硬断点**，规则即可执行。
  Turtle 只是 `[]Shape` 的一种序列化，可以后补。
- **路 B（完整语义）**：写 Turtle/N-Triples 解析器 + 对象存储客户端，才叫真正"产 .ttl/.owl/.shacl.ttl 文件"。
  代价大（RDF 解析要处理前缀、IRI 解析、集合、空白节点标签、字面量转义、`a` 关键字）。

### 好消息：SHACL 报告的落点**已经建好了**

迁移 `000023_complete_ontology_validation_schema.sql` 专门为此补齐：
`ontology.validation_runs` 加了 `validation_profile`（决定该类本体必需过哪些检查）+ `summary_json` + `created_at`；
并新建 `ontology.validation_findings`，列含 `severity`(INFO/WARNING/ERROR/CRITICAL)、`finding_code`、
**`focus_node`**、**`path`**、`source_reference`、`details_json` —— 与 `shacl.Result{FocusNode,Path,Component,Message,Severity}` **一一对应**。
该迁移注释直言："这正是 SHACL 报告最有价值的部分，也是前端展示校验失败原因的唯一数据源"。
→ **表等着填，校验器也写好了，中间只差接线。**

### 规则驱动流程的接线点（待实现）

`shacl.Report` → 写 `validation_runs` + `validation_findings` → `ontology_versions.status`

### 新门禁 ⑤：前端写方法 ↔ openapi（contract-lint）

三条断言，**全部经反例自证可失败**（这是本轮最重要的方法学产出）：
1. 前端调用的写端点必须在 openapi 登记 → 注入假路径后 FAIL；
2. `AsyncTask` 只能配声明了 202 的端点 → 把 201 的 `/ontologies/generate` 声明为 AsyncTask 后 FAIL；
3. `unregisteredWebEndpoints` 不得有陈旧条目 → 注入假条目后 FAIL。

手写了一个**缩进感知的 openapi 扫描器**（2/4/8 空格约定），因为 go.mod 只有 pgx + x/crypto
且 GOPROXY=off，引 YAML 库会打断离线构建。解析到的 path 数 < 30 时**fail-closed 报错**，
避免"解析器失效"被读成"零违规"。

**能力边界要写清**：它判不了"内联对象类型与响应 schema 逐字段一致"——`{accepted: boolean}`
那类正是这样漏过去的。根治靠 `web/src/api/generated/types.ts`（当前是刻意留空的占位）。

### 门禁一上线就抓出 7 处真实契约漂移（原清单未记载）

- **4 处 validate/publish 把同步 200 端点声明成 `AsyncTask`**（ontologies×2、agents、workflows）：
  页面会去轮询**不存在**的任务号；ontologies 的详情页更是把真正的结论（conforms/findings）
  **完全不展示**，只挂一个永远停在"获取任务状态…"的空面板。
- **发布说明被静默丢弃**：前端发 `{release_notes}`，后端 `publishOntologyRequest` 只认
  `{version, environment}`，且 `decodeJSONLoose` **不做** `DisallowUnknownFields` → 字段消失无声。
- **最危险的一条：发布目标环境**。前端不传 `environment`，后端默认 `DEVELOPMENT`。
  顶部栏显示"生产环境"时点发布，会静默发到开发环境。改用
  `PUBLISH_ENVIRONMENT: Record<EnvName, …>` 映射并显式传参——**用全键 Record 而非带 default 的
  switch**，将来新增环境值时编译失败而不是静默落默认分支。
- **cancel/reconcile 声明了服务端不返回的字段**：`{accepted}` vs 实际 `{id, status}`；
  `{reconciliation_id}` vs 实际 `{task_id, status_url}`。reconcile 那处**不是潜伏问题**：
  TaskDetailPage 直接渲染它，所以"相关编号"**一直显示 `—`**。
- **5 个端点前端已调用但契约与服务端都没有**：`/admin/connectors/{id}/test`、
  `/admin/subjects/{id}/disable`、`/policies/{id}/versions`（契约只有 GET）、
  `/releases/{id}/promote`、`/releases/{id}/rollback`。已登记进 `unregisteredWebEndpoints`
  并写明理由（任务 #146 跟踪补齐）。

### 规律沉淀（可复用）

1. **"包已实现 + 测试全绿" ≠ "能力可用"**：`internal/ontology/{shacl,rdfs,semantic,cache}` 2545 行、
   测试全绿、生产 import 数为 0。这是装配可达性门禁存在的理由。
2. **"返回 200 是假绿的高发区"**：SHACL 空图返回 conforms=true、未知 severity 映射到不阻断、
   未执行的三值检查写成 `true` —— 三者都是"看起来通过"。反假绿要用**正向证据**
   （"图里确实有 N 个待校验实例"），而不是"没找到反例"。
3. **同一缺陷类几乎从不只出现一次**：AsyncTask 错用在 4 个端点上、未登记端点在 5 个上。
   发现一处就该写门禁扫全仓，而不是逐个手改。
4. **"字面量类型"是契约漂移的温床**：`{accepted: boolean}` 看着无害，实际两处都错。
   TypeScript 侧的内联契约类型应当由 openapi 生成。
