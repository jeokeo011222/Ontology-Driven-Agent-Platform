### 本轮修复的三个新缺陷（均由实测暴露，非文档问题）
1. **`runstate.SchedulingClassOf` 把 CREATED/CONTEXT_BUILDING 排除在可调度集之外** → 新建 Run 无人领取、永久卡死。按第六篇 §3.1「是否可调度」列修正为 {CREATED, CONTEXT_BUILDING, READY, RUNNING}；同时 PLANNING/PLAN_VALIDATING 从可调度集移除（§3.1 标"否"），其租约过期由恢复扫描转 RECOVERING。同步修正 state_test 与 machine_test 期望。新增迁移 `000013` 对齐队列部分索引状态集。
2. **Inbox 分区表无任何分区**（000008 声明 PARTITION BY RANGE 但未建分区）→ 插入必然报 "no partition of relation"。新增迁移 `000014` 建 2026-10~2027-12 按月分区 + DEFAULT 兜底；同时补 `execution.consumer_inbox` / `consumer_inbox_dedup` 两处租户 RLS 缺口（000011 遗漏）。
3. **审计哈希链在真实 PG 上必然校验失败**（两个叠加根因）：① `event_payload` 是 JSONB，PG 会重排键（按长度+字节序）、改写数字（1e2→100）、补空格，摘要无法往返；② `timestamptz` 只有微秒精度，纳秒级 occurred_at 写读不一致。修法：迁移 `000015` 新增 `event_payload_canonical TEXT` 保存写入时确定的规范化字节，摘要改覆盖它（JSONB 列保留为可查询索引，校验时要求二者语义一致）；`Append` 在摘要前把 occurred_at 取整到微秒并与摘要使用同一值落库。
- 教训：单测全绿 ≠ 真库可用。这三处都只能靠"跑真实 PostgreSQL 的集成测试"暴露，必须保留 `-tags integration` 这条验证通道。

### 第七处修正：应用角色 odap_app 未设密码（真实启动阻断）
- **症状**：`docker compose up -d --build` 时 api/worker 必然 `FATAL: password authentication failed for user "odap_app"`。
- **根因**：迁移 `000011` 只 `CREATE ROLE odap_app LOGIN NOBYPASSRLS NOSUPERUSER;`（**未设密码**）；postgres 官方镜像对 TCP 追加 `host all all all scram-sha-256`，跨容器（非回环 IP）连接必须走密码认证。此前"全绿"未暴露，是因为：odap-pg-test 的 `pg_hba` 首行 `host ... 127.0.0.1/32 trust` 会命中**回环**连接 → 手工 `psql -h 127.0.0.1` 无需密码即成功，掩盖了缺陷；集成测试虽跨容器需要密码，但当时是**手工 ALTER ROLE** 补的。
- **为何设计书自身也埋雷**：第十六篇 §8.3 的 `ODAP_DATABASE_URL` 用的是 **owner 账号 odap**（超级用户，`rolbypassrls=t`）→ 会绕过全部 RLS，违反第二篇 §9.2。实现侧已改回 `odap_app`（正确），但漏了补密码这一步。
- **修法（单一真值来源）**：
  - 新增迁移 `migrations/platform/000017_set_app_role_password.sql`：读会话 GUC `odap.app_password`，`ALTER ROLE odap_app WITH LOGIN PASSWORD %L`；未注入时回退本地默认 `apppw`（与 .env.example 一致）。角色不存在则显式 `RAISE EXCEPTION`（不静默跳过）。
  - `cmd/migrate`：连库后解析 `ODAP_DATABASE_URL`，**仅当用户名为 odap_app** 时用 `set_config('odap.app_password',$1,false)` 注入（因此**不新增**环境变量，避免密码两处漂移）。新增 `appRolePassword()` 及表驱动测试。
  - `.env.example` 补注释说明"为何用 odap_app 而非 §8.3 的 odap"。
- **预检证据（真实集群，非回环网络）**：注入路径设 `pf_inject_pw` → 跨容器 scram 认证成功且 `is_superuser=off`；回退路径打印 NOTICE 并设 `apppw` → 认证成功；`pg_authid` 复核 `rolsuper=f, rolbypassrls=f, rolcanlogin=t, has_pw=t`。两条路径均绿。

## 修复「企业本体」页面 tone 崩溃（缺陷 #19 / #20）—— 前端状态投影与详情端点缺口

**用户上报**：`TypeError: Cannot read properties of undefined (reading 'tone')`（`/admin/ontologies` 整页白屏）。

### 三层根因（只修表面会留下两层）
1. **索引写法不安全**：`META[item.state].tone` 直接索引，运行期取值不在词表 → `undefined.tone` → 整棵 React 树卸载。前端共 **21 处**、跨 **12 个页面**。
2. **词表/字段/取值三方错位**（真正根因）：后端返回 `status`(本体级) + `latest_version_status`(版本级)，**无 `state`**；前端却按自造的小写别名 `draft/validating/...` 索引 `OntologySummary.state`。
3. **fixture 自造契约**：`web/src/api/generated/fixtures.ts` 按前端自造类型造数据（含 `state`）→ 页面"对 fixture 全绿、对真实接口必崩"。该文件头部自己写着"不改变任何契约路径与响应结构"，它违反了这条。

### 关键洞察：空数据集会让坏页面"看起来是好的"
缺陷 #19 在注入演示数据**之前**一直不存在——`/admin/ontologies` 返回空列表 → 表格一行都不渲染 → `META[item.state].tone` **从未被执行** → 逐路由体检给出"页面正常"的**假绿**。故：凡断言"页面正常"，必须**同时断言渲染出了预期数据行数**。

### 顺带修掉的后端契约违例：空列表返回 `items: null`
`store.queryMaps` 零行时返回 `nil`（`var out []map[string]any` 从未 append），调用方 `res.Items = rows` 覆盖了空切片初始化 → `{"items":null}`；而 `contracts/03 §1.4` 要求 `items` 是数组。**只在表为空时显形**（policies/audit-events/approvals/evaluations 恰好无种子数据）。修：两处改为 `out := make([]map[string]any, 0)`。

## 第二轮：用户复报"这几个页面还报同样的错" → 查出部署可送达性缺陷（#23）与端点落后于数据（#24）

### #23 入口 HTML 缺 `Cache-Control`（高：修复到不了用户）
- `web.conf.template` 只给 `/assets/` 配了 `expires 7d` + `immutable`，`location /`（SPA 回退）**没有任何缓存指令**。
- 形成不可自愈的链：旧 `index-<old>.js` 被 immutable 缓存 **7 天** → 入口 `index.html` 走**启发式缓存**、从不回源 → 浏览器永远跑旧包。
- **判据（可复现）**：`curl -sI` 看入口头（原先只有 `ETag`/`Last-Modified`，**无 `Cache-Control`**）；`curl /assets/index-<旧哈希>.js` → **404**。
- **用户列表本身就是证据**：4 个"有数据→崩"的页面（旧包行为）+ `/admin/models` 不在列（旧包是静默假空、不报错）。
- 修：`location = /index.html` 加 `no-store, no-cache, must-revalidate` + `Pragma: no-cache`；`/assets/` 收敛为**单一** immutable 头（原先 `expires` + `add_header` 产生**两个** `Cache-Control`）；`/favicon.svg` 加 `no-cache`。
- 验证：`/`、`/index.html`、`/admin/workflows` 三处均 `no-store`（深链经 `try_files` 内部重定向也命中 `location = /index.html`）；资产头恰好 1 条。
- **新增门禁 `tools/http-entry-cache-verify.sh`（7 项）**：入口 no-store / 资产单条 immutable / 入口引用的哈希可访问 / **服务端哈希 == 本地 `web/dist`**。纯 curl，不依赖浏览器。

> **核心教训**：`docker compose up` 成功、19/19 路由体检、目录门禁全绿——**对 #23 全是假阴性**，因为它们每次新起浏览器，从不复用用户的缓存。**"验证环境"与"用户环境"不同，是这类缺陷能长期存活的根本原因。**

## 2026-10-13（第四轮）新增项目启动 / 停止 / 重启脚本

用户要求"给项目编写启动脚本、停止脚本和重新启动脚本"，并选择放在**仓库根目录**。

### 交付
- `start.sh` —— 前置检查（docker / 守护进程 / compose v2 / curl / `.env` / 必需变量全查）→
  `docker compose up -d`（`--build` 可选，`--profile` 可选）→ **校验一次性迁移 job 退出码** →
  **轮询真实探针**等待就绪 → 打印入口与演示身份提示 → 可选 `--seed` / `--reseed`。
- `stop.sh` —— `compose down`（保留数据卷）；`--purge` 删除数据卷，**必须同时 `--yes`**，
  否则拒绝并打印完整警告（含会丢什么、如何恢复）；停止后校验容器已清空、列出保留的卷。
- `restart.sh` —— 复用 stop + start 并透传选项；**明确拒绝 `--purge`**（重启不该丢数据）。

### 关键设计取舍
- **`up -d` 返回 0 ≠ 可用**：迁移 job 是 `restart:"no"` 的一次性容器，失败时依赖它的
  api/worker 根本不启动，compose 只在 stderr 提一句。故脚本自己查 `ps -a` 的
  `State|ExitCode`，失败即打日志并退出 1。
- **就绪用 `/readyz` 而非 `/healthz`**：前者真的查库（`{"checks":{"database":"ok"}}`）。

### 4 条活体实测缺陷（现有全部门禁全绿，即全为假阴性）

- **L1 租户上下文注入有两套实现**：`store.setTenant()` 写 `SET LOCAL app.current_tenant_id = $1`
  ——(a) PostgreSQL 的 `SET` **不接受参数占位符**（探针：`syntax error at or near "$1"`）；
  (b) 即便如此，`app.current_tenant_id` 与 RLS 函数 `app.current_tenant_id()` 读取的
  `app.tenant_id` 是**两个不同 GUC**（探针：两列均 NULL）。
  → 实测 `/api/v1/admin/users`、`/admin/organizations`、`/admin/ontology-categories` 全 **500**
  `"SET LOCAL tenant 失败"`；走 `s.TenantTx` 的 `/admin/roles`、`/role-bindings`、`/overview` 为 200。
  爆炸半径：3 文件 23 个方法；但**"含 setTenant 的方法数 ≠ 受损端点数"**（role-bindings 走的是另一份实现）。
- **L2 `/api/v1/auth/` 前缀遮蔽**：`root.Handle("/api/v1/auth/", authChain)` 比 `/api/v1/` 更具体，
  而 `publicMux` 只挂 register/login → **logout 与 session 恒 404**（Go 默认纯文本 `404 page not found`）。
  两个契约门禁只断言 `routes()` **声明表**，从不发 HTTP，故全绿。
- **L3 `POST /ontologies/{id}/validate` 恒 503**（诚实报错），但 `PublishOntology` 允许
