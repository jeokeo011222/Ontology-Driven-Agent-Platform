# ODAP 第十一篇：可观测性、审计证据链与企业级运维治理详细设计

版本：V1.0 · 技术栈：Go + React/TypeScript + PostgreSQL · 部署模式：企业私有化部署

> **本篇 scope 标签**：`[MVP-V1.0]` 结构化日志与统一关联标识（§4/§5）、关键事件审计账本（§8）、事件摘要 + 段内哈希链 + 检查点 + 签名归档四级完整性（§9）、证据包构建与验证（§10/§11）、审计写入 fail-closed 分级与 SLO（§9.7）、Prometheus + PostgreSQL 结构化日志的最小三支柱（§3.3）；`[V1.5]` 分布式 Trace 后端与分层采样（§6，按 §3.3 决策后置）、语义缓存类高级指标（§7.4 之后）、治理中心完整前端（§14）；`[V2]` 亿级事件全量重算验证、跨区域多活审计归档。审计事件物理 DDL 以第二篇 §8.1 `audit.audit_events` 为权威，本篇 §9.2 概念 Schema 与其列名对齐；告警分级统一为 SEV1/SEV2/SEV3（§7.3）。

## 1. 设计目标与总体原则

在前十篇中，ODAP 已经建立了企业本体运行时、Agent Runtime、Harness、ERP Gateway、LLM Gateway、异步事件总线和分布式可靠执行机制。

但当平台真正进入企业生产环境后，还必须回答一组新的问题：

- 一笔业务为什么得到这个结果？
- 哪个 Agent 做出了什么判断，依据了哪些数据和企业制度？
- 模型调用了什么工具，工具实际执行了什么操作？
- 本体验证、授权决策、人工审批和 ERP 回执是否能够相互印证？
- 某个任务停滞、失败或产生异常业务结果时，运维人员如何快速定位？
- 企业安全负责人能否发现越权访问、异常重试、敏感数据泄露和可疑操作？
- 如果有人修改或删除审计记录，平台能否发现？
- 当企业需要内部审计、合规检查或事故调查时，能否导出一份完整、可验证的证据包？

本篇要建设的不是简单的日志页面，而是 ODAP 的生产运行治理与业务证据体系。

核心目标是让每一次重要的智能体行为都具备四种能力：

1. 可观察：知道系统正在做什么、哪里出现异常。
2. 可追溯：从最终业务结果反向追踪完整执行链路。
3. 可验证：检查关键事实、规则依据、审批和操作回执之间是否一致。
4. 可治理：让有权限的人员能够调查、处置、复核和审计异常。

### 1.1 本篇与前十篇的关系

业务执行层

Agent Runtime · Harness · Ontology Runtime · ERP Gateway

可观测性

Logs / Metrics / Traces

审计证据链

Events / Evidence / Receipts

企业运维治理中心

告警 · 事故 · SLO · 审计 · 风险处置 · 证据导出

本篇与第十篇的职责边界如下：

- 第十篇解决事件如何可靠传递、任务如何恢复。
- 第十一篇解决事件和任务如何被观测、记录、解释、验证和审计。
- 两篇共同依赖前文的 Run、Step、Approval、ERP Operation、Ontology Version 和模型调用记录。

重要设计原则：业务审计记录、技术遥测和正式证据不能混为一谈。

一条日志可以帮助定位问题，但不能自动证明某项业务操作已经发生；一条 Trace 可以展示调用顺序，但不能自动证明授权合法；一个模型给出的解释也不能代替企业制度、权威数据和真实回执。

## 2. 设计范围与非目标

### 2.1 本篇覆盖范围

| 模块                | 主要职责              |

| Alert Manager     | 告警规则、分组、升级与抑制     |

### 2.2 本篇不负责的事情

本篇不重新实现：

- Agent 的任务编排与状态机。
- 本体推理、SHACL 验证和业务规则引擎。
- 权限决策与人工审批流程。
- ERP 操作账本和外部结果对账。
- 消息代理自身的底层持久化机制。

这些模块负责产生权威业务状态。本篇负责统一关联、记录、展示和验证相关证据。

## 3. 总体架构设计

建议将 ODAP 可观测性与治理体系分为六层。

L1 · 业务与管理操作

API · Agent · Harness · Ontology · LLM · ERP · 管理员

L2 · 统一遥测采集层

Trace Context · Structured Logs · Metrics · Audit Events

L3A · 技术遥测

日志、指标、Trace、告警

L3B · 业务审计

业务事件、操作记录、审批轨迹

L4 · 证据构建与完整性验证

Evidence Bundle · Digest · Signature · Chain Verification

L5 · 企业运维治理中心

业务追溯、运行健康、事故管理、合规审计、证据导出

### 3.1 六层架构的核心职责

L1：业务执行层

各模块在发生重要事件时，通过统一 SDK 或领域服务写入遥测和审计记录。业务模块不应自行定义一套互不兼容的日志格式。

L2：统一采集层

为日志、Trace、指标和审计事件注入一致的上下文，完成格式校验、数据分类、敏感字段处理和路由。

L3：双通道持久化

技术遥测与业务审计使用不同的保留、访问与完整性策略。技术遥测可以采样；关键业务审计不应因为 Trace 采样而丢失。

L4：证据构建层

将业务输入、版本锁定信息、事实引用、规则结果、审批记录和 ERP 回执组合成可验证的证据包。

L5：治理中心

为业务人员、平台运维、安全人员和审计人员提供各自授权范围内的查看、调查、告警处理和证据导出能力。

### 3.2 推荐技术选型

第一阶段不必把所有组件都做成独立微服务。

| 能力                     | 建议实现                      |
| ---------------------- | ------------------------- |
| 统一遥测协议                 | OpenTelemetry             |
| Go Trace 与 Metrics SDK | OpenTelemetry Go SDK      |
| 指标存储与告警                | Prometheus 兼容方案           |
| Trace 存储               | Tempo、Jaeger 或同类系统        |
| 日志存储                   | Loki、OpenSearch 或企业现有日志平台 |
| 业务审计                   | PostgreSQL                |
| 证据制品                   | 企业对象存储                    |
| 完整性校验                  | SHA-256 摘要、签名与分段归档        |
| 前端                     | React + TypeScript        |
| 服务端                    | Go                        |

以上是可选的技术组合，不是对某一具体产品的强制依赖。私有化部署应优先复用企业已有的监控、日志和对象存储设施。

另外，不要把 Prometheus、Trace 后端或日志搜索引擎当作业务审计账本。这些系统适合查询和诊断，不应成为唯一的正式业务证据存储。

### 3.3 MVP 三支柱成本合并：Prometheus + PostgreSQL 结构化日志，Trace 后置

三支柱（Metrics/Logs/Traces）全套引入（Prometheus + Loki/OpenSearch + Tempo/Jaeger + OTel Collector 全链路）对 MVP 是过度运维。本节显式固化成本决策：

| 支柱 | MVP（V1.0）决策 | 后置计划 |
|---|---|---|
| Metrics | Prometheus（单实例 + 本地 TSDB，抓取间隔 15s，保留 15 天） | V1.5 按租户/业务域拆分抓取与远程存储 |
| Logs | PostgreSQL 结构化日志表（§5 字段规范）+ 分区与保留期；检索走 SQL，不做全文搜索引擎 | V1.5 数据量或检索延迟触阈后引入 Loki/OpenSearch |
| Traces | **不引入 Trace 后端**；仅保留 OTel SDK 的 Trace Context 传播（span 生成后丢弃或仅落 `trace_id`/`span_id` 关联字段到日志与审计） | V1.5 引入 Tempo/Jaeger，补 §6 分层采样与长任务 Span Link |

理由：MVP 阶段排障主要依赖"统一关联标识 + 结构化日志 + 审计账本"（§4/§5/§8），Trace 的诊断增益低于其存储与运维成本；把 Trace 后置到 V1.5 可减少两个需要持续运维的组件。

存储量估算公式（用于容量规划，按实测修正系数 k 校准）：

```
logs_storage_per_day  = R x S x (1 + k)          # R=每秒日志条数, S=平均单条字节(含索引放大)
metrics_storage       = C x T x I x D            # C=活跃序列数, T=每序列字节, I=抓取间隔倒数(每日样本数), D=保留天数
audit_storage_per_day = A x P x (1 + k)          # A=每日审计事件数, P=平均单事件字节(含哈希链列)
evidence_storage      = E x B                    # E=每日证据包数, B=平均证据包制品字节(对象存储)
total_daily           = logs_storage_per_day + audit_storage_per_day + metrics_storage/D + evidence_storage
```

示例量级（仅演示公式用法，非承诺值）：R=200 条/s、S=1 KB、k=0.3 ⇒ 日志约 21 GB/天；A=5 万事件/天、P=2 KB ⇒ 审计约 100 MB/天。审计表按 §9.2 的按月分区与归档策略落地后，在线库只保留近 90 天，冷数据进对象存储。当 `logs_storage_per_day` 超过单库可承载写入（以压测为准）或审计在线分区超过 90 天窗口，即触发 V1.5 的日志后端选型 ADR（选型框架见 ADR-003）。

## 4. 统一关联模型：让一笔业务贯穿所有系统

ODAP 的业务流程可能跨越多个 Agent、模型、插件、数据库、审批服务和 ERP。没有统一关联模型，就会产生大量无法拼接的孤立日志。

### 4.1 核心关联标识

建议在全平台统一以下标识：

| 标识                    | 含义           | 生命周期             |
| --------------------- | ------------ | ---------------- |
| `tenant_id`           | 企业租户         | 跨越该租户范围内的请求      |
| `business_request_id` | 原始业务请求       | 从用户发起到业务流程结束     |
| `run_id`              | Harness 运行实例 | 一次完整执行           |
| `step_id`             | 执行步骤         | 一个逻辑工作单元         |
| `attempt_id`          | 执行尝试         | 某个步骤的一次尝试        |
| `trace_id`            | 分布式调用链       | 一条技术追踪链          |
| `span_id`             | Trace 中的调用单元 | 单次操作或调用          |
| `event_id`            | 业务事件         | 一个不可混淆的事件实例      |
| `operation_id`        | 外部操作         | 一次逻辑 ERP 或外部业务操作 |
| `approval_id`         | 审批实例         | 一次审批生命周期         |
| `evidence_bundle_id`  | 证据包          | 一组可验证证据          |
| `incident_id`         | 事故实例         | 一次运维或安全事件        |

这些标识各自承担不同作用，不能全部用 `run_id` 代替。

例如，一个 Run 可以重试同一个 Step 多次；一个 Step 可以调用多个模型请求；一个 ERP Operation 也可能经历多次状态查询和对账尝试。

### 4.2 关联关系

```
business_request_id
  └── run_id
       ├── trace_id
       │    ├── span: Agent Planner
       │    ├── span: LLM Gateway
       │    ├── span: Ontology Runtime
       │    └── span: ERP Gateway
       ├── step_id
       │    ├── attempt_id: 1
       │    └── attempt_id: 2
       ├── approval_id
       ├── operation_id
       └── evidence_bundle_id
```

这里的图是逻辑关联图，而不是严格的一对一关系。Trace 可能因异步执行而分叉；同一个业务请求也可能创建多个 Run。

### 4.3 Go 上下文传递

建议为业务上下文定义统一结构：

```

package telemetry

type BusinessContext struct {
    TenantID        string
    BusinessRequestID string

    RunID           string
    StepID          string
    AttemptID       string

    OperationID     string
    ApprovalID      string
    EvidenceBundleID string
}

```

在实现中，应将该结构与 OpenTelemetry 的 Trace Context 结合使用。Trace ID 用于技术调用链，业务 ID 用于业务追溯；两者应分别保留。

需要特别注意：

- 租户身份应由可信认证与授权上下文提供。
- 不允许通过客户端自定义 `tenant_id` 获得跨租户访问能力。
- 业务 ID 可以作为检索线索，但不代表调用者有权查看相关数据。
- 日志、Trace 和证据引用都必须在读取时执行访问控制。

### 4.4 异步场景的 Trace 关联

第十篇中的 Outbox、消息代理和 Worker 会让执行跨越进程甚至跨越较长时间。此时不能只依赖 HTTP 请求中的上下文。

发布事件时，应将必要的 Trace Context 放入消息头，并同时保留 `run_id`、`step_id`、`event_id` 等业务关联字段。

消费者收到消息后，可以根据业务语义选择：

- 在同一 Trace 中继续创建 Span。
- 在异步边界创建新的 Trace，并通过 Span Link 关联上游执行。

对于等待数小时的审批流程，强行将整个业务生命周期塞进一条极长的 Trace 并不理想。建议以业务关联 ID 串联多条 Trace，再由治理中心提供统一业务时间线。

## 5. 结构化日志设计

日志的目标是回答“某个组件在特定时间做了什么，以及为什么失败”。

ODAP 不应依赖自由文本作为唯一日志格式，而应统一为结构化事件。

### 5.1 日志分类

建议分为六类：

1. `application`：应用运行信息。
2. `execution`：Run、Step 和 Worker 执行日志。
3. `integration`：模型、工具、ERP 和其他外部系统调用。
4. `security`：认证、授权、越权拒绝和敏感操作。
5. `audit`：正式业务与管理审计记录。
6. `diagnostic`：受控的调试信息。

其中，`audit` 应写入专门的审计服务或审计表，不应只输出到普通文本日志文件。

### 5.2 统一日志字段

推荐字段：

```
{
  "timestamp": "2026-10-12T12:00:00Z",
  "level": "INFO",
  "service": "odap-worker",
  "service_version": "1.0.0",
  "environment": "production",
  "tenant_id": "tenant_01",
  "business_request_id": "req_001",
  "run_id": "run_001",
  "step_id": "step_002",
  "attempt_id": "attempt_001",
  "trace_id": "trace_001",
  "span_id": "span_001",
  "event_code": "STEP_OUTPUT_PERSISTED",
  "message": "Step output persisted",
  "duration_ms": 125,
  "result": "success"
}
```

上述值仅为格式示例，不代表实际租户、任务或 Trace。

### 5.3 日志级别规范

| 级别      | 使用场景                   |
| ------- | ---------------------- |
| `DEBUG` | 本地调试、受控诊断信息            |
| `INFO`  | 任务开始、状态转换、正常完成         |
| `WARN`  | 重试、降级、延迟、可恢复异常         |
| `ERROR` | 操作失败、依赖不可用、任务异常终止      |
| `FATAL` | 进程无法继续安全运行，需要退出或触发严重告警 |

`FATAL` 应谨慎使用，避免普通业务错误导致进程退出。

### 5.4 日志脱敏

禁止将以下信息无条件写入普通日志：

- API Key、访问令牌和密码。
- ERP 连接凭据。
- 完整的员工个人信息。
- 银行账户等高敏业务数据。
- 完整的模型 Prompt 和模型响应。
- 企业制度中的受限内容。
- 附件正文与大型业务载荷。

推荐采用白名单字段采集，而不是先记录全部内容再尝试删除敏感字段。

对于需要保留的诊断内容，应记录内容摘要、受控对象存储引用、数据分类和访问策略；有需要时通过专门的受权流程查看原始数据。

### 5.5 日志与审计的边界

例如，以下日志：

```
ERP request returned HTTP 200
```

只能说明客户端观察到某个 HTTP 响应，不能证明业务操作成功。

正式审计事件应引用 ERP Operation ID、响应验证结果、远端业务状态和回执摘要。只有经过业务层验证后，才能形成“操作成功”的正式记录。

## 6. 分布式 Trace：还原跨服务执行过程

Trace 的目标是回答“一个请求经过哪些服务、各阶段耗时多少、在哪里失败”。

### 6.1 ODAP 标准 Span 层级

以一次企业报销审核为例：

```
HTTP POST /api/v1/runs
  └── Run.Create
       └── Harness.Execute
            ├── Agent.Planner
            │    └── LLM.Generate
            ├── Ontology.Query
            ├── Ontology.Validate
            ├── Authorization.Decide
            ├── Approval.Request
            └── ERP.Operation.Dispatch
                 ├── ERP.Adapter.Request
                 ├── ERP.Receipt.Verify
                 └── ERP.Reconciliation
```

实际 Trace 应反映真实调用关系，而不是为了好看而强行生成固定层级。某些步骤可能异步执行，或者在人工审批后通过另一条 Trace 恢复。

### 6.2 Span 属性规范

建议定义统一属性：

- `odap.tenant_id`
- `odap.run_id`
- `odap.step_id`
- `odap.attempt_id`
- `odap.agent_id`
- `odap.ontology_version`
- `odap.tool_id`
- `odap.operation_id`
- `odap.approval_id`
- `odap.outcome`
- `odap.error_code`

其中，标识类属性适合用于 Trace 检索，但不应无条件作为所有指标的标签。对于敏感业务对象 ID，可采用受控映射标识或仅保存在访问受限的审计记录中。

### 6.3 Span 命名与错误处理

Span 名称应描述操作，而不是包含动态参数。例如：

- 推荐：`ontology.validate`
- 不推荐：`ontology.validate.expense_claim_123`

前者有利于聚合分析，也能避免把业务对象标识大量写入遥测索引。

发生错误时，应记录统一错误类别，例如：

- `AUTHORIZATION_DENIED`
- `ONTOLOGY_VALIDATION_FAILED`
- `MODEL_TIMEOUT`
- `ERP_OPERATION_UNKNOWN`
- `BUDGET_EXCEEDED`

错误信息应便于定位，但不能把完整 Prompt、个人信息或远端返回的敏感正文直接放进 Span 属性。

### 6.4 Trace 采样策略

建议采用分层采样：

- 普通成功请求：按配置比例采样。
- 高延迟请求：尽可能保留。
- 失败和异常请求：提高采样概率，必要时采用尾部采样。
- 安全拒绝与高风险业务操作：确保有独立的审计记录。
- 审计要求保留的业务事件：不依赖 Trace 采样。

要注意，尾部采样也不能替代审计账本。Trace 后端发生故障或采样配置变更，不应导致关键授权、审批或 ERP 操作记录丢失。

### 6.5 长任务与异步 Trace

一个 Run 可能持续数小时甚至数天，因此不建议让单个 Trace 无限延长。

建议每个关键执行阶段创建独立 Trace 或独立根 Span，通过以下标识建立业务关联：

- `business_request_id`
- `run_id`
- `step_id`
- `causation_id`
- `event_id`

这样既能保留调用链，又能避免 Trace 后端出现过长的生命周期和难以维护的 Span 结构。

## 7. Metrics 与 SLO：从“系统在线”转向“业务可靠”

企业运维不能只看 CPU、内存和服务是否存活。ODAP 还需要判断业务是否按时推进、外部操作是否能够确认、证据是否完整。

### 7.1 指标分层

建议分为四类。

基础设施指标

- CPU、内存、磁盘与网络。
- PostgreSQL 连接池、事务耗时和锁等待。
- Worker 并发、Goroutine 数量。
- 对象存储容量和请求错误率。
- 消息代理积压与消费者滞后。

应用指标

- API 请求成功率。
- 请求 P50/P95/P99 延迟。
- Go 服务错误率。
- 数据库查询失败率。
- 依赖服务健康状态。

执行指标

- Run 成功率与失败率。
- Step 重试率。
- 任务排队时间。
- Worker 租约过期率。
- 人工审批等待时间。
- 恢复成功率。

业务与证据指标

- ERP 操作确认率。
- `UNKNOWN` 外部操作积压。
- 本体验证失败率。
- 授权拒绝率。
- 证据包生成失败率。
- 审计写入延迟。
- 证据完整性验证失败数。

这些指标用于监测运行情况，不应直接替代业务正确性判断。例如，本体验证失败率突然下降不一定代表质量提高，也可能是验证步骤没有执行。

### 7.2 SLI 与 SLO

SLI 是实际观测指标，SLO 是内部服务目标。ODAP 应按业务重要程度为不同工作流定义目标，而不是为所有任务使用同一组数字。

例如：

| SLI      | 建议定义                 |
| -------- | -------------------- |
| API 可用性  | 成功处理的有效请求比例          |
| 任务启动延迟   | 从任务被接受到首次执行的时间       |
| 任务完成延迟   | 在限定业务类型和工作量内的完成时间    |
| 审计持久化延迟  | 关键审计事件持久化所需时间        |
| 证据生成成功率  | 满足证据包生成条件的任务中成功生成的比例 |
| 外部操作对账时延 | 外部结果未知到确认或转人工的时间     |

建议先收集基线，再制定目标。例如，可以先观察一周的任务启动延迟分布，再为不同业务等级制定 SLO，而不是直接承诺所有任务都在几秒内完成。

### 7.3 告警分级

告警分级统一采用 SEV1/SEV2/SEV3 三级（与事故表 `ops.incidents.severity` 枚举一致，CI 一致性 lint 校验；历史上的 P1/P2/P3 写法已废弃，不得在新规则中出现）。

SEV1 · 严重事故

可能影响数据完整性、跨租户安全、关键业务操作或审计可信度。

示例：证据完整性校验失败、发现未经授权的 ERP 写入、审计记录出现无法解释的缺口、审计哈希链验证失败。

SEV2 · 高优先级故障

关键业务持续受阻或积压接近业务截止时间。

示例：ERP 对账队列持续增长、核心任务长时间停滞、Outbox 无法正常发布、审计写入 SLO 持续跌破降级阈值（见 §9.7）。

SEV3 · 一般异常

部分服务退化，但仍有安全可控的降级路径。

示例：非关键模型供应商不可用、普通任务重试增加、单个 Worker 健康状态异常、审计 WAL 补写延迟超过预警线。

告警应配置负责人、处置手册、升级条件和恢复验证标准。单纯发送一条通知而没有明确的责任人和处置流程，不算完整的运维治理能力。

### 7.4 错误预算

对于适合使用 SLO 的平台服务，可以引入错误预算：

\\[ B\_{\text{error}}=1-\text{SLO} \\]

如果某项服务的可用性 SLO 为 99.9%，对应的错误预算为 0.1%。当错误预算快速消耗时，应减少高风险变更、加强观察或暂停非必要发布。

但错误预算适用于服务可靠性治理，不适用于放宽授权或业务正确性要求。不能因为系统错误率很低，就允许一次未经授权的 ERP 写入被视为可接受。

## 8. 业务审计模型：记录关键行为与状态变化

审计的核心问题是：谁在什么时间，基于什么上下文，执行了什么动作，结果如何，能够提供哪些验证材料？

### 8.1 必须记录的审计事件

建议将审计事件分为以下类别：

| 类别       | 记录内容                              |
| -------- | --------------------------------- |
| 身份认证     | 登录、身份提供方、会话异常、服务身份                |
| 权限治理     | Allow、Deny、RequireApproval、权限策略变更 |
| Agent 管理 | 创建、升级、发布、停用、撤销                    |
| 本体治理     | 制度来源、候选本体、验证、审核、发布、回滚             |
| 模型治理     | 模型版本、路由策略、数据策略、预算策略变更             |
| 任务执行     | Run 创建、状态转换、暂停、恢复、取消              |
| 工具执行     | 工具身份、参数摘要、执行结果、失败原因               |
| 审批       | 审批请求、审批人、决定、绑定载荷摘要                |
| ERP 操作   | 操作请求、授权引用、回执、对账与补偿                |
| 管理操作     | 用户与角色变更、配置变更、导出、重放                |
| 证据管理     | 证据生成、校验、访问、导出与归档                  |

并非每次普通查询都需要生成同等级别的正式审计记录。应根据数据等级、风险和企业政策制定审计级别，但不能因为事件数量大就遗漏关键写操作、权限决策或治理变更。

### 8.2 标准审计事件结构

```

package audit

import "time"

type AuditEvent struct {
    EventID        string    `json:"event_id"`
    TenantID       string    `json:"tenant_id"`

    ActorType      string    `json:"actor_type"`
    ActorID        string    `json:"actor_id"`

    Action         string    `json:"action"`
    ResourceType   string    `json:"resource_type"`
    ResourceID     string    `json:"resource_id"`

    Outcome        string    `json:"outcome"`
    ReasonCode     string    `json:"reason_code,omitempty"`

    BusinessRequestID string `json:"business_request_id,omitempty"`
    RunID          string    `json:"run_id,omitempty"`
    StepID         string    `json:"step_id,omitempty"`
    OperationID    string    `json:"operation_id,omitempty"`

    PolicyVersion  string    `json:"policy_version,omitempty"`
    PayloadDigest  string    `json:"payload_digest,omitempty"`
    EvidenceRef    string    `json:"evidence_ref,omitempty"`

    OccurredAt     time.Time `json:"occurred_at"`
    RecordedAt     time.Time `json:"recorded_at"`
}

```

正式实现还应包含事件 Schema 版本、服务身份、数据分类、来源引用、请求关联 ID、记录完整性元数据和必要的前后状态摘要。

`occurred_at` 与 `recorded_at` 的时间基准：`occurred_at` 由事件源服务在事件产生时采样，`recorded_at` 由审计服务落库时采样，两者分离用于发现时钟异常与补写延迟；可信时间源（RFC 3161 TSA 或企业 HSM）的接入与 `trusted_time_ref` 字段见 §9.8，验证层的"时间可信度"检查见 §11.1。

对于高风险动作，应记录足以复核决策的字段，但避免直接保存全部敏感载荷。可使用摘要、受控证据引用和受限访问记录来保持可追溯性。

### 8.3 记录拒绝事件

审计不仅要记录成功操作，还应记录关键拒绝行为，例如：

- Agent 请求了超出权限范围的工具。
- 用户尝试访问其他租户的数据。
- 本体验证发现必要事实缺失。
- 模型调用因数据分类策略被拒绝。
- 审批载荷摘要与待执行载荷不匹配。
- ERP Adapter 尝试执行不受支持的操作。

拒绝事件应区分正常业务拒绝与安全异常，避免大量正常拒绝淹没真正需要调查的异常行为。

## 9. 审计存储、不可篡改性与完整性验证

审计系统的关键要求不是简单地给表增加 `created_at`，而是能够发现记录被修改、删除、重排或替换的情况。

需要明确一个边界：哈希链只能帮助发现特定类型的篡改，不能单独保证审计系统绝对不可篡改。 如果攻击者同时控制数据库、链头和所有密钥，单靠同一数据库中的哈希字段无法建立独立信任。

### 9.1 推荐的分层完整性机制

建议从四个层次建设。

1. 事件级摘要：对规范化后的审计载荷计算 SHA-256。
2. 分段哈希链：将同一审计分区内的事件按确定顺序链接。
3. 周期性检查点：将分段最终摘要写入独立的受保护存储。
4. 数字签名与归档：由受控签名密钥签署检查点，并将归档写入具有访问控制、保留策略或 WORM 能力的存储。

其中 WORM 指写入后不能在设定保留期内被普通操作覆盖或删除的存储能力。它有助于降低篡改风险，但仍需验证管理员权限、保留锁配置和密钥管理是否真正独立。

### 9.2 审计事件表

建议采用独立 Schema。物理 DDL 以第二篇 §8.1 `audit.audit_events` 为权威；本节为概念 Schema，哈希链支撑列名与其对齐（`seq_no`/`prev_digest`/`segment_id`），避免两篇各写一套列名：

```

CREATE SCHEMA IF NOT EXISTS audit;

CREATE TABLE audit.events (
    event_id UUID PRIMARY KEY,
    tenant_id UUID NOT NULL,

    segment_id TEXT NOT NULL,
    seq_no BIGINT NOT NULL,

    event_type TEXT NOT NULL,
    schema_version TEXT NOT NULL,

    actor_type TEXT NOT NULL,
    actor_id TEXT NOT NULL,
    action TEXT NOT NULL,

    resource_type TEXT NOT NULL,
    resource_id TEXT,

    outcome TEXT NOT NULL,
    reason_code TEXT,

    occurred_at TIMESTAMPTZ NOT NULL,
    recorded_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    trusted_time_ref TEXT,

    payload JSONB NOT NULL,
    payload_digest TEXT NOT NULL,

    prev_digest TEXT,
    event_digest TEXT NOT NULL,

    trace_id TEXT,
    run_id UUID,
    step_id UUID,
    operation_id UUID,

    UNIQUE (tenant_id, segment_id, seq_no)
) PARTITION BY RANGE (occurred_at);

CREATE INDEX idx_audit_tenant_time
    ON audit.events (tenant_id, occurred_at DESC);

CREATE INDEX idx_audit_run
    ON audit.events (tenant_id, run_id, occurred_at);

CREATE INDEX idx_audit_operation
    ON audit.events (tenant_id, operation_id);

```

`trusted_time_ref` 保存可信时间戳引用（RFC 3161 token 摘要或企业 HSM 签名引用），方案见 §9.8。

防误改约束（与第二篇 §8.1 一致，DDL 层强制）：

- **只读角色分离**：应用写入使用 `audit_writer` 角色，仅授 `INSERT` + `SELECT`；查询与治理界面使用 `audit_reader` 角色，仅 `SELECT`；任何应用角色不授 `UPDATE`/`DELETE`。
- **触发器兜底**：对 `BEFORE UPDATE OR DELETE` 建触发器直接 `raise exception`，即使授权被误改也能在数据库层拒绝；修正错误数据只能追加新事件（补偿语义），不能改写历史。
- **按月分区**：表按 `occurred_at` 做范围分区（如 `audit_events_2026_10`），分区按月预创建；`seq_no` 分配器（每租户每段一个计数器行锁，§9.4）与分区解耦，避免跨分区计数竞争；归档到期的整分区 `DETACH` 后转入冷存储，不执行行级 `DELETE`。
- **保留与归档**：在线窗口默认 90 天（按企业政策调整，§12.4），超期分区归档到 WORM/对象存储并保留完整性元数据。

这是概念 Schema。实际部署还应处理审计事件的规范化序列化、索引成本、密钥轮换和迁移兼容。

### 9.3 哈希链构造

可定义：

\\[ H_i = \operatorname{SHA256} \left( D \parallel H\_{i-1} \parallel C(E_i) \right) \\]

其中：

- \\(H_i\\) 是当前事件的摘要。
- \\(H\_{i-1}\\) 是上一事件的摘要。
- \\(C(E_i)\\) 是当前事件经过规范化编码后的完整载荷。
- \\(D\\) 是固定的协议域分隔符，用于避免不同用途的摘要被错误混用。

规范化编码必须明确字段排序、字符串编码、数字格式、时间格式、空值处理和二进制字段编码。直接对任意 JSON 文本计算摘要可能因字段顺序或序列化差异产生不同结果。

### 9.3.1 段根聚合：Merkle 树

段根（`segment_root`）不取链末值，而由段内全部事件的 Merkle 树根计算：

```
leaf_i      = H(D_merkle || segment_id || seq_no || event_digest_i)
parent_node = H(D_merkle || left || right)      # 奇数节点按固定规则补齐，规则写入协议版本
segment_root = MerkleRoot(leaf_1 .. leaf_n)
```

理由与验证策略：

- Merkle 根同样覆盖段内全部事件（任一事件被篡改，根必然变化），但验证单条事件只需读取根加沿路径的 O(log n) 个中间哈希，不必顺序重放整条链。
- **亿级事件的全量重算不可行**：时间与 IO 成本随 n 线性增长，与检查点周期（§9.5）耦合后无法满足篡改发现时延 SLA。因此验证策略固定为"验证只读根 + 抽样"：常规验证只重算抽样事件的 Merkle 路径与段根比对；全量重算仅作为离线审计演练（季度或按需），不进入常规验证路径。
- Merkle 算法版本（如 `sha256-merkle-v1`）随检查点记录，算法升级必须新起段，不得在段内切换。

### 9.4 并发写入与顺序

不能简单地让多个服务分别读取当前链头、计算新摘要并写入数据库，否则并发请求可能基于同一个旧链头创建分叉。

建议为每个审计分区维护一个序号和链头：

- 分配序号时使用数据库事务和行锁，或使用能够保证顺序的单写入器。
- 在事务中记录事件、序号和前序摘要。
- 定期生成分段检查点。
- 检查点提交后，异步签名并写入独立归档。
- 验证时重算事件摘要、前序关系和检查点签名。

分区可以按租户或审计流划分。需要注意，按租户分区意味着每个租户内部的顺序可验证，但不能自动证明所有租户之间存在一个统一的全局顺序。

### 9.5 独立检查点

推荐定期生成检查点记录：

```
{
  "checkpoint_id": "checkpoint_20261012_001",
  "segment_id": "tenant_01:2026-10-12",
  "first_seq_no": 1001,
  "last_seq_no": 2000,
  "event_count": 1000,
  "segment_root": "sha256:...",
  "merkle_algorithm": "sha256-merkle-v1",
  "previous_checkpoint_digest": "sha256:...",
  "signature_key_id": "audit-signing-key-v3",
  "trusted_timestamp_ref": "rfc3161:sha256:...",
  "created_at": "2026-10-12T12:00:00Z"
}
```

该示例只展示字段结构。生产环境中，`segment_root` 应按 §9.3.1 的 Merkle 算法生成，`signature_key_id` 应引用受控密钥管理设施，而不是密钥本身，`trusted_timestamp_ref` 的可信时间源方案见 §9.8。

**检查点周期与篡改发现时延 SLA**：

- 检查点周期 **≤ 15 分钟**（按租户按段滚动；段关闭时立即生成，不等待周期）。
- **篡改发现时延 SLA = 检查点周期 + 验证周期，即 ≤ 15min + 60min = ≤ 75min**。验证周期定义为：增量验证每小时一次（重算上一检查点覆盖段的 Merkle 根，与独立存储中的检查点比对），每日一次段级全量验证（只验证根与抽样路径，见 §9.3.1）。
- 该 SLA 度量的是"发现"时延而非"发生"时延：检查点只能证明该时刻之前的历史未被篡改；检查点生成之后、下次检查点之前发生的篡改，由下次检查点或验证作业发现。
- SLA 违约（检查点延迟 > 15 分钟、验证作业失败、可信时间戳缺失或无效）按 SEV1 告警（§7.3）：审计可信度受损直接影响合规证据能力，不能静默跳过。

检查点应写入与主数据库权限边界分离的存储。验证工具需要能够读取检查点和公钥，即使主数据库中的记录被修改，也能够发现与可信检查点不一致的情况。

### 9.6 关键安全边界

- 应用服务不应具有任意更新、删除历史审计事件的权限。
- 审计写入应通过专门的服务接口或受控数据库角色执行。
- 数据库超级管理员仍然是重要的信任边界，应通过独立归档、外部检查点和权限审计降低风险。
- 签名私钥应保存在受控密钥管理系统中，不能写入应用配置文件或数据库。
- 密钥轮换后应保留验证历史签名所需的公钥与元数据。
- 审计验证失败应触发高优先级安全告警，不能静默跳过。

### 9.7 审计写入不可用时的 fail-closed 分级策略

审计不可用（数据库故障、写入超时、WAL 补写失败）时，不同风险等级的操作有不同处置。核心原则：**高危操作的审计写入失败时必须阻断执行，不得继续操作**。

| 操作类别 | 示例 | 审计写入失败时的行为 |
|---|---|---|
| 高危（fail-closed 阻断） | ERP 写操作、权限变更（角色/策略/授权变更）、证据导出 | 本地 WAL 排队重试；超过阻断超时（默认 5s，可配置）仍失败则**拒绝执行该操作**，返回 `UNAVAILABLE`（contracts/02 基础码），操作不进入执行链；已排队 WAL 条目在审计恢复后按序补写 |
| 普通（缓冲补写） | 查询、普通状态变更、一般任务事件 | 写入本地 WAL 缓冲后异步补写；补写延迟进入监控，不阻断业务 |

要点：

1. **阻断语义**：高危操作的审计事件与业务事务在同一数据库事务中提交（§16.3）。审计存储不可用导致事务无法提交时，业务操作同样不生效——这是 fail-closed 的自然结果，不需要额外回滚逻辑。若采用异步 WAL 路径（审计与业务不同库），WAL 持久化失败即等同阻断条件成立。
2. **排队重试有界**：WAL 重试采用指数退避（初始 100ms，上限 2s），重试期间业务线程占用受租户级并发限制；超时后拒绝执行并释放资源，不得无限期挂起 Worker。
3. **审计写入 SLO 与降级阈值**：同步路径审计写入延迟 P99 < 50ms；P99 > 200ms 持续 5 分钟或写入失败率 > 0.1% 持续 5 分钟，触发 SEV2 告警；WAL 积压 > 10,000 条或补写延迟 > 15 分钟，升级 SEV1。
4. **WAL 完整性**：本地 WAL 为 append-only 文件（fsync），崩溃重启后按序重放；`seq_no` 以数据库计数器为准（§9.4），WAL 重放只补写未确认条目，不重复产生审计事件。
5. **边界**：普通事件的 Outbox 发布失败按第十篇策略重试，不适用本节阻断语义；本节只约束"审计账本写入"这一条路径。

### 9.8 可信时间源：RFC 3161 与企业 HSM

`occurred_at` 与 `recorded_at` 默认取服务端数据库时钟，而本地时钟可被持有主机权限的攻击者或管理员篡改；只依赖本地时钟的审计链无法独立证明"事件确实发生在该时间"。本节定义可信时间源方案。

方案选型（按部署条件二选一或混合）：

| 方案 | 机制 | 适用条件 |
|---|---|---|
| RFC 3161 时间戳服务（TSA） | 对检查点摘要（`segment_root` + `previous_checkpoint_digest`）向受信任 TSA 申请时间戳 token，token 由 TSA 私钥签署并内含权威时间 | 可访问企业信任的 TSA（内网自建或经审批的公共 TSA 白名单） |
| 企业 HSM | 由 HSM 在受保护边界内对检查点摘要签名并附加 HSM 时钟读数，签名私钥不出 HSM | 企业已有 HSM/KMS 设施（私有化部署首选） |

接入方式：

1. 检查点生成时（§9.5），除应用签名外附加可信时间戳：`trusted_timestamp_ref` 保存 token 摘要或 HSM 签名引用，token 原文随检查点归档。
2. 高频审计事件不逐条申请 token（吞吐与成本不允许）；事件级可信时间通过"段内事件落在由可信时间戳锚定的检查点区间内"间接获得：事件 `occurred_at` 不晚于锚定检查点的权威时间，即落在该可信区间。
3. 服务启动与每班次执行一次时钟校准：本地时钟与可信时间源偏差 > 阈值（如 5s）时告警并在审计中登记校准事件；持续偏差按 SEV2 处理。
4. 密钥与 token 管理：TSA 证书链与 HSM 公钥纳入受信任密钥版本管理（§9.6）；轮换后保留验证历史 token 所需的公钥与元数据。

## 10. Evidence Service：从运行记录生成业务证据包

可观测性告诉我们系统发生了什么，审计记录告诉我们哪些关键行为被正式记录，而 Evidence Service 要解决的是：

能否将一次业务结果所依赖的输入、事实、规则、模型、审批与外部回执组合成一份可追溯、可复核、可验证的证据包？

这是 ODAP 与普通 Agent 运行平台的重要区别。

### 10.1 证据包的定位

例如，一笔报销单被自动提交时，证据包应能够回答：

- 当时使用的是哪个 Agent 版本？
- 本体、SHACL 约束和业务规则分别是什么版本？
- 报销单的关键字段来自哪里？
- 哪些字段缺失，哪些事实是推导出来的？
- 模型给出了什么建议，结构化输出是否通过 Schema 验证？
- 授权决策为什么允许该操作？
- 是否需要人工审批？审批绑定的载荷是什么？
- 实际发送给 ERP 的请求是什么逻辑版本？
- ERP 返回了什么结果，回执是否验证通过？
- 事后能否重新验证证据完整性？

### 10.2 证据类型

建议统一以下证据类别：

| 类型                   | 内容                       | 可信依据             |
| -------------------- | ------------------------ | ---------------- |
| `SOURCE_FACT`        | ERP 事实、制度条款、上传文件         | 来源标识、快照、摘要       |
| `DERIVED_FACT`       | 计算或规则推导出的事实              | 推导规则、输入事实、计算版本   |
| `MODEL_OUTPUT`       | LLM 输出或 Agent 建议         | 模型版本、请求记录、输出摘要   |
| `VALIDATION_RESULT`  | Schema、SHACL 或业务规则验证结果   | 验证器版本、规则版本、输入摘要  |
| `POLICY_DECISION`    | 授权与数据策略决策                | 主体、资源、动作、策略版本    |
| `APPROVAL_RECORD`    | 人工审批决定                   | 审批身份、时间、绑定摘要     |
| `ERP_RECEIPT`        | 外部系统回执                   | 远端引用、回执摘要、校验结果   |
| `AUDIT_REFERENCE`    | 正式审计记录引用                 | 审计事件 ID、摘要、完整性状态 |
| `EXECUTION_METADATA` | Run、Step、Attempt 与工具执行信息 | 平台权威状态与执行账本      |

这些证据的证明能力不同。比如，模型输出可以证明模型曾返回某个结果，但不能单独证明该结果真实；一个 `VALIDATION_RESULT` 也只有在验证器、输入数据和规则版本可信且可复核时，才有明确的验证意义。

### 10.3 证据包组成

建议每个证据包包含以下内容：

1. `manifest.json`：证据包清单。
2. `request.json`：经过数据分类和脱敏的业务输入摘要。
3. `version-lock.json`：Agent、本体、规则、工具、模型和映射版本。
4. `facts.json`：关键来源事实及其引用。
5. `reasoning-records.json`：可审计的决策步骤和规则轨迹，不要求保存模型全部隐式推理内容。
6. `validation.json`：Schema、SHACL、业务规则验证结果。
7. `authorization.json`：授权决策及相关策略版本。
8. `approval.json`：适用时的审批记录与绑定摘要。
9. `operations.json`：外部操作请求、状态和回执引用。
10. `audit-references.json`：关联的审计事件。
11. `integrity.json`：文件摘要、签名与验证元数据。

证据包不必将所有原始数据复制到同一个压缩文件中。敏感数据和大型附件可以使用受控引用，以降低重复存储和数据泄露风险。

### 10.4 Manifest 示例

```

{
  "apiVersion": "odap.io/v1",
  "kind": "EvidenceBundle",
  "metadata": {
    "bundle_id": "eb_001",
    "tenant_id": "tenant_01",
    "business_request_id": "req_001",
    "run_id": "run_001",
    "created_at": "2026-10-12T12:00:00Z"
  },
  "spec": {
    "purpose": "expense_submission",
    "classification": "CONFIDENTIAL",
    "agent_version": "finance-expense@1.2.0",
    "ontology_digest": "sha256:...",
    "policy_digest": "sha256:...",
    "mapping_digest": "sha256:...",
    "model_revision": "model-revision-01",
    "validation_status": "PASS",
    "business_outcome": "CONFIRMED_SUCCEEDED",
    "artifacts": [
      {
        "name": "facts.json",
        "digest": "sha256:...",
        "storage_ref": "artifact://evidence/eb_001/facts.json"
      }
    ]
  }
}

```

这里的 URI 仅为协议示例。正式实现应使用 ODAP 自己的受控制品引用格式，且不能因为证据包生成成功，就自动将业务结果标记为成功。

`business_outcome` 应来自权威业务状态。若 ERP 结果仍然未知，证据包必须明确表示未知或待对账，而不是将其转换为成功。

### 10.5 证据状态

建议定义：

- `BUILDING`：正在构建。
- `READY`：所需证据已收集，可以进行验证。
- `VERIFIED`：通过指定的完整性与规则验证。
- `INCOMPLETE`：缺少部分必要证据。
- `INVALID`：发现摘要不一致、签名无效或关键证据矛盾。
- `REVOKED`：证据包因后续发现的问题被撤销其有效使用状态，但原始记录仍保留。

`VERIFIED` 必须说明验证范围。它可以表示“文件摘要与签名有效”，也可以表示“特定规则下的业务证据检查通过”，两者不是同一个概念。

## 11. 证据链验证与业务结果复核

证据包构建完成后，还需要提供独立的验证流程。否则系统只是把各种记录打包在一起，并没有证明这些记录之间的一致性。

### 11.1 验证分层

建议分为五层：

第一层：文件完整性

- 文件是否存在。
- 摘要是否匹配。
- 清单中的文件是否齐全。
- 签名是否有效。
- 签名密钥是否属于受信任的密钥版本。
- **时间可信度**：可信时间戳是否有效（`trusted_timestamp_ref` 指向的 RFC 3161 token 或 HSM 签名，见 §9.8）；权威时间与声明时间偏差是否在阈值内。

第二层：事件完整性

- 审计事件是否存在。
- 哈希链是否连续。
- 检查点是否匹配。
- 事件是否存在重复、缺口或摘要冲突。
- 事件时间是否落在可信时间戳锚定的检查点区间内（无法锚定的事件标记为时间可信度 `UNKNOWN`，不得自动视为可信）。

第三层：版本一致性

- Agent 版本是否与 Run 锁定版本一致。
- 本体、规则、映射和模型策略是否可识别。
- 验证结果是否引用了正确的输入摘要。
- 审批是否绑定了当前待执行载荷。

第四层：业务一致性

- 授权决定是否覆盖当前主体、动作和资源。
- 审批是否适用于当前操作。
- ERP 回执是否与操作 ID 和请求摘要对应。
- 本地操作账本与外部状态是否一致。

第五层：规则复核

- 能否使用原始输入、规则版本和验证器重新执行相关检查。
- 是否存在制度版本变更或事实变化导致的结果差异。
- 哪些结论是来源事实，哪些是规则推导，哪些只是模型建议。

### 11.2 验证结果

建议采用明确的结构化状态：

| 状态           | 含义                 |
| ------------ | ------------------ |
| `PASS`       | 指定范围内的检查全部通过       |
| `FAIL`       | 存在明确的完整性、业务或规则检查失败 |
| `INCOMPLETE` | 缺少必要材料，无法完成验证      |
| `UNKNOWN`    | 当前无法确定结果           |
| `ERROR`      | 验证过程发生技术错误         |

不能把 `UNKNOWN` 自动转换为 `PASS`。同样，缺少证据也不一定证明业务违规，因此应区分“证据不完整”和“已发现违规”。

### 11.3 重新验证不等于重新执行

这是一个非常重要的安全边界。

证据验证可以重新运行只读查询、摘要校验、Schema 检查和确定性规则计算。但不应为了“复现原流程”而自动重新执行：

- ERP 写操作。
- 支付、转账或审批动作。
- 会发送外部通知的工具。
- 会产生额外费用的模型调用。
- 其他具有不可逆副作用的操作。

对于这些步骤，验证应使用已保存的请求摘要、操作账本、回执和历史结果；确实需要重新执行时，应建立独立的授权和业务流程。

### 11.4 本体与规则版本的历史复核

ODAP 的本体可能升级，企业制度也可能变化。历史业务操作应按照执行当时锁定的版本复核，而不是直接用最新版本覆盖历史判断。

建议同时支持：

- 历史复核：使用原本体、规则、映射和验证器版本，检查原执行依据。
- 当前规则重评估：使用当前规则对历史事实进行重新评估，明确标记这是新的分析结果。
- 差异分析：解释两个版本产生不同结果的原因。

当前规则认为某操作不再符合要求，并不自动意味着该操作在历史执行时违反了当时的制度。反过来，历史执行通过也不代表它符合今天的规则。

## 12. 证据与审计的访问控制

证据通常比普通运行日志包含更多业务信息，因此应比一般可观测性数据具有更严格的访问控制。

### 12.1 角色设计

建议至少定义以下逻辑角色：

| 角色                  | 典型权限                |
| ------------------- | ------------------- |
| `PlatformOperator`  | 查看平台健康状态、队列和服务级指标   |
| `TenantAdmin`       | 管理本租户配置与运行治理        |
| `BusinessOwner`     | 查看授权业务域的运行结果与证据摘要   |
| `SecurityAuditor`   | 查看安全事件、权限决策和相关审计记录  |
| `ComplianceAuditor` | 查看批准范围内的历史业务证据与审计报告 |
| `EvidenceExporter`  | 在授权范围内生成并导出证据包      |

这些是逻辑权限模板，应继续与第三篇的 RBAC + ABAC 引擎结合。角色本身不能绕过租户隔离、对象级权限、数据分类和字段级访问策略。

### 12.2 字段级访问控制

同一证据包可以包含不同敏感等级的数据。例如：

- 普通业务用户可以查看“规则验证通过”。
- 业务负责人可以查看相关金额、业务规则和审批结果。
- 安全审计人员可以查看授权决策与异常访问记录。
- 只有获得额外权限的人员才能访问原始敏感附件。

建议证据服务提供分层视图，而不是将完整证据 JSON 原样返回给所有具有查看权限的人。

### 12.3 证据导出治理

每次导出应记录：

- 导出人和所属租户。
- 导出目的与业务理由。
- 证据包 ID。
- 导出范围与数据分类。
- 脱敏策略版本。
- 导出时间和目标格式。
- 导出文件摘要。
- 审批记录（若适用）。

对高敏感证据，可要求双人审批或额外的授权策略。导出文件的访问权限和保留期限应与原始证据一致或更严格。

### 12.4 数据保留与删除

审计记录、证据制品、Trace 和普通日志的保留期限应分别配置。

- 普通日志可以采用较短保留期。
- Trace 应根据诊断价值与存储成本配置保留策略。
- 正式审计与证据应按企业政策、合同要求和适用法律设定保留期限。
- 涉及个人信息的数据应遵循最小化、访问控制和合法保留原则。

不能将“审计不可随意删除”理解为“所有数据永远不能删除”。应设计受授权、可审计的到期处理、保留冻结和依法删除流程，同时保留允许保留的完整性与处置记录。

## 13. 告警管理与事故响应

发现异常只是第一步。ODAP 还需要把告警转化为可追踪的事故处理过程。

### 13.1 告警生命周期

建议采用以下状态：

```
FIRING
  ↓
ACKNOWLEDGED
  ↓
INVESTIGATING
  ↓
MITIGATING
  ↓
RESOLVED
  ↓
POSTMORTEM
```

对于误报或重复告警，可以使用 `SUPPRESSED` 或 `CLOSED_AS_DUPLICATE` 等补充状态。

每次状态变化都应记录责任人、时间、处置说明和关联的告警事件。

### 13.2 Incident 数据模型

建议新增 `ops.incidents`：

```
CREATE SCHEMA IF NOT EXISTS ops;

CREATE TABLE ops.incidents (
    incident_id UUID PRIMARY KEY,
    tenant_id UUID,

    title TEXT NOT NULL,
    description TEXT,

    severity TEXT NOT NULL,
    category TEXT NOT NULL,
    status TEXT NOT NULL,

    owner_id TEXT,
    detected_at TIMESTAMPTZ NOT NULL,
    acknowledged_at TIMESTAMPTZ,
    resolved_at TIMESTAMPTZ,

    related_run_id UUID,
    related_operation_id UUID,

    root_cause_code TEXT,
    resolution_summary TEXT,

    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

平台级事故可能影响多个租户，因而需要明确区分平台级事故与租户级事故。平台级记录不能成为绕过租户权限查看业务明细的通道。

### 13.3 事故处理流程

1. 告警规则触发。
2. 告警管理器聚合重复告警。
3. 根据严重程度分派责任人。
4. 关联受影响的 Run、Step、Worker、操作账本和证据包。
5. 评估业务影响及安全风险。
6. 采取安全的缓解措施。
7. 验证服务恢复和业务状态。
8. 关闭事故。
9. 形成复盘报告与整改任务。

对于涉及未知 ERP 操作结果的事故，恢复服务不等于恢复业务正确性。必须确认受影响的外部操作已经对账，或者明确转交人工处理。

### 13.4 事故复盘模板

建议在治理中心内置以下结构：

- 事故摘要。
- 发现时间与影响时间。
- 受影响租户和业务域。
- 影响范围与业务后果。
- 关键时间线。
- 触发条件与根本原因。
- 为什么现有监控未能提前发现。
- 处置动作与验证结果。

复盘应以系统性改进为目标，而不只是记录某个 Worker 或某位操作者“出了问题”。

| `GET`  | `/api/v1/audit/checkpoints`     | 查询完整性检查点        |

| 方法     | 接口                                       | 功能         |

## 16. 数据库 Schema 与工程模块补充

### 16.1 推荐新增的数据表

在前两篇的 PostgreSQL 数据模型基础上，建议新增以下逻辑模块：

| Schema / 表                   | 职责                                  |
| ---------------------------- | ----------------------------------- |
| `audit.events`               | 正式审计事件                              |
| `audit.checkpoints`          | 审计分段完整性检查点                          |
| `audit.verification_runs`    | 审计完整性验证记录                           |
| `audit.access_events`        | 敏感审计数据的查看与导出记录                      |
| `evidence.bundles`           | 证据包元数据与状态                           |
| `evidence.artifacts`         | 证据制品清单、摘要与存储引用                      |
| `evidence.links`             | 证据与 Run、Step、Approval、Operation 的关联 |
| `evidence.verification_runs` | 证据验证记录                              |
| `evidence.exports`           | 证据导出任务                              |
| `ops.alerts`                 | 告警实例与处理状态                           |
| `ops.incidents`              | 事故管理                                |
| `ops.incident_events`        | 事故时间线                               |
| `ops.slo_definitions`        | SLO 定义与版本                           |
| `ops.runbooks`               | 告警处置手册引用                            |

这些是逻辑分组，不要求所有数据都存放在 PostgreSQL。例如，原始 Trace 可以存放在专用 Trace 后端，证据制品可以存放在对象存储；PostgreSQL 主要保存元数据、引用、权限边界和必要的正式状态。

### 16.2 证据制品表

建议为 `evidence.artifacts` 保存：

- `artifact_id`
- `tenant_id`
- `bundle_id`
- `artifact_type`
- `schema_version`
- `content_digest`
- `storage_ref`
- `media_type`
- `classification`
- `created_at`
- `retention_policy_id`
- `integrity_status`

制品内容应在上传时由可信服务计算摘要。不能仅信任客户端提交的 `content_digest`。

### 16.3 数据库事务边界

以下操作建议在同一个事务中完成：

- 写入正式审计事件及其必要的链式元数据。
- 创建证据包构建任务及对应 Outbox 事件。
- 更新事故状态并记录事故时间线事件。
- 记录敏感证据导出申请及其待处理事件。

以下操作通常不应放在长时间的数据库事务内：

- 生成大型证据包。
- 查询远端 ERP。
- 请求外部模型。
- 对大批归档文件逐个计算摘要。
- 向外部存储上传大型文件。

对于这些长任务，应先持久化任务和必要上下文，再异步执行，并记录每个阶段的状态。

## 17. Go 工程接口设计

建议将可观测性、审计、证据和运维模块分离，避免把所有逻辑都塞入 Harness。

### 17.1 审计服务

```

package audit

import "context"

type AppendResult struct {
    EventID     string
    EventDigest string
}

type QueryFilter struct {
    TenantID string
    RunID    string
    Action   string
    Limit    int
}

type Service interface {
    Append(
        ctx context.Context,
        event AuditEvent,
    ) (AppendResult, error)

    Query(
        ctx context.Context,
        filter QueryFilter,
    ) ([]AuditEvent, error)

    VerifyPartition(
        ctx context.Context,
        partitionKey string,
    ) (VerificationReport, error)
}

```

审计服务的 `Append` 应由可信服务端完成事件标准化、摘要计算和必要的链式元数据更新。调用者不能自行指定任意前序摘要，从而构造不受控的审计链。

### 17.2 证据服务

```

package evidence

import "context"

type BundleRef struct {
    BundleID string
    TenantID string
}

type BuildRequest struct {
    RunID               string
    VerificationProfile string
}

type VerificationReport struct {
    VerificationID string
    Status         string
    Findings       []Finding
}

type Service interface {
    Build(
        ctx context.Context,
        req BuildRequest,
    ) (BundleRef, error)

    Verify(
        ctx context.Context,
        ref BundleRef,
    ) (VerificationReport, error)

    Get(
        ctx context.Context,
        ref BundleRef,
    ) (Bundle, error)
}

```

这里的 `Build` 可以先返回一个已创建的构建任务引用，后续通过任务状态查询获取结果。生产接口应明确同步和异步语义，避免让调用者误以为返回成功就代表证据包已构建完成。

### 17.3 依赖关系原则

推荐依赖关系：

```
Business Modules
    ├── Telemetry SDK
    ├── Audit Service
    └── Domain Event Outbox

Evidence Service
    ├── Run / Step Store
    ├── Ontology / Policy Version Registry
    ├── Approval Store
    ├── ERP Operation Ledger
    └── Audit Service

Governance Center
    ├── Metrics / Logs / Traces
    ├── Audit Service
    ├── Evidence Service
    └── Incident Manager
```

可观测性模块可以读取业务状态并展示，但不应直接修改 Agent、权限或 ERP 操作状态。需要执行取消、重放、撤销或恢复时，应调用相应领域服务的正式接口。

## 18. 安全与治理风险清单

ODAP 的可观测性系统本身也可能成为高价值攻击目标，因为它集中记录企业业务活动、权限决策、模型调用和外部操作。

建议至少覆盖以下风险：

| 风险              | 防护措施                   |
| --------------- | ---------------------- |
| 审计记录被修改或删除      | 独立权限边界、哈希链、外部检查点、签名归档  |
| 审计管理员越权读取业务数据   | RBAC + ABAC、租户隔离、字段级脱敏 |
| Prompt 或附件泄露到日志 | 白名单采集、敏感字段检测、受控原文访问    |
| 伪造证据包           | 服务端计算摘要、受控签名、版本和来源校验   |
| 旧审批被用于新操作       | 审批绑定载荷摘要、重新验证授权和有效性    |
| 历史本体版本被替换       | 不可变版本、制品摘要和依赖锁定        |
| 证据导出后扩散         | 导出审批、访问记录、加密与保留策略      |
| 告警被人为关闭         | 关闭原因、操作者身份、状态变更审计      |
| 监控数据伪造          | 服务身份、采集认证、权限分离         |
| 运维操作绕过业务规则      | 运维界面只调用领域服务，不直接修改业务表   |

### 18.1 信任边界必须明确

ODAP 应把以下系统视为不同的信任域：

- 业务执行服务。
- 技术遥测后端。
- 正式审计存储。
- 证据对象存储。
- 签名密钥管理设施。
- 企业身份与权限系统。
- 外部 ERP。

即使这些系统部署在同一企业内网，也不应默认彼此完全可信。

尤其需要防止一种情况：同一个管理员可以修改业务记录、删除审计记录、替换证据文件并重写校验结果。如果所有关键数据都受同一个权限域控制，那么所谓“不可篡改”就缺乏独立验证基础。

## 19. 测试与验收标准

可观测性与证据体系不能只验证页面能否展示数据，还必须验证记录是否完整、权限是否正确、摘要是否可复算，以及异常能否被发现。

### 19.1 功能测试

- 一个 Run 能关联所有 Step、Attempt 和主要 Trace。
- 异步消息能关联到正确的业务请求和 Run。
- 任务失败后可以定位到具体步骤与错误类别。
- 审计记录能按主体、动作、资源、租户和时间查询。
- 证据包包含必需的版本、事实、规则、审批和操作引用。
- 证据包构建与导出均具有独立状态。
- 事故处理过程有完整的状态变更时间线。
- SLO、告警规则和处置手册能够关联。

### 19.2 完整性测试

- 修改证据文件内容后，摘要校验失败。
- 删除或修改已被检查点覆盖的审计事件后，链式验证失败。
- 使用错误的签名密钥时，签名验证失败。
- 缺少必要的 ERP 回执时，证据状态不能被标记为业务成功。
- 版本锁定信息与实际制品不一致时，验证失败。
- 审批绑定摘要与待执行载荷不一致时，验证失败。
- 同一事件 ID 对应不同载荷摘要时，系统报警。
- 证据归档后仍能按保留的密钥与检查点进行验证。

### 19.3 安全测试

- 一个租户不能读取其他租户的审计事件。
- 业务用户不能查看无权访问的原始敏感附件。
- 普通运维人员不能导出高敏感证据。
- 未授权人员不能修改告警处理状态。
- 重放与恢复操作均经过正式权限检查。
- 读取审计记录本身可以在适当场景下留下访问审计。
- 日志脱敏测试能够覆盖常见凭据和个人信息模式。
- 证据下载链接具有租户范围、有效期和访问控制。

### 19.4 故障注入测试

建议重点模拟以下情况：

1. 审计数据库短暂不可用。
2. 证据文件上传成功，但数据库状态更新失败。
3. 数据库事务成功，但证据构建事件尚未发布。
4. 签名服务不可用。
5. Trace 后端不可用，但业务审计仍可正常写入。
6. 审计归档任务重复执行。
7. 证据验证期间，关联 ERP 操作从未知状态转为已确认成功。
8. 告警通知渠道不可用。
9. 审计检查点生成期间出现并发写入。
10. 数据库恢复后，需要重新验证最近一段审计链。

这些场景应验证系统能否恢复、是否出现重复记录，以及异常是否能被明确标记，而不是被静默忽略。

### 19.5 建议的验收原则

正式上线前，至少满足以下条件：

- 关键业务操作都有可查询的正式审计记录。
- 业务状态、审计事件和证据引用之间具有稳定关联。
- 关键证据能够独立验证其完整性。
- 验证失败、证据缺失和结果未知有明确区分。
- 技术遥测故障不会直接导致正式审计记录无声丢失。
- 敏感证据读取与导出有明确权限边界。
- 关键告警有责任人、处置流程和恢复验证。
- 审计完整性检查有自动化测试与定期演练。

## 20. 实施路线图

建议分六个阶段完成，避免一开始就建设过度复杂的审计基础设施。

P1：统一关联标识与遥测规范

建立 `BusinessContext`、结构化日志规范、OpenTelemetry 集成和标准错误码。

交付：跨 API、Harness、Agent、LLM Gateway 和 ERP Gateway 的基础追踪能力。

P2：正式审计服务

建立审计事件 Schema、持久化接口、查询 API、权限策略与保留规则。

交付：关键业务行为和管理操作的统一审计账本。

P3：完整性验证机制

实现事件摘要、分段哈希链、检查点、签名和归档验证。

交付：可发现历史审计记录被修改或删除的验证流程。

P4：Evidence Service

建立证据清单、版本锁定、事实引用、验证报告、签名和导出机制。

交付：针对单笔业务生成可复核的证据包。

P5：SLO、告警与事故治理

建立服务指标、业务指标、告警分级、责任人、事故状态机和复盘机制。

交付：从发现异常到确认恢复的完整运维闭环。

P6：前端治理中心与故障演练

实现运行总览、业务追踪、审计中心、证据工作台、事故中心和治理配置。

交付：企业管理员、运维、安全与审计人员可以使用的完整工作台。

## 22. 本篇最终架构决策

综合 ODAP 前十一篇，建议将以下原则固化为 V1.0 的企业级治理基线：

1. 统一 `tenant_id`、`business_request_id`、`run_id`、`step_id`、`attempt_id` 和 `operation_id` 等关联标识。
2. 使用 OpenTelemetry 建立跨服务 Trace，但不把 Trace 当作正式审计账本。
3. 技术遥测和业务审计分开管理，采用不同的采样、保留和访问策略。
4. 关键授权、审批、本体发布、ERP 操作和治理变更必须生成正式审计记录。
5. 审计事件使用规范化载荷、摘要和明确的 Schema 版本。
6. 通过分段哈希链、独立检查点、受控签名和归档提升审计篡改可发现性。
7. Evidence Service 必须关联来源事实、规则版本、验证结果、授权决策、审批和 ERP 回执。
8. 明确区分文件完整性、业务一致性与业务真实性，不能把签名有效等同于业务正确。
9. `PASS`、`FAIL`、`INCOMPLETE`、`UNKNOWN` 和 `ERROR` 必须保持明确的语义区别。
10. 历史业务复核应使用执行时锁定的版本；使用新版本重评估时，必须明确标记为新的分析。
11. 敏感证据的查看、下载、导出和重放都必须执行授权检查并留下审计记录。
12. 告警、事故、恢复和复盘应形成完整的运维闭环。
13. 监控、日志或 Trace 后端故障不能成为关键审计记录被静默丢失的理由。
14. 所有完整性和恢复承诺都必须通过篡改测试、故障注入和恢复演练验证。

第十一篇完成后，ODAP 就不仅能够执行企业业务，而且具备解释执行过程、追溯决策依据、验证关键证据和管理生产风险的基础能力。

这对于企业本体驱动的智能体平台尤其重要：企业需要的不只是一个能给出答案的 Agent，而是一个能够说明数据从哪里来、规则如何生效、权限为何允许、操作是否真正完成，并且可以接受复核的业务执行系统。
