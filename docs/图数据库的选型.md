# 图数据库的选型

我会重点考察它与 ODAP 已规划的几个模块之间的关系：

- Ontology Runtime：存储和查询 OWL/RDF 本体。
- GraphStore：管理命名图、数据来源、版本与访问边界。
- SHACL Validation Engine：执行 SHACL 约束验证。
- Semantic Query Engine：将 ODAP 的受控语义查询编译为实际图查询。
- Evidence Service：保存验证输入、结果、数据来源和版本证据。

## 一、Fuseki 在 ODAP 中到底负责什么？

首先区分两个组件：

- Apache Jena Fuseki：提供 HTTP 服务接口，包括 SPARQL 查询、SPARQL Update 和 Graph Store Protocol 等。
- Apache Jena TDB2：Fuseki 可以使用的持久化 RDF 数据集存储引擎。

两者通常搭配使用。Fuseki 不是单纯的数据库文件，也不是 SHACL 专用数据库。官方文档明确支持 Fuseki 与 TDB2 配合部署。

对于 ODAP，我建议将它们作为一个可替换的 RDF 存储服务来使用：

ODAP Go 应用层

Ontology Runtime · Harness · Policy Engine · Evidence Service

ODAP GraphStore Adapter

统一图存储接口、租户上下文、查询约束、版本与来源管理

Apache Jena Fuseki

SPARQL · RDF Graph Store · 图数据服务

Apache Jena TDB2

RDF 持久化、索引与数据集存储

这里我会特别坚持一点：不要让所有 Go 业务模块直接拼接 SPARQL 并访问 Fuseki。 所有访问都经过 ODAP 的 GraphStore Adapter，由它统一处理身份、租户、允许查询的图、资源预算、版本和审计。

## 二、Fuseki 能不能直接做 SHACL 验证？

可以。Apache Jena 提供独立的 SHACL 实现，也支持通过配置为 Fuseki 暴露 SHACL 验证端点。它支持 SHACL Core 和 SHACL-SPARQL 约束。

[image](https://www.google.com/s2/favicons?domain=https://jena.apache.org\&sz=32)

因此，ODAP 有两种集成方式：

| 方式                          | 实现                                 | 我的建议                                   |
| --------------------------- | ---------------------------------- | -------------------------------------- |
| Fuseki 内置 SHACL 端点          | 通过 HTTP 提交 Shapes Graph，对指定数据图执行验证 | 适合快速原型和简单验证流程                          |
| 独立 SHACL Validation Service | 单独部署验证服务，使用 Jena SHACL 库或其他经过验证的实现 | 更适合 ODAP 的生产架构，便于隔离资源、控制并发、记录结果和升级验证引擎 |

需要注意，Fuseki 的 SHACL 端点需要显式配置，不是所有数据集默认都会提供。

[image](https://www.google.com/s2/favicons?domain=https://jena.apache.org\&sz=32)

Apache Jena SHACL



我更倾向第二种方式。这样即使将来 RDF 存储从 Fuseki 换成其他产品，SHACL 验证服务和 ODAP 的业务流程也不必跟着重写。

## 三、我会如何设计 ODAP 的 SHACL 验证链路？

建议把一次验证作为独立的、可追踪的任务，而不是一次普通的数据库查询。

1\. 固定验证输入

记录本体版本、Shapes 版本、待验证数据图、数据来源及其版本。

2\. 检查授权和资源预算

验证服务只能读取被授权的数据图，并限制执行时间、内存、并发和查询复杂度。

3\. 执行 SHACL 验证

由验证引擎读取约束和数据，产生标准验证报告。

4\. 持久化结果

完整报告保存为 RDF 或对象存储文件，PostgreSQL 保存状态、摘要、错误索引和关联版本。

5\. 决定后续业务动作

由 Harness 和策略引擎决定继续、补充数据、拒绝执行或转人工处理。验证失败、验证不完整和引擎异常必须分别处理。

还有一个重要边界：如果 SHACL 验证的是即将写入的 RDF 数据，必须明确采用什么一致性策略。Jena 提供了针对图更新进行验证、验证不通过时中止更新的 API；但跨 Fuseki、PostgreSQL 和 ERP 的分布式业务操作，不能因此就自动获得一个原子事务。

## 四、最终技术选型建议

对于 ODAP，我建议采用以下初始方案：

| 模块                | 建议选型                                  |
| ----------------- | ------------------------------------- |
| RDF 图存储服务         | Apache Jena Fuseki                    |
| RDF 持久化           | Apache Jena TDB2                      |
| SHACL 验证          | 独立验证服务，优先评估 Apache Jena SHACL         |
| 企业业务数据、权限、任务和验证索引 | PostgreSQL                            |
| 完整验证报告和大型证据文件     | RDF 存储或对象存储，按查询需要选择                   |
| Go 与 Fuseki 通信    | 内部 HTTP API，经 GraphStore Adapter 统一访问 |
| 部署                | Docker Compose 起步，生产环境根据负载与客户要求规划高可用  |

正式选型前，应使用 ODAP 的真实本体和业务数据做基准测试，尤其检查 SHACL-SPARQL 支持、复杂关系查询性能、增量验证需求、并发读写、备份恢复和租户隔离。不要只根据功能列表决定生产数据库。

我的结论：ODAP 完全可以将 Fuseki + TDB2 作为第一版 RDF 基础设施。 它能帮助你快速建立标准化的语义图服务，同时保留未来替换底层存储的空间。关键是把 Fuseki 定位为基础设施，而不是让它成为 ODAP 的业务执行引擎；本体版本、权限、业务流程、验证任务和证据治理仍然由 ODAP 自己负责。
