# ODAP 第十三篇：企业本体知识图谱存储、查询优化与多源语义推理引擎详细设计

版本：V1.0 · 架构体系：Ontology Runtime + Semantic Graph Engine · 技术基线：Go + React/TypeScript + PostgreSQL + 可插拔语义存储

> **Scope 标签（本篇范围声明，对齐评审报告 §5 的 MVP 治理要求）**

## 1. 设计目标：让企业本体从知识模型变成可执行的语义基础设施

在前十二篇中，ODAP 已经逐步建立起完整的企业智能体平台架构：

- 企业本体定义业务对象、属性、关系和约束。
- 数据接入平台将 ERP、HR、CRM、数据库和文件数据映射为标准业务事实。
- Ontology Factory 负责本体生产、验证、版本管理和发布。
- Agent Runtime 与 Harness 负责智能体协作、执行、暂停、恢复和审批。
- ERP Gateway 负责受控业务写入。
- Evidence Service 负责记录业务执行所依赖的事实、规则、授权和回执。

现在还缺少一个关键的运行时核心：

当企业本体中存在数百万甚至数亿条业务事实，多个数据源持续更新，Agent 又需要进行多跳关系查询、约束验证和语义推理时，ODAP 如何高效、准确且可追溯地计算结果？

例如，企业报销 Agent 需要回答：

1. 某笔报销属于哪个员工和部门？
2. 该部门当前有效的预算是多少？
3. 员工在报销发生时是否属于该部门？
4. 该笔费用适用哪个版本的企业制度？
5. 哪些业务事实存在冲突或缺失？
6. 哪些规则能够从现有事实推出该报销需要升级审批？
7. 结果使用的是哪个数据快照、本体版本和推理规则版本？

这些问题并非简单的向量检索或数据库字段查询，而是涉及图关系遍历、逻辑规则、时间语义、跨源事实协调、约束验证和推导证据的组合计算。

本篇的目标，是设计 ODAP 的企业本体知识图谱存储、查询优化和多源语义推理引擎，使前十二篇的设计真正形成一个可以实现、测试和扩展的运行时系统。

## 2. 设计原则与明确的技术边界

### 2.1 本体语义、事实存储、推理与业务执行分离

建议坚持以下职责划分：

- Ontology Registry：保存正式发布的本体包及版本。
- Semantic Graph Store：存储本体实例、关系和来源事实。
- Query Engine：执行结构化语义查询。
- Reasoning Engine：执行明确配置的逻辑推理规则。
- SHACL Engine：检查 RDF 数据图是否满足声明的形状约束。
- Business Rule Engine：执行企业业务条件与决策规则。
- Authorization Engine：判断主体是否有权访问数据或执行操作。
- Harness：管理任务、重试、审批、恢复和执行预算。
- ERP Gateway：负责正式的外部业务写入。

这些组件可以在同一进程中部署，也可以独立部署，但接口和职责必须明确。

例如，推理引擎可以推导出“该员工属于财务部门”，却不能自行得出“当前 Agent 有权读取该员工的所有薪酬数据”。前者是语义事实，后者是授权决策。

同样，SHACL 验证通过也不意味着业务规则通过，更不意味着 ERP 写入获得授权。

### 2.2 不追求一次实现全部 OWL 语义

OWL 具有多种表达能力和推理复杂度。若 V1.0 直接承诺支持全部 OWL 2 DL 推理，将显著增加实现、验证和性能控制难度。

建议采用分阶段能力模型：

- V1.0：RDF 基础图查询、受控 RDFS 推理（逐条锚定 W3C RDFS 规则编号，清单见 §14.1）、少量受控 OWL 特性（`owl:equivalentClass` / `owl:inverseOf` / `owl:TransitiveProperty` 等，逐条声明规则来源与状态）、SHACL 核心约束验证（显式排除 `sh:sparql`，见 §15.1）、受限业务规则。
- V1.5：**OWL 2 RL 二选一决策点**（不允许用“分阶段支持”含糊表述）——要么外挂成熟 reasoner 服务（接入支持 OWL 2 RL 规则集的开源推理器，以其实际实现的规则清单为准写入支持矩阵，并通过 §14.1 的一致性测试套件验证），要么把范围收紧为 RDFS + 商业规则（OWL 特性维持 V1.0 受控清单，不扩张）。决策依据为 V1.0 阶段收集的真实本体规模、规则数量与查询模式。同一里程碑交付增量推理（DRed 基线，见 §13.5/§13.6）与跨源事实协调。
- V2.0：根据客户需求评估更完整的 OWL 配置、外部推理后端和大规模分布式语义计算；成本优化器（CBO）也在此阶段评估（见 §11.1）。

必须为每种推理能力建立正式的支持矩阵。不能因为系统解析了某个 OWL 文件，就声称已经完整实现其全部语义。

### 2.3 语义存储与业务数据库不必统一

ODAP 不需要把所有数据都迁移到图数据库，也不应该将所有业务数据强制转换为 RDF。

建议采用混合架构：

- PostgreSQL：平台元数据、版本、任务、权限、映射、运行记录。
- RDF Store：语义图、命名图和适用的推理结果。
- 对象存储：原始快照、制品、导入文件和大型证据包。
- 可选列式分析存储：高吞吐统计与历史分析。
- 可选向量索引：语义检索或候选实体匹配，但不作为事实权威源。

关键不是让每种数据都使用同一存储技术，而是通过统一的语义接口、版本契约和证据机制，让不同存储对上层 Agent 表现为一致、可治理的企业语义系统。

## 3. 总体架构：语义图存储与推理引擎

建议把 ODAP 的语义运行时划分为九个逻辑层。

L1 · Semantic Consumer API

Agent · Harness · 业务应用 · 治理工作台

L2 · Semantic Query API

受控查询 DSL · 查询校验 · 身份与数据范围绑定

L3 · Query Compiler & Optimizer

解析 · 类型检查 · 逻辑计划 · 物理计划 · 成本优化

L4 · Query Executor

索引查找、图遍历、连接、过滤、聚合

L5 · Reasoning & Validation

RDFS/OWL 子集、规则推理、SHACL、业务规则

L6 · Semantic Data Access

数据快照、命名图、事实来源、权限过滤、缓存

L7 · Semantic Graph Store

RDF 三元组、索引、图分区、派生事实

L8 · Metadata & Version Store

PostgreSQL：版本、任务、统计、血缘、发布

L9 · Data Sources & Evidence

第十二篇数据平台 · 来源记录 · 映射版本 · Evidence Service

### 3.1 运行时请求的完整路径

一个典型的 Agent 查询按以下步骤执行：

1. Harness 提交带有租户、主体、业务任务和版本要求的查询请求。
2. API 验证调用者身份、查询类型、数据范围和资源预算。
3. 查询编译器解析查询，检查类型、属性和关系是否合法。
4. 优化器生成候选执行计划，选择索引、遍历方向和推理策略。
5. 执行器获取原始或已物化的语义事实。
6. 如果查询要求推理，则执行指定推理配置；如果要求约束检查，则调用相应验证器。
7. 结果处理阶段补充来源引用、数据新鲜度、质量状态和版本信息。
8. 返回结构化结果，并根据策略构建证据引用。

重要约束： 权限检查不能只在入口执行一次。查询计划访问不同数据集、命名图和敏感属性时，必须继续受到数据访问策略约束。

### 3.2 逻辑部署与物理部署

MVP 可以把 Query Compiler、Optimizer、Executor 和基础推理模块放在一个 Go 服务中，使用独立接口组织代码。

随着数据规模增加，可以将以下模块拆成独立服务：

- 语义查询服务。
- 推理与物化服务。
- 图存储适配器。
- 数据重建与索引维护 Worker。
- 证据构建服务。

是否拆分应依据吞吐、资源隔离、故障域和运维需求决定，而不是为了追求微服务数量。

## 4. 企业语义图的数据模型

### 4.1 RDF 三元组模型

语义图的基础事实采用 RDF 三元组：

\\[ (s,p,o) \\]

其中：

- \\(s\\)：Subject，主语，通常是业务对象或资源。
- \\(p\\)：Predicate，谓词，表示属性或关系。
- \\(o\\)：Object，宾语，可以是另一个资源，也可以是字面值。

例如：

```
@prefix odap: <https://ontology.example/odap#> .

odap:ExpenseClaim_CLM1024
    a odap:ExpenseClaim ;
    odap:claimAmount "1250.00" ;
    odap:currency "CNY" ;
    odap:submittedBy odap:Employee_E1024 .

odap:Employee_E1024
    a odap:Employee ;
    odap:belongsTo odap:Department_FIN .
```

这段数据表达报销单、员工和部门之间的语义关系。

在正式本体中，金额最好定义为具有明确类型和单位的值，或者关联到专门的金额对象，而不只是一个没有单位语义的字符串。上述示例用于说明三元组结构。

### 4.2 资源、字面值与数据类型

存储层必须区分：

- IRI 资源。
- 空白节点。
- 字符串字面值。
- 数值字面值。
- 布尔值。
- 日期、时间与日期时间。
- 语言标签字面值。
- 带数据类型的字面值。

例如，以下值不能简单地全部作为字符串比较：

```
odap:claimAmount "1250.00"^^xsd:decimal .
odap:claimDate "2026-10-12"^^xsd:date .
odap:isActive true .
```

字面值的规范化必须遵循 RDF 与相应数据类型的语义规则。不能为了索引方便而擅自改变其逻辑含义。

### 4.3 事实不能只有三元组

对企业系统而言，只有 `(s,p,o)` 往往不足以支持完整治理。

一条业务事实还可能需要记录：

- 来源系统和来源记录。
- 映射版本。
- 数据快照。
- 观察时间。
- 业务有效时间。
- 权威性策略。
- 质量状态。
- 敏感等级。
- 验证状态。

因此建议把 RDF 三元组作为语义事实的核心表示，同时通过命名图、事实元数据表或独立的来源追踪模型关联治理信息。

不应把所有这些信息都硬编码为三元组中的普通业务属性，否则本体会混入大量存储和运行时细节。

### 4.4 事实、推导与验证结果分开

建议至少区分五类结果：

| 类型                   | 含义          | 示例        |
| -------------------- | ----------- | --------- |
| `SOURCE_FACT`        | 来源系统明确提供的事实 | ERP 报销金额  |
| `NORMALIZED_FACT`    | 经标准化得到的事实   | 统一精度的金额   |
| `DERIVED_FACT`       | 根据规则推导的事实   | 员工属于某组织层级 |
| `VALIDATION_FINDING` | 约束检查结果      | 缺少必需的员工关系 |
| `POLICY_DECISION`    | 业务政策或授权决策   | 需要升级审批    |

这些类型不能相互替代。特别是，`VALIDATION_FINDING` 不是业务事实，`POLICY_DECISION` 也不能仅凭某个 RDF 三元组就被认为具有合法授权效力。

## 5. 语义图存储引擎设计

### 5.1 存储引擎的职责

Semantic Graph Store 负责：

1. 保存经过规范化的 RDF 事实。
2. 支持基于主语、谓词和宾语的查询。
3. 管理命名图与数据分区。
4. 维护事实来源和版本关联。
5. 支持事务或批次级写入。
6. 支持快照、恢复和索引重建。
7. 为查询引擎提供统一存储接口。
8. 支持派生事实与原始事实的区分。
9. 与第十二篇的数据更新流程协作。
10. 为历史查询与证据复核提供必要的版本信息。

存储引擎不负责决定 Agent 是否有权执行某项业务，也不应把所有业务规则直接写入底层数据库触发器。

### 5.3 推荐路线与存储选型门禁（P0）

对 ODAP，建议采用：

- P1：定义统一 `GraphStore` 接口，并完成 PostgreSQL 适配器的可测试实现；同时保留一个受控 RDF Store 适配器接口位，供 Spike 对比使用。
- **存储选型 Spike（进入 P2 的硬门禁）**：使用 Medium 数据集（1000 万三元组，构造方式见 §26.6）实测对比：自研 PG 索引方案（PK+POS+OSP 三索引 + tenant 声明式分区，§6.3）vs 1-2 个成熟 RDF Store（如 Blazegraph / GraphDB / Fuseki，任选其二做代表）。选型报告必须输出四项指标：查询 P95、写入吞吐、租户隔离成本、运维复杂度。**报告未经平台架构评审通过，不得进入 P2 本体工程建设。**
- V1.5：按选型报告结论扩展适配器能力、压测边界与标准兼容性。
- V2.0：在明确出现瓶颈后，再评估分片、图计算引擎或混合存储。

**PG 方案的承诺范围**：若 Spike 后 PG 方案入选，其适用范围显式承诺为“≤1000 万三元组/租户”；更大规模必须走专用 Store 路线，并把规模阈值（三元组数、查询 P95、写入吞吐下限）写入验收阈值（§26.6），不允许在超出承诺范围后继续用 PG 硬扛。

不要在没有数据规模、查询模式和性能基准的情况下，直接决定必须自研完整图数据库。ODAP 的核心差异化应优先放在企业语义治理、可控推理、版本一致性和智能体执行闭环上。

**选型调研支撑材料**：`docs/research/图数据库的选型.md`（含 Fuseki 在 ODAP 架构中的职责边界、与 PG 方案的取舍分析），作为 Spike 报告的输入参考；最终结论以 Spike 实测数据为准，调研材料不替代压测。

## 6. 物理存储结构与索引设计

如果 V1.0 选择 PostgreSQL 作为基础 RDF 存储，建议在 `graph` Schema 中建立三元组表、命名图表、字典表和事实元数据表。

### 6.1 RDF 资源字典

为了避免每条三元组都重复存储长 IRI 和数据类型信息，可以将资源与字面值规范化到字典中。

```
CREATE SCHEMA IF NOT EXISTS graph;

CREATE TABLE graph.terms (
    term_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    term_kind SMALLINT NOT NULL,
    lexical_form TEXT NOT NULL,
    datatype_iri TEXT,
    language_tag TEXT,
    canonical_digest TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_terms_digest
    ON graph.terms (canonical_digest);

CREATE INDEX idx_terms_lexical
    ON graph.terms (lexical_form);
```

`term_kind` 应使用受控枚举或检查约束，区分 IRI、空白节点和字面值。

字典层还需要处理以下问题：

- IRI 与字面值不能混为一类。
- 字面值数据类型和语言标签需要参与语义比较。
- 空白节点的标识不能被错误地当成跨数据集的稳定业务 ID。
- 字典中的值可能包含敏感信息，应限制普通运维人员直接查询原始词项。
- 摘要索引应使用规范化编码和足够的摘要长度，必要时在摘要命中后验证原始内容，不能仅凭哈希值就假定绝对没有碰撞。

### 6.2 命名图与三元组

```
CREATE TABLE graph.named_graphs (
    graph_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id UUID NOT NULL,
    graph_iri TEXT NOT NULL,
    graph_type TEXT NOT NULL,
    dataset_id UUID,
    snapshot_id TEXT,
    ontology_version TEXT,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (tenant_id, graph_iri)
);

CREATE TABLE graph.triples (
    tenant_id UUID NOT NULL,
    graph_id BIGINT NOT NULL
        REFERENCES graph.named_graphs(graph_id),
    subject_id BIGINT NOT NULL
        REFERENCES graph.terms(term_id),
    predicate_id BIGINT NOT NULL
        REFERENCES graph.terms(term_id),
    object_id BIGINT NOT NULL
        REFERENCES graph.terms(term_id),
    fact_kind TEXT NOT NULL,
    mapping_version_id UUID,
    observed_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    valid_from TIMESTAMPTZ,
    valid_to TIMESTAMPTZ,
    PRIMARY KEY (
        tenant_id,
        graph_id,
        subject_id,
        predicate_id,
        object_id
    )
);
```

这是面向当前有效三元组的基础示例。正式实现还需要定义：

- 事实重复与来源合并策略。
- 同一三元组由多个来源支持时如何关联来源。
- 历史版本与删除标记。
- 同一图中多条事实的有效时间重叠规则。
- 事务与批次发布边界。
- 派生事实的推理配置和物化版本。

尤其需要注意：如果同一三元组由多个数据源提供，不能仅靠三元组主键记录一条来源。应使用独立的事实来源关联表，或者使用具备多来源支持能力的事实元数据模型。

### 6.3 三元组索引（V1.0 采用 PK + POS + OSP 三索引）

RDF 查询需要按不同绑定模式访问图，但索引数量直接决定写入放大。V1.0 采用**精简三索引**方案，不采用评审前版本的五索引（PK + SPO + POS + OSP + graph_predicate）：

- **PK（主键）**：`(tenant_id, graph_id, subject_id, predicate_id, object_id)`（§6.2 的 `PRIMARY KEY`），天然覆盖"已知主语"的 SPO 访问前缀。
- **idx_triples_pos**：`(tenant_id, predicate_id, object_id, subject_id)`，覆盖"已知谓词+宾语反向查找主语"的 PO 模式。
- **idx_triples_osp**：`(tenant_id, object_id, subject_id, predicate_id)`，覆盖"已知宾语查找所有引用关系"的 O 模式。

```
CREATE INDEX idx_triples_pos
    ON graph.triples (
        tenant_id, predicate_id, object_id, subject_id
    );

CREATE INDEX idx_triples_osp
    ON graph.triples (
        tenant_id, object_id, subject_id, predicate_id
    );
```

**为什么不单独建 idx_spo**：主键列序 `(tenant_id, graph_id, subject_id, predicate_id, object_id)` 与 SPO 索引 `(tenant_id, subject_id, predicate_id, object_id)` 高度重叠，唯一差异是 `graph_id` 与 `subject_id` 的相对顺序。限定单图的查询可直接走 PK；不限定 graph_id 的跨图 SPO 查询在 V1.0 由 POS/OSP 加结果过滤近似承担。若 §5.3 Spike 压测表明跨图 SPO 是热点，再以受控方式补充，而不是默认创建。

**为什么删除 idx_triples_graph_predicate**：`(graph_id, predicate_id)` 访问可由 POS 索引的谓词段加图过滤承担；单独建索引的写入成本高于其查询收益，故删除。

索引顺序应根据真实查询模式调整；最终组合以 §5.3 存储选型 Spike 的查询计划与压测数据为准。

### 6.3.1 按 tenant 声明式分区

`graph.triples` 与 `graph.fact_sources` 是增长最快的表，按租户做**声明式分区**（PostgreSQL 声明式分区表）。§6.2 的非分区定义是逻辑示例，V1.0 的物理落地形态如下：

```
CREATE TABLE graph.triples (
    tenant_id UUID NOT NULL,
    graph_id BIGINT NOT NULL
        REFERENCES graph.named_graphs(graph_id),
    subject_id BIGINT NOT NULL
        REFERENCES graph.terms(term_id),
    predicate_id BIGINT NOT NULL
        REFERENCES graph.terms(term_id),
    object_id BIGINT NOT NULL
        REFERENCES graph.terms(term_id),
    fact_kind TEXT NOT NULL,
    mapping_version_id UUID,
    observed_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    valid_from TIMESTAMPTZ,
    valid_to TIMESTAMPTZ,
    PRIMARY KEY (
        tenant_id,
        graph_id,
        subject_id,
        predicate_id,
        object_id
    )
) PARTITION BY LIST (tenant_id);
```

- 每个租户一个分区（`CREATE TABLE graph.triples_t<tenant> PARTITION OF graph.triples FOR VALUES IN ('<tenant_uuid>')`），新租户初始化时由迁移流程建分区；分区 DDL 与迁移规范按第二篇工程要求补齐复合外键与租户约束。
- **分区裁剪（partition pruning）**：所有查询都从可信上下文注入 `tenant_id`（§7.2、§21.5），规划器按分区键裁剪，跨租户扫描在计划层即被排除；"删租户"也变为 `DETACH PARTITION` 加归档，而不是逐行 DELETE。
- POS/OSP 二级索引建在分区表上时自动按分区创建对应本地索引，索引维护总量与三索引方案一致。

**写放大量化对比（每条三元组一次 INSERT 的二级索引维护代价）**：

| 方案 | 索引数 | 每次写入的 B-tree 维护次数 | 近似写入放大 | 说明 |
| --- | --- | --- | --- | --- |
| 五索引（PK+SPO+POS+OSP+graph_predicate） | 5 | 5 | ~5x | SPO 与 PK 高度重叠属重复建设；graph_predicate 收益低 |
| 三索引（PK+POS+OSP） | 3 | 3 | ~3x | 覆盖三种绑定模式；V1.0 采用 |

表中倍数为索引维护的近似相对值（不含 WAL、autovacuum 与分区开销）；Medium 集（1000 万三元组）批量导入场景的实测差额以 §5.3 Spike 报告为准。按行宽约 80 字节估算，1000 万三元组数据体量约 1 GB 量级，三索引的索引体量约为数据体量的 1.5-2.5 倍（取决于 term_id 分布），单机 PostgreSQL 可承载——这正是 PG 方案承诺范围定为 ≤1000 万三元组/租户的量化依据之一。

### 6.4 为什么需要 SPO、POS、OSP 三种访问路径？

假设查询：

```
已知主语与谓词，查找宾语
```

适合以 `(subject, predicate)` 为前缀的索引。

如果查询：

```
已知谓词与宾语，反向查找主语
```

则需要以 `(predicate, object)` 为前缀的访问路径。

如果查询：

```
已知宾语，查找所有引用它的关系
```

则可能更适合以 `object` 开头的索引。

三种访问模式分别服务不同的图遍历方向。V1.0 的落地取舍：SPO 模式由主键前缀承担（见 §6.3），POS 与 OSP 各建一个二级索引，不追求三种模式完全对称——这是写入成本与查询覆盖的显式折中；热点偏移时以 §5.3 Spike 数据驱动调整。

### 6.5 事实来源表

建议将事实内容与来源证据分离：

```
CREATE TABLE graph.fact_sources (
    tenant_id UUID NOT NULL,
    graph_id BIGINT NOT NULL,
    subject_id BIGINT NOT NULL,
    predicate_id BIGINT NOT NULL,
    object_id BIGINT NOT NULL,
    source_id UUID NOT NULL,
    source_record_ref TEXT NOT NULL,
    mapping_version_id UUID,
    snapshot_id TEXT,
    source_digest TEXT,
    source_authority TEXT,
    observed_at TIMESTAMPTZ NOT NULL,
    valid_from TIMESTAMPTZ,
    valid_to TIMESTAMPTZ,
    PRIMARY KEY (
        tenant_id,
        graph_id,
        subject_id,
        predicate_id,
        object_id,
        source_id,
        source_record_ref
    )
);
```

这使同一语义事实能够保留多个来源。删除某个来源的记录时，可以撤销该来源的支持关系，而不必错误地删除仍然受到其他有效来源支持的事实。

### 6.6 历史版本与快照

建议把当前图与历史数据集快照区分开。

- 当前图用于普通在线查询。
- 数据快照记录某个时间点的数据状态。
- 历史事实记录业务有效时间和系统观察时间。
- 推理结果记录生成时使用的事实、规则和本体版本。
- Evidence Bundle 保存完成审计所需的必要引用与制品。

不要简单地为每次更新复制一份完整图。如果数据规模较大，可以采用不可变快照、变更日志和版本指针组合的策略。

## 7. 多图模型与租户隔离

企业语义数据通常包括本体定义、企业实例、来源数据、派生结果和临时验证数据。建议使用命名图或等效的数据分区表达不同用途。

### 7.1 推荐的图分层

| 图类型              | 作用        | 典型内容             |
| ---------------- | --------- | ---------------- |
| Schema Graph     | 本体模式定义    | 类、属性、类型和约束引用     |
| Source Graph     | 来源事实      | ERP、HR 等系统映射来的事实 |
| Canonical Graph  | 标准化后的业务事实 | 统一实体与字段          |
| Derived Graph    | 推理生成的事实   | 受控规则推出的关系        |
| Validation Graph | 验证结果与问题引用 | SHACL 发现项        |
| Workspace Graph  | 临时测试和候选变更 | 映射测试、候选本体        |

其中，约束形状与业务规则不一定要全部作为普通业务三元组存储；可以在独立的规则资产中管理，并在运行时通过版本引用与相关图关联。

### 7.2 多租户隔离

建议将租户隔离作为物理和逻辑两层的共同约束：

- 每个查询请求必须绑定可信的 `tenant_id`。
- 存储访问必须限制在允许的租户与图集合。
- 关系遍历不能意外跨租户。
- 缓存键必须包含租户与权限范围。
- 证据引用必须执行租户和对象权限检查。
- 运维后台的跨租户访问必须具备明确授权并产生审计事件。

如果企业存在共享的全局本体，应把“共享的 Schema”与“租户的业务实例”分开处理。共享本体可在经过发布和访问控制后被多个租户引用，但不能因此让租户之间的业务事实互相可见。

### 7.3 权限过滤与图遍历

在查询编译阶段，授权引擎应把可访问的数据范围转化为执行约束。

例如，某个 Agent 可以查询：

- 当前租户的报销单。
- 与该报销单关联的部门名称。
- 但不能读取员工薪酬属性。

此时，即使图上存在 `Employee.salary`，查询执行器也不能因为遍历到 Employee 节点，就自动返回其全部属性。

建议采用：

1. 查询入口的权限预检查。
2. 查询计划中的图与属性范围约束。
3. 存储访问阶段的租户过滤。
4. 结果输出阶段的字段过滤与脱敏。
5. 对敏感访问和拒绝行为进行审计。

## 8. 统一 GraphStore 接口与 Go 实现骨架

为了避免业务层直接绑定 PostgreSQL、某个 RDF Store 或图数据库，建议定义统一存储接口。

### 8.1 核心接口

```

package graphstore

import (
    "context"
    "time"
)

type TermKind string

const (
    TermIRI     TermKind = "IRI"
    TermBlank   TermKind = "BLANK_NODE"
    TermLiteral TermKind = "LITERAL"
)

type Term struct {
    Kind      TermKind
    Value     string
    Datatype  string
    Language  string
}

type TriplePattern struct {
    Subject   *Term
    Predicate *Term
    Object    *Term
    Graphs    []string
}

type FactRef struct {
    GraphIRI       string
    Subject        Term
    Predicate      Term
    Object         Term
    FactKind       string
    ObservedAt     time.Time
    ValidFrom      *time.Time
    ValidTo        *time.Time
    SourceRefs     []string
}

type QueryOptions struct {
    MaxRows       int
    Deadline      time.Time
    SnapshotID    string
    IncludeDerived bool
}

type QueryResult struct {
    Facts      []FactRef
    Truncated  bool
    SnapshotID string
}

type GraphStore interface {
    Match(
        ctx context.Context,
        pattern TriplePattern,
        options QueryOptions,
    ) (QueryResult, error)

    ApplyBatch(
        ctx context.Context,
        graphIRI string,
        facts []FactRef,
    ) error

    CreateSnapshot(
        ctx context.Context,
        graphIRIs []string,
    ) (string, error)

    Health(ctx context.Context) error
}

```

这个接口展示核心访问能力。正式实现还需要增加游标分页、事务语义、删除标记、并发版本检查、查询计划统计和错误分类。

### 8.2 接口设计原则

- 不把任意 SPARQL 字符串作为底层通用业务 API。
- 不允许 Agent 自行决定读取哪些租户或命名图。
- 存储层应支持稳定的分页与查询取消。
- 大型结果集应使用游标或流式接口，避免一次性加载到内存。
- 推理事实应明确标记，不能与来源事实混为一谈。
- 写入应由受控的数据更新服务执行，而不是开放给任意 Agent 工具。

对于确实需要标准 SPARQL 的高级用户，可以提供单独的受限 SPARQL 入口，执行语法、权限、资源和查询复杂度检查后再运行。

## 9. 语义查询语言与查询 API

ODAP 需要让 Agent 查询企业语义，而不必了解底层图存储的物理结构。

建议采用两层查询接口：

1. Semantic Query DSL：面向 Agent 与业务应用的受控结构化查询。
2. 内部 Logical Query IR：用于优化器与执行器之间传递查询计划。

标准 SPARQL 可以作为后续高级接口，但不应成为 Agent 默认直接操作的查询语言。

### 9.1 为什么不直接让 LLM 生成 SPARQL？

让 LLM 直接生成 SPARQL 有几个问题：

- 可能访问未经授权的图或敏感属性。
- 可能产生过度复杂的属性路径和笛卡尔积。
- 可能遗漏租户范围、时间条件或数据新鲜度约束。
- 可能错误地把缺失值当成否定条件。
- 可能生成语法正确但业务语义错误的查询。
- 难以为每个查询建立稳定的资源预算和执行计划。

因此，建议 Agent 生成结构化查询意图，由 ODAP 校验、编译和执行。

### 9.2 Semantic Query DSL

例如，查询某个部门的报销单，并获取员工、金额和状态：

```
{
  "query_id": "expense-query-001",
  "from": {
    "class": "ExpenseClaim",
    "as": "claim"
  },
  "select": [
    {
      "path": "claim.sourceClaimId",
      "as": "claimId"
    },
    {
      "path": "claim.submittedBy.employeeId",
      "as": "employeeId"
    },
    {
      "path": "claim.claimAmount",
      "as": "amount"
    },
    {
      "path": "claim.claimStatus",
      "as": "status"
    }
  ],
  "where": [
    {
      "path": "claim.submittedBy.belongsTo.departmentId",
      "op": "EQ",
      "value": "FIN"
    }
  ],
  "options": {
    "limit": 100,
    "consistency": "SNAPSHOT",
    "includeEvidence": true
  }
}
```

这是一个结构化查询示例，不是完整的正式 DSL。正式实现需要定义路径语法、类型规则、空值语义、时间条件、分页、聚合和推理模式。

其中的 `claim.submittedBy.belongsTo.departmentId` 表示受控的多跳语义路径，不应简单地把它当成数据库中的点分隔字段名。

### 9.3 运算符白名单

V1.0 建议只允许：

| 类别  | 运算符                              |
| --- | -------------------------------- |
| 比较  | `EQ`、`NEQ`、`GT`、`GTE`、`LT`、`LTE` |
| 集合  | `IN`、`NOT_IN`                    |
| 存在性 | `EXISTS`、`IS_NULL`、`IS_NOT_NULL` |
| 逻辑  | `AND`、`OR`、`NOT`                 |
| 文本  | `CONTAINS`、`PREFIX`              |
| 时间  | `BEFORE`、`AFTER`、`DURING`        |
| 聚合  | `COUNT`、`SUM`、`MIN`、`MAX`、`AVG`  |
| 图关系 | 受控的路径遍历、类型约束、关系存在性               |

每个运算符都应有明确的类型、缺失值和错误语义。

例如，`NOT_IN` 不应自动将缺失值当成“不在集合中”。应明确采用三值逻辑、显式缺失判断，或由查询 Schema 规定缺失值的处理方式。

### 9.4 查询结果模型

查询结果不应只有一组字段值。

建议返回：

```
{
  "status": "OK",
  "query_id": "expense-query-001",
  "snapshot_id": "snapshot-20261012-001",
  "ontology_version": "finance-ontology@1.2.0",
  "reasoning_profile": "odap-rdfs-basic@1.0",
  "rows": [
    {
      "claimId": "CLM-1024",
      "employeeId": "E1024",
      "amount": {
        "value": "1250.00",
        "currency": "CNY"
      },
      "status": "PENDING_APPROVAL"
    }
  ],
  "metadata": {
    "truncated": false,
    "freshness_status": "FRESH",
    "quality_status": "VALID",
    "evidence_available": true
  }
}
```

其中 `OK` 只表示查询执行成功，并不表示业务条件满足或数据已经获得授权用于某项写入操作。后续业务规则与授权决策仍需独立执行。

### 9.5 查询 API

建议提供：

- `POST /api/v1/semantic/query`
- `POST /api/v1/semantic/query/validate`
- `POST /api/v1/semantic/query/explain`
- `GET /api/v1/semantic/query/{id}`
- `GET /api/v1/semantic/query/{id}/evidence`
- `POST /api/v1/semantic/validate`
- `POST /api/v1/semantic/reason`
- `GET /api/v1/semantic/reason/{id}`

长时间运行的查询和推理应采用异步任务模式，与第十篇的任务事件总线集成。

## 10. 查询编译器与逻辑计划

### 10.1 编译流水线

建议查询执行采用以下流程：

```
Semantic Query DSL
        ↓
Parser
        ↓
Schema & Type Checker
        ↓
Authorization Scope Injection
        ↓
Logical Query IR
    ↓
Rule / Ontology Expansion
    ↓
Rule-Based Optimizer
（V1.0：Join 选择性排序 + 谓词/投影下推）
    ↓
Physical Query Plan
    ↓
Query Executor
    ↓
Result + Quality + Evidence
```

每一步都应能够输出明确的错误类型和诊断信息。

例如：

- `UNKNOWN_CLASS`
- `UNKNOWN_PROPERTY`
- `TYPE_MISMATCH`
- `UNAUTHORIZED_PROPERTY`
- `UNSUPPORTED_PATH`
- `QUERY_TOO_COMPLEX`
- `STALE_SNAPSHOT`
- `REASONING_PROFILE_UNSUPPORTED`

**优化器分级（V1.0 规则式，CBO 移入 V2.0 评估清单）**：V1.0 优化器为**规则式**，只实现两类经评审的变换：

1. **Join 选择性排序**：按谓词/类实例数（来自 §11.1 统计信息）对多跳 Join 重排序，从高选择性端开始执行。
2. **谓词/投影下推**：把过滤条件下推为 PG SQL 的 `WHERE` 与最小列集，避免把无关三元组拉回应用层。

规则式优化不枚举候选计划空间。“优化前后语义等价”的正确性风险由**规则白名单**控制：只有白名单内的变换允许启用，每个变换必须有等价性测试（§26.2）；白名单之外的“优化”一律禁止。成本优化器（CBO：基于统计信息枚举候选计划、估算成本、择优执行）**移入 V2.0 评估清单**（见 §11.1），V1.0 不实现。

### 10.2 Logical Query IR

查询 IR 应独立于底层存储。

建议定义以下算子：

- `ScanClass`：扫描指定本体类的实例。
- `MatchTriple`：匹配三元组模式。
- `Join`：连接两个中间结果集。
- `PathExpand`：执行受控关系路径遍历。
- `Filter`：过滤结果。
- `Project`：选择输出字段。
- `Aggregate`：聚合。
- `Sort`：排序。
- `Limit`：限制结果数。
- `TemporalFilter`：过滤业务有效时间。
- `SourceFilter`：限定来源或数据快照。
- `Reason`：执行指定推理规则。
- `Validate`：执行约束验证。
- `AttachEvidence`：附加来源和推导证据。

查询 IR 可以使用 Go 结构体表示：

```

package queryir

type NodeID int64

type Operator string

const (
    OpScanClass    Operator = "SCAN_CLASS"
    OpMatchTriple  Operator = "MATCH_TRIPLE"
    OpJoin         Operator = "JOIN"
    OpFilter       Operator = "FILTER"
    OpProject      Operator = "PROJECT"
    OpAggregate    Operator = "AGGREGATE"
    OpPathExpand   Operator = "PATH_EXPAND"
    OpTemporal     Operator = "TEMPORAL_FILTER"
    OpReason       Operator = "REASON"
    OpValidate     Operator = "VALIDATE"
    OpAttachEvidence Operator = "ATTACH_EVIDENCE"
)

type PlanNode struct {
    ID       NodeID
    Op       Operator
    Inputs   []NodeID
    Params   map[string]any
    EstimatedRows float64
    EstimatedCost float64
}

type LogicalPlan struct {
    Root NodeID
    Nodes []PlanNode
    OntologyVersion string
    SnapshotID string
    ReasoningProfile string
}

```

正式实现中，建议用类型化参数结构替代大量无约束的 `map[string]any`，以便进行静态校验、序列化和兼容性管理。

### 10.3 逻辑计划与物理计划分离

同一个查询可以采用不同的物理执行策略：

- 通过 SPO 索引查找三元组。
- 通过 POS 索引反向查找。
- 从选择性更高的类实例集合开始。
- 先过滤敏感或不满足时间条件的候选记录。
- 先执行低成本过滤，再执行昂贵的路径扩展。
- 使用已经验证的物化推理结果。
- 对小结果集使用内存连接，对大结果集采用分批或外部连接。

因此，不应在 DSL 编译阶段就把查询写死为某种 SQL 或 RDF Store 专属语法。

### 10.4 类型检查

在进入执行阶段前，查询编译器应检查：

- 类是否存在。
- 属性是否属于目标类或适用的类型层次。
- 对象属性与字面值属性是否使用正确。
- 比较操作符是否适用于相应类型。
- 关系路径的目标类型是否兼容。
- 聚合操作是否适用于相应值。
- 本体版本是否支持所请求的特性。
- 查询者是否具有所需的数据访问权限。

类型检查失败的查询应返回明确诊断，而不是等到底层数据库执行后再出现难以解释的错误。

## 11. 查询优化策略

语义查询的主要成本往往来自低选择性扫描、多跳遍历、重复推理、跨源连接和结果集膨胀。

建议采用以下优化机制。

### 11.1 统计信息与规则式优化（V1.0）

为每个图和关键谓词维护统计信息，例如：

- 图中的三元组数量。
- 各谓词出现次数。
- 类实例数量。
- 不同主语和宾语的数量估计。
- 属性空值或缺失比例。
- 高频关系的平均度数。
- 数据快照与统计信息的版本。

**V1.0 的定位**：这些统计信息只服务于规则式优化——Join 选择性排序依据谓词/类实例数决定连接顺序，谓词与投影下推依据列选择性决定过滤位置。V1.0 **不实现 CBO**（成本优化器：枚举候选计划、估算成本、择优执行），理由是自研 CBO 的性价比低：企业本体查询以点查、二到四跳遍历为主，规则式排序已覆盖主要收益；而 CBO 的正确性风险（统计失真导致计划劣化、变换语义不等价）需要大量回归测试才能收敛。**CBO 移入 V2.0 评估清单**，与 PG 执行器下推能力、专用 Store 的计划器能力一并评估；若 V2.0 引入 CBO，必须同样经过规则白名单与等价性测试门禁（§10.1）。

统计信息过期时，应允许重新估算或选择更保守的执行计划（按谓词字典序等确定性规则回退）。

### 11.2 Join Reordering（规则式）

假设查询涉及：

```
ExpenseClaim
  → submittedBy → Employee
  → belongsTo → Department
  → hasBudget → Budget
```

如果某个部门只关联少量预算对象，而全企业员工数量很大，规则式优化器应按统计信息中的实例数，从选择性更高的一端（本例为部门/预算侧）开始遍历，而不是固定按查询文本中的顺序。V1.0 只做单次选择性排序，不枚举全部连接顺序——枚举与成本择优是 CBO 的职责，已移入 V2.0 评估清单（§11.1）。

### 11.3 路径扩展限制

多跳关系查询可能出现指数级结果膨胀。

因此 V1.0 建议限制：

- 最大路径深度。
- 每个中间节点的最大扩展数。
- 总候选节点数。
- 总访问三元组数。
- 查询总耗时。
- 最大返回行数。
- 最大证据引用数。

限制触发后，返回 `QUERY_BUDGET_EXCEEDED` 或 `TRUNCATED`，并明确说明结果是否完整。

不能在超过预算后直接返回部分结果并伪装成完整结果。

### 11.4 谓词索引与常用路径索引

对高频业务路径可以维护专用索引，例如：

- `ExpenseClaim → submittedBy → Employee`
- `Employee → belongsTo → Department`
- `Department → hasBudget → Budget`

这些索引可以是底层三元组索引、物化关系表或其他适合的结构。

但应注意：专用索引属于性能优化，不应成为另一个独立的事实权威源。它必须能够从权威语义数据重建，并与版本和更新机制保持一致。

### 11.5 缓存策略

建议建立分层缓存：

- 本体 Schema 与类型信息缓存。
- 查询计划缓存。
- 稳定统计信息缓存。
- 经过版本锁定的推理结果缓存。
- 受控的只读查询结果缓存（**只存最宽权限投影结果**，见下）。

缓存键至少包含：

```
tenant_id
+ authorization_scope_digest
+ ontology_digest
+ import_lock_digest
+ snapshot_id
+ mapping_version_set_digest
+ reasoning_profile_digest
+ query_digest
+ data_policy_digest
```

如果查询依赖实时权限、动态 ERP 状态或高频变化数据，必须验证缓存的新鲜度，并在需要时重新查询权威来源。

缓存命中不能跳过授权检查。 同样，缓存的推理结果不能在本体、数据快照或规则版本改变后被当作当前有效结果。

**结果缓存的安全边界（只存最宽权限投影）**：缓存条目只允许保存**最宽权限投影**的结果——对该租户内所有通过基础认证的调用方均可见的字段与行。收窄授权范围（按部门、密级、对象 ACL 过滤）的查询，不得把收窄结果写入共享缓存：缓存键中的 `authorization_scope_digest` 只能防止跨版本串用，不能把“窄权限结果被写宽后泄露”的风险归零。正确做法是缓存最宽投影，命中后按当前调用方的授权范围重新过滤输出（§7.3、§21.4）。

## 12. 多源语义推理引擎

这是本篇最重要的部分之一。

企业语义推理不是让 LLM 阅读几条记录后给出一个看似合理的答案，而是基于明确的事实、类型体系、逻辑规则和可验证的执行过程，计算出哪些结论能够成立。

### 12.1 将推理划分为四类

建议把 ODAP 的推理能力分为四个独立层次。

第一类：本体逻辑推理

根据 RDFS 或明确支持的 OWL 语义推导类型和关系。

例如：某个类是另一个类的子类，实例属于该子类时，可以推出其属于父类。

第二类：规则推理

根据显式规则，从已有事实推出新的业务关系或派生属性。

例如：员工属于某部门，且该部门属于某组织单元，可以在相应规则条件下推出员工归属该组织单元。

第三类：约束验证

根据 SHACL 形状与数据契约，检查当前数据图是否符合声明的要求。

例如：报销单必须具有员工引用，金额必须是合法的非负数。

第四类：业务决策推理

根据企业制度、业务状态、阈值、授权和审批政策，形成业务决策结果。

例如：某笔费用是否需要额外审批；最终操作仍须经过独立授权和审批流程。

这四类推理的输出可以互相引用，但不能互相替代。

### 12.2 推理配置（Reasoning Profile）

建议将推理配置作为独立版本化资产，而不是将所有规则默认打开。

示例：

```
apiVersion: odap.io/v1
kind: ReasoningProfile

metadata:
  id: enterprise-rdfs-basic
  version: 1.0.0

spec:
  semantics:
    rdfs: true
    owlProfile: none

  rules:
    bundle: enterprise-derived-relations@1.0.0

  execution:
    mode: query_rewrite
    maxIterations: 10
    maxDerivedFacts: 100000
    timeoutSeconds: 10

  evidence:
    trackSourceFacts: true
    trackRuleApplications: true

  unsupportedSemantics:
    behavior: reject
```

这只是一个配置示例。正式版本必须定义 `owlProfile`、规则包依赖、闭包语义、递归规则、冲突策略和推理器版本等字段。

这里的 `owlProfile: none` 表示该配置不启用 OWL 配置文件推理，不代表 RDF 或 RDFS 基础语义被关闭。

### 12.3 RDFS 推理示例

假设企业本体声明：

```
odap:FinanceEmployee rdfs:subClassOf odap:Employee .
odap:Employee rdfs:subClassOf odap:Person .

odap:E1024 a odap:FinanceEmployee .
```

在正确应用相关 RDFS 语义后，可以推出：

```
odap:E1024 a odap:Employee .
odap:E1024 a odap:Person .
```

对应的 W3C RDFS 官方规则编号（RDF Semantics 规范的 entailment rules）：

- `rdfs11`：`(?u rdfs:subClassOf ?v) ∧ (?v rdfs:subClassOf ?w) → (?u rdfs:subClassOf ?w)`——子类传递闭包，先把 `FinanceEmployee → Employee → Person` 的传递关系算入。
- `rdfs9`：`(?u rdfs:subClassOf ?v) ∧ (?x rdf:type ?u) → (?x rdf:type ?v)`——子类关系应用到实例类型。

本例实际触发链：`rdfs11` 计算子类传递闭包，再对实例应用 `rdfs9`。若本体启用 `rdfs:domain`，还会触发 `rdfs2`：`(?p rdfs:domain ?c) ∧ (?x ?p ?y) → (?x rdf:type ?c)`。V1.0 的 RDFS 子集**逐条锚定 W3C 规则编号**，完整清单与状态见 §14.1；派生记录必须携带规则编号（如 `rdfs9`）与规则包版本，供 Evidence Service 复核。

这里的派生类型不是来源系统直接提供的事实，而是根据本体结构推导出来的事实。

ODAP 应能够说明该结论来自哪条原始类型事实、哪几条子类声明，以及哪个推理配置。

### 12.4 受控规则推理示例

假设业务规则定义：

```
如果 Employee belongsTo Department，
且 Department belongsTo OrganizationUnit，
那么 Employee belongsToOrganizationUnit OrganizationUnit。
```

可将其表示为受控规则：

```
{
  "rule_id": "employee-org-unit-v1",
  "rule_type": "derived_relation",
  "body": [
    {
      "pattern": "Employee(?e)",
      "bind": "e"
    },
    {
      "pattern": "belongsTo(?e, ?d)",
      "bind": "d"
    },
    {
      "pattern": "belongsTo(?d, ?u)",
      "bind": "u"
    }
  ],
  "head": [
    {
      "predicate": "belongsToOrganizationUnit",
      "subject": "?e",
      "object": "?u"
    }
  ]
}
```

这只是规则表达的示意。正式规则 IR 应定义变量类型、前置条件、空值语义、递归限制、规则冲突和输出类型检查。

规则编译器必须确保：

- 输入事实与变量类型兼容。
- 输出关系的主语和宾语类型正确。
- 规则不越过租户或权限边界。
- 推导结果具有来源和规则引用。
- 规则执行不会无限递归。
- 同一事实被重复推导时可以去重。

### 12.5 为什么不把所有推理都交给 LLM？

LLM 可以协助生成候选规则、解释推理结果和建议映射，但不适合作为事实闭包、类型检查和确定性业务约束的唯一执行器。

原因是：

- 模型输出不一定稳定。
- 同样输入可能产生不同解释。
- 模型无法自动保证完整覆盖所有逻辑后果。
- 生成的解释不能替代实际执行轨迹。
- 业务阈值、授权和审批需要明确规则与责任边界。

推荐的模式是：

LLM 负责提出假设与候选规则；规则编译器负责类型与语法检查；推理引擎负责执行；验证器负责检查；Evidence Service 负责记录结果。

## 13. 推理执行策略：查询时、预计算与增量物化

不同类型的推理应采用不同执行方式。

### 13.1 三种执行模式

| 模式                          | 原理                | 适用场景        |
| --------------------------- | ----------------- | ----------- |
| Query Rewriting             | 将推理规则转换为查询扩展      | 规则简单、查询范围较小 |
| Full Materialization        | 预先计算并存储全部目标派生事实   | 规则稳定、查询频繁   |
| Incremental Materialization | 根据变化的事实重新计算受影响的结论 | 持续更新的企业业务图  |

### 13.2 查询时推理

查询时推理适合范围小、规则少、实时性要求高的请求。

例如，查询某个员工的全部父级类型时，可以根据子类关系递归扩展，而不必将每个实例的所有父级类型永久写入事实存储。

优点是减少冗余存储，规则更新后更容易使用新配置。

缺点是复杂查询可能重复计算相同的逻辑结果，延迟较高。

### 13.3 全量物化

全量物化将派生事实提前计算并存储。

例如：

```
Source Graph
    ↓
Reasoning Profile
    ↓
Materialization Job
    ↓
Derived Graph
```

适合稳定的组织层级、类型继承和经常查询的派生关系。

物化结果必须记录：

- 输入数据快照。
- 本体版本。
- 规则包版本。
- 推理器版本。
- 生成时间。
- 计算状态。
- 来源与规则追踪引用。

不能把派生事实写入与来源事实完全相同的记录类别，再失去其推导来源。

### 13.4 增量物化

企业业务数据持续变化，完全重建整张图可能代价过高。因此需要增量推理。

假设一条事实发生变化：

```
Employee_E1024 belongsTo Department_FIN
```

受影响的派生结果可能包括：

- 员工所属组织单元。
- 员工所在部门的统计集合。
- 依赖部门归属的某些规则结果。
- 与该员工有关的下游验证状态。

增量引擎应维护依赖关系，只重新计算可能受影响的派生事实。

### 13.5 删除事实比增加事实更复杂

增加一条事实可能产生新的结论；删除一条事实则需要判断哪些结论不再成立。

如果某个派生事实由两个独立的规则路径支持，删除其中一条来源并不意味着该结论一定应删除。

因此，增量推理需要记录：

- 派生事实由哪些规则实例产生。
- 每个规则实例依赖哪些前提事实。
- 是否还有其他有效推导路径。
- 对应前提事实是否仍然有效。
- 是否存在来源撤销、时间过期或规则版本变更。

对于复杂递归规则，不能仅靠简单的反向传播删除所有依赖结果，否则可能误删仍然成立的结论。

**V1.5 算法基线：DRed（Delete-Redata）**。增量删除采用 DRed 算法作为正确性基线：对每条待删事实，先通过“过度删除”（over-delete）标记所有可能受影响的派生事实及规则头，再用重新推导（re-derive）验证每个被标记事实是否仍被其他有效推导支持，只撤销确实失去全部支持的结论。关键不变量：**重新推导确认前，不得物理删除任何派生事实**；所有撤销以“逻辑失效标记 + 重算确认”两阶段完成。

DRed 的适用边界：在非递归或受限递归规则集（企业组织层级、类型继承类规则）内可给出完整的正确性论证；对任意用户自定义递归规则，DRed 只保证“不漏删、可能多标”，多标部分由局部重算收敛。

### 13.6 V1.0 的推荐实现

先实现：

1. 基础 RDFS 子类与子属性推理（锚定 `rdfs7`/`rdfs9`/`rdfs11` 等规则编号，清单见 §14.1）。
2. 有类型约束的受控规则引擎。
3. 查询时推理。
4. 对少量稳定关系的全量物化。
5. 推理结果版本化与可重建。
6. 对复杂增量删除采用受控失效与局部重算；**增量删除的算法基线为 DRed**（§13.5），非递归与受限递归规则集内要求完整正确性论证。

**DRed 删除测试矩阵**（每条用例必须可复现、可断言，纳入 §26.3 推理正确性回归）：

| 用例 | 场景 | 期望行为 |
| --- | --- | --- |
| D1 | 单路径支持的事实被删除 | 派生结论被撤销，撤销记录保留前提与规则引用 |
| D2 | 多路径支持的结论删一条来源 | 结论保留，推导记录中该路径标记失效，其余路径有效 |
| D3 | 删除后又有新事实补回同一支持 | 结论恢复有效，不产生重复派生记录 |
| D4 | 递归规则（组织层级）中间节点删除 | 下游按 DRed 过度删除 + 重新推导收敛，无误删 |
| D5 | 来源撤销 vs 业务有效期过期（`valid_to`） | 两者走同一失效路径，派生结论按规则版本重新判定 |
| D6 | 规则包升级导致原推导不再成立 | 旧结论逻辑失效并保留历史引用，新规则闭包另行构建 |
| D7 | 并发删除与并发推导竞争 | 以快照隔离 + 物化版本指针保证不出现"删到一半的闭包"对外可见 |

等到有实际业务数据和性能测试后，再实现更复杂的增量闭包算法。

## 14. OWL 语义支持与一致性检查

OWL 推理必须有明确的支持范围，不能把 OWL 文件解析成功等同于本体一致性验证成功。

### 14.1 建议的支持矩阵

| 能力                       | V1.0 建议  | 说明                 |
| ------------------------ | -------- | ------------------ |
| RDF 基础图模型                | 支持       | 资源、字面值、命名图等        |
| `rdfs:subClassOf`        | 支持       | 子类推理，规则 `rdfs9` / `rdfs11` |
| `rdfs:subPropertyOf`     | 支持       | 子属性推理，规则 `rdfs5` / `rdfs7` |
| `rdfs:domain` / `range`  | 支持       | 在相应 RDFS 语义下推导类型，规则 `rdfs2` / `rdfs3` |
| `owl:equivalentClass`    | 受控支持     | 需明确处理双向类关系及相关语义    |
| `owl:equivalentProperty` | 受控支持     | 需验证推理规则和循环         |
| `owl:inverseOf`          | 受控支持     | 允许推导逆关系            |
| `owl:TransitiveProperty` | 受控支持     | 必须限制递归和计算资源        |
| `owl:SymmetricProperty`  | 受控支持     | 根据规则推导反向关系         |
| `owl:FunctionalProperty` | 谨慎处理     | 不能简单地将多个值判定为非法 RDF |
| `owl:sameAs`             | 谨慎处理     | 可能造成大量等价关系扩展，仅限审核后的实体合并（§17） |
| OWL 2 RL                 | V1.5 决策点 | V1.0 不实现；V1.5 二选一：外挂成熟 reasoner 服务，或范围收紧为 RDFS+商业规则（§2.2），不以"分阶段支持"含糊表述 |
| OWL 2 DL 完整推理            | 不承诺 V1.0 | 需要专门推理后端与复杂度评估     |

表中的“受控支持”表示需要通过明确的功能契约、规则定义和测试来实现，并不代表已经实现了全部相关 OWL 语义。

**RDFS / OWL 子集实现清单（锚定 W3C 官方规则编号）**——V1.0 逐条声明，未列入的规则即未实现：

| 规则编号 | 语义 | V1.0 状态 |
| --- | --- | --- |
| `rdfs2` | `rdfs:domain` 推导主体类型 | 实现 |
| `rdfs3` | `rdfs:range` 推导客体类型 | 实现 |
| `rdfs5` | `rdfs:subPropertyOf` 传递 | 实现 |
| `rdfs7` | `rdfs:subPropertyOf` 应用到实例三元组 | 实现 |
| `rdfs9` | `rdfs:subClassOf` 应用到实例类型 | 实现 |
| `rdfs11` | `rdfs:subClassOf` 传递 | 实现 |
| `owl:sameAs` | 等价个体（受控，§17） | 受控支持，仅审核后的合并 |
| `owl:equivalentClass` / `owl:equivalentProperty` | 等价类/属性 | 受控支持（展开为双向子类/子属性后复用 rdfs 规则） |
| `owl:inverseOf` | 逆属性 | 受控支持 |
| `owl:TransitiveProperty` | 传递属性 | 受控支持，递归预算受限（§21.2） |
| `owl:SymmetricProperty` | 对称属性 | 受控支持 |
| `owl:FunctionalProperty` | 函数式属性 | 谨慎处理（见上表），不推导非法性 |
| OWL 2 RL 其余规则 | 完整 RL 规则集 | **V1.0 不实现；V1.5 二选一决策点**（§2.2） |

**假阴性风险提示**：上表“未实现”的规则不是语义中立——对于依赖这些规则的推导，引擎将**漏推导（假阴性）**，即结论客观可由本体推出，但 ODAP 不会推出。因此：

1. 每个发布的本体包必须声明其依赖的规则集合；若依赖未实现规则，发布时给出明确告警并由本体负责人确认（与第五篇发布流程衔接）。
2. 查询结果中的"未找到"必须结合 §14.2 开放世界语义解释，不得把漏推导表现为"事实为假"。
3. `GET /api/v1/semantic/capabilities`（§23.1）必须返回本清单的运行时版本，供上层 Agent 与治理工作台显式展示推理能力边界。

**一致性测试套件**：RDFS / OWL 子集实现必须配套 W3C 官方测试集（RDFS 与 OWL 2 RL 的 W3C Approved Test Suites）等价用例——每条实现的规则至少覆盖正向推导、负向（不变量不破坏）、边界（空图、自反/循环子类声明）三类用例；测试随推理器版本固定，回归门禁见 §26.3。

### 14.2 开放世界假设

企业语义系统必须清楚区分开放世界假设（Open World Assumption，OWA）与封闭世界业务查询。

在开放世界假设下：

> 当前图中没有某条事实，并不意味着该事实为假。

例如，当前没有找到：

```
ExpenseClaim_X hasEvidence Receipt_Y
```

这并不能单独证明报销单没有凭证。可能是数据尚未同步，也可能是凭证存储在另一个系统，或者当前主体没有权限查看。

因此，ODAP 应区分：

- 已知为真。
- 已知为假，且具有明确依据。
- 当前未知。
- 数据缺失。
- 数据过期。
- 无权访问。
- 查询执行不完整。

### 14.3 开放世界与企业业务规则

企业业务规则有时确实要求在指定范围内执行封闭世界判断。

例如：

“在已确认完整的报销凭证清单中，如果报销单没有关联任何有效凭证，则要求补充凭证。”

这个判断依赖于“凭证清单已经完整”的前提。若数据接入状态未知，就不能仅凭图中没有凭证关系，直接得出业务违规结论。

建议将以下内容写入规则上下文：

- 事实来源范围。
- 数据快照。
- 必需的数据集是否完整。
- 数据新鲜度要求。
- 当前主体是否有权查看相关事实。
- 查询是否完整执行。

### 14.4 一致性状态

建议统一定义：

- `CONSISTENT`：在指定语义与检查范围内未发现不一致。
- `INCONSISTENT`：发现明确的逻辑或约束冲突。
- `INCOMPLETE`：缺少必要数据或检查未覆盖全部范围。
- `UNKNOWN`：无法确定。
- `ERROR`：检查器或执行过程发生技术错误。

对于 OWL，逻辑一致性与 SHACL 数据约束是两种不同检查。一个 RDF 图可能在 OWL 语义下保持一致，却违反企业 SHACL 约束；反之，也不能仅凭 SHACL 验证通过就证明本体逻辑一致。

## 15. SHACL 验证引擎设计

SHACL 主要用于验证 RDF 数据图是否满足声明的形状约束。它应当是 ODAP 语义验证体系中的独立模块。

### 15.1 SHACL 的职责

例如，企业规定每笔报销必须具有员工引用，并且金额必须为非负数。

```
@prefix sh: <http://www.w3.org/ns/shacl#> .
@prefix odap: <https://ontology.example/odap#> .
@prefix xsd: <http://www.w3.org/2001/XMLSchema#> .

odap:ExpenseClaimShape
    a sh:NodeShape ;
    sh:targetClass odap:ExpenseClaim ;

    sh:property [
        sh:path odap:submittedBy ;
        sh:minCount 1 ;
        sh:maxCount 1 ;
        sh:class odap:Employee ;
    ] ;

    sh:property [
        sh:path odap:claimAmount ;
        sh:minCount 1 ;
        sh:datatype xsd:decimal ;
        sh:minInclusive 0 ;
    ] .
```

这段示例表达报销单的结构约束。正式模型还应考虑币种、精度、对象关系的唯一性、来源质量和适用的业务规则。

**V1.0 SHACL 支持矩阵（核心约束，显式排除 `sh:sparql`）**：

| 约束组件 | V1.0 状态 | 说明 |
| --- | --- | --- |
| `sh:targetClass` / `sh:targetNode` / `sh:targetSubjectsOf` / `sh:targetObjectsOf` | 实现 | 目标声明 |
| `sh:property` + `sh:path`（单步谓词路径） | 实现 | `sh:alternativePath`、序列路径 V1.5 评估 |
| `sh:minCount` / `sh:maxCount` | 实现 | 基数约束 |
| `sh:datatype` / `sh:class` / `sh:node` | 实现 | 类型与节点约束 |
| `sh:minInclusive` / `sh:maxInclusive` / `sh:minExclusive` / `sh:maxExclusive` | 实现 | 值域约束 |
| `sh:pattern` / `sh:minLength` / `sh:maxLength` | 实现 | 字符串约束 |
| `sh:in` | 实现 | 枚举约束 |
| `sh:not` / `sh:and` / `sh:or` / `sh:xone` | 实现 | 逻辑组合 |
| `sh:closed` / `sh:ignoredProperties` | 实现 | 封闭形状 |
| `sh:equals` / `sh:disjoint` / `sh:lessThan` / `sh:lessThanOrEquals` | 实现 | 比较约束 |
| `sh:hasValue` | 实现 | 固定值约束 |
| `sh:qualifiedValueShape` 及 `sh:qualifiedMinCount` / `sh:qualifiedMaxCount` | 实现 | qualified 约束（递归深度受限） |
| `sh:sparql`（含 `sh:ask` / `sh:select`） | **显式排除** | 与 §8.2/§9.1"不自研 SPARQL"的边界一致：V1.0 不实现 `sh:sparql`；需要此类约束的业务场景改用受控规则（§12.4）或 V1.5 的 reasoner 服务实现 |
| SHACL Advanced Features（`sh:expression`、`sh:rule` 等） | 显式排除 | 派生规则走 §12 推理引擎，不走 SHACL 规则扩展 |

形状文件中出现 `sh:sparql` 时，验证器**不得静默跳过该约束后报告“通过”**——必须返回明确的 `UNSUPPORTED_SEMANTICS` 诊断（§23.3 错误码表），否则会制造“验证通过”的假象。

### 15.2 验证结果模型

建议统一输出：

```
{
  "validation_id": "validation-001",
  "status": "FAIL",
  "shapes_digest": "sha256:...",
  "data_snapshot_id": "snapshot-001",
  "findings": [
    {
      "focus_node": "ExpenseClaim/CLM-1024",
      "result_path": "submittedBy",
      "severity": "Violation",
      "source_shape": "ExpenseClaimShape",
      "message_code": "REQUIRED_EMPLOYEE_REFERENCE_MISSING"
    }
  ]
}
```

验证结果应区分：

- `PASS`
- `FAIL`
- `INCOMPLETE`
- `UNKNOWN`
- `ERROR`

其中，`FAIL` 应表示在指定检查范围内发现了明确违规；`INCOMPLETE` 表示数据范围或验证过程不完整。不能在验证器超时后将结果标记为通过。

### 15.3 增量 SHACL 验证

对大规模企业图，每次数据变化后重跑所有形状可能代价很高。

建议按影响范围进行增量验证：

1. 根据变化事实识别受影响的节点。
2. 查找相关的目标形状。
3. 重新执行相关约束。
4. 更新验证发现项。
5. 对依赖全局约束的规则安排更大范围的检查。

对于涉及全局唯一性、复杂 SPARQL 约束或大量跨节点依赖的形状，增量验证的安全性需要专门评估。无法可靠限定影响范围时，应执行完整验证或明确标记验证不完整。

### 15.4 验证与写入隔离

SHACL 验证不应直接修改业务数据以消除错误。

如果验证发现报销单缺少员工引用，正确流程是：

- 保留原始事实。
- 创建验证发现项。
- 进入隔离或待修复状态。
- 通过数据映射或业务流程补齐数据。
- 重新验证。
- 保留原始失败与修复记录。

这样才能避免“数据为了通过验证而被系统偷偷改写”的问题。

## 16. 多源事实协调与语义冲突处理

企业本体图中的事实可能来自多个系统。真正的困难不在于把它们放到同一张图中，而在于判断不同来源的事实如何共同成立。

### 16.1 四种常见冲突

身份冲突

两个来源可能把不同实体映射到同一个本体实例。

属性冲突

不同系统对员工所属部门、合同状态或业务日期给出不同值。

时间冲突

一个来源记录的是历史状态，另一个来源记录的是当前状态。

口径冲突

两个系统都提供“预算余额”，但一个表示会计余额，另一个表示扣除预占后的可用预算。

这四类问题需要不同的处理策略，不能统一用“取最新值”解决。

### 16.2 属性级权威策略

建议为每个关键本体属性定义治理策略：

```
property: odap:employmentStatus

authority:
  preferredSources:
    - hr-master
  fallbackSources:
    - erp-main

temporal:
  mode: valid_time
  requireFreshness: true

conflict:
  strategy: quarantine
  requireReview: true
```

这表示 HR 是优先来源，ERP 可以作为后备来源，但出现冲突时需要隔离并复核。

它不代表 HR 的任何字段都自动可信。正式策略还需要指定有效时间、来源质量、允许的后备条件、冲突处理和审批责任人。

### 16.3 来源优先级不等于事实真实性

即使某来源具有较高权威性，也可能出现：

- 来源数据延迟。
- 记录被错误修改。
- 字段映射版本错误。
- 数据快照不完整。
- 业务有效时间不一致。

因此，协调策略至少应综合考虑：

\\[ R = f(A, T, Q, V, C) \\]

其中：

- \\(A\\)：来源权威等级。
- \\(T\\)：时间有效性和新鲜度。
- \\(Q\\)：数据质量。
- \\(V\\)：映射与 Schema 版本。
- \\(C\\)：上下文和业务规则。

这里的 \\(R\\) 不是自动证明真实性的数学公式，而是表达来源协调应考虑的因素。具体优先级与决策必须由企业规则定义。

### 16.4 事实协调结果

建议使用：

- `ACCEPTED`
- `ACCEPTED_WITH_WARNING`
- `CONFLICT`
- `STALE`
- `UNRESOLVED`
- `INSUFFICIENT_EVIDENCE`

当存在冲突时，可以同时保留多个来源事实，并将协调结论存为单独的派生结果或治理决策。不能为了让查询返回一个值，就删除其他来源提供的事实。

### 16.5 事实协调服务接口

```

package resolver

import (
    "context"
    "time"
)

type FactCandidate struct {
    Subject        string
    Predicate      string
    Object         string
    SourceID       string
    SourceRecord   string
    ObservedAt     time.Time
    ValidFrom      *time.Time
    ValidTo        *time.Time
    QualityStatus  string
    MappingVersion string
}

type ResolutionResult struct {
    Status          string
    AcceptedFacts   []FactCandidate
    ConflictingFacts []FactCandidate
    PolicyVersion   string
    EvidenceRefs    []string
}

type Resolver interface {
    Resolve(
        ctx context.Context,
        candidates []FactCandidate,
        policyVersion string,
    ) (ResolutionResult, error)
}

```

Resolver 应保持确定性：给定相同的输入事实、快照、策略版本和配置，应能得到可复现的协调结果。若涉及人工判断，必须把人工决策记录为明确输入，而不是隐藏在运行时状态中。

## 17. 实体等价与 `owl:sameAs` 治理

在跨系统数据中，身份关联尤其需要谨慎。

假设 HR 和 ERP 中的两条记录已经经过正式流程确认，代表同一个员工。系统可以维护一个统一的 Canonical Employee，并将两个来源记录关联到它。

但不建议把所有实体匹配结果都自动转换成 `owl:sameAs`。

### 17.1 为什么要谨慎使用 `owl:sameAs`？

在 OWL 中，`owl:sameAs` 表达两个名称指向同一个个体。它不是普通的“相似”或“可能相同”关系。

错误使用 `owl:sameAs` 可能带来广泛的语义后果，例如把两个来源对象的属性、关系和身份视为同一实体的事实。

因此，建议区分：

- `candidateMatch`：候选匹配。
- `reviewedMatch`：经过审核的匹配。
- `resolvesTo`：来源记录解析到统一实体。
- `owl:sameAs`：仅在确实需要、语义上成立并且通过审核时使用。

### 17.2 实体合并与拆分

如果两个 Canonical Entity 被错误合并，系统必须能够纠正：

1. 建立合并决策及其证据。
2. 记录合并前的实体标识。
3. 更新来源记录到 Canonical Entity 的关联。
4. 重新计算依赖该身份关系的派生事实。
5. 重新验证相关业务规则。
6. 保留历史 Run 使用旧实体关系的版本引用。
7. 对受影响的业务流程执行风险评估。

实体拆分不应直接删除旧标识并静默重写历史。应通过版本化的实体解析记录，保留当时系统使用的身份判断及后续修正。

## 18. 证据感知查询与推导解释

ODAP 不仅要返回结果，还需要说明结果如何产生。

不过，必须区分三件事：

1. 来源追溯：结果引用了哪些原始事实。
2. 推导解释：哪些规则应用产生了派生结论。
3. 形式证明：结论在特定形式系统与前提下是否能够被严格证明。

不是所有业务查询都需要完整形式证明，但重要结论至少应具有可复核的来源和推导轨迹。

### 18.1 推导记录模型

建议每次规则应用记录：

- `derivation_id`
- `derived_fact_ref`
- `rule_id`
- `rule_version`
- `reasoning_profile_digest`
- `premise_fact_refs`
- `data_snapshot_id`
- `ontology_version`
- `reasoner_version`
- `execution_status`
- `created_at`

对于具有多条推导路径的结论，应允许关联多个 `derivation_id`，而不是只保留一条路径。

### 18.2 推导解释示例

假设系统推出：

```
Employee_E1024 belongsToOrganizationUnit Finance
```

证据轨迹可以表示为：

```
来源事实 F1：
Employee_E1024 belongsTo Department_FIN

来源事实 F2：
Department_FIN belongsToOrganizationUnit Finance

规则 R1：
belongsTo + belongsToOrganizationUnit
    → belongsToOrganizationUnit

派生事实 D1：
Employee_E1024 belongsToOrganizationUnit Finance
```

这里的 D1 是基于 F1、F2 和 R1 的派生事实。若任一前提事实被撤销，系统应检查 D1 是否仍有其他有效推导路径。

### 18.3 证据级别

建议区分：

- `SOURCE_TRACEABLE`：可追溯到来源记录。
- `RULE_TRACEABLE`：可追溯到规则和前提事实。
- `VALIDATED`：通过指定的验证流程。
- `FORMALLY_PROVEN`：在明确的形式系统、前提和证明检查器范围内获得证明。
- `INCOMPLETE`：证据链缺失或验证范围不完整。

`VALIDATED` 不能自动等同于 `FORMALLY_PROVEN`。同样，拥有来源记录也不能证明来源内容本身绝对真实。

### 18.4 与 Evidence Service 的关系

第十一篇的 Evidence Service 仍然是证据包的统一管理组件。

本篇只负责生成：

- 查询使用的快照引用。
- 原始事实与派生事实引用。
- 推理规则轨迹。
- 本体验证结果。
- 数据质量和冲突状态。
- 相关版本摘要。

随后由 Evidence Service 将这些引用与 Agent Run、审批记录、ERP 回执和审计事件关联，生成统一的 Evidence Bundle。

不要在 Semantic Graph Engine 内再实现一套与 Evidence Service 相互竞争的证据包存储系统。

## 19. 查询一致性与数据快照

查询执行过程中，语义图可能继续更新。如果没有明确的一致性语义，同一个查询可能先读取到旧的员工关系，再读取到新的部门关系，从而形成实际上从未存在过的组合状态。

### 19.1 建议的查询一致性级别

| 级别                          | 语义                 | 适用场景           |
| --------------------------- | ------------------ | -------------- |
| `BEST_EFFORT`               | 允许使用当前可用数据，但必须暴露状态 | 探索性查询          |
| `SNAPSHOT`                  | 在指定数据快照下查询         | 审计、业务复核        |
| `VERSION_LOCKED`            | 锁定本体、映射、规则和数据版本引用  | 可复现的 Agent Run |
| `SOURCE_FRESHNESS_REQUIRED` | 要求指定来源满足新鲜度策略      | 预算、库存等时效敏感查询   |

具体级别应根据业务风险选择，而不是所有查询一律要求最昂贵的快照机制。

### 19.2 版本锁定清单

一个需要可复现的 Run 至少应记录：

```
{
  "tenant_id": "tenant-001",
  "ontology_version": "finance-ontology@1.2.0",
  "mapping_version_set_digest": "sha256:...",
  "reasoning_profile": "enterprise-rdfs-basic@1.0.0",
  "rule_bundle": "finance-rules@2.1.0",
  "data_snapshot_id": "snapshot-20261012-001",
  "query_digest": "sha256:...",
  "policy_version": "finance-policy@3.0.0"
}
```

这是运行上下文的示例。正式版本还应包含适用的 Schema、推理器、查询编译器和必要的数据源版本信息。

### 19.3 快照不能替代实时权威校验

对于预算、付款状态或 ERP 操作结果，即使查询使用固定快照，也可能已经过时。

因此，如果某个业务动作要求使用最新权威状态，应在执行前重新读取相应来源，并根据第七篇的 ERP Gateway 流程进行版本检查或对账。

历史快照适合复现历史分析，但不一定适合当前写入决策。

### 19.4 结果不完整必须显式返回

当执行器遇到超时、资源限制、来源不可用或部分图不可读时，结果应返回相应状态。

例如：

- `COMPLETE`
- `TRUNCATED`
- `INCOMPLETE`
- `STALE`
- `UNKNOWN`
- `ERROR`

不能因为已找到一部分符合条件的记录，就将未完成的查询包装成完整结果。

## 20. 缓存、物化视图与索引维护

### 20.1 缓存分层

建议缓存以下内容：

- 本体类与属性定义。
- Schema 类型检查结果。
- 查询逻辑计划。
- 查询优化统计信息。
- 经过版本锁定的派生事实。
- 低变化率的只读语义结果。

但下列信息默认应采用更严格的缓存策略：

- 实时授权决策。
- 人工审批状态。
- ERP 写入回执。
- 高时效性预算或库存状态。
- 敏感个人信息。
- 与当前权限范围紧密绑定的查询结果。

### 20.2 物化视图

对于高频业务查询，可以建立物化视图，例如：

- 员工当前组织路径。
- 部门层级闭包。
- 各部门当前有效预算摘要。
- 报销单与员工、部门的常用关联。
- 经验证的高频类型继承结果。

每个物化视图都应定义：

- 输入图与快照。
- 依赖的本体和映射版本。
- 更新触发条件。
- 重建方式。
- 新鲜度 SLA。
- 失败状态。
- 数据质量要求。

物化视图应可从权威数据重建，而不是成为无法追溯的第二事实来源。

### 20.3 索引重建

当本体、数据映射或图存储版本升级时，可能需要重建索引或物化结果。

建议流程：

```
Create New Build
    ↓
Load Versioned Inputs
    ↓
Build Index / Materialization
    ↓
Run Consistency & Regression Tests
    ↓
Compare Counts and Query Results
    ↓
Publish New Build Pointer
    ↓
Retain Old Build for Rollback
```

采用新构建完成后再切换当前版本，可以避免重建期间查询到部分新、部分旧的结果。

## 21. 运行时安全与资源治理

语义查询和推理虽然主要是读取操作，但依然可能成为安全风险入口。

复杂递归、超大结果集、跨图遍历和高成本规则可能消耗大量 CPU、内存与存储 I/O。查询 DSL 如果允许任意路径扩展，还可能意外访问超出业务范围的数据。

### 21.1 查询资源预算

建议每次查询携带：

- `max_execution_time`
- `max_rows`
- `max_intermediate_rows`
- `max_graph_expansions`
- `max_path_depth`
- `max_derived_facts`
- `max_memory_estimate`
- `max_evidence_items`
- `max_concurrent_queries`

其中实际内存限制应由服务端执行环境保障，不能只依赖请求中的声明。

### 21.2 推理资源预算

每个推理任务应设置：

- 最大推导事实数。
- 最大规则应用次数。
- 最大迭代次数。
- 最大递归深度或等效终止条件。
- 最大运行时长。
- 最大内存。
- 最大证据记录数量。

当预算耗尽时，应返回明确状态，例如 `REASONING_BUDGET_EXCEEDED`，不能将不完整的推理结果标记为完整闭包。

### 21.3 防止查询侧信道

即使结果经过字段过滤，查询耗时、错误信息和计数结果也可能暴露敏感数据是否存在。

建议：

- 统一受保护对象的错误返回策略。
- 对计数、聚合和高敏数据访问执行授权检查。
- 避免在错误信息中返回未授权对象的具体标识。
- 对敏感查询施加适当的频率限制。
- 将敏感访问行为纳入审计。
- 避免在普通应用日志中记录完整的高敏查询参数。

### 21.4 推理与权限的隔离

推理引擎不应自动遍历所有可见或不可见事实，再把派生结果直接暴露给调用者。

推荐执行模型：

1. 根据请求主体建立可访问数据范围。
2. 明确推理允许使用的数据集合与规则。
3. 运行推理。
4. 检查派生结果是否会泄露受保护信息。
5. 根据策略过滤输出，并保留必要审计信息。

对于涉及跨部门汇总或敏感属性推导的规则，应特别评估推导结果是否可能绕过原始字段的权限限制。

### 21.5 可信的查询上下文

`tenant_id`、用户身份、授权范围和安全策略版本应由可信平台组件注入，不能由 Agent 在请求 JSON 中自由指定。

Agent 可以提出查询条件，但不能通过修改参数把自己切换到其他租户、提升数据范围或关闭访问控制。

## 22. PostgreSQL 元数据与推理任务 Schema

前面已经定义了三元组、图和事实来源表。本节补充推理任务、派生事实元数据、查询记录与物化构建等运行时数据。

### 22.1 推理配置与任务

```
CREATE SCHEMA IF NOT EXISTS reasoning;
CREATE SCHEMA IF NOT EXISTS semantic_query;

CREATE TABLE reasoning.profiles (
    profile_id UUID PRIMARY KEY,
    tenant_id UUID,
    profile_name TEXT NOT NULL,
    version_number INTEGER NOT NULL,
    profile_digest TEXT NOT NULL,
    profile_document JSONB NOT NULL,
    status TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE reasoning.jobs (
    reasoning_job_id UUID PRIMARY KEY,
    tenant_id UUID NOT NULL,
    profile_id UUID NOT NULL
        REFERENCES reasoning.profiles(profile_id),
    ontology_version TEXT NOT NULL,
    snapshot_id TEXT NOT NULL,
    status TEXT NOT NULL,
    input_fact_count BIGINT,
    derived_fact_count BIGINT,
    rules_applied BIGINT,
    started_at TIMESTAMPTZ,
    completed_at TIMESTAMPTZ,
    error_code TEXT,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_reasoning_jobs_tenant_time
    ON reasoning.jobs (tenant_id, created_at DESC);
```

正式实现中，`tenant_id` 为空的全局推理配置必须受到明确约束；共享配置不能因此成为跨租户业务事实的访问入口。

### 22.2 派生事实元数据

```
CREATE TABLE reasoning.derivations (
    derivation_id UUID PRIMARY KEY,
    tenant_id UUID NOT NULL,
    reasoning_job_id UUID NOT NULL
        REFERENCES reasoning.jobs(reasoning_job_id),
    derived_fact_ref JSONB NOT NULL,
    rule_id TEXT NOT NULL,
    rule_version TEXT NOT NULL,
    premise_refs JSONB NOT NULL,
    derivation_digest TEXT NOT NULL,
    status TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_derivations_job
    ON reasoning.derivations (tenant_id, reasoning_job_id);

CREATE INDEX idx_derivations_rule
    ON reasoning.derivations (tenant_id, rule_id, rule_version);
```

对于大型推导图，不建议把全部前提和推导轨迹无限嵌入单个 JSONB 字段。可以把详细推导数据存储在专用关联表或对象存储中，元数据表保留稳定引用和摘要。

### 22.3 查询执行记录

```
CREATE TABLE semantic_query.executions (
    query_execution_id UUID PRIMARY KEY,
    tenant_id UUID NOT NULL,
    caller_type TEXT NOT NULL,
    caller_id TEXT NOT NULL,
    query_digest TEXT NOT NULL,
    ontology_version TEXT NOT NULL,
    snapshot_id TEXT,
    reasoning_profile_digest TEXT,
    authorization_scope_digest TEXT NOT NULL,
    status TEXT NOT NULL,
    rows_returned BIGINT NOT NULL DEFAULT 0,
    truncated BOOLEAN NOT NULL DEFAULT false,
    started_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    completed_at TIMESTAMPTZ,
    error_code TEXT
);

CREATE INDEX idx_semantic_query_tenant_time
    ON semantic_query.executions (tenant_id, started_at DESC);
```

查询记录不必默认保存全部查询正文。对包含敏感数据的查询，应根据数据分类、审计要求和保留策略，决定保存完整查询、脱敏查询还是摘要与受控引用。

### 22.4 物化构建记录

```
CREATE TABLE reasoning.materialization_builds (
    build_id UUID PRIMARY KEY,
    tenant_id UUID NOT NULL,
    target_graph_id BIGINT NOT NULL
        REFERENCES graph.named_graphs(graph_id),
    ontology_version TEXT NOT NULL,
    profile_digest TEXT NOT NULL,
    input_snapshot_id TEXT NOT NULL,
    build_digest TEXT,
    status TEXT NOT NULL,
    derived_fact_count BIGINT,
    started_at TIMESTAMPTZ,
    completed_at TIMESTAMPTZ,
    published_at TIMESTAMPTZ,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

构建任务完成后，需要经过一致性检查、回归测试和发布控制，才能切换到新的物化版本。数据库中的 `SUCCEEDED` 状态不能单独证明推理语义正确。

### 22.5 数据保留与分区

对于长期运行的企业平台，查询日志、推导轨迹和验证发现项可能持续增长。

建议根据访问模式设计分区与归档：

- 查询执行记录按时间分区。
- 推理任务与构建记录按时间分区。
- 当前有效三元组与历史事实分开管理。
- 大型推导证据归档到对象存储。
- 审计记录遵循第十一篇的独立保留与完整性策略。

分区、归档和删除策略都必须遵循租户隔离、法律保留和证据完整性要求。

## 23. 统一运行时 API 与错误模型

### 23.1 核心 API

建议将 API 按查询、推理、验证和管理分组。

| 方法     | 接口                                       | 功能             |
| ------ | ---------------------------------------- | -------------- |
| `POST` | `/api/v1/semantic/query`                 | 执行语义查询         |
| `POST` | `/api/v1/semantic/query/validate`        | 检查查询语法、类型和权限   |
| `POST` | `/api/v1/semantic/query/explain`         | 返回逻辑计划与物理计划    |
| `POST` | `/api/v1/semantic/reason`                | 创建推理任务         |
| `GET`  | `/api/v1/semantic/reason/{id}`           | 查询推理状态         |
| `POST` | `/api/v1/semantic/validate`              | 执行 SHACL 或指定验证 |
| `GET`  | `/api/v1/semantic/validate/{id}`         | 查询验证结果         |
| `POST` | `/api/v1/semantic/materializations`      | 创建物化构建         |
| `GET`  | `/api/v1/semantic/materializations/{id}` | 查询物化状态         |
| `GET`  | `/api/v1/semantic/lineage`               | 查询事实和推导血缘      |
| `GET`  | `/api/v1/semantic/capabilities`          | 查询引擎支持能力       |

所有接口均应受第三篇的身份和权限引擎控制。

### 23.2 同步与异步执行

建议采用以下策略：

- 小型、低成本查询：同步执行。
- 大结果集或长路径查询：游标分页或异步执行。
- 全量推理和物化：异步任务。
- 大规模 SHACL 验证：异步任务。
- 索引重建和历史数据重算：异步任务。
- 证据包构建：由 Evidence Service 负责异步执行。

长任务应使用第十篇的事件总线和持久化任务状态，支持取消、恢复、失败分类和人工干预。

### 23.3 统一错误码

建议至少定义：

| 错误码                         | 含义          |
| --------------------------- | ----------- |
| `UNKNOWN_CLASS`             | 查询引用的本体类不存在 |
| `UNKNOWN_PROPERTY`          | 属性或关系未定义    |
| `TYPE_MISMATCH`             | 类型不兼容       |
| `UNAUTHORIZED_GRAPH`        | 无权访问目标图     |
| `UNAUTHORIZED_PROPERTY`     | 无权访问目标属性    |
| `QUERY_TOO_COMPLEX`         | 查询复杂度超限     |
| `QUERY_BUDGET_EXCEEDED`     | 查询资源预算耗尽    |
| `REASONING_BUDGET_EXCEEDED` | 推理预算耗尽      |
| `UNSUPPORTED_SEMANTICS`     | 请求了引擎不支持的语义 |
| `SNAPSHOT_UNAVAILABLE`      | 所需快照不可用     |
| `STALE_DATA`                | 数据不满足新鲜度要求  |
| `INCOMPLETE_RESULT`         | 结果不完整       |
| `VALIDATION_FAILED`         | 验证发现违规      |
| `REASONING_FAILED`          | 推理任务失败      |
| `STORE_UNAVAILABLE`         | 图存储不可用      |

错误响应应包含关联 ID、错误类别、可安全披露的诊断信息以及是否可以安全重试。

## 24. 与 ODAP 各模块的集成边界

### 24.1 与第五篇 Ontology Factory

Ontology Factory 负责生产和发布本体、约束与映射资产。本篇负责加载指定版本并执行语义查询、推理和验证。

本体发布后，应具备：

- 规范化的资产摘要。
- 完整的依赖版本锁定。
- 语义支持能力声明。
- SHACL 约束集版本。
- 业务规则包版本。
- 查询与推理回归测试。
- 兼容性和影响分析报告。

新版本发布不能自动改变已经运行中的历史 Run 所使用的语义。

### 24.2 与第六篇 Harness

Harness 负责管理查询与推理任务的执行生命周期。

例如，Harness 应能够：

1. 创建查询或推理任务。
2. 保存输入和版本上下文。
3. 调用语义运行时。
4. 接收任务进度与结果。
5. 在预算耗尽或外部故障时暂停。
6. 恢复任务或执行安全重试。
7. 将结果交给验证、授权或审批流程。

语义运行时不应自行创建无约束的业务重试循环。

### 24.3 与第七篇 ERP Gateway

语义引擎可以计算“该报销单需要升级审批”，但不能因为该结论存在于派生图中，就直接写入 ERP。

正式流程应为：

```
Semantic Query
    ↓
Reasoning Result
    ↓
Business Rule Validation
    ↓
Authorization Decision
    ↓
Approval Service (if required)
    ↓
ERP Gateway
    ↓
ERP Receipt Verification
```

执行前应重新验证与操作相关的事实是否仍然有效。对于预算、付款状态和其他高时效数据，还应在必要时向权威来源重新校验。

### 24.4 与第十一篇 Evidence Service

本篇负责生成查询与推理过程的证据引用；Evidence Service 负责统一证据包的构建、完整性检查、访问控制和导出。

应保持证据内容与技术遥测分离：

- Trace 用于观察执行路径。
- 日志用于诊断系统问题。
- 业务审计记录关键操作。
- 推导轨迹解释结论如何生成。
- Evidence Bundle 汇总复核所需的业务证据。

它们可以通过关联 ID 相互连接，但不能相互替代。

如果第十一篇的 `internal/evidence` 已经存在，应扩展现有模块，而不是再建立第二套独立 Evidence Service。

### 25.1 Rust 的使用边界

结合 ODAP 的 Go 应用层和 React/TypeScript 前端规划，V1.0 建议先用 Go 完成主要运行时。

只有当压测表明特定模块存在明显性能瓶颈时，才考虑用 Rust 实现：

- 高吞吐 RDF 解析与规范化。
- 三元组批量排序和压缩。
- 特定索引结构。
- 大规模规则匹配内核。
- 内存密集型图遍历算子。

Rust 模块应通过明确的进程协议或稳定 FFI 边界集成。不要在尚未确定算法与性能瓶颈时，将存储、查询、推理全部拆成不同语言实现，以免增加调试和版本管理成本。

## 26. 性能与正确性验收测试

ODAP 的语义引擎不能只用“查询能返回结果”作为验收标准。它必须同时满足语义正确性、可追溯性、权限隔离和性能预算要求。

### 26.1 存储与查询测试

- RDF 资源、字面值、数据类型和语言标签能正确存储与读取。
- SPO、POS、OSP 等访问模式返回正确结果。
- 同一三元组存在多个来源时，不会丢失来源关联。
- 命名图与租户隔离策略得到强制执行。
- 查询取消后能够停止后续执行。
- 大结果集可以分页或流式读取。
- 快照查询不会静默混用不兼容的数据版本。
- 查询超限时返回明确的不完整状态。
- 物化视图可以从权威数据与指定规则版本重建。

### 26.2 查询优化测试

- 优化前后的查询结果保持语义等价。
- Join Reordering 不改变结果的逻辑含义。
- 缺失值、空值和类型比较符合 DSL 规范。
- 路径扩展受到深度与资源预算限制。
- 统计信息过期时，优化器可以采取安全的保守策略。
- 缓存键包含租户、权限范围和相关版本。
- 缓存命中不会绕过授权检查。
- 查询计划能够说明主要访问路径与估算成本。

### 26.3 推理正确性测试

- 子类与子属性推理结果符合声明的语义。
- 受控规则生成的派生事实具有完整前提引用。
- 同一结论存在多条推导路径时能够保留必要的支持关系。
- 删除某条来源事实后，不会错误删除仍然有效的派生结论。
- 规则循环与递归能够受到资源限制。
- 不支持的 OWL 特性会被明确拒绝或按正式契约处理。
- 推理超时不会被标记为完整闭包。
- 派生事实与来源事实可以区分。
- 相同的版本锁定输入可以得到可复核的结果。

### 26.4 SHACL 与业务规则测试

- SHACL 验证结果包含焦点节点、形状引用和违规路径。
- 验证器错误不会被误报为验证通过。
- 增量验证不会遗漏其影响范围内的违规。
- 未知数据与明确违规保持区别。
- 业务规则不会替代授权与审批。
- 验证修复会保留原始失败记录和审计轨迹。

### 26.5 多源语义与证据测试

- 不同来源的冲突事实能够并存。
- 属性级权威策略可以按版本执行。
- 历史有效时间不会被当前状态覆盖。
- 实体误合并可以通过受控流程纠正。
- 每条关键派生事实能够追溯到前提事实和规则版本。
- 证据不完整时明确返回 `INCOMPLETE`。
- 跨租户查询和跨租户推导均被阻止。
- 证据查看与导出受到独立权限控制。

### 26.6 性能测试设计

建议先建立三组可重复的数据集：

| 测试集    | 规模         | 目标           |
| ------ | ---------- | ------------ |
| Small  | 10 万条三元组   | 验证功能与回归      |
| Medium | 1000 万条三元组 | 验证索引、查询计划和并发 |
| Large  | 1 亿条及以上三元组 | 评估存储选择与扩展路径  |

这些是建议的测试规模，不代表 ODAP 当前已达到相应性能。

测试查询至少包括：

- 主语和谓词精确查询。
- 按类型查询实例。
- 反向关系查询。
- 两跳与四跳关系遍历。
- 类型继承查询。
- 规则推理。
- SHACL 批量验证。
- 跨源事实协调。
- 大结果集聚合。
- 增量更新后的派生结果重算。

应同时测量 P50、P95、P99 延迟、吞吐量、CPU、内存、索引体积、写入延迟和恢复时间。

最终验收阈值应由真实业务 SLA、数据规模和硬件配置确定，不应在没有实测数据的情况下承诺固定性能数字。

## 27. 实施路线：从可运行引擎到企业级语义计算平台

P1：Semantic Graph Store 基础版

实现 RDF 词项、三元组、命名图、事实来源、基础索引与 GraphStore 接口。

交付标准：能将第十二篇的报销语义实例写入图存储，并按类型、属性和关系查询。

P1.5：存储选型 Spike（进入 P2 的硬门禁，P0 级流程约束）

内容：在 Medium 数据集（1000 万三元组）上实测自研 PG 索引方案（PK+POS+OSP 三索引 + tenant 声明式分区，§6.3）与 1-2 个成熟 RDF Store（Blazegraph / GraphDB / Fuseki 任选其二做代表），输出选型报告：查询 P95、写入吞吐、租户隔离成本、运维复杂度（口径见 §26.6）。

门禁规则：**报告未经平台架构评审通过，不得启动 P2 本体工程建设。** 若 PG 入选，承诺范围固定为“≤1000 万三元组/租户”；更大规模切专用 Store 的触发条件与验收阈值同步写入 §26.6 与第十六篇路线。

P2：Semantic Query DSL 与执行器

完成查询 Schema、类型检查、查询 IR、基础执行器、分页与资源限制。

交付标准：Agent 能通过受控 API 查询员工、部门、报销单和预算关系。

P3：RDFS 与受控规则推理

实现基础类型推理、规则编译、推导记录和推理资源预算。

交付标准：推导结果可以区分来源事实，并追溯到前提与规则版本。

P4：SHACL 与业务规则验证

建立独立验证接口、验证发现项、增量验证的初步能力和状态模型。

交付标准：缺失员工、金额异常和错误关系能够被明确检测并隔离。

P5：多源协调与查询优化

实现属性级权威策略、冲突状态、成本优化、缓存和高频关系物化。

交付标准：能够处理 HR、ERP 和预算系统之间的冲突，并生成稳定的查询计划。

P6：版本快照、推导证据与 Agent 联调

锁定本体、映射、规则与数据快照，接入 Harness 和 Evidence Service。

交付标准：从来源数据到 Agent 决策，可以完整追溯语义事实、规则和版本。

P7：企业级性能与存储升级

根据压测决定是否采用专用 RDF Store、增量物化、分区、专用图索引或 Rust 性能内核。

交付标准：满足实际数据规模、延迟、可靠性和部署要求。

### 27.1 第一条端到端验收链路

建议以报销业务域作为第一个完整的运行时验收场景：

1. 从 Mock HR 导入员工与部门。
2. 从 Mock ERP 导入报销单。
3. 从预算数据源导入部门预算。
4. 通过第十二篇的映射引擎生成语义事实。
5. 通过 SHACL 检查关键关系与字段约束。
6. 通过 RDFS 或受控规则推导组织关系。
7. 通过语义查询 API 获取报销单、员工、部门和预算。
8. 由业务规则引擎计算是否需要升级审批。
9. 由授权与审批模块决定是否允许执行。
10. 通过 ERP Gateway 执行受控操作。
11. 验证 ERP 回执，并由 Evidence Service 生成证据包。

验收时还要人为制造数据冲突、过期快照、权限撤销、推理超时和 ERP 回执丢失等故障，验证系统不会把不确定结果当作成功。

## 28. 本篇最终架构决策

综合 ODAP 前十三篇，建议将以下内容作为 V1.0 的架构基线。

1. 语义图存储与业务数据库分离。 PostgreSQL 可用于 MVP 的 RDF 存储实现，但应保留独立 `GraphStore` 接口，便于替换或接入专用 RDF Store。
2. 原始事实、标准化事实、派生事实、验证结果和业务决策分别管理。 不允许推理结果覆盖来源事实。
3. 本体版本、数据快照、映射版本和推理配置共同构成查询语义上下文。
4. 使用受控 Semantic Query DSL 作为 Agent 的默认查询入口。 查询必须经过类型检查、权限检查、成本估算与资源预算验证。
5. 将查询编译器、逻辑计划、优化器和物理执行器分离。 允许更换存储实现而不改变业务查询语义。
6. V1.0 不承诺完整 OWL 2 DL 推理。 先实现经过测试的 RDFS 基础语义、受控规则和 SHACL 验证。
7. 推理结果必须保留前提事实、规则版本和执行上下文。 重要结论可以复核，历史结果可以按当时的版本引用重现。
8. 多源事实协调必须保留冲突与来源信息。 不以简单的最后写入优先代替属性级权威策略。
9. 查询优化不得改变语义结果。 索引、缓存和物化视图都必须可以验证、重建与回退。
10. 开放世界语义与业务封闭世界规则明确分离。 未找到事实不等于事实为假。
11. SHACL 验证、业务规则与授权决策保持独立。 任何一个模块通过都不能代替其他模块的检查。
12. 所有长时间推理、验证和物化任务使用持久化任务机制。 超时、预算耗尽与结果不完整必须明确表达。
13. 租户、对象、属性和推导结果都受权限治理。 不能让多跳遍历成为绕过访问控制的路径。
14. 查询与推理证据统一交由 Evidence Service 管理。 不在语义引擎内建立另一套独立的证据包系统。
15. 先完成报销领域的端到端验证，再扩展到采购、合同、人力资源和财务分析。

## 29. 第十三篇完成后，ODAP 的核心闭环

企业数据接入

ERP · HR · CRM · 文件 · 数据库

企业本体与语义图

统一概念 · 业务事实 · 关系 · 数据血缘

语义查询与推理

查询优化 · 逻辑推理 · SHACL · 多源协调

Agent Runtime + Harness

理解上下文 · 制定计划 · 调用工具 · 暂停恢复

授权、审批与 ERP Gateway

受控执行 · 权威回执 · 状态核验

审计与 Evidence Service

来源事实 · 推导轨迹 · 版本锁定 · 业务结果

我认为，第十三篇补齐了 ODAP 一个非常关键的技术环节：企业本体不再只是描述业务对象的静态知识模型，而成为可以查询、推理、验证、优化和追溯的运行时语义基础设施。

这也是 ODAP 与简单的“LLM + 数据库查询”方案的核心区别之一。真正有价值的部分，不是让模型生成更多查询，而是让平台明确回答：数据从哪里来、关系为什么成立、结论使用了哪些规则、当前结果是否完整，以及系统是否有权据此执行业务动作。

## 30. 下一篇建议

建议第十四篇编写：

《ODAP 企业级语义执行计划、智能体工具编排与本体驱动业务工作流详细设计》

第十三篇解决了语义数据的存储、查询、推理和验证。下一篇可以进一步将这些能力转化为可执行的企业工作流，重点设计：

- 本体对象与 Agent Tool 的自动绑定。
- 从业务目标到语义查询计划的编译。
- 查询、推理、验证、审批与 ERP 操作的统一工作流。
- 多智能体之间的语义上下文与证据传递。
- 基于本体约束的工具参数校验。
- 计划执行前的权限预检查与风险评估。
- 动态数据变化后的计划失效与重新验证。
- 工作流状态机、补偿机制、人工接管和恢复。
- 端到端业务流程的回归测试与评估。

这样，ODAP 的设计将从“数据如何进入平台、平台如何理解数据”，继续推进到“平台如何基于企业语义可靠地完成业务”。
