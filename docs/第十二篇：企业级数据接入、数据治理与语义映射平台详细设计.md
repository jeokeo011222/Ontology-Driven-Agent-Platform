## 1. 设计目标与核心问题

在前十一篇中，ODAP 已经建立了企业本体、Ontology Factory、Agent Runtime、Harness、ERP Port、LLM Gateway、异步事件总线、可观测性和审计证据链等核心模块。

现在需要解决一个更基础的问题：

企业的数据分散在不同系统中，ODAP 如何将这些数据安全、持续、可验证地转化为智能体能够理解和使用的企业语义数据？

例如，一家企业可能同时使用：

- ERP：员工、部门、费用、采购、供应商和财务凭证。
- HR 系统：组织架构、岗位、员工状态与汇报关系。
- CRM：客户、联系人、销售机会和合同。
- 财务系统：预算、报销、应付账款和付款状态。
- 数据库与数据仓库：业务明细、统计指标和历史快照。
- 文件与知识库：企业制度、合同、操作规程和审批文件。
- 消息系统：订单变化、审批结果、付款状态等业务事件。

这些系统往往使用不同的字段名称、对象标识、状态编码、时间格式、金额单位和业务口径。

例如：

| 来源系统    | 原始字段                  | 实际含义         |
| ------- | --------------------- | ------------ |
| ERP     | `emp_no`              | 员工编号         |
| HR      | `employee_code`       | 员工编码         |
| 财务系统    | `staff_id`            | 财务系统中的员工关联标识 |
| ODAP 本体 | `Employee.employeeId` | 统一语义层中的员工标识  |

这些字段不能因为名称相似就直接合并。必须确认标识的语义、作用域、唯一性和映射依据。

ODAP 数据接入与语义映射平台的任务，就是在保持原始数据可追溯的前提下，完成数据连接、标准化、质量检查、语义映射、实例构建和持续更新。

三者不应混成一个由 LLM 自由解释数据的过程。

## 2. 架构原则与设计边界

### 2.1 六项基本原则

原则一：原始数据、标准数据与语义数据分层。

来源系统中的原始记录必须能够保留或通过版本化快照重建。标准化数据和语义实例都是派生层，不能覆盖原始事实。

原则二：映射是正式、可版本化的资产。

字段映射、枚举转换、单位换算、实体关联和语义关系均应经过验证、测试和发布，不应散落在 Agent Prompt 或业务代码中。

原则三：来源事实与推导事实必须区分。

例如，ERP 明确记录员工所属部门属于来源事实；根据某条组织关系推导员工属于某业务域，属于推导事实。两者应保留不同的来源和证据。

原则四：未知不等于不存在。

数据未采集、同步延迟、字段未映射和业务关系确实不存在，是不同状态。不能把缺失字段直接转换为 `false`，也不能将未同步的付款记录视为未付款。

原则五：权限贯穿数据全生命周期。

连接凭据、原始记录、标准数据、语义实例、缓存、查询结果、日志和导出均需受租户与对象权限控制。

原则六：接入与执行分离。

Connector 负责读取、采集与同步；ERP Port 负责受控的外部业务操作。数据接入组件不能绕过第七篇的 ERP Gateway 直接执行业务写入。

### 2.2 本篇不负责什么

以下能力由前文模块继续承担：

- 本体概念、关系和规则建模：第五篇 Ontology Factory。
- Agent 的任务编排与执行：第六篇、第八篇。
- ERP 业务写入与回执：第七篇 ERP Gateway。
- 模型调用与推理治理：第九篇 LLM Gateway。
- 事件可靠投递与任务恢复：第十篇。
- 运行追踪、审计与证据包：第十一篇。

本篇会调用这些模块的正式接口，而不复制它们的核心职责。

## 3. 总体架构：七层数据平台

建议将 ODAP 数据接入与语义映射能力划分为七层。

L1 · Source Registry

数据源注册、连接配置、凭据引用、能力发现

L2 · Connector Runtime

数据库、ERP API、CDC、消息、文件与文档连接器

L3 · Ingestion & Raw Data

批量采集、增量游标、原始记录、隔离区、重放

L4 · Canonical Data & Quality

标准数据模型、类型归一化、质量规则、实体解析

L5 · Semantic Mapping

字段映射、值转换、关系映射、版本验证与发布

L6 · Ontology Data Services

语义实例、数据快照、查询、数据血缘与新鲜度

L7 · Consumer APIs

Ontology Runtime、Agent、报表、证据服务和治理工作台

### 3.1 为什么要增加 Canonical Model？

这里有两个不同层次的映射：

- 来源系统 → Canonical Model：解决不同系统的数据结构、类型、单位和基本业务对象表达不一致的问题。
- Canonical Model → 企业本体：解决业务语义、概念层次、约束和关系不一致的问题。

例如，两个系统都提供员工数据。首先将其标准化为统一的 `CanonicalEmployee`，然后根据企业本体中 `Employee` 的正式定义，生成或更新对应的语义实例。

并非所有数据都必须经过同一个标准模型。如果某个专业领域具有高度特殊的结构，也可以直接通过领域映射进入本体，但必须仍然经过版本管理、数据质量检查和来源追溯。

### 3.2 为什么不直接把所有数据导入 RDF？

RDF 是表示语义事实的合适方式，但它不应该成为所有来源数据的唯一存储格式。

企业可能有大量时序数据、日志、明细账、文档和宽表。全部转换为 RDF 后再执行每种类型的分析，可能带来存储、查询和维护成本。

建议采用混合存储：

- 原始数据：保存在来源系统或受控的原始数据存储中。
- 标准化数据：根据规模存储在 PostgreSQL、对象存储或专用分析系统。
- 语义事实：由本体运行时使用适合的 RDF Store 或其他语义存储实现。
- 数据血缘和版本元数据：保存在 ODAP 元数据数据库。
- 大型附件：保存在对象存储，并由语义实例引用。

本体是统一的语义契约，不意味着每个字节都必须存储在同一种数据库中。

## 4. 数据源注册中心与连接管理

数据源注册中心（Data Source Registry）负责管理企业有哪些数据源、如何安全连接、能够读取什么，以及数据源当前是否健康。

### 4.1 数据源类型

建议 V1.0 支持以下连接器类别：

| 类型                 | 接入方式            | 优先级 |
| ------------------ | --------------- | --- |
| REST API           | 官方 API、分页与增量查询  | P1  |
| PostgreSQL / MySQL | 只读账号、快照与增量查询    | P1  |
| CSV / JSON / Excel | 文件上传、批量导入       | P1  |
| ERP Adapter        | 复用第七篇的适配器能力     | P1  |
| Webhook            | 来源系统主动推送        | P2  |
| 消息队列               | 消费业务事件          | P2  |
| CDC                | 数据库变更捕获         | P2  |
| 企业文档               | PDF、DOCX、制度文件解析 | P2  |
| 专业 SaaS            | 按企业实际需要开发       | P3  |

建议不要一开始就支持几十种数据源。优先把通用连接器协议、错误模型、权限、增量游标和数据质量机制做扎实，再逐步扩展驱动。

### 4.2 Data Source Manifest

每个连接器都应有 Manifest，声明其能力和限制。

```
apiVersion: odap.io/v1
kind: DataSourcePlugin

metadata:
  id: postgres-readonly
  name: PostgreSQL Read Connector
  version: 1.0.0

spec:
  connectorType: database
  capabilities:
    - schema_discovery
    - snapshot_read
    - incremental_read

  security:
    credentialRefRequired: true
    writeAccess: false

  limits:
    maxConcurrentJobs: 4
    maxBatchSize: 1000

  runtime:
    mode: isolated_process
    timeoutSeconds: 30
```

以上是示例 Manifest。正式版本应通过 Schema 校验，并定义连接器版本、签名、权限声明、依赖和兼容性规则。

### 4.3 连接配置与凭据分离

连接配置应存储：

- 数据源类型。
- 连接端点或主机标识。
- 数据库名称或 API 基础路径。
- 连接器版本。
- 认证方式。
- 数据分类与允许访问的范围。
- 连接健康状态。
- 同步策略与限流配置。

实际密码、Token、私钥等敏感凭据应存放在企业密钥管理系统中。数据库只保存 `credential_ref`，不能保存明文密钥。

### 4.4 连接能力发现

连接建立后，Connector 应执行能力探测，例如：

- 能否列出数据表和字段？
- 是否支持稳定分页？
- 是否具有可靠的增量游标？
- 是否支持 CDC？
- 是否支持一致性快照？
- 是否支持按业务对象读取？
- 是否能识别删除事件？
- 是否有速率限制和请求配额？

能力探测结果必须来自实际测试或可信的连接器契约，不能仅凭 Manifest 中的声明就认为能力已得到验证。

### 4.5 Go 接口设计

```

package connector

import "context"

type Capability string

const (
    CapabilitySchemaDiscovery Capability = "schema_discovery"
    CapabilitySnapshotRead   Capability = "snapshot_read"
    CapabilityIncrementalRead Capability = "incremental_read"
)

type DataSource struct {
    ID            string
    TenantID      string
    ConnectorID   string
    CredentialRef string
    Config        map[string]any
}

type Field struct {
    Name     string
    DataType string
    Nullable bool
}

type SourceSchema struct {
    SourceID string
    ObjectID string
    Version  string
    Fields   []Field
}

type ReadRequest struct {
    ObjectID   string
    Cursor     string
    BatchSize  int
    SnapshotID string
}

type SourceRecord struct {
    SourceKey    string
    SourceVersion string
    Payload      map[string]any
    ObservedAt   string
}

type Connector interface {
    DiscoverSchema(
        ctx context.Context,
        source DataSource,
    ) ([]SourceSchema, error)

    ReadSnapshot(
        ctx context.Context,
        source DataSource,
        req ReadRequest,
    ) ([]SourceRecord, string, error)

    ReadIncremental(
        ctx context.Context,
        source DataSource,
        req ReadRequest,
    ) ([]SourceRecord, string, error)

    Health(
        ctx context.Context,
        source DataSource,
    ) error
}

```

这是接口骨架。实际实现还应增加取消、速率限制、分页连续性、游标过期、删除事件、错误分类和连接器能力声明。

另外，不应把任意 SQL 字符串作为 Agent 可以直接调用的通用工具。数据库 Connector 应通过受控查询模板、白名单表和字段权限，或只读语义接口暴露数据。

## 5. 数据目录、元数据发现与 Schema Registry

数据目录的目标是回答：企业有哪些数据、每个字段是什么意思、谁负责、质量如何、是否允许某个 Agent 使用？

### 5.1 元数据分层

建议分为四类：

技术元数据

表名、字段名、数据类型、主键、索引、更新时间、文件格式、API 版本。

业务元数据

业务名称、字段含义、责任部门、数据口径、业务主键、状态枚举和业务有效时间。

治理元数据

数据分类、所有者、保留期限、访问策略、允许用途、脱敏规则和合规标签。

语义元数据

对应的本体类、属性、关系、单位、约束、映射版本、来源引用和验证状态。

四类元数据应关联，但不能混为同一个字段。例如，一个字段在技术层面是 `VARCHAR`，并不代表其业务语义是员工编号。

### 5.2 Schema Registry

建议为每个来源对象维护可版本化 Schema：

- `schema_id`
- `source_id`
- `object_id`
- `schema_version`
- `schema_digest`
- `fields`
- `primary_key_definition`
- `change_type`
- `detected_at`
- `approved_at`

当来源系统增加字段、改变类型、修改枚举或删除字段时，创建新的 Schema 版本，并计算差异。

### 5.3 Schema 演化分类

| 变化          | 默认处理            |
| ----------- | --------------- |
| 增加可选字段      | 可接受，但需要映射评估     |
| 增加必填字段      | 需要映射与数据质量审核     |
| 删除已映射字段     | 阻止自动发布，评估影响     |
| 字段类型变更      | 创建新版本并重新验证      |
| 枚举值增加       | 检查未知值和业务规则      |
| 主键语义变化      | 高风险，要求人工确认      |
| 单位或币种语义变化   | 高风险，必须重新验证      |
| 字段含义变化但类型不变 | 必须通过业务契约与变更审核识别 |

Schema Diff 只能检测结构变化，不能可靠判断字段的业务含义是否发生改变。因此应结合业务负责人确认、数据样例、契约测试和历史映射记录。

#### 5.3.1 值分布与枚举基数监控

结构之外，还必须监控已映射字段的值分布画像，作为"类型不变但含义变"的第一道自动信号：

- 画像内容：枚举基数（distinct 计数）、Top-N 值及频次、数值分位数（P50/P95）、空值率、未见新值比例。
- 突变规则（任一触发即生成人工确认工单，确认前新数据按隔离处理）：
  - 枚举基数骤降（如 20 → 2）或骤增（如 2 → 200）；
  - 出现分布外的新枚举值超过阈值（如 > 0.5%）；
  - 数值分位数跳变超过阈值（如 P50 变化 > 50%）；
  - 空值率跳升超过阈值（如 +10 个百分点）。
- 突变不等于错误：来源系统正常业务演化也会触发；工单的目的是**强制人工确认**，由数据负责人判定是接受新分布、调整映射还是隔离数据。

#### 5.3.2 "类型不变含义变"的自动检测手段

字段类型与名称都不变、但业务含义被重新定义（如 `status` 从"单据状态"改为"同步状态"）是最危险的漂移。除人工确认外，提供以下自动检测手段：

1. **双跑比对**：同一输入在新/旧映射版本下并行处理（只读），输出差异率超阈值即报警——与 §15.6 backfill 双跑共用机制，身份/金额/状态类字段默认低阈值。
2. **下游规则命中率漂移**：依赖该字段的业务规则通过率、拒绝原因分布在短时间内突变，反推字段语义可能已变。
3. **新旧约束对照验证**：用旧本体/SHACL 约束与新约束分别验证同一批数据，冲突率突增即报警。
4. **来源变更日志关联**：对接来源系统的发布说明/变更公告做关键词关联（如某字段被声明重新定义），自动生成待确认项。

这些手段只能提高发现概率，不能替代业务负责人确认（§5.3 表末行原则不变）：自动检测的输出是"需要确认的信号"，不是"语义已变的结论"。

### 5.4 元数据 API

建议提供：

- `GET /api/v1/data-sources`
- `POST /api/v1/data-sources`
- `POST /api/v1/data-sources/{id}/test`
- `POST /api/v1/data-sources/{id}/discover`
- `GET /api/v1/data-catalog/assets`
- `GET /api/v1/data-catalog/assets/{id}`
- `GET /api/v1/schemas/{id}/versions`
- `GET /api/v1/schemas/{id}/diff`

所有查询都必须执行租户、对象与字段权限检查，不能因为某个用户能看见数据目录，就自动允许读取底层业务数据。

## 6. 数据采集、同步与一致性设计

数据接入不仅是读取一次数据，更要确保数据可以持续更新、重复处理不会造成错误，并能在中断后恢复。

### 6.1 四种采集模式

6.1.1 全量快照（Snapshot）

首次接入或重建数据集时，从来源系统读取一个明确范围内的数据快照。

适合：员工名册、部门目录、供应商主数据、历史业务记录。

关键要求：明确快照时间、分页一致性、记录数量和校验结果。

### 6.2 推荐的同步状态机

```
CREATED
  ↓
DISCOVERING
  ↓
READY
  ↓
SNAPSHOT_RUNNING
  ↓
INCREMENTAL_RUNNING
  ├──→ PAUSED
  ├──→ DEGRADED
  └──→ FAILED
```

实际工程中，应将连接状态、同步任务状态和数据集状态分开管理。例如，某次同步失败不意味着连接器失效；某个数据集存在质量问题，也不一定意味着整个数据源不可用。

建议状态至少包括：

- 连接：`HEALTHY`、`DEGRADED`、`UNAVAILABLE`。
- 同步任务：`PENDING`、`RUNNING`、`PAUSED`、`SUCCEEDED`、`FAILED`、`CANCELLED`。
- 数据集质量：`VALID`、`WARNINGS`、`INVALID`、`UNKNOWN`。

### 6.3 游标设计

不要把 `updated_at` 当成所有数据源都可靠的增量游标。

有些系统会在多条记录上产生相同时间戳；有些系统允许回填历史数据；还有些系统的时钟不一致。因此，优先级建议如下：

1. 来源系统提供的可靠 CDC 位点或变更序号。
2. 来源系统提供的稳定、可排序变更游标。
3. 由多个字段组成的复合游标，例如 `(updated_at, primary_key)`。
4. 带有重叠窗口的时间轮询，并结合去重与周期性对账。

例如：

```
SELECT *
FROM expense_claims
WHERE updated_at > :last_updated_at
   OR (
       updated_at = :last_updated_at
       AND id > :last_id
   )
ORDER BY updated_at, id
LIMIT :batch_size;
```

这只是针对特定数据源的示例。如果来源系统不保证 `updated_at` 单调递增，或者历史记录可能在旧时间戳下被修改，还需要重叠窗口、变更日志或周期性全量对账。

### 6.4 检查点与幂等

每个同步任务至少应记录：

- `sync_job_id`
- `source_id`
- `dataset_id`
- `sync_mode`
- `snapshot_id`
- `cursor_before`
- `cursor_after`
- `records_read`
- `records_accepted`
- `records_rejected`
- `started_at`
- `completed_at`
- `status`

推荐将以下操作分开：

1. 读取来源数据。
2. 写入原始数据或暂存区。
3. 完成数据校验。
4. 写入标准化数据。
5. 生成映射与语义更新事件。
6. 持久化新游标。

游标推进必须与已确认持久化的数据范围保持一致。否则一旦进程在写入中途崩溃，可能出现数据尚未保存但游标已经前进的情况。

#### 6.4.1 接入链路幂等链

重复投递、Worker 崩溃与同步任务重放是接入层的常态，幂等必须在链路的每一环都有数据库层面的保证，而不是只依赖上游"尽量不重发"：

```
来源消息 ──► ingestion.inbox(source_id, message_key)      # 唯一约束去重，重复消息直接确认
                │ 首次到达
                ▼
           ingestion.raw_records(source_id, record_key, record_version)   # 唯一约束 upsert
                │
                ▼
           canonical ──► 语义 upsert（以映射身份键 identity.key_fields 为准）
                │
                ▼
           下游事件 ──► 第十篇 Outbox（与语义写同一事务提交）──► consumer_inbox 去重消费
```

1. **入口去重**：`ingestion.inbox` 以 `(source_id, message_key)` 唯一约束去重（DDL 见 §14.2）。同键消息重复到达时插入冲突即视为已处理，按幂等成功路径记录 `BUS_DUPLICATE_EVENT`（contracts/02，INFO 级），不产生下游副作用。
2. **原始层去重**：`raw_records` 以 `(source_id, record_key, record_version)` 唯一约束写入；同键同版本的重复写入是空操作，同键新版本才产生新行并保留历史（§7.1 Raw Layer 的可重建性）。
3. **语义 upsert 以映射身份键为准**：语义实例的 upsert 键为映射 Manifest 中 `identity.strategy`/`key_fields` 声明的身份键（§8.3），而不是消息到达顺序或 `record_version`；同身份键的重复处理必须收敛到同一语义实例，后写入不得 silently 覆盖未解决冲突（§11.3 冲突规则优先）。
4. **下游事件走 Outbox**：语义更新与 Outbox 事件在同一数据库事务提交（第十篇事务型 Outbox），消费者侧由 `consumer_inbox` 去重；事件重复投递不能导致语义实例被重复写入。
5. **崩溃重放不产生重复派生事实**：Worker 在写入中途崩溃后，从检查点恢复并重放该批次；由于 inbox、raw_records、语义 upsert 三级唯一约束的存在，重放的所有写入都是幂等空操作或版本递增，不会产生重复的派生事实或重复的下游事件。验收对应 §19.2"相同批次重复投递不会造成重复的业务事实"与 §19.5"同步任务重复执行但不重复产生业务副作用"。

### 6.5 数据删除的语义

删除事件是最容易被忽略的部分。

ODAP 应区分：

- `SOURCE_DELETED`：来源系统明确删除了记录。
- `SOURCE_TOMBSTONE`：来源系统发送了删除标记。
- `MISSING_FROM_SNAPSHOT`：记录没有出现在某次快照中。
- `ACCESS_REVOKED`：ODAP 已经无法读取该记录。
- `NOT_YET_SYNCED`：记录尚未同步。

仅仅因为一条记录没有出现在增量结果中，不能推断该记录已被删除。

当来源明确删除业务对象时，应根据本体策略执行软删除、撤销当前有效性或保留历史版本。对于被审批、合同或审计证据引用的对象，通常不应直接物理删除其全部历史记录。

### 6.6 数据更新的最终一致性

ODAP 应为每个数据集定义新鲜度目标，例如：

- 实时事件：秒级或分钟级。
- 普通业务主数据：数分钟到数小时。
- 历史统计数据：按日或按批次。

这些目标应由业务需求决定，而不是由统一技术默认值决定。

Agent 查询数据时，应能获知数据的最后同步时间、来源版本、质量状态和适用新鲜度。如果数据已经过期，平台应按策略拒绝、降级、要求人工复核或明确标记结果不确定。

## 7. 原始数据层与标准数据模型

建议在 ODAP 中建立可重建的数据处理链，而不是直接把来源记录覆盖成统一格式。

### 7.1 三层数据模型

Raw Layer：原始数据层

保留来源记录、来源主键、来源版本、采集时间、来源时间、数据集版本和原始摘要。

Canonical Layer：标准数据层

将不同来源的数据转换为统一字段、统一类型、统一单位与明确的空值语义。

Semantic Layer：语义数据层

根据企业本体，将标准记录映射为类实例、属性和关系，并通过适用的 SHACL 与业务规则检查。

```
Source Record
  ↓
Raw Record
  ↓
Canonical Record
  ↓
Semantic Mapping
  ↓
Ontology Instance / Relation
  ↓
Validation & Evidence
```

并非每一条记录都必须成功进入下一层。质量不合格、映射缺失或冲突记录应进入隔离区，等待修复或审核。

### 7.2 Canonical Model 示例

以报销业务为例：

```

package canonical

import "time"

type ValueState string

const (
    ValuePresent     ValueState = "PRESENT"
    ValueMissing     ValueState = "MISSING"
    ValueNull        ValueState = "NULL"
    ValueUnmapped    ValueState = "UNMAPPED"
    ValueConflict    ValueState = "CONFLICT"
    ValueStale       ValueState = "STALE"
    ValueUnsupported ValueState = "UNSUPPORTED"
)

type Money struct {
    Amount   string
    Currency string
}

type FieldValue[T any] struct {
    State  ValueState
    Value  *T
    Source string
}

type ExpenseClaim struct {
    CanonicalID string
    SourceRefs  []SourceReference

    EmployeeID  FieldValue[string]
    DepartmentID FieldValue[string]
    Amount      FieldValue[Money]
    Status      FieldValue[string]

    BusinessTime *time.Time
    ObservedAt   time.Time
    SchemaVersion string
}

type SourceReference struct {
    SourceID       string
    DatasetID      string
    RecordKey      string
    RecordVersion  string
    PayloadDigest  string
}

```

这个模型的重点是显式表达值的状态，而不只是保存一个普通字符串。

例如，`DepartmentID` 的值可能是：

- `PRESENT`：已获取且成功映射。
- `MISSING`：来源记录没有该字段。
- `NULL`：来源明确提供空值。
- `UNMAPPED`：字段存在，但映射尚未配置。
- `CONFLICT`：多个来源给出无法自动协调的值。
- `STALE`：已有值，但超过了适用的新鲜度期限。

具体业务可以扩展更多状态，但必须定义各状态的语义和允许的下游操作。

### 7.3 金额、时间与单位

金额

金额应使用十进制定点数或规范化十进制字符串，避免二进制浮点误差。必须明确币种、精度、舍入规则和换算依据。

时间

建议区分：

- `event_time`：业务事件实际发生时间。
- `source_updated_at`：来源系统记录更新时间。
- `observed_at`：ODAP 观察到该记录的时间。
- `ingested_at`：数据被持久化的时间。
- `valid_from` / `valid_to`：业务事实在现实世界中的有效时间范围。

这些时间不能互相替代。尤其是业务事实的有效时间和系统观察到事实的时间不同，后续才能准确解释历史状态。

单位

长度、重量、币种和比例等字段应有明确单位。只有单位定义与转换规则均已确认时才允许换算，不能仅因为两个字段都是数字就直接比较。

### 7.4 标准模型的版本

Canonical Model 本身也是平台资产，应具备：

- Schema 版本。
- 字段定义。
- 类型与空值语义。
- 兼容性规则。
- 变更记录。
- 测试数据。
- 映射兼容报告。

如果标准模型中的 `status` 字段原本表示业务状态，后来改为表示同步状态，即使数据库类型仍然是字符串，也应被视为语义破坏性变更。

## 8. 语义映射引擎设计

这是第十二篇的核心模块。

语义映射引擎（Semantic Mapping Engine）负责把来源字段、标准记录和企业本体连接起来。它不只是字段改名工具，而是一个能够表达类型转换、关系构造、条件映射、实体引用、来源证据和验证约束的执行引擎。

### 8.1 映射对象的五个层次

1. Source Mapping：来源对象映射到标准数据对象。
2. Field Mapping：来源字段映射到标准字段或本体属性。
3. Value Mapping：枚举、单位、币种、时间和状态转换。
4. Entity Mapping：不同系统中的记录如何对应同一个业务实体。
5. Relation Mapping：如何依据外键、业务键或受控规则生成本体关系。

### 8.2 映射工作流

```
Schema Discovery
  ↓
Candidate Mapping Generation
  ↓
Human / Rule Review
  ↓
Type & Constraint Validation
  ↓
Mapping Test
  ↓
Impact Analysis
  ↓
Publish Immutable Version
  ↓
Run Mapping Job
  ↓
Data Quality & Ontology Validation
```

AI 可以协助生成候选映射，例如根据字段描述、样例值和已有本体提出 `employee_code → Employee.employeeId` 的建议。

但候选映射必须经过类型、语义、数据质量和冲突检查；对关键字段、身份标识、金额、权限和业务状态，应要求业务负责人或数据管理员确认。

### 8.3 Mapping Manifest

建议使用结构化 Manifest 管理映射：

```

apiVersion: odap.io/v1
kind: SemanticMapping

metadata:
  id: finance-expense-mapping
  version: 1.0.0
  owner: finance-data-team

spec:
  source:
    sourceId: erp-main
    datasetId: expense-claims
    schemaVersion: 3

  target:
    ontologyId: finance-ontology
    ontologyVersion: 1.2.0

  canonicalModel:
    id: expense-claim
    version: 1.0.0

  identity:
    strategy: source_key
    keyFields:
      - claim_id

  fields:
    - sourceField: claim_id
      targetProperty: odap:sourceClaimId
      required: true

    - sourceField: employee_no
      targetProperty: odap:submittedBy
      transform: resolve_employee
      required: true

    - sourceField: amount
      targetProperty: odap:claimAmount
      transform: decimal_money
      required: true

    - sourceField: status
      targetProperty: odap:claimStatus
      transform: expense_status_v1
      required: true

  validation:
    rejectOnIdentityConflict: true
    quarantineOnUnmappedEnum: true

```

这是映射协议的示例，不是最终 Schema。正式版本还需定义命名空间、属性类型、关系目标类、数据分类、单位规则、空值语义、转换函数版本、来源追踪、删除策略和兼容性约束。

这里的 `odap:submittedBy` 是对象关系，而不是普通字符串字段。其映射必须能够解析到员工实体，并验证目标对象的类型和可访问性。

### 8.4 映射表达式必须受控

建议为映射转换提供受限表达式语言或经过注册的转换函数，例如：

- `trim`
- `normalize_case`
- `parse_decimal`
- `parse_timestamp`
- `enum_map`
- `money_normalize`
- `resolve_entity`
- `compose_key`
- `derive_relation`

禁止将任意 SQL、Shell、JavaScript 或 Go 代码直接嵌入映射 Manifest 并在服务端执行。

每个转换函数都应具有明确的输入类型、输出类型、错误语义、版本和测试集。需要复杂业务逻辑时，应通过经过审核的插件或领域服务实现。

### 8.5 映射执行结果

建议为每条输入记录生成结构化结果：

- `ACCEPTED`：记录通过映射并可进入下游。
- `ACCEPTED_WITH_WARNINGS`：记录可用，但存在已允许的警告。
- `QUARANTINED`：记录被隔离，不能进入正常业务查询。
- `REJECTED`：违反明确的硬性契约。
- `SKIPPED`：根据明确策略未处理。
- `RETRYABLE_ERROR`：技术性失败，可安全重试。
- `UNKNOWN`：当前无法确定是否完成了目标更新，需要检查状态。

记录级状态与整个同步任务状态应分开。例如，一个批次可以成功处理 99% 的记录，同时将 1% 隔离；是否将整个任务标记为成功，应由数据集的质量门槛和业务政策决定。

## 9. 跨系统实体解析与身份关联

企业本体驱动平台很容易遇到一个表面简单、实际复杂的问题：两个来源中的记录，是否代表现实世界中的同一个实体？

例如：

- ERP 员工编号为 `E1024`。
- HR 员工编号为 `0001024`。
- 财务系统使用内部主键 `78391`。
- 邮箱地址可能因员工调岗或更换而变化。

不能只凭名称相同、邮箱相同或字符串归一化结果相同，就断定它们属于同一个人。

### 9.1 实体解析分为三层

第一层：确定性关联

优先使用经过确认的稳定标识，例如来源系统的业务主键、企业统一员工编号或受控的主数据映射表。

第二层：规则化关联

在有明确业务规则时，可以组合多个字段，例如企业编号、来源系统和业务主键。规则必须明确唯一性范围和冲突处理方式。

第三层：候选匹配

当缺少稳定标识时，可以使用名称、地址、日期等特征生成候选匹配，但匹配分数只用于辅助判断，不能自动成为正式身份事实，尤其是员工、供应商、客户和财务主体等高风险对象。

### 9.2 Entity Resolution 模型

建议增加 `entity_resolution` 模块，管理：

- `resolution_job_id`
- `entity_type`
- `source_record_refs`
- `candidate_entity_id`
- `match_method`
- `match_score`
- `evidence_refs`
- `decision_status`
- `reviewer_id`
- `decision_at`

建议状态包括：

- `UNMATCHED`
- `CANDIDATE`
- `CONFIRMED_MATCH`
- `CONFIRMED_DISTINCT`
- `CONFLICT`
- `NEEDS_REVIEW`

这里的 `match_score` 是算法的匹配评分，不是现实身份的真实性证明。

### 9.3 映射关系与实体身份必须分开

假设两个系统中的员工记录已经确认代表同一个人，可以维护：

```
SourceRecord(ERP, E1024)
          │
          ├── resolvesTo → CanonicalEmployee(CE_001)
          │
SourceRecord(HR, 0001024)
```

语义层可以把二者连接到同一个 Canonical Employee，但仍应保留各来源自己的标识和版本。

不要简单删除来源标识，也不要直接把所有来源 ID 当成一个永久全局 ID。

### 9.4 实体冲突处理

如果两个来源出现不同的员工部门、在职状态或法人归属，应根据属性定义权威来源和有效时间处理，而不是把整条记录粗暴地标记为冲突。

例如：

- HR 系统可能是员工任职状态的权威来源。
- ERP 可能是报销单状态的权威来源。
- 组织架构数据可能存在生效日期。
- 财务系统可能保留历史部门编码。

同一个属性可以具有不同的来源权威性和时间有效范围。因此，实体解析应与字段级权威策略协同工作。

## 10. 数据质量引擎

数据质量引擎负责检查数据是否满足使用条件，并向业务调用方明确报告问题。它不是简单地统计空值数量。

### 10.1 七类数据质量维度

| 维度    | 检查内容              | 示例               |
| ----- | ----------------- | ---------------- |
| 完整性   | 必需字段是否存在          | 报销金额缺失           |
| 有效性   | 值是否符合类型与规则        | 日期格式错误           |
| 唯一性   | 唯一标识是否重复          | 相同来源主键出现两次       |
| 一致性   | 多个字段或来源是否矛盾       | 币种与金额单位不匹配       |
| 准确性   | 数据是否与权威来源或可核验事实一致 | 员工状态与 HR 权威记录不一致 |
| 及时性   | 数据是否在允许的时间范围内更新   | 预算快照超过有效期        |
| 完整关联性 | 关系目标是否存在且类型正确     | 报销单引用了不存在的员工     |

准确性通常不能仅凭数据本身完全判断，必须依赖权威来源、业务规则或外部核验。

### 10.2 质量规则模型

建议统一定义：

- `rule_id`
- `rule_version`
- `dataset_id`
- `scope`
- `dimension`
- `severity`
- `expression`
- `threshold`
- `owner`
- `enabled`
- `effective_from`
- `effective_to`

规则类型可以包括：

- 字段规则。
- 记录规则。
- 跨字段规则。
- 跨表关系规则。
- 跨来源一致性规则。
- 新鲜度规则。
- 本体约束规则。
- 业务政策规则。

数据质量引擎负责检测并报告问题；正式业务政策是否允许继续执行，仍由相应的业务规则和授权流程决定。

### 10.3 质量评分

可以为数据集建立综合质量评分：

\\[ Q=\sum\_{i=1}^{n}w_iq_i,\qquad \sum\_{i=1}^{n}w_i=1 \\]

其中 \\(q_i\\) 表示某一质量维度的标准化得分，\\(w_i\\) 表示相应权重。

但不建议只用一个总分控制所有业务操作。即使某个数据集的总体评分为 98 分，只要员工身份关联或支付金额存在关键冲突，该记录仍然不能用于相应的高风险操作。

#### 10.3.1 权重模板与归一化方法

默认权重模板（按数据集类型预置，企业可按政策覆盖，覆盖记录走与映射版本一致的发布流程）：

| 字段类别 | 默认维度权重 \(w_i\) | 主要覆盖维度 |
|---|---|---|
| 身份类字段（主键、外键、实体解析键，如 `employee_no`、`claim_id`） | 0.30 | 完整性 + 完整关联性 |
| 金额类字段（金额、币种、数量） | 0.25 | 有效性 + 一致性 |
| 状态类字段（业务状态、枚举） | 0.20 | 有效性 + 及时性 |
| 其余描述性字段 | 0.25 | 按各维度均分 |

归一化方法（保证 \(q_i \in [0,1]\) 且可复算）：

1. 字段级通过率 \(q_{f} = \text{passed\_checks}(f) / \text{total\_checks}(f)\)；缺失字段（`MISSING`/`UNMAPPED`，§7.2 值状态）计入分母，不得按空值静默跳过。
2. 维度得分 \(q_{i} = \sum_{f \in \text{dim}(i)} (q_f \times \text{fieldWeight}_f) / \sum_{f \in \text{dim}(i)} \text{fieldWeight}_f\)，字段权重来自上表类别。
3. 综合分 \(Q = \sum w_i q_i\)，权重和必须为 1（发布时校验，否则质量规则版本无法发布）。

#### 10.3.2 关键字段硬门槛：一票否决的可配置 Schema

硬门槛与综合分相互独立：任一 gate 失败，无论 \(Q\) 多高，记录或数据集按 `on_fail` 策略处置（默认 `QUARANTINE`，见 §10.5），不得进入高风险业务使用：

```yaml
hard_gates:
  - gate_id: identity_resolved
    dimension: 完整关联性
    expression: "employee_id resolves to a CONFIRMED_MATCH Employee entity"
    on_fail: QUARANTINE
  - gate_id: amount_valid
    dimension: 一致性
    expression: "amount.currency == declared_currency AND amount.value > 0"
    on_fail: QUARANTINE
  - gate_id: status_known
    dimension: 有效性
    expression: "status IN declared_enum_set"
    on_fail: QUARANTINE
```

约束：gate 表达式必须来自 §8.4 的受控规则语言或注册转换函数，不允许任意代码；gate 集合随数据集的质量规则版本发布（§10.2），变更留痕；身份类 gate 默认零容忍——实体解析未确认即否决，不因综合分高而放行。

建议同时设置：

- 整体质量评分。
- 各维度评分。
- 关键规则硬性门槛。
- 隔离记录比例。
- 数据新鲜度。
- 未解决冲突数。

### 10.4 数据质量状态

建议数据集状态至少包括：

- `VALID`：通过当前质量策略。
- `WARNINGS`：存在已允许的非关键问题。
- `INVALID`：存在违反硬性契约的问题。
- `INCOMPLETE`：关键字段或数据范围缺失。
- `STALE`：数据超过适用的新鲜度阈值。
- `UNKNOWN`：当前缺少足够信息完成判断。

这些状态应在 Agent 查询结果中保留。Agent 不应将 `STALE` 的预算数据默认为最新预算，也不能把 `UNKNOWN` 解释为“没有风险”。

### 10.5 隔离区与修复工作流

质量失败的数据不应直接丢弃，也不应默认进入生产语义图。

建议设置 Data Quarantine：

```
Ingestion
  ↓
Canonicalization
  ↓
Quality Validation
  ├── PASS → Semantic Mapping
  ├── WARNING → Accept With Warning
  └── FAIL → Quarantine
                ↓
          Diagnose / Review
                ↓
          Correct / Remap
                ↓
          Reprocess
```

隔离记录应保存失败原因、来源引用、映射版本、质量规则版本和修复历史。修复后应通过正式流程重新处理，不能直接手工修改最终语义数据来绕过原始问题。

## 11. 语义实例存储与本体运行时集成

数据接入的最终目标不是让数据停留在暂存区，而是让它能被本体运行时安全、准确地查询。

### 11.1 语义实例的身份

每个语义实例应具有稳定标识，例如：

```
odap:ExpenseClaim/tenant_01/erp-main/CLM-1024
```

这个例子展示了标识组成思路，并非强制采用该 URI 格式。正式标识策略应考虑：

- 租户边界。
- 来源系统。
- 来源主键。
- 实体合并和拆分。
- 标识稳定性。
- URI 编码规则。
- 隐私与信息泄露风险。

不要把姓名、邮箱或身份证号码直接编码进可公开访问的 URI。

### 11.2 语义事实的来源信息

对于关键事实，建议保留以下元数据：

- 目标本体实例。
- 属性或关系。
- 值或目标实例。
- 来源系统与来源记录 ID。
- 来源版本或快照 ID。
- 映射版本。
- 数据质量状态。
- 观察时间。
- 业务有效时间。
- 数据分类与访问策略。

RDF 图中的业务三元组可以承载语义事实，而这些来源和时间信息可以通过命名图、独立元数据表或其他适当的证据模型管理。

不建议为了保存元数据而随意给业务本体增加大量临时属性。应明确区分领域语义模型与来源追踪模型。

### 11.3 冲突与多来源事实

如果 ERP 与 HR 对同一员工的部门归属不同，不应简单地让最后写入的数据覆盖之前的数据。

建议将冲突表示为多个有来源、有时间、有权威等级的事实，然后由领域规则决定：

- 哪个来源对该属性具有权威性。
- 哪条事实在当前时间有效。
- 是否需要人工复核。
- 是否允许下游 Agent 使用。
- 是否可以生成新的推导事实。

对于高风险事实，冲突未解决时应返回 `CONFLICT` 或 `UNKNOWN`，而不是静默选择一个值。

### 11.4 本体验证的分层

推荐分成三种验证：

1. 数据 Schema 验证：字段类型、必需字段、格式和基本值约束。
2. 语义结构验证：本体类型、关系目标、SHACL 形状和基数约束。
3. 业务政策验证：业务规则、审批条件、权限条件和其他业务约束。

三者分别承担不同职责。例如，报销金额格式正确，不代表报销符合制度；本体结构验证通过，也不代表当前用户有权提交报销单。

### 11.5 语义数据更新与版本

建议采用明确的数据更新策略：

- 当前有效事实可以按业务键更新。
- 重要业务变化应保留历史版本。
- 删除或撤销事实应保留必要的历史证据。
- 数据集更新应记录快照或版本引用。
- 本体与映射发布应与数据同步状态分开管理。

本体版本不应随着每次业务数据变化而变化。反过来，映射版本升级也不意味着所有数据已经成功重建。平台应分别记录 Schema、Mapping、Ontology 和 Data Snapshot 的版本。

## 12. 数据血缘与端到端可追溯性

数据血缘（Data Lineage）需要回答三个方向的问题：

- 向前追踪：某个来源字段发生变化，会影响哪些本体属性、Agent 和业务流程？
- 向后追踪：某个业务结果依赖了哪些来源记录、映射版本和规则？
- 横向追踪：两个来源系统中的事实如何关联到同一个业务实体？

### 12.1 血缘节点

建议将以下对象作为血缘图中的节点：

- Data Source。
- Dataset。
- Schema Version。
- Source Record。
- Canonical Record。
- Mapping Version。
- Ontology Instance。
- Ontology Property / Relation。
- Quality Finding。
- Agent Run。
- Evidence Bundle。
- ERP Operation。

节点之间的边可以包括：

- `INGESTED_FROM`
- `NORMALIZED_BY`
- `MAPPED_BY`
- `RESOLVES_TO`
- `DERIVED_FROM`
- `VALIDATED_BY`
- `CONSUMED_BY`
- `RECORDED_IN`
- `AFFECTED_BY`

### 12.2 血缘示例

假设某个报销 Agent 判断一笔报销需要升级审批，系统应能够追溯：

```
ERP ExpenseClaim record
    ↓ INGESTED_FROM
Raw Record Snapshot
    ↓ NORMALIZED_BY
Canonical ExpenseClaim
    ↓ MAPPED_BY
Mapping Version 1.0.0
    ↓ MATERIALIZED_AS
Ontology ExpenseClaim Instance
    ↓ VALIDATED_BY
Ontology / Business Rule Result
    ↓ CONSUMED_BY
Agent Run
    ↓ TRIGGERED
Approval Request
    ↓ RECORDED_IN
Evidence Bundle
```

这条链路不能仅依赖 Agent 事后生成的文字解释。关键关联应在实际处理过程中由可信服务记录。

### 12.3 字段级血缘

对重要字段，建议进一步记录字段级血缘：

- 目标字段。
- 来源字段。
- 转换函数及版本。
- 转换参数。
- 来源记录引用。
- 转换结果摘要。
- 验证结果。
- 计算时间。

例如，报销单的 `claimAmount` 应能追溯到 ERP 中的原始金额字段、币种字段、金额标准化函数和映射版本。

### 12.4 影响分析

当某个来源字段或映射发生变化时，系统应能生成影响清单：

- 哪些标准字段受到影响。
- 哪些本体类和属性使用这些字段。
- 哪些 SHACL 约束或业务规则依赖相关属性。
- 哪些 Agent 使用该本体。
- 哪些尚未完成的 Run 锁定了旧版本。
- 哪些证据包引用了旧版本。

影响分析的结果用于决定是否需要阻止发布、执行回归测试、安排数据重建或通知业务负责人。

### 12.5 血缘完整性的边界

并非所有数据源都能提供精确的字段级变更记录。对于只支持全量导出的系统，ODAP 可能只能追溯到数据集快照和记录级摘要。

因此，应为血缘设置明确的精度等级，例如：

- `FIELD_LEVEL`
- `RECORD_LEVEL`
- `DATASET_LEVEL`
- `UNKNOWN`

不要将不完整的血缘图展示为绝对完整的来源证明。

## 13. 数据治理、权限与隐私保护

数据治理必须贯穿连接、采集、转换、存储、查询、导出和删除全过程。

### 13.1 数据分类

建议沿用第九篇的分类，并在数据层进一步定义使用规则：

| 分类             | 典型示例       | 默认要求           |
| -------------- | ---------- | -------------- |
| `PUBLIC`       | 可公开的企业资料   | 允许按授权范围共享      |
| `INTERNAL`     | 普通内部业务数据   | 仅企业内部授权使用      |
| `CONFIDENTIAL` | 财务、合同、经营数据 | 严格按业务域和角色控制    |
| `RESTRICTED`   | 高敏感个人或业务数据 | 最小授权、受控处理、额外审计 |

具体分类应由企业的数据政策定义。不同法律辖区和行业可能有不同要求，不能仅凭这四个标签就认为满足所有合规义务。

### 13.2 权限的三层控制

建议将权限控制分为三层：

连接器层

决定 Connector 是否可以连接指定系统、读取指定数据集和访问指定字段。

数据服务层

决定调用者能否查询某条记录、某个语义实例或某个属性。

消费端层

决定 Agent、业务用户和证据服务是否可以将数据用于特定业务目的。

这三层都必须执行权限检查。不能因为某个 Agent 已经通过本体查询获得数据，就允许它绕过授权直接读取原始数据库。

### 13.3 目的限制与数据最小化

每个数据源连接应声明允许用途，例如：

- 业务查询。
- 报销审核。
- 经营分析。
- 审计调查。
- 模型评估。

如果某数据源仅授权用于报销审核，不应自动将其提供给其他无关的 Agent 或模型评估任务。

外部模型调用还应继续遵循第九篇的模型数据分类、脱敏和路由治理。数据接入平台有权读取某项数据，不代表允许把它发送给任何 LLM 供应商。

### 13.4 数据删除、保留与法律冻结

建议定义统一的治理动作：

- `RETENTION_EXPIRED`
- `DELETE_REQUESTED`
- `DELETE_APPROVED`
- `DELETE_COMPLETED`
- `LEGAL_HOLD`
- `ACCESS_REVOKED`
- `REDACTED`

当来源记录被删除时，应评估原始数据、标准化数据、语义实例、缓存、索引和证据包分别需要怎样处理。

对已进入审计或证据链的数据，不应随意删除其完整性元数据；但这也不意味着原始个人信息可以无期限保留。应根据适用法律和企业保留政策决定是否删除原始内容、进行不可逆匿名化、限制访问或保留必要的摘要。

### 13.5 连接器安全

连接器通常具有访问企业核心系统的能力，因此应特别关注：

- 凭据存储和轮换。
- 数据库只读账号。
- API 端点白名单。
- SSRF 与任意网络访问风险。
- 分页与查询资源限制。
- 响应体大小限制。
- 连接超时和请求取消。
- 恶意文件与压缩炸弹。
- 解析器漏洞。
- 插件进程隔离。
- 连接器日志脱敏。
- 多租户凭据隔离。

尤其不要允许用户仅通过填写任意 URL，就让服务端 Connector 访问未经审核的内部网络地址。应使用网络出口策略、域名或 IP 白名单、私有地址限制和经过审核的连接配置。

## 14. 数据平台数据库 Schema 设计

以下为建议新增的 PostgreSQL 逻辑 Schema。它们与前两篇的任务和插件表、第五篇的本体 Registry、第七篇的 ERP 连接表及第十一篇的审计和证据表协同工作。

### 14.1 数据源与数据集

```

CREATE SCHEMA IF NOT EXISTS ingestion;
CREATE SCHEMA IF NOT EXISTS catalog;
CREATE SCHEMA IF NOT EXISTS mapping;
CREATE SCHEMA IF NOT EXISTS quality;
CREATE SCHEMA IF NOT EXISTS lineage;

CREATE TABLE ingestion.data_sources (
    source_id UUID PRIMARY KEY,
    tenant_id UUID NOT NULL,
    connector_id TEXT NOT NULL,
    source_name TEXT NOT NULL,
    source_type TEXT NOT NULL,
    credential_ref TEXT,
    config JSONB NOT NULL DEFAULT '{}',
    status TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE catalog.datasets (
    dataset_id UUID PRIMARY KEY,
    tenant_id UUID NOT NULL,
    source_id UUID NOT NULL
        REFERENCES ingestion.data_sources(source_id),
    dataset_name TEXT NOT NULL,
    dataset_type TEXT NOT NULL,
    owner_id TEXT,
    classification TEXT NOT NULL,
    active_schema_version TEXT,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_datasets_tenant_source
    ON catalog.datasets (tenant_id, source_id);

```

这段 Schema 只展示核心结构。正式实现还需补充租户复合外键、数据访问策略、连接器能力、状态约束、唯一性规则和必要的行级安全策略。

### 14.2 Schema 版本、同步任务与原始记录表

```

CREATE TABLE catalog.schema_versions (

        REFERENCES catalog.datasets(dataset_id),
    version_number INTEGER NOT NULL,

    schema_document JSONB NOT NULL,

    detected_at TIMESTAMPTZ NOT NULL DEFAULT now(),

    UNIQUE (dataset_id, version_number)
);

CREATE TABLE ingestion.sync_jobs (
    sync_job_id UUID PRIMARY KEY,
    tenant_id UUID NOT NULL,
    dataset_id UUID NOT NULL
        REFERENCES catalog.datasets(dataset_id),
    sync_mode TEXT NOT NULL,
    status TEXT NOT NULL,
    cursor_before JSONB,
    cursor_after JSONB,
    snapshot_id TEXT,
    records_read BIGINT NOT NULL DEFAULT 0,
    records_accepted BIGINT NOT NULL DEFAULT 0,
    records_rejected BIGINT NOT NULL DEFAULT 0,
    started_at TIMESTAMPTZ,
    completed_at TIMESTAMPTZ,
    error_code TEXT,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_sync_jobs_dataset_time
    ON ingestion.sync_jobs
       (tenant_id, dataset_id, created_at DESC);

-- 接入链路幂等链（§6.4.1）：入口去重表。
-- message_key 为来源系统提供的稳定消息标识（Webhook 事件 ID、消息队列 message_id
-- 或 Connector 生成的稳定批次键）；同键重复插入即视为已处理。
CREATE TABLE ingestion.inbox (
    inbox_id UUID PRIMARY KEY,
    tenant_id UUID NOT NULL,
    source_id UUID NOT NULL
        REFERENCES ingestion.data_sources(source_id),
    message_key TEXT NOT NULL,
    message_digest TEXT NOT NULL,
    sync_job_id UUID
        REFERENCES ingestion.sync_jobs(sync_job_id),
    status TEXT NOT NULL DEFAULT 'RECEIVED',
    received_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    processed_at TIMESTAMPTZ,
    UNIQUE (tenant_id, source_id, message_key)
);

CREATE INDEX idx_inbox_job
    ON ingestion.inbox (tenant_id, sync_job_id);

-- 原始记录层（§7.1 Raw Layer）：同来源同记录键同版本的重复写入是空操作；
-- 新版本产生新行，历史版本保留以支持重建。
CREATE TABLE ingestion.raw_records (
    raw_record_id UUID PRIMARY KEY,
    tenant_id UUID NOT NULL,
    source_id UUID NOT NULL
        REFERENCES ingestion.data_sources(source_id),
    record_key TEXT NOT NULL,
    record_version TEXT NOT NULL,
    dataset_id UUID
        REFERENCES catalog.datasets(dataset_id),
    payload_ref TEXT NOT NULL,
    payload_digest TEXT NOT NULL,
    observed_at TIMESTAMPTZ NOT NULL,
    ingested_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    sync_job_id UUID
        REFERENCES ingestion.sync_jobs(sync_job_id),
    UNIQUE (tenant_id, source_id, record_key, record_version)
);

CREATE INDEX idx_raw_records_key
    ON ingestion.raw_records (tenant_id, source_id, record_key, ingested_at DESC);

```

`cursor_before` 和 `cursor_after` 可以使用 JSONB 表达不同来源的游标格式，但每种 Connector 必须定义其游标 Schema 和比较规则。不能将任意 JSON 游标都视为可以直接比较的版本号。

`ingestion.inbox` 与 `ingestion.raw_records` 的两条唯一约束是接入幂等的数据库层保证（§6.4.1）：前者保证同一来源消息只被处理一次，后者保证同一来源记录的同一版本只落地一次。两者都不依赖应用层"先查后写"，插入冲突即走幂等路径。大载荷 `payload_ref` 指向对象存储，行内只存摘要，避免原始表膨胀。

### 15.6 映射升级与历史数据重建：backfill 任务模型

映射版本升级后，新写入按新版本处理，但历史数据是否重建、如何重建必须有显式任务模型（§11.5：映射版本升级不意味着所有数据已经成功重建）：

```
backfill_job:
  backfill_job_id
  mapping_id
  from_version -> to_version          # 版本对照（diff 见 §16.9 发布前差异视图）
  scope                               # 全量 / 按业务键范围 / 按数据集
  mode                                # DUAL_RUN（双跑比对，默认）/ DIRECT_CUTOVER（受控直切）
  status                              # PENDING -> DUAL_RUNNING -> COMPARING -> CUTOVER_PENDING
                                      #   -> CUTTING_OVER -> COMPLETED / ROLLED_BACK / ABORTED
  diff_report_ref                     # 差异比对报告引用
  approval_ref                        # 切换审批（高风险映射必需）
  created_by / created_at / completed_at
```

流程五步：

1. **版本对照**：确定 `from_version` 与 `to_version` 的 mapping_document 差异，结合 §12.4 影响分析列出受影响的标准字段、本体属性、规则、Agent 与未完成 Run。
2. **双跑比对（dual-run）**：新版本与旧版本对同一批历史输入并行处理（只读，不写生产语义层），产出差异报告：按字段分类统计值变化、关系目标变化、隔离率变化。身份/金额/状态类字段差异率超过阈值（默认趋近零容忍，阈值随质量规则版本配置）即阻断升级，回退到影响分析。
3. **差异比对与人工确认**：抽样差异记录交数据负责人与业务负责人复核；确认"差异是预期修正"后才允许进入切换。
4. **指针切换**：受控切换 active mapping pointer（新写入走新版本）。切换与 Outbox 事件同事务提交（§6.4.1），语义 upsert 仍以映射身份键为准；进行中的 Run 继续使用其锁定的旧版本直至终态，不中途换版。
5. **回退**：切换后发现问题，pointer 回退到旧版本并生成新的受控发布版本——回退是新建版本，不是修改历史（§15.3 原则）。

历史数据重建的附加约束：

- 重建作业必须幂等（身份键 upsert）、可断点恢复（游标 + 批次检查点）、可重复执行不产生重复派生事实（§6.4.1 三级唯一约束覆盖）。
- 重建不静默覆盖冲突事实：未解决冲突仍按 §11.3 多来源事实规则处理。
- 每次 backfill 的状态变化与切换都产生审计事件，证据包可引用 backfill_job_id 与 diff_report_ref（§22 决策 15）。
- 是否重建历史由业务决定：仅当历史与新语义的不一致会影响业务判断时才执行；否则只切换指针并在数据目录登记"历史数据按旧版本解释"。

## 17. 与前十一篇的集成契约

第十二篇不是一个孤立的数据平台，而是 ODAP 各核心模块的基础数据服务。必须明确各模块之间的契约，避免出现重复存储、重复授权和状态不一致。

### 17.1 与 Ontology Factory 的集成

Ontology Factory 管理概念模型、约束和映射资产；本篇的数据平台负责发现来源 Schema、执行映射、采集事实并验证结果。

两者的协作关系是：

1. 数据目录提供来源字段和业务元数据。
2. Ontology Factory 根据企业本体生成或审核候选映射。
3. 数据平台执行映射测试与质量检查。
4. 本体管理员批准并发布相应资产版本。
5. 数据平台锁定已发布的本体和映射版本。
6. Ontology Runtime 查询经过验证的语义事实。

不能让数据接入 Agent 自行修改正式本体并立即生效。

### 17.2 与 Ontology Runtime 的集成

Ontology Runtime 应通过统一的数据服务接口获取语义实例或受控查询结果。

返回内容除了业务字段，还应携带必要的元数据：

```
{
  "data_snapshot_id": "snapshot_001",
  "ontology_version": "finance-ontology@1.2.0",
  "mapping_version": "finance-expense-mapping@1.0.0",
  "freshness": {
    "observed_at": "2026-10-12T12:00:00Z",
    "status": "FRESH"
  },
  "quality_status": "VALID",
  "facts": [
    {
      "subject": "ExpenseClaim/CLM-1024",
      "predicate": "claimAmount",
      "value": {
        "amount": "1250.00",
        "currency": "CNY"
      },
      "evidence_ref": "source-record-ref-001"
    }
  ]
}
```

该示例只展示数据契约。正式实现中，实例标识、证据引用和租户信息都应受访问控制。`FRESH` 与 `VALID` 的含义必须由数据集策略明确定义。

### 17.3 与 Agent Runtime 的集成

Agent 不应直接访问原始数据库，也不应自由编写任意查询语句来绕过语义层。

推荐流程：

```
Agent
  ↓
Harness
  ↓
Data / Ontology Query API
  ↓
Authentication + Authorization
  ↓
Query Plan & Data Policy
  ↓
Ontology Runtime / Data Service
  ↓
Facts + Quality + Freshness + Evidence References
  ↓
Agent Decision
```

如果 Agent 需要调用数据工具，工具应声明允许访问的数据集、对象类型、字段范围、数据分类和预算。

Agent 可以提出查询意图，但最终查询必须由受控查询引擎执行。

### 17.4 与 Evidence Service 的集成

第十一篇的证据服务需要记录：

- 来源数据集及快照版本。
- 来源记录的稳定引用。
- 映射版本和转换函数版本。
- 本体版本与规则版本。
- 数据质量与新鲜度状态。
- 关键事实的来源引用。
- 数据读取时执行的权限与策略信息。

如果一个 Agent 的决策依赖预算余额，则证据包不仅要记录“预算余额为多少”，还应记录该值来自哪个系统、哪个时间点、采用什么单位、是否满足新鲜度要求。

### 17.5 与 ERP Gateway 的集成

数据接入层可以读取 ERP 数据并建立语义视图，但不能因此拥有业务写入权限。

- 查询员工和报销单：通过只读数据服务或受控 ERP Adapter。
- 提交报销单：必须经过 ERP Gateway。
- 确认操作是否完成：以权威操作账本和 ERP 回执为准。
- 更新语义实例：根据已经确认的业务状态和来源事件执行。

不要让数据同步任务通过直接修改 ERP 数据库的方式完成业务写入，也不要将本地语义图的更新当成 ERP 操作成功的证明。

#### 17.5.1 ERP 回执驱动的语义实例失效闭环

ERP 写操作经 Gateway 执行、回执验证通过后，如果语义层仍缓存着写入前的旧值，Agent 随后读到的就是"写入后陈旧读"——旧值可能直接导致重复提交或错误审批。闭环定义如下：

```
ERP Gateway 提交 ──► 操作账本记录 ──► 回执验证通过（第七篇 §7）
                                        │
                                        ▼
                            发布 domain event（第十篇 Outbox，与回执落库同事务）
                                        │
                                        ▼
                            语义实例刷新（按身份键 upsert，§6.4.1）
                                        │
                                        ▼
                            缓存失效：递增该租户/本体的 data_graph_version
                                        │
                                        ▼
                            第十三篇查询缓存键含 data_graph_version，旧键自然失效
```

1. **事件源自主权**：只有"回执验证通过"才触发刷新；请求已发送但结果未知时只记录 `REQUIRES_RECONCILIATION` 语义（contracts/01），不提前刷新，也不把旧值当新值。
2. **缓存联动**：第十三篇 §11.5 的缓存键包含 `data_graph_version`（与 `ontology_digest`、`mapping_version_set_digest` 并列）；语义刷新递增该版本号，所有旧缓存键随之失效，不需要逐条删除缓存，也不会出现"删了又写入旧值"的竞态。
3. **顺序保证**：语义 upsert 与 Outbox 事件同事务（§6.4.1 第 4 条），消费者重放不产生重复派生事实；刷新失败时事件重试，`data_graph_version` 只在语义写成功后才递增。
4. **读路径可见性**：Agent 查询返回的 `data_snapshot_id`/`data_graph_version`（§17.2 契约）必须反映刷新后的版本；若查询快照版本早于最近一次已确认 ERP 写，平台按新鲜度策略（§6.6）拒绝、降级或明确标记，不得静默返回旧值。
5. **验收**：对应 §19.5 端到端场景"ERP 提交成功后的即时查询返回新值，且不出现重复派生事实"；故障注入"回执到达但语义刷新 Worker 崩溃"时，恢复后按 Outbox 重放完成刷新，`data_graph_version` 不重复递增。

## 18. 端到端示例：企业报销数据接入

为了让架构能够直接落地，建议以员工报销业务域作为第一条完整的数据链路。

### 18.1 数据源

假设企业提供三个数据源：

| 数据源    | 主要内容          | 权威范围     |
| ------ | ------------- | -------- |
| HR 系统  | 员工、部门、任职状态    | 员工与组织主数据 |
| ERP 系统 | 报销单、费用金额、业务状态 | 报销单业务状态  |
| 财务预算系统 | 部门预算、预算占用和余额  | 财务预算口径   |

这里的权威范围只是项目设计示例，正式接入前必须由企业业务负责人确认。

### 18.2 接入流程

步骤 1：注册数据源

配置连接器、凭据引用、访问范围、数据分类和同步方式。

步骤 2：发现 Schema

识别字段、类型、主键、枚举和增量读取能力。

步骤 3：建立标准数据模型

规范员工编号、金额、币种、状态和业务时间。

步骤 4：配置语义映射

生成 Employee、Department、ExpenseClaim、Budget 等本体实例与关系。

步骤 5：质量与本体验证

检查身份关联、金额、必需关系、预算新鲜度与冲突记录。

步骤 6：发布并供 Agent 查询

锁定 Schema、Mapping、Ontology 与数据快照版本，并保留证据引用。

### 18.3 示例映射

```
HR.employee_code
    → CanonicalEmployee.sourceEmployeeCode
    → Employee.employeeId

HR.department_code
    → CanonicalEmployee.departmentRef
    → Employee.belongsTo → Department

ERP.claim_id
    → CanonicalExpenseClaim.sourceClaimId
    → ExpenseClaim

ERP.employee_no
    → Entity Resolution
    → ExpenseClaim.submittedBy → Employee

Budget.department_code
    → Entity Resolution
    → Budget.appliesTo → Department
```

这些关系只有在标识语义、目标实体类型和关联规则经过验证后才能发布。

### 18.4 质量失败示例

假设 ERP 中有一笔报销：

- 报销单编号存在。
- 金额为 `1250.00 CNY`。
- 员工编号为 `E1024`。
- HR 数据中暂时没有对应员工。
- 预算数据最后更新时间为三天前，而该业务要求使用当天预算。

平台不应简单地把报销单映射为完整有效的语义实例。

建议结果为：

- 报销单本身：可以作为来源事实保留。
- 员工关联：`UNRESOLVED` 或 `CONFLICT`。
- 预算数据：`STALE`。
- 本体验证：根据规则返回 `INCOMPLETE` 或 `FAIL`。
- Agent 决策：不得将缺失员工和过期预算解释为通过。
- Evidence Service：保留来源引用、映射版本、质量发现和验证结果。

### 18.5 正常业务执行

当数据通过检查后：

1. Agent 查询报销单、员工与预算的语义事实。
2. Harness 锁定 Agent、本体、规则和映射版本。
3. Ontology Runtime 返回来源事实、质量状态和新鲜度。
4. 业务规则引擎检查费用政策。
5. 授权引擎判断是否允许执行。
6. 若需要人工审批，进入 Approval Service。
7. ERP Gateway 执行受控操作。
8. ERP 回执经验证后更新业务状态。
9. Evidence Service 汇总整个过程的来源、规则、审批和回执。

这条链路将数据来源、业务语义、智能体执行和审计证据连接起来，构成 ODAP 的完整企业业务闭环。

## 19. 测试体系与验收标准

数据接入平台的验收不能只看同步任务是否返回成功，还要验证数据语义是否正确、更新是否可靠、权限是否得到执行。

### 19.1 Connector 契约测试

- 连接器正确发现来源 Schema。
- 不支持的能力会明确返回错误。
- 分页读取不会遗漏或意外重复记录。
- 游标能够在任务中断后恢复。
- 凭据过期、限流和远端不可用均有明确错误分类。
- 取消任务后，Connector 能停止后续读取。
- 原始记录的来源 ID、版本和摘要能够追溯。
- 删除事件能够被正确识别，或明确声明无法可靠检测删除。

### 19.2 同步可靠性测试

- 相同批次重复投递不会造成重复的业务事实。
- 数据写入成功但游标更新失败时，可以安全恢复。
- 游标推进不会越过尚未持久化的数据。
- CDC 断点恢复后不会静默丢失已提交变更。
- 迟到事件不会无条件覆盖更新的权威事实。
- 来源 Schema 变化会触发兼容性检查。
- 部分记录失败时，任务状态和质量统计保持一致。
- 隔离记录重新处理后仍保留原始失败历史。

### 19.3 语义映射测试

- 字段类型不兼容时，映射发布失败。
- 未知枚举值按政策隔离，而不是随意映射到默认状态。
- 金额、币种和单位转换符合预先定义的精度规则。
- 对象关系目标存在且类型正确。
- 缺失字段与显式空值保持区别。
- 实体解析冲突不会自动合并高风险业务主体。
- 已发布映射版本不可被原地修改。
- 映射回退后，历史 Run 仍能引用原版本。

### 19.4 数据质量与安全测试

- 数据集质量状态能够准确反映关键规则失败。
- 过期数据不能被静默标记为新鲜数据。
- 冲突事实能够保留多个来源及各自的有效时间。
- 不同租户的数据源、数据集和语义实例不能交叉访问。
- 无权访问的字段不能通过错误信息、日志或血缘接口泄露。
- Connector 无法访问未授权的内部网络地址。
- 敏感数据不会未经策略检查发送给外部模型。
- 数据删除和保留操作都有明确的授权与审计记录。

### 19.5 端到端验收

建议用 Mock ERP 和 Mock HR 构建可重复的测试环境，至少覆盖：

1. 正常导入员工、部门、报销单和预算。
2. 重复员工编号与跨系统实体关联冲突。
3. 报销金额缺失或币种不合法。
4. 来源 Schema 新增、删除和类型变更。
5. 增量游标失效与同步任务恢复。
6. 来源删除事件与语义实例撤销。
7. 映射升级导致目标属性变化。
8. 数据过期导致 Agent 业务流程进入待复核状态。
9. 同步任务重复执行但不重复产生业务副作用。
10. 历史证据包能够追溯到执行时的映射和数据快照版本。

## 20. 部署与容量设计

### 20.1 MVP 部署架构

建议在 Docker Compose 环境中部署：

- `odap-api`：管理 API 与业务接口。
- `odap-connector-worker`：执行连接器与采集任务。
- `odap-mapping-worker`：执行标准化、语义映射与质量验证。
- `odap-scheduler`：调度周期任务。
- `odap-postgres`：平台元数据、任务、权限与映射版本。
- `odap-mock-erp`：模拟企业业务系统。
- `odap-object-store`：原始文件、快照和证据制品。
- `odap-ontology-runtime`：本体查询与语义验证服务。
- 可选的消息代理和可观测性组件。

初期可以将 Scheduler 与部分 Worker 合并部署，但应保留独立的逻辑接口，便于后续扩容。

### 20.2 数据规模与存储选择

建议根据数据规模选择存储策略：

| 数据类型      | MVP 建议      | 规模增长后的选择                |
| --------- | ----------- | ----------------------- |
| 平台元数据     | PostgreSQL  | PostgreSQL 分区与读写扩展      |
| 同步任务与游标   | PostgreSQL  | PostgreSQL + 消息代理       |
| 小型标准业务数据  | PostgreSQL  | PostgreSQL 或专用数据存储      |
| 大型原始快照    | 对象存储        | 对象存储 + 列式数据格式           |
| 高频分析数据    | 按需选择        | 数据仓库或 OLAP 引擎           |
| RDF 语义数据  | 封装后的语义存储适配器 | 专用 RDF Store 或经过验证的替代实现 |
| 数据血缘      | PostgreSQL  | 专用血缘或图存储                |
| 日志与 Trace | 复用第十一篇基础设施  | 独立扩展遥测后端                |

不要在 MVP 阶段就为每一类数据引入一个独立数据库。先用清晰的存储抽象与数据访问契约，再根据实际规模决定迁移。

### 20.3 容量规划指标

至少监测：

- 每秒读取记录数。
- 每批处理耗时。
- 来源 API 限流次数。
- 采集到语义更新的端到端延迟。
- 原始数据与标准数据的存储增长。
- 质量失败比例。
- 映射执行失败率。
- 实体解析冲突率。
- 数据集新鲜度。
- 数据同步任务积压。
- 本体实例更新耗时。

容量规划应使用真实数据规模、字段复杂度和来源系统限制进行压测，不宜直接假定某个 Worker 能稳定处理固定数量的记录。

## 21. 实施路线图

建议按以下顺序推进。

P1：数据源注册中心与 Connector SDK

建立连接器协议、凭据引用、健康检查、Schema 发现和统一错误模型。

交付：能够注册并安全连接 Mock ERP、PostgreSQL 和 CSV/JSON 数据源。

P2：原始数据层与同步引擎

实现全量快照、增量轮询、游标、检查点、重试、隔离和同步统计。

交付：任务可以中断、恢复和重复处理，且不静默丢失数据。

P3：Canonical Model 与数据目录

建立标准业务对象、Schema Registry、元数据和字段级空值语义。

交付：不同来源能够转换成统一、可版本化的标准记录。

P4：语义映射引擎

实现字段、值、实体和关系映射，增加版本发布、测试和影响分析。

交付：报销数据能够转换为经过验证的本体实例与关系。

P5：数据质量与实体解析

实现质量规则、隔离工作流、权威来源策略、冲突检测和新鲜度治理。

交付：不合格或未知数据不会被静默当作可靠业务事实。

P6：血缘、证据与治理中心

将数据来源、映射版本、Run、业务规则和证据包关联，完成前端工作台与端到端验收。

交付：业务结果可以追溯到原始数据和映射过程。

### 21.1 MVP 范围控制

为了让 ODAP 尽快形成可运行产品，建议首版仅完成：

- Mock ERP + 一个模拟 HR 数据源。
- PostgreSQL 只读 Connector。
- CSV/JSON 文件导入。
- 全量快照与增量轮询。
- Canonical Employee、Department、ExpenseClaim、Budget。
- 字段映射、枚举转换、关系映射。
- 基础质量规则与隔离区。
- 映射版本管理与发布审批。
- Ontology Runtime 查询接口。
- Evidence Service 的来源记录与映射版本引用。
- React 数据源、映射、同步和质量工作台。

暂不建议首版就实现通用 CDC 平台、复杂的模糊实体匹配、多数据仓库适配和全自动本体重建。先验证一条报销数据链路的正确性，再扩展到采购、合同和人力资源等领域。

## 22. 本篇最终架构决策

综合 ODAP 前十二篇，建议将以下内容固化为 V1.0 的架构基线。

1. 数据源、标准数据、语义实例和证据记录分层管理。 原始数据不能被标准化过程静默覆盖。
2. 使用统一 Connector SDK，连接器必须声明能力、访问范围和限制。
3. 数据源凭据只保存安全引用，连接器运行时实行最小权限和网络访问控制。
4. 建立 Schema Registry，来源结构变化必须触发兼容性检查。
5. 同步任务必须具备稳定游标、幂等处理、检查点、失败恢复和删除语义。
6. 增量同步不能默认依赖时间戳；应根据来源系统能力选择 CDC、可靠游标或重叠窗口与对账。
7. 建立 Canonical Model，将技术结构标准化与企业业务语义建模分开。
8. 语义映射作为独立、不可变、可测试、可审核的版本化资产。
9. 映射执行必须支持类型验证、枚举转换、单位换算、实体解析和关系构造。
10. 数据质量、来源权威性、新鲜度和实体冲突必须能够被下游查询感知。
11. 未知、缺失、冲突、过期和明确不存在必须具有不同的语义。
12. 本体实例必须保留来源、映射版本、数据快照和必要的时间信息。
13. 历史 Run 应锁定执行时使用的映射、本体、规则与数据版本引用。
14. 数据接入组件不具备绕过 ERP Gateway 的业务写入权限。
15. 关键数据转换、映射发布、质量修复和敏感数据导出必须纳入第十一篇的审计与证据体系。
16. MVP 优先完成 Mock ERP、Mock HR 和报销数据链路，再逐步扩展连接器与数据规模。

## 23. 第十二篇完成后，ODAP 的架构进展

数据从哪里来？

通过连接器、数据库、企业 API、文件、消息和后续 CDC 接入，保留来源标识与数据版本。

不同系统的数据如何统一？

通过 Canonical Model、字段与单位转换、实体解析和版本化语义映射，形成可管理的业务事实。

智能体如何理解企业数据？

通过 Ontology Runtime 查询有明确语义、来源、质量状态和新鲜度的事实，而不是直接猜测数据库字段的含义。

结果如何被验证？

通过本体验证、授权审批、ERP 回执、数据血缘和 Evidence Service，形成从业务结果到来源数据的可复核链路。

我认为，ODAP 的核心价值正在这里体现出来：它不是把一个 LLM 简单接到 ERP 上，而是在企业现有业务系统之上建立一层有明确语义、受权限约束、可持续更新、可验证且可追溯的智能执行体系。

其中，企业本体定义业务对象和关系；数据平台负责把真实业务数据持续映射到这些语义结构中；Agent 在 Harness、授权和业务规则的约束下使用这些数据；审计与证据服务则记录实际发生的过程和结果。

这几部分结合起来，才能使企业智能体从演示性质的问答工具走向可以参与正式业务流程的平台。
