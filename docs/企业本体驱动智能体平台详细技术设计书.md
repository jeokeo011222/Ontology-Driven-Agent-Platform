# 《企业本体驱动智能体平台详细技术设计书》

版本：V1.0 · 部署模式：企业私有化 · ERP 策略：标准适配接口 · 首期目标：完整平台骨架，暂不接入真实 ERP

## 一、设计目标与架构决策

本设计书将前面的总体方案进一步落到可实施的工程层面，明确模块边界、接口契约、核心数据模型、权限判定、插件协议、执行状态机和实施验收标准。

平台暂定名称为 Ontology-Driven Agent Platform（ODAP），中文名称为“企业本体驱动智能体平台”。名称只是工程代号，后续可以独立进行品牌设计。

### 1.1 首期必须遵守的六项原则

1. ERP 解耦。 不绑定 SAP、Oracle、用友、金蝶或任何特定 ERP；首期只定义标准接口和模拟适配器。
2. 本体驱动。 专业智能体通过注册中心发现本体、读取语义定义、执行 SHACL 验证，并遵循版本兼容规则。
3. Harness 统一。 所有智能体共用执行内核，业务差异通过插件声明和工作流配置实现。
4. 默认拒绝。 未明确授权的读取、工具调用、数据导出和写操作一律拒绝。
5. 执行可恢复。 任务具有持久化状态、检查点、幂等机制、失败处理和审计记录。
6. 先模拟、后接真系统。 在没有真实 ERP 的阶段，必须通过 Mock ERP 验证读写契约、审批、异常和恢复逻辑。

### 1.2 首期范围

V1.0 必须交付

组织与身份模型、RBAC/ABAC 权限引擎、Agent Harness、插件注册中心、本体注册中心、OWL/RDF/SHACL 校验、制度驱动的本体生成工作流、任务状态机、审计系统、标准 ERP Adapter、Mock ERP、Web 管理台。

V1.0 暂不交付

真实 ERP 写入、真实付款或过账、全自动合同签署、复杂跨企业协同、完全自动化的本体生产发布，以及生产级多租户 SaaS。

这里有一个重要取舍：虽然首期不接入真实 ERP，但接口契约不能设计成临时模拟接口。Mock ERP 必须实现未来正式 ERP Adapter 将遵守的同一套契约，否则后续接入时仍然需要重写执行流程。

## 二、总体技术架构

建议采用“模块化单体 + 可隔离插件执行器”的起步架构。平台内部先统一接口和事务边界，后续根据负载、团队分工与安全要求拆分服务。

### Web 管理台与用户工作台

React + TypeScript · 任务中心 · 本体工作台 · 插件管理 · 组织权限 · 审批中心

### API Gateway / Application API

身份认证 · 请求校验 · 版本控制 · 限流 · 请求关联 ID

### Agent Runtime

Harness、Planner、Context Builder、Execution Loop、Checkpoint

### Governance Runtime

授权决策、策略管理、审批、审计、风险等级

### Ontology Runtime

OWL/RDF、SHACL、版本解析、映射、验证

### Plugin Runtime

Agent、Tool、Policy、Model Provider 插件

### Integration Boundary

统一 ERP Port · Adapter Registry · Mock ERP · 事件与回执 · 幂等和重试

### 基础设施

PostgreSQL · 对象存储 · RDF/SHACL 引擎 · 可选消息队列 · 密钥管理 · 日志与监控

### 2.1 技术栈建议

| 层次     | 建议技术                              | 主要职责                     |
| ------ | --------------------------------- | ------------------------ |
| 前端     | React + TypeScript                | 管理台、工作台、审批和本体可视化         |
| 应用服务   | Go                                | API、Harness、权限、注册中心、集成接口 |
| 高性能组件  | Rust，按需                           | 大规模数据转换、性能敏感的校验或计算       |
| 元数据与状态 | PostgreSQL                        | 注册信息、任务、授权、审批、审计索引       |
| 本体校验   | RDF/OWL/SHACL 兼容引擎                | 语义加载、约束验证和报告             |
| 文档与制品  | S3 兼容对象存储或本地对象存储                  | 制度文件、插件包、发布制品            |
| 模型接入   | Model Provider 接口                 | 私有化模型、企业授权模型和模型路由        |
| 部署     | Docker Compose 起步，后续可选 Kubernetes | 私有化安装、升级、备份与恢复           |

本体引擎应封装在统一接口后面，不让业务智能体直接依赖某个具体的 RDF 库。选定具体 Go/Rust 实现前，需要通过 OWL 语义支持、SHACL 覆盖率、性能和维护状态做验证。

## 三、模块划分与接口契约

建议将平台划分为 17 个核心模块。模块之间通过明确的接口通信，避免业务代码直接访问其他模块的数据库表。

| 编号  | 模块                                 | 核心职责                          |

| M02 | Authorization Engine               | RBAC、ABAC、策略判定、工具授权           |
| M03 | Agent Registry                     | 智能体元数据、版本、依赖、发布状态             |

| M06 | Ontology Runtime                   | RDF 加载、OWL 语义处理、SHACL 验证      |
| M07 | Harness Runtime                    | 上下文组装、执行循环、检查点、恢复             |
| M08 | Tool Registry & Runtime            | 工具发现、Schema 验证、调用与隔离          |
| M09 | Workflow & Approval                | 工作流、人工审批、任务交接、职责分离            |
| M10 | ERP Integration                    | 统一 ERP 接口、适配器、Mock ERP、回执     |

首期采用模块化单体时，这些模块可以编译在一个 Go 应用中，但应分别定义接口和包边界。具有不可信代码执行能力的插件必须单独隔离，不能因为采用模块化单体就允许插件任意访问宿主进程。

### 3.2 推荐的内部接口

以下接口采用 Go 风格的伪代码表达，重点是定义职责，不意味着所有接口必须直接照搬。

```
type AgentRegistry interface {
    GetVersion(ctx Context, agentID, version string) (AgentSpec, error)
    Resolve(ctx Context, capability string, ontologyIDs []string) ([]AgentSpec, error)
}

type OntologyRegistry interface {
    GetPackage(ctx Context, ontologyID, version string) (OntologyPackage, error)
    ResolveImports(ctx Context, ontologyID, version string) ([]OntologyPackage, error)
    Publish(ctx Context, packageID, approvalID string) error
}

type AuthorizationService interface {
    Authorize(ctx Context, req AuthorizationRequest) (Decision, error)
}

type OntologyValidator interface {
    Validate(ctx Context, req ValidationRequest) (ValidationReport, error)
}

type Harness interface {
    Start(ctx Context, req RunRequest) (Run, error)
    Resume(ctx Context, runID string) (Run, error)
    Cancel(ctx Context, runID string) error
}

type ToolRuntime interface {
    Invoke(ctx Context, req ToolInvocation) (ToolResult, error)
}

type ERPPort interface {
    GetObject(ctx Context, req GetObjectRequest) (ERPObject, error)
    SearchObjects(ctx Context, req SearchObjectsRequest) (ERPObjectPage, error)
    ValidateOperation(ctx Context, req ValidateOperationRequest) (ERPValidation, error)
    SubmitOperation(ctx Context, req SubmitOperationRequest) (ERPReceipt, error)
    GetOperationStatus(ctx Context, operationID string) (ERPReceipt, error)
}
```

这里的 `Context` 是平台自定义的请求上下文，不应直接将可修改的用户身份字段作为可信授权依据。身份主体必须来自已验证的认证凭据；调用链中的 Agent ID、租户 ID 和任务 ID 也应由服务端绑定。

### 3.3 API 版本规范

对外 API 建议统一采用 `/api/v1` 前缀，JSON 作为默认数据交换格式。

GET

读取与查询

`/api/v1/agents`、`/api/v1/ontologies`、`/api/v1/runs/{run_id}`

POST

创建与执行

`/api/v1/runs`、`/api/v1/ontologies/{id}/validate`、`/api/v1/approvals/{id}/decision`

管理 API

发布与授权变更

`/api/v1/agents/{id}/publish`、`/api/v1/ontologies/{id}/publish`、`/api/v1/policies`

所有请求都应返回统一错误结构，并带有 `request_id`：

```
{
  "error": {
    "code": "ONTOLOGY_VALIDATION_FAILED",
    "message": "本体校验未通过",
    "details": {
      "report_id": "vr_123"
    }
  },
  "request_id": "req_456"
}
```

生产环境中，`message` 和 `details` 必须经过脱敏，不能向普通用户泄露内部提示词、密钥、受限数据或其他租户信息。

### 3.4 首期关键 API

| API                                     | 功能        | 关键校验                |
| --------------------------------------- | --------- | ------------------- |
| `POST /api/v1/runs`                     | 创建智能体任务   | Agent 发布状态、权限、本体兼容性 |
| `GET /api/v1/runs/{id}`                 | 查询任务状态    | 任务可见范围              |
| `POST /api/v1/runs/{id}/cancel`         | 取消任务      | 所有权、取消权限、当前状态       |
| `POST /api/v1/ontologies/{id}/validate` | 验证本体包     | 包完整性、格式、导入依赖        |
| `POST /api/v1/ontologies/{id}/publish`  | 发布本体      | 审核、验证、版本与发布权限       |
| `POST /api/v1/approvals/{id}/decision`  | 审批任务      | 审批人身份、职责分离、任务版本     |
| `GET /api/v1/audit-events`              | 查询审计事件    | 审计读取权限、数据范围         |
| `GET /api/v1/erp/capabilities`          | 查看 ERP 能力 | 适配器状态与能力授权          |

首期不接真实 ERP，因此 `/api/v1/erp/capabilities` 只返回 Mock ERP 所支持的能力。接口可以先稳定下来，但不能虚构真实 ERP 的可用功能。

## 四、核心数据模型与存储设计

核心数据模型分成五组：身份与组织、智能体与插件、本体与规则、任务与审批、ERP 集成与审计。

### 4.1 统一的基础字段

所有核心实体建议包含以下字段：

```
id
tenant_id
created_at
created_by
updated_at
updated_by
version
status
```

其中：

- `tenant_id` 用于隔离企业数据；即使首期只部署一家企业，也应保留该字段。
- `version` 用于乐观并发控制或记录业务版本，具体机制由实体类型决定。
- `created_by`、`updated_by` 保存稳定的主体 ID，不使用可变的显示名称作为主键。
- 审计事件与发布制品需要更强的不可变性设计，不能仅依赖普通实体的 `updated_at`。

### 4.2 身份与组织模型

核心实体：

```
Tenant
  └── LegalEntity
        └── OrganizationUnit

User ── Membership ── OrganizationUnit
User ── RoleBinding ── Role
Role ── RolePermission ── Permission
```

建议的数据表：

| 表                    | 关键字段                                                      |
| -------------------- | --------------------------------------------------------- |
| `tenants`            | `id`, `name`, `status`                                    |
| `legal_entities`     | `id`, `tenant_id`, `code`, `name`                         |
| `organization_units` | `id`, `tenant_id`, `parent_id`, `unit_type`               |
| `users`              | `id`, `tenant_id`, `subject_id`, `status`                 |
| `memberships`        | `user_id`, `organization_id`, `valid_from`, `valid_until` |
| `roles`              | `id`, `tenant_id`, `role_code`, `scope_type`              |
| `role_bindings`      | `principal_id`, `role_id`, `scope_ref`, `expires_at`      |
| `permissions`        | `resource_type`, `action`, `risk_level`                   |

用户与部门的关系通过 `memberships` 维护，而不是直接在 `users` 表中设置唯一的 `department_id`。这样可以支持兼职、跨部门项目和临时授权。

### 4.3 Agent 与插件模型

建议区分逻辑身份和不可变版本。

```
Agent
 ├── AgentVersion
 │     ├── OntologyDependency
 │     ├── ToolDependency
 │     ├── PolicyDependency
 │     └── WorkflowDefinition
 └── AgentRelease
```

| 表                             | 关键字段                                                       |
| ----------------------------- | ---------------------------------------------------------- |
| `agents`                      | `id`, `tenant_id`, `agent_code`, `category`                |
| `agent_versions`              | `agent_id`, `version`, `manifest_hash`, `artifact_uri`     |
| `agent_ontology_dependencies` | `agent_version_id`, `ontology_id`, `version_range`         |
| `agent_tool_dependencies`     | `agent_version_id`, `tool_id`, `tool_version`              |
| `agent_releases`              | `agent_version_id`, `environment`, `released_at`, `status` |

发布后的 Agent 版本应视为不可变制品。修改 Prompt、工具权限、依赖本体或工作流，都应形成新的版本或明确的新发布记录。

### 4.4 本体模型

本体管理必须支持“包—版本—内容—依赖—验证—发布”的完整生命周期。

| 表或对象                    | 关键字段                                                   |
| ----------------------- | ------------------------------------------------------ |
| `ontology_packages`     | `id`, `domain`, `ontology_type`, `owner_org`           |
| `ontology_versions`     | `package_id`, `version`, `status`, `content_hash`      |
| `ontology_artifacts`    | `version_id`, `artifact_type`, `storage_uri`           |
| `ontology_imports`      | `source_version_id`, `target_version_id`               |
| `ontology_validations`  | `version_id`, `engine_version`, `report_uri`, `result` |
| `ontology_publications` | `version_id`, `environment`, `approval_id`             |
| `ontology_evidence`     | `version_id`, `document_id`, `locator`, `claim_id`     |

`artifact_type` 可包括 `OWL`、`RDF`、`SHACL`、`MAPPING`、`RULES` 和 `TESTS`。

RDF 三元组内容可以保存在专门的 RDF 存储中，也可以按包存储为版本化文件。首期更推荐不可变本体制品 + 元数据数据库 + 独立验证引擎的组合，先降低运行复杂度。


### 4.5 任务运行与审批模型

建议至少设计以下表：

| 表                                 | 作用                     |
| --------------------------------- | ---------------------- |
| `runtime.agent_runs`              | 一次智能体任务的总体状态           |
| `runtime.run_steps`               | 规划、执行、验证等步骤            |
| `runtime.tool_calls`              | 每次工具调用的参数摘要、状态和回执      |
| `runtime.checkpoints`             | 可恢复的任务检查点              |
| `runtime.authorization_decisions` | 授权决策持久化（tool_calls 引用） |
| `workflow.approvals`              | 待人工决策的操作               |
| `workflow.approval_actions`       | 审批人、决策、理由和任务版本         |
| `integration.erp_operations`      | ERP 操作请求及幂等状态          |
| `integration.erp_receipts`        | ERP 返回的正式结果            |
| `audit.audit_events`              | 不可随意修改的审计事件            |
| `audit.evidence_records`          | 制度条款、数据来源和校验依据         |

（权威 DDL 以第二篇为准；本表为逻辑索引。状态词表以 `docs/contracts/01-全局状态注册表.md` 为准，错误码以 `docs/contracts/02-统一错误码注册表.md` 为准，API 路径以 `docs/contracts/03-API命名与契约规范.md` 为准。）

对于 `tool_calls`，敏感参数不能直接完整落库。应采用字段级脱敏、最小必要记录和受控证据引用；需要保留原始输入时，使用受限存储和独立访问策略。

### 4.6 任务与业务状态必须分离

例如：

```
Agent Run:
    COMPLETED

ERP Operation:
    UNKNOWN
```

这种组合完全可能出现：智能体完成了请求发送，但 ERP 响应超时，尚不能确认是否提交成功。

因此，平台不得仅凭 `agent_runs.status = COMPLETED` 就显示“ERP 业务已成功”。必须通过正式回执、状态查询或对账流程确认。

## 五、权限检查引擎的详细设计

权限系统应成为独立的服务端安全边界。Agent、Harness、Tool Runtime、Ontology Runtime 和 ERP Adapter 都必须遵守同一套授权协议，不能各自实现一套互不一致的权限判断。

### 5.1 权限判定模型

每次操作都构造一个标准化的 `AuthorizationRequest`。

```
{
  "subject": {
    "user_id": "user_001",
    "tenant_id": "tenant_001",
    "roles": ["finance_operator"]
  },
  "action": "erp.expense.submit",
  "resource": {
    "type": "ExpenseClaim",
    "id": "expense_001",
    "organization_id": "org_finance"
  },
  "context": {
    "agent_id": "expense_agent",
    "run_id": "run_001",
    "amount": 3200,
    "currency": "CNY",
    "environment": "production"
  }
}
```

这里的 JSON 仅用于说明字段结构。实际系统中，`roles`、`tenant_id` 和资源属性不能无条件信任客户端传入的内容，必须从可信身份、服务端授权数据和受控资源查询中构建。

### 5.2 权限检查链路

### 1. 身份认证

验证登录凭证、会话有效性和用户状态。

### 2. 租户隔离

确认请求主体、资源和服务端上下文属于同一授权边界。

### 3. 角色与属性判断

检查角色、部门、法人主体、数据范围、金额和资源状态。

### 4. 业务策略判断

检查审批条件、职责分离、时间窗口及业务前置条件。

### 5. Agent 与 Tool 双重约束

检查智能体版本声明的能力，并在工具执行前重新鉴权。

### 6. 形成授权决策

返回 ALLOW、DENY 或 REQUIRE_APPROVAL，并记录策略版本和原因。

### 5.3 授权决策协议

建议将授权结果定义为：

```
type Decision string

const (
    Allow           Decision = "ALLOW"
    Deny            Decision = "DENY"
    RequireApproval Decision = "REQUIRE_APPROVAL"
)

type AuthorizationResult struct {
    Decision       Decision
    ReasonCode     string
    PolicyVersions []string
    Obligations    []string
    ApprovalPolicy string
    DecisionID     string
}
```

`REQUIRE_APPROVAL` 不等于执行授权。它意味着系统可以创建审批任务，但在审批完成之前不得执行受保护的写操作。

`Obligations` 可以表达附加条件，例如“字段脱敏”“限制结果条数”“仅允许只读操作”。如果附加条件无法被执行环境可靠实施，则不能把它当作已满足条件。

### 5.4 自动执行与人工审批的决策规则

| 操作             | 默认策略       | 说明                |
| -------------- | ---------- | ----------------- |
| 查询授权范围内的普通数据   | 可自动执行      | 每次调用仍需鉴权          |
| 查询敏感财务或人事数据    | 条件授权       | 字段和行级权限检查         |
| 创建业务草稿         | 可自动执行      | 校验输入与操作权限         |
| 提交一般业务申请       | 按授权策略执行    | 可根据金额、组织和业务类型设置阈值 |
| 发布生产本体或策略      | 人工审核       | 版本验证与发布权限分离       |
| 审批自身提交的业务      | 默认禁止       | 按职责分离策略处理         |
| 付款、过账、签署等高风险操作 | 人工审批       | 必须检查业务前置条件和授权链    |
| 删除审计记录、修改历史审计  | 禁止普通管理角色执行 | 采用独立保留与受控运维机制     |

以上是平台默认策略，不代表所有企业必须采用完全相同的金额阈值。企业可以配置差异化策略，但不能通过简单修改 Agent Prompt 绕过这些控制。

### 5.5 审批授权必须绑定具体操作

审批任务应绑定：

- 操作类型与目标资源。
- 经过验证的操作参数摘要或规范化 Payload Hash。
- 操作者和执行 Agent。
- 目标租户与组织范围。
- 本体版本、规则版本和策略版本。
- 有效期、审批人及职责分离条件。

如果审批后操作金额、收款对象、合同版本或关键参数发生变化，应使原审批失效并重新审批。

安全底线： 不允许将“用户批准了整个任务”解释为“该任务之后的所有工具调用都已获得授权”。

## 六、插件协议与生命周期

插件系统需要解决三个问题：如何声明能力、如何验证兼容性、如何安全运行。

建议采用统一的 Manifest、JSON Schema、版本化接口和运行时权限契约。

### 6.1 统一插件 Manifest

所有插件使用统一的外层清单，但不同插件类型可以拥有各自的扩展字段。

下面是一个费用报销 Agent 的示意性清单：

```
apiVersion: odap/v1
kind: AgentPlugin

metadata:
  id: expense-agent
  version: 1.0.0
  displayName: 费用报销智能体
  category: business
  domain: finance

spec:
  runtime:
    type: wasi
    entrypoint: /plugin/expense-agent.wasm

  dependencies:
    ontologies:
      - id: finance.expense
        version: "1.0.0"
      - id: organization.employee
        version: "1.0.0"

    tools:
      - id: erp.expense.read
        version: "1.0.0"
      - id: erp.expense.create_draft
        version: "1.0.0"

  permissions:
    requested:
      - resource: expense_claim
        actions: [read, create_draft]

  execution:
    timeoutSeconds: 120
    maxToolCalls: 20
    requiresHumanApprovalFor:
      - submit
      - payment

  schemas:
    input: schemas/input.json
    output: schemas/output.json

  audit:
    evidenceRequired: true
```

这里采用 WASI 作为一种可选的隔离运行方式。实际 Go 插件可以通过独立进程、受限容器或 RPC 执行，不应强迫所有语言使用同一种运行时。对于首期内置、可信的 Go 模块，可以使用进程内接口，但外部第三方插件应默认使用隔离执行。

Manifest 中的权限是插件申请的能力范围，不是已经授予的权限。实际授权由管理员配置和运行时策略决定。

### 6.2 五种核心插件协议

| 插件类型                  | 输入                    | 输出              | 主要约束                |
| --------------------- | --------------------- | --------------- | ------------------- |
| Agent Plugin          | 用户任务、上下文引用、能力列表       | 计划、工具请求、最终结果    | 不直接执行未经授权的工具        |
| Ontology Plugin       | RDF/OWL/SHACL 制品、依赖版本 | 本体元数据、验证结果、查询能力 | 制品校验、依赖固定、语义兼容      |
| Tool Plugin           | 结构化参数、授权上下文           | 结构化结果、错误、证据引用   | 每次调用鉴权、限时、幂等        |
| Policy Plugin         | 主体、动作、资源和环境属性         | 授权决策与附加条件       | 默认拒绝、可审计、确定性优先      |
| Model Provider Plugin | 推理请求、数据分级标签、预算上下文     | 模型输出、用量计量、降级决策  | 不持有密钥、按数据政策路由、预算内调用 |

五种类型的权威定义、Manifest 结构与生命周期以第四篇为准；第一篇 §8.3 的插件类型清单、总书本节与第四篇必须保持一致（五类，含 `model_provider`）。

### 6.3 Agent 与 Harness 的消息协议

建议所有 Agent 输出都采用受约束的结构化消息，而不是直接把自然语言文本当成执行指令。

```
{
  "protocol_version": "1.0",
  "run_id": "run_001",
  "agent_id": "expense-agent",
  "message_type": "tool_request",
  "sequence": 4,
  "payload": {
    "tool_id": "erp.expense.create_draft",
    "arguments": {
      "employee_id": "emp_001",
      "currency": "CNY"
    },
    "requires_validation": true
  }
}
```

Harness 收到消息后必须依次执行：

1. 校验消息 Schema 和版本。
2. 验证任务状态和 Agent 身份。
3. 校验工具是否已注册且版本兼容。
4. 从服务端加载授权上下文。
5. 执行权限检查。
6. 校验业务参数与本体约束。
7. 根据风险等级决定直接执行、请求审批或拒绝。
8. 记录工具调用与执行结果。
9. 将结构化结果返回给 Agent。

不能让模型通过伪造 `authorized: true`、`approved: true` 等参数来决定自身权限。

### 6.4 工具接口协议

```
{
  "tool_id": "erp.expense.create_draft",
  "version": "1.0.0",
  "input_schema": {
    "type": "object",
    "required": ["employee_id", "currency"],
    "properties": {
      "employee_id": {"type": "string"},
      "currency": {"type": "string", "minLength": 3, "maxLength": 3}
    },
    "additionalProperties": false
  },
  "risk_level": "L1",
  "idempotency_required": true
}
```

`additionalProperties: false` 可以阻止未经定义的字段被静默接受，但应根据接口兼容策略审慎设置。

每个 Tool Plugin 还应声明：

- 权限要求和资源类型。
- 是否只读、是否有副作用。
- 是否支持幂等与取消。
- 超时、重试和并发限制。
- 是否需要人工审批。
- 输入输出中的敏感字段。
- 错误码及可恢复性。
- 结果是否必须提供证据或业务回执。

## 七、Agent Harness 执行状态机

建议把 Harness 设计为平台级执行引擎，负责从用户请求一直推进到任务完成、人工审批、失败或恢复。

这里需要区分两个状态机：

- 任务状态机：描述整个 Agent Run 的生命周期。
- 操作状态机：描述每一次具有副作用的 Tool Call 或 ERP Operation 的生命周期。

二者不能合并。一个智能体任务可能包含十次工具调用，其中一次等待审批、另一次提交失败，而前面的只读步骤已经成功。

### 7.1 任务状态定义

| 状态                 | 含义          | 允许的后续操作      |
| ------------------ | ----------- | ------------ |
| `CREATED`          | 任务已创建       | 解析上下文、取消     |
| `CONTEXT_READY`    | 上下文已构建      | 开始规划         |
| `PLANNING`         | 生成执行计划      | 进入校验、失败      |
| `VALIDATING`       | 校验权限、依赖与计划  | 执行、等待补充、失败   |
| `RUNNING`          | 执行计划步骤      | 继续、暂停、审批、失败  |
| `WAITING_APPROVAL` | 存在待审批操作     | 批准、拒绝、过期     |
| `PAUSED`           | 主动暂停或等待外部条件 | 恢复、取消        |
| `RECOVERING`       | 检查点恢复与状态核对  | 继续、失败        |
| `COMPLETED`        | 所有要求的步骤已完成  | 只读查询、归档      |
| `FAILED`           | 任务不可继续      | 诊断、按策略重新发起   |
| `CANCELLED`        | 任务已取消       | 只读查询         |
| `EXPIRED`          | 任务超过有效期     | 只读查询、按策略重新发起 |

`COMPLETED` 只表示任务满足其完成条件。若任务要求写入 ERP，则必须将 ERP 回执确认作为任务完成条件之一。

### 7.3 单次工具调用状态机

工具调用应独立记录状态：

```
PENDING
   ↓
VALIDATING
   ├──→ REJECTED
   ├──→ WAITING_APPROVAL
   └──→ READY
           ↓
        DISPATCHED
           ↓
        EXECUTING
           ├──→ SUCCEEDED
           ├──→ FAILED
           └──→ UNKNOWN
                    ↓
                RECONCILING
                    ├──→ SUCCEEDED
                    ├──→ FAILED
                    └──→ MANUAL_REVIEW
```

其中 `UNKNOWN` 尤其重要：网络超时不代表远端执行失败。

假设平台向 ERP 提交一笔报销后连接中断。此时不应盲目重发，而应先使用原幂等键查询执行结果，确认操作是否已生效。

### 7.4 Harness 的一次完整运行

建议固定为以下执行循环：

1. 接收任务：校验用户身份、请求格式、租户和请求幂等键。
2. 解析意图：确定任务目标和候选业务域。
3. 解析依赖：加载兼容的 Agent、Ontology、Tool 和 Policy 版本。
4. 构建上下文：注入必要的制度证据、业务对象、历史状态与工具说明。
5. 生成计划：输出结构化步骤、依赖、预期结果和风险等级。
6. 预检：检查工具可用性、权限、业务规则与本体约束。
7. 执行步骤：由 Harness 调用受控工具，而不是让 Agent 直接访问底层系统。
8. 验证结果：对工具输出做 Schema 校验、业务验证和回执检查。
9. 持久化检查点：保存状态转移、已完成步骤和待执行操作。
10. 完成或交接：返回结果、等待审批、暂停或进入恢复流程。

### 7.5 检查点设计

每个检查点建议保存：

```
run_id
checkpoint_id
sequence
run_status
completed_step_ids
pending_step_ids
agent_version
ontology_versions
policy_versions
tool_call_refs
evidence_refs
state_hash
created_at
```

不建议把完整对话、所有 ERP 数据和全部模型上下文无差别地塞进检查点。应保存最小必要状态与可追溯引用；恢复时重新获取敏感业务数据并重新检查权限。

对于待审批操作，还必须保存操作参数摘要和授权依据。恢复后如相关本体、策略、用户权限或目标资源状态发生变化，应重新验证，必要时要求重新审批。

## 八、标准 ERP 接口层与 Mock ERP

虽然首期不接真实 ERP，但这一层应在第一阶段就建立。

### 8.1 ERP Port 与 Adapter 的边界

```
Agent
  ↓
Harness
  ↓
Tool Runtime
  ↓
ERP Port（平台统一接口）
  ↓
Adapter Registry
  ├── Mock ERP Adapter
  ├── SAP Adapter（未来）
  ├── Oracle Adapter（未来）
  └── 其他 ERP Adapter（未来）
```

业务智能体只能依赖 ERP Port，不允许直接依赖具体 ERP 厂商的 SDK、数据库表或专有 API。

### 8.2 标准对象模型

建议为平台定义统一的 ERP 对象信封：

```
{
  "object_type": "ExpenseClaim",
  "external_id": "ERP-EXP-000123",
  "tenant_id": "tenant_001",
  "legal_entity_id": "entity_001",
  "version": "7",
  "status": "PENDING_APPROVAL",
  "data": {
    "currency": "CNY",
    "amount": 3200
  },
  "source": {
    "adapter_id": "mock-erp",
    "observed_at": "2026-10-12T10:00:00Z"
  }
}
```

`version` 是示例中的对象版本，不保证所有 ERP 都使用数字递增版本。正式 Adapter 必须将厂商的版本、ETag 或其他并发控制标识映射到平台统一契约。

### 8.3 标准提交请求

```
{
  "operation_id": "op_001",
  "idempotency_key": "idem_001",
  "action": "expense.submit",
  "target": {
    "object_type": "ExpenseClaim",
    "external_id": "ERP-EXP-000123"
  },
  "expected_version": "7",
  "payload": {
    "submit_comment": "出差费用报销"
  },
  "correlation_id": "run_001"
}
```

标准 Adapter 应当：

- 校验参数与目标对象。
- 根据 ERP 能力映射操作。
- 使用原系统支持的幂等机制，或实现受控的操作去重记录。
- 使用乐观并发控制或 ERP 提供的版本校验能力。
- 返回规范化回执与原始错误码的安全摘要。
- 明确区分成功、失败和结果未知。

平台不能凭空保证所有 ERP 都原生支持幂等键。对于不支持的系统，需要由 Adapter 实现去重账本和结果查询；如果仍无法确定操作结果，则必须进入人工核查。

### 8.4 Mock ERP 必须模拟的场景

首期 Mock ERP 不应只是一个返回固定 JSON 的假服务。至少要支持：

1. 员工、供应商、合同、报销单等测试对象。
2. 查询、过滤、分页和版本读取。
3. 创建草稿、提交申请、查询业务状态。
4. 参数校验失败和业务规则拒绝。
5. 幂等键重复提交。
6. 版本冲突和并发更新。
7. 请求超时、服务不可用与未知结果。
8. 审批通过、拒绝、过期与重复审批。
9. 数据范围与租户隔离测试。
10. 回执查询、审计关联和故障恢复。

Mock 环境必须有明确标识，前端也要显示“模拟环境”，避免测试人员误以为操作已经进入真实企业系统。

## 九、本体工程流水线与 OWL/RDF/SHACL 运行时

本体工厂是平台区别于普通企业 Agent 平台的关键能力。首期不仅要能保存本体文件，还要具备可重复的验证、审核、发布和依赖管理流程。

### 9.1 本体制品包规范

建议每个本体包采用固定目录结构：

```
finance-expense/
├── manifest.yaml
├── ontology/
│   ├── core.ttl
│   ├── expense.ttl
│   └── employee-imports.ttl
├── shapes/
│   ├── expense-shapes.ttl
│   └── travel-shapes.ttl
├── mappings/
│   └── erp-field-mapping.yaml
├── rules/
│   └── expense-policy.yaml
├── evidence/
│   └── source-index.json
└── tests/
    ├── valid-cases/
    └── invalid-cases/
```

其中 `manifest.yaml` 声明包标识、版本、导入依赖、语义文件、SHACL 文件、映射文件、验证引擎兼容范围及发布策略。

### 9.2 本体发布流水线

### 导入与解包

检查制品大小、文件类型、目录结构和内容哈希。

### 安全检查

禁止任意外部网络导入、路径穿越和未经批准的可执行内容。

### 语法与依赖检查

解析 RDF，验证命名空间、OWL/RDF 格式和导入依赖。

### 语义与约束验证

运行所选 OWL 推理能力、SHACL Shapes 和跨文件一致性检查。

### 回归测试

运行正例、反例、历史用例和版本差异测试。

### 审核与发布

展示制度依据、差异报告、依赖清单和测试结果，批准后生成不可变发布制品。

### 9.3 OWL 推理与 SHACL 验证必须分开

建议将验证结果分为不同维度：

- 语法有效性：文件是否可解析。
- 语义一致性：在指定推理器和语义配置下，是否存在不一致。
- 数据形状有效性：数据是否满足 SHACL 约束。
- 业务规则有效性：是否满足企业特定规则。
- 来源完整性：关键概念和约束是否具备制度依据。
- 兼容性：依赖本体、Agent 和 ERP 字段映射是否兼容。

这些维度不能简单地合并成一个“本体正确率”。例如，SHACL 校验通过并不意味着本体的数学语义正确，也不意味着业务制度本身合理。

### 9.4 本体变更与兼容性

建议采用语义版本策略：

- PATCH：不改变已发布契约的修复。
- MINOR：新增向后兼容的概念或可选属性。
- MAJOR：删除、重命名、改变关键语义或引入不兼容约束。

这只是建议的版本约定。自动判断语义兼容性并不总是可靠，因此发布流程必须结合自动差异分析和人工审核。

当某个 Agent 依赖 `finance.expense@1.2.0` 时，运行任务必须锁定实际使用的本体版本。不能让运行中的任务在执行到一半时悄悄切换到新版本。

## 十、制度驱动的本体生成工程

### 10.1 本体设计智能体的子任务

可以在同一个 Harness 下配置多个逻辑角色：

| 角色       | 输出                 |
| -------- | ------------------ |
| 制度解析器    | 制度条款、主体、条件、义务和例外   |
| 概念建模器    | 候选类、属性、关系和层级       |
| 约束生成器    | SHACL Shapes 与规则候选 |
| ERP 映射助手 | 本体字段与 ERP 对象字段映射建议 |
| 冲突分析器    | 与现有本体、制度版本的冲突列表    |
| 测试生成器    | 正例、反例、边界值和回归测试     |
| 审核助手     | 差异摘要、证据引用、风险等级     |

这些角色可以复用同一个模型，也可以使用不同的模型或确定性工具。重点在于输入输出契约清晰，而不是一定要部署七个独立的大模型 Agent。

### 10.2 制度条款的中间表示

不要让制度解析结果直接转成 OWL 文件。建议先建立一个结构化的中间表示（Policy IR）：

```
{
  "rule_id": "travel.expense.limit.001",
  "source": {
    "document_id": "doc_travel_policy",
    "document_version": "3.0",
    "section": "4.2"
  },
  "subject": "Employee",
  "action": "SubmitExpense",
  "condition": {
    "field": "expense.amount",
    "operator": "greater_than",
    "reference": "travel_policy.limit"
  },
  "effect": "RequireAdditionalApproval",
  "confidence": 0.96,
  "review_status": "pending"
}
```

这里的 `confidence` 是模型的抽取置信度，不是规则正确性的证明。生产发布还需要制度来源核验、字段映射验证、规则测试和审核。

### 10.3 制度版本变化后的影响分析

当制度文件更新时，平台应建立依赖图：

```
制度文档版本
  ↓
制度条款与 Policy IR
  ↓
本体类 / 属性 / SHACL 约束 / 业务规则
  ↓
专业 Agent 与 Workflow
  ↓
ERP 字段映射 / 测试用例
```

系统据此生成变更影响报告，列出需要重新验证的对象。

例如，报销限额调整可能只影响一条业务规则，也可能影响 SHACL 约束、审批策略、报销智能体和回归测试。系统应根据依赖关系定位变更，而不是重新生成全部本体。

## 十一、企业私有化部署与安全基线

### 11.1 首期部署拓扑

建议采用单企业私有化部署，服务和数据均在企业控制的基础设施内。

```
企业用户
   ↓ HTTPS
反向代理 / API Gateway
   ↓
ODAP Application
   ├── Identity & Authorization
   ├── Agent Harness
   ├── Ontology Runtime
   ├── Plugin Registry
   ├── Approval & Audit
   └── ERP Adapter
          └── Mock ERP
   ↓
PostgreSQL / 对象存储 / RDF 存储
```

首期可以部署在单台开发服务器或企业内网测试环境；生产环境再根据可用性要求增加数据库高可用、应用副本和备份恢复能力。

### 11.2 安全要求

| 安全领域 | 最低要求                        |
| ---- | --------------------------- |
| 身份   | 支持企业 SSO/OIDC 或可替换的身份提供方接口  |
| 传输   | TLS，内部服务按风险设置认证             |
| 密钥   | 使用专门的密钥管理机制，不把密钥写进插件清单      |
| 插件隔离 | 不可信插件使用独立进程或容器，限制文件、网络和系统调用 |
| 数据访问 | 默认拒绝，租户、组织、行级和字段级策略按需执行     |
| 提示注入 | 将制度文档、合同和外部内容视为不可信输入        |
| 审计   | 关键操作记录身份、策略版本、资源、结果和关联 ID   |
| 备份   | 数据库、本体制品、策略和密钥配置分别备份        |
| 供应链  | 制品哈希、依赖锁定、来源记录和发布审核         |
| 恢复   | 支持任务恢复、操作对账、故障演练和版本回滚       |

企业制度文档可能包含恶意提示或诱导内容。本体设计智能体只能把这些文本当作待解析资料，不能将文档中的“忽略系统规则”“调用某工具”等语句当成平台指令。

### 11.3 模型服务的私有化边界

企业私有化部署不一定意味着所有模型都必须在本地运行，但应由企业明确数据出域政策。

建议支持两种模式：

- 完全本地模式：模型、文档、向量检索与业务数据全部在企业内网。
- 受控外部模型模式：通过模型网关调用外部服务，对可发送字段、脱敏、留存和日志进行策略控制。

对于财务、人事、合同等敏感数据，默认不向未经批准的外部模型发送原始内容。模型供应商的调用记录、保留政策和数据使用条款应纳入企业的安全审查。

## 十三、测试体系与上线验收

建议从第一天就建设自动化测试，而不是等业务模块开发完成后再集中补测试。

### 13.1 测试分层

L1 · 单元测试

授权规则、状态转移、版本解析、Schema 校验、幂等键、错误映射。

L2 · 契约测试

Agent、Tool、Ontology、ERP Adapter 的接口输入输出是否符合协议。

L3 · 集成测试

Harness、权限、SHACL、审批、Mock ERP 和审计之间的端到端交互。

L4 · 故障恢复测试

工作进程崩溃、数据库断连、ERP 超时、重复事件、未知结果、任务恢复。

L5 · 安全与对抗测试

越权调用、提示注入、恶意插件、跨租户读取、敏感字段泄露、审批参数篡改。

### 13.2 必须通过的关键场景

建议至少建立以下端到端测试：

1. 无权限员工尝试调用合同 Agent，系统拒绝。
2. 有读取权限、没有提交权限的员工可以查询，但不能提交。
3. Agent 申请的工具权限超出管理员授权范围，运行时拒绝。
4. SHACL 校验失败的业务对象不能进入受保护的提交操作。
5. 待审批操作的关键参数被修改，原审批不能复用。
6. 同一幂等键重复提交，不产生重复业务操作。
7. ERP 返回超时但实际已成功，恢复流程可以查明结果。
8. 运行中本体版本更新，任务仍按已锁定版本执行或被要求重新验证。
9. 部门变更或授权过期后，恢复任务重新检查权限。
10. 本体生成智能体输出不合法的 OWL/RDF/SHACL，不能发布生产版本。
11. 恶意文档要求模型忽略规则或调用工具，系统不执行文档中的越权指令。
12. 租户 A 的员工无法通过 ID 猜测、查询过滤或工具参数读取租户 B 的数据。

### 13.3 V1.0 验收建议

建议将以下指标作为首期工程目标，而非预先宣称已经达到的性能结果：

- 核心 API 和状态转移逻辑具备自动化测试。
- 所有高风险工具在执行前都经过服务端授权。
- 关键写操作的执行结果能够通过回执或核对流程确认。
- 本体发布必须具备验证报告、版本和审核记录。
- 关键操作的审计事件覆盖率达到 100%。
- 跨租户、跨组织、字段级权限的负向测试全部通过。
- 模拟 ERP 的重复提交和未知结果测试不产生未经核实的成功状态。
- 私有化部署具备可重复安装、备份与恢复说明。

对于模型生成质量、推理性能、复杂本体规模和高并发能力，应先通过代表性数据集做基准测试，再确定具体 SLA。不能在没有测试的情况下承诺固定吞吐量或生成准确率。

## 十五、我建议的实际开发顺序

虽然前面已经给出完整的阶段计划，但如果现在就准备开始编码，最合理的顺序不是先写本体生成 Agent，也不是先搭建一个漂亮的聊天界面。

建议依次完成：

1. 第一篇：工程架构与代码骨架。 确定 Go 模块边界、React 工程结构、配置、数据库迁移、日志、错误码和测试规范。
2. 第二篇：核心数据模型与数据库设计。 完成组织、权限、Agent、Ontology、Plugin、Run、Approval、Audit 的逻辑模型和 SQL 迁移。
3. 第三篇：身份认证与企业权限引擎。 先保证系统知道谁在操作、能访问哪些资源，以及为什么允许或拒绝。
4. 第四篇：插件协议与 Registry。 定义 Manifest、版本、依赖、发布、兼容性和运行时调用契约。
5. 第五篇：本体运行时与本体工厂。 实现 RDF/OWL/SHACL 处理、制度证据、本体版本和验证发布流程。
6. 第六篇：Agent Harness 与执行状态机。 完成 Context Builder、Tool Registry、执行循环、检查点、审批暂停和恢复。
7. 第七篇：标准 ERP Port 与 Mock ERP。 完成模拟查询、草稿、提交、回执、幂等和异常对账。
8. 第八篇：管理台与端到端验收。 将各模块串联成可操作、可审计的企业平台。

其中，身份和权限虽然可以与其他模块并行开发，但任何真实业务写操作都必须在授权与审计机制完成后才能接入。

最终目标不是做一个能够回答企业问题的聊天机器人，而是做一个能够理解企业业务语义、遵循企业制度、在权限边界内完成工作，并且能够证明自己做了什么的智能体运行平台。

这也是我建议你坚持“本体 + Harness + ERP 标准接口”这条路线的原因：未来更换模型、增加本体、扩展智能体或接入不同 ERP，都不应该要求重建整套业务系统。
