# 第一篇：工程架构与代码骨架详细设计

版本：V1.0 · 架构阶段：MVP 工程落地 · 部署方式：企业私有化部署

> **Scope 标签（本篇范围声明，对齐评审报告 §5 的 MVP 治理要求）**
> - `[MVP-V1.0]`：Go 模块化单体（server/worker/web 三进程）、PostgreSQL 元数据与任务状态、插件 Manifest 与注册表骨架、Harness 最小执行框架、Docker Compose 私有化部署（含 pluginruntime 与对象存储）。
> - `[V1.5]`：独立消息队列评估（吞吐/积压明确后）、插件容器 Runner 受控接入（第四篇 §8.1）、Rust 性能内核（压测证明有必要后）。
> - `[V2]`：Kubernetes 化部署、WASI 插件沙箱、分布式语义执行。

本篇承接总体设计，重点解决一个问题：如何把本体驱动的智能体平台，从架构设计转化为可以持续开发、测试、部署和扩展的工程项目。

平台暂定名称为 ODAP（Ontology-Driven Agent Platform）。名称仅用于工程设计，后续可以独立调整品牌。

核心设计思路是：以 Go 构建平台主服务和任务运行时，以 React + TypeScript 构建管理控制台，以 PostgreSQL 保存平台元数据和任务状态，以标准接口封装 OWL/RDF/SHACL 本体引擎、模型服务与 ERP 系统。Rust 暂不进入 MVP 主链路，待性能测试证明有必要时，再用于计算密集型模块。

平台不替代 ERP，而是在 ERP 上构建一层理解业务语义、执行业务流程、管理权限并能够追溯操作证据的智能体系统。

## 一、工程目标与边界

### 1.1 MVP 必须具备的能力

企业组织与权限

组织、部门、员工、角色、权限、数据范围、审批权限及租户隔离。

本体管理与验证

本体包注册、版本管理、OWL/RDF 解析、SHACL 约束验证、发布与回滚。

智能体与 Harness 运行时

智能体注册、插件加载、上下文构建、工具调用、状态持久化、故障恢复和执行审计。

授权与人工审批

每次敏感操作均经过策略判断；高风险操作进入审批流程，批准后才能执行。

标准 ERP 接口与模拟系统

先完成 ERP Port、Adapter 和 Mock ERP，不依赖某一家真实 ERP，即可端到端验证平台。

### 1.2 MVP 暂不实现的内容

- 不直接连接真实企业 ERP 生产环境。
- 不实际付款、记账、签约或执行其他生产级不可逆操作。
- 不允许模型绕过授权服务直接访问数据库或调用外部系统。
- 不允许模型生成的本体未经验证和发布流程直接投入运行。
- 不在第一阶段构建复杂微服务集群，也不强制引入 Kubernetes。

这些不是永久限制，而是为了先建立可验证、可恢复、可审计的工程底座。

### 1.3 工程设计原则

| 原则      | 工程要求                     |
| ------- | ------------------------ |
| 模块化单体优先 | 一个主服务、一个异步 Worker，模块边界清晰 |
| 契约先行    | API、插件协议、ERP 接口先定义，再实现   |
| 默认拒绝    | 没有明确授权的工具调用不得执行          |
| 状态持久化   | 关键执行状态不能只保存在内存           |
| 版本固定    | 每次任务绑定智能体、本体、策略和工具版本     |
| 失败可恢复   | 超时、重复请求、未知执行结果必须有处理机制    |
| 依赖可替换   | 模型、本体引擎、ERP 适配器均通过接口接入   |
| 全程留痕    | 关键决策、审批、工具调用和外部操作具有审计记录  |

## 二、总体工程架构

### 2.1 系统分层

### 表现层 · Web Console

React · TypeScript · Vite

组织权限 / 本体工作台 / 智能体管理 / 执行监控 / 审批中心

### 应用层 · Go API Server

REST API · 身份认证 · 业务服务 · 统一错误处理

模块化单体，统一依赖注入与事务边界

智能体运行时

Harness / Planner / Tool Runtime / Checkpoint

本体运行时

OWL / RDF / SHACL / 查询 / 语义映射

治理运行时

RBAC / ABAC / Policy / Approval / Audit

集成运行时

Plugin Registry / ERP Port / Model Provider

PostgreSQL

元数据 / 任务状态

本体存储

RDF / OWL / SHACL

外部系统

Mock ERP / 模型服务

这张图描述的是逻辑分层，不要求每个方框都独立部署。第一阶段的重点是模块边界独立、进程数量克制、接口标准化。

### 2.2 部署进程划分

建议从一开始划分两个 Go 进程，而不是把 HTTP 请求和长时间智能体执行全部塞进同一个执行循环。

| 进程         | 职责                            | 是否需要独立扩容        |
| ---------- | ----------------------------- | --------------- |
| `server`   | HTTP API、身份认证、任务创建、查询、审批、管理操作 | 需要时可横向扩容        |
| `worker`   | 执行 Harness、模型调用、工具调度、状态恢复     | 根据任务量独立扩容       |
| `web`      | 前端静态资源及开发服务                   | 可独立发布           |
| `postgres` | 事务、元数据、执行状态、审计索引              | 独立维护            |
| 本体引擎       | RDF 图管理、SHACL 验证、OWL 推理       | 初期可作为进程内或独立服务实现 |

异步任务可以先利用 PostgreSQL 实现可靠的任务领取、租约和重试，不必一开始就引入 Kafka、RabbitMQ 等消息中间件。等吞吐量、队列积压或多系统事件需求明确后，再评估独立消息队列。

### 2.3 一次业务请求的完整调用链

例如，员工要求智能体检查一张差旅报销单：

```
用户提交请求
    ↓
API 身份认证与租户识别
    ↓
创建 AgentRun 并固定相关版本
    ↓
Worker 领取任务
    ↓
加载员工权限、报销本体、企业制度
    ↓
Harness 构建受限上下文
    ↓
Agent 生成执行计划
    ↓
Ontology Runtime 验证业务对象
    ↓
Authorization Engine 检查操作权限
    ↓
Tool Runtime 调用只读工具或提交审批
    ↓
必要时等待人工审批
    ↓
ERP Port → Mock ERP
    ↓
记录外部操作回执、证据和审计日志
    ↓
任务完成并返回结构化结果
```

注意：如果 ERP 请求超时，系统不能直接认定操作失败。必须先通过幂等键查询、回执查询或对账机制确定实际执行状态。

## 三、推荐技术栈与依赖边界

### 3.1 技术选型

| 层次   | 建议技术                      | 设计理由                  |
| ---- | ------------------------- | --------------------- |
| 前端   | React + TypeScript + Vite | 适合构建企业管理台和复杂表单        |
| 后端   | Go                        | 适合 API、并发任务、集成接口与运维工具 |
| 数据库  | PostgreSQL                | 事务、索引、JSONB、任务状态和审计查询 |
| 本体标准 | OWL 2、RDF、SHACL           | 分别承担语义建模、图数据表达、数据约束验证 |
| 本体引擎 | 可替换的 `OntologyEngine` 接口  | 避免业务代码绑定特定实现          |
| 文件存储 | S3 兼容接口或本地文件存储            | 保存本体包、版本文件和执行证据       |
| 模型接入 | `ModelProvider` 接口        | 统一本地模型与获批的外部模型        |
| 测试   | Go test、前端测试、集成与安全测试      | 分层验证契约、流程和权限          |
| 部署   | Docker Compose            | MVP 私有化部署成本低          |

OWL/RDF/SHACL 不是同一种验证机制：RDF 表达图数据，OWL 表达语义公理与类关系，SHACL 则适合验证数据是否符合规定的结构约束。三者应分别建模、分别报告结果。

### 3.2 Go 依赖管理

推荐使用 Go Modules 管理依赖，初期依赖应控制在必要范围内：

- HTTP 路由：选择一个成熟路由库，或使用标准库。
- 配置：集中加载环境变量和配置文件。
- 数据访问：`pgx` 或等价 PostgreSQL 驱动。
- 日志：结构化日志。
- Schema 校验：JSON Schema 验证库。
- 数据迁移：版本化数据库迁移工具。
- OpenTelemetry：在需要时统一接入追踪、指标与日志关联。

具体第三方库的版本应在项目初始化时锁定并执行兼容性测试，不在架构设计阶段将未经验证的版本写死。

### 3.3 哪些模块将来可以使用 Rust？

初期不建议为了“底层性能”而把所有模块拆成 Rust 服务。以下模块在测量到瓶颈后，可以单独考虑 Rust：

- 大规模 RDF 图计算或专用图索引。
- 高成本的几何、图结构和语义计算。
- 大批量规则匹配、特征提取。
- 高吞吐数据转换与校验。

届时通过进程间 RPC、稳定的 C ABI 或独立计算服务调用，不让 Rust 类型渗透到 Go 的业务领域模型中。

### 4.1 模块依赖规则

必须从第一天开始限制依赖方向：

1. `transport/http` 负责协议转换，不承载业务规则。
2. 各业务模块通过公开接口交互，不能随意访问其他模块的私有实现。
3. `harness` 只能通过 `authorization`、`toolruntime`、`ontologyruntime` 等接口执行受控操作。
4. `ontologyengineering` 只能生成候选版本，不能绕过 `ontologyregistry` 直接发布。
5. `erpintegration` 不负责决定用户是否有业务权限；它只执行已授权、已验证的适配器请求。
6. `audit` 负责记录关键事件，但不应该被用作业务状态的唯一存储。
7. `pkg/contracts` 只放跨模块真正需要共享的稳定契约，不能变成所有代码的公共垃圾桶。

\*\*特别注意 Go 的 `internal/` 机制：\*\*它能够限制包的导入范围，但不能自动建立完整的业务架构边界。还需要通过代码评审、静态检查和架构测试维护模块依赖规则。

## 五、核心领域模型与契约

### 5.1 全局 ID 与上下文

所有跨模块的业务实体均使用稳定 ID。建议统一封装为字符串类型，具体采用 UUIDv7 或其他有序 ID 方案时，在工程初始化阶段统一确定。

```
package contracts

type TenantID string
type UserID string
type OrgID string
type AgentID string
type AgentVersionID string
type OntologyID string
type OntologyVersionID string
type RunID string
type ToolID string
type ApprovalID string
type ERPOperationID string

type RequestContext struct {
    TenantID TenantID
    ActorID  UserID
    OrgID    OrgID
    RequestID string
    TraceID   string
}
```

这里的 `RequestContext` 是跨模块业务调用上下文，不等于完整的授权凭证。服务端必须从可信认证结果构建它，不能直接信任用户请求体传来的 `TenantID` 或 `ActorID`。

### 5.2 统一错误契约

错误必须区分业务拒绝、输入错误、权限拒绝、暂时不可用和执行结果未知。

```
package errors

type Code string

const (
    CodeInvalidArgument  Code = "INVALID_ARGUMENT"
    CodeUnauthenticated  Code = "UNAUTHENTICATED"
    CodePermissionDenied Code = "PERMISSION_DENIED"
    CodeConflict         Code = "CONFLICT"
    CodeValidationFailed Code = "VALIDATION_FAILED"
    CodeUnavailable      Code = "UNAVAILABLE"
    CodeExecutionUnknown Code = "EXECUTION_UNKNOWN"
    CodeInternal         Code = "INTERNAL"
)

type AppError struct {
    Code      Code
    Message   string
    RequestID string
    Retryable bool
}

func (e *AppError) Error() string {
    return string(e.Code) + ": " + e.Message
}
```

生产环境的响应不应向客户端暴露 SQL、密钥、内部路径或完整堆栈。详细错误应进入受控日志，并通过 `RequestID` 关联排查。

### 5.3 本体版本契约

本体不仅是一份 Turtle 文件，还包括约束、映射、测试、依赖及其校验结果。

```
package contracts

type OntologyPackage struct {
    ID          OntologyID
    Name        string
    Domain      string
    Granularity string
    Versions    []OntologyVersion
}

type OntologyVersion struct {
    ID             OntologyVersionID
    Version        string
    Status         string
    ContentDigest  string
    DependencyRefs []string
}

type OntologyValidationResult struct {
    SyntaxValid        bool
    OWLConsistent      bool
    SHACLConformant    bool
    BusinessRulesValid bool
    Findings           []ValidationFinding
}

type ValidationFinding struct {
    RuleID   string
    Severity string
    Message  string
    Evidence []string
}
```

实现时，应将状态值改为明确的枚举，并为每项验证记录引擎版本、规则版本、输入摘要与运行时间。`SyntaxValid`、`OWLConsistent`、`SHACLConformant` 之间不能互相替代。

### 5.4 智能体执行契约

```
package contracts

type RunStatus string

const (
    RunCreated                RunStatus = "CREATED"
    RunContextBuilding        RunStatus = "CONTEXT_BUILDING"
    RunReady                  RunStatus = "READY"
    RunPlanning               RunStatus = "PLANNING"
    RunPlanValidating         RunStatus = "PLAN_VALIDATING"
    RunRunning                RunStatus = "RUNNING"
    RunWaitingInput           RunStatus = "WAITING_INPUT"
    RunWaitingApproval        RunStatus = "WAITING_APPROVAL"
    RunPaused                 RunStatus = "PAUSED"
    RunRecovering             RunStatus = "RECOVERING"
    RunCancelling             RunStatus = "CANCELLING"
    RunRequiresReconciliation RunStatus = "REQUIRES_RECONCILIATION"
    RunManualReview           RunStatus = "MANUAL_REVIEW"
    RunCompleted              RunStatus = "COMPLETED"
    RunFailed                 RunStatus = "FAILED"
    RunCancelled              RunStatus = "CANCELLED"
    RunExpired                RunStatus = "EXPIRED"
)

type AgentRun struct {
    ID                 RunID
    TenantID           TenantID
    RequestedBy        UserID
    AgentVersionID     AgentVersionID
    OntologyVersionIDs []OntologyVersionID
    PolicyVersionIDs   []string
    Status             RunStatus
    InputDigest        string
}
```

`RunStatus` 全集共 **17 个状态**，唯一真源是 `docs/contracts/01-全局状态注册表.md`（权威转换矩阵见第六篇 §3.1/§14.2），本篇与第二篇 DDL、事件 Schema、前端标签只允许引用该表，不得另行定义。历史词表映射：旧 `QUEUED` 已删除——排队语义由 `available_at` + 执行队列表达，直接映射到 `READY`；`CONTEXT_READY` → `READY`；`VALIDATING` → `PLAN_VALIDATING`；`UNKNOWN_OUTCOME`/`WAITING_RECONCILIATION` → `REQUIRES_RECONCILIATION`（等价重命名，不是两个状态）。

每次运行都必须绑定明确的版本。执行过程中发布新本体，不能静默改变已经启动的任务所使用的语义。

如果任务需要升级到新版本，应通过显式迁移、重新验证或新建任务实现，而不是在原任务里自动替换依赖。

## 六、依赖倒置与核心接口

这部分是整个工程最重要的代码设计之一。我们要保证：更换模型厂商、更换本体引擎、更换 ERP 系统时，不需要重写 Harness 和核心业务逻辑。

### 6.1 本体引擎接口

```
package ontologyruntime

import (
    "context"

    "odap/pkg/contracts"
)

type LoadRequest struct {
    PackageID contracts.OntologyID
    VersionID contracts.OntologyVersionID
}

type QueryRequest struct {
    VersionID contracts.OntologyVersionID
    Query     string
    Parameters map[string]any
}

type ValidateRequest struct {
    VersionID contracts.OntologyVersionID
    Data      map[string]any
}

type OntologyEngine interface {
    Load(
        ctx context.Context,
        req LoadRequest,
    ) error

    Query(
        ctx context.Context,
        req QueryRequest,
    ) (any, error)

    Validate(
        ctx context.Context,
        req ValidateRequest,
    ) (contracts.OntologyValidationResult, error)
}
```

这里的 `any` 仅用于展示接口边界。正式实现应将查询结果封装成带有类型、分页、证据和版本信息的结构体。

同样，`Query` 不能直接接受任意不受限制的查询语句。需要由对应引擎实施查询类型限制、资源限制和权限过滤。

### 6.2 授权接口

授权接口与 `Decision` 类型（`ALLOW` / `DENY` / `REQUIRE_APPROVAL`）的权威定义在第三篇授权引擎的 domain 类型（第三篇 §7.1 授权决策模型，含 Obligations、决策 ID 强类型等字段），**本篇不重复定义**：Harness、Tool Runtime、ERP Adapter 等调用方一律引用第三篇的授权领域类型，不得在本地再建一套 `Decision` / `AuthorizationRequest` / `AuthorizationResult` 结构。错误码同理只引用 `docs/contracts/02-统一错误码注册表.md`（AUTHZ 域），状态词表只引用 `docs/contracts/01-全局状态注册表.md`。

授权服务的默认策略必须是拒绝。系统内部发生策略服务故障时，不能为了保证业务可用而默认放行敏感操作。

需要特别区分：

- Allow：允许在当前授权范围内执行。
- Deny：明确拒绝。
- RequireApproval：操作只有经过符合要求的审批后才能继续。

审批本身不能覆盖租户隔离、硬性数据访问限制或法律合规约束。

### 6.3 模型供应商接口

```
package modelruntime

import "context"

type Message struct {
    Role    string
    Content string
}

type GenerateRequest struct {
    Model        string
    Messages     []Message
    MaxTokens    int
    Temperature  float64
}

type GenerateResponse struct {
    Content      string
    FinishReason string
    Model        string
    Usage         TokenUsage
}

type TokenUsage struct {
    InputTokens  int
    OutputTokens int
}

type ModelProvider interface {
    Generate(
        ctx context.Context,
        req GenerateRequest,
    ) (GenerateResponse, error)
}
```

模型返回的内容必须视为不可信输入。涉及工具调用时，应解析为受 Schema 约束的结构化动作，并经过 Harness、权限服务和工具运行时验证。

模型供应商接口还应支持超时、调用取消、重试分类、敏感数据策略和使用量统计。生产实现不得将访问密钥写入日志或智能体上下文。

### 6.4 ERP 统一接口

```
package erpintegration

import "context"

type OperationRequest struct {
    TenantID       string
    OperationID    string
    IdempotencyKey string
    ObjectType     string
    ObjectID       string
    Action         string
    Payload        []byte
    ExpectedVersion string
}

type OperationReceipt struct {
    OperationID string
    ExternalID  string
    Status      string
    ResultDigest string
}

type ERPPort interface {
    GetObject(
        ctx context.Context,
        tenantID string,
        objectType string,
        objectID string,
    ) ([]byte, error)

    SubmitOperation(
        ctx context.Context,
```

该接口是平台与 ERP 之间的隔离层。

后续可以实现 SAP Adapter、用友 Adapter、金蝶 Adapter 或企业自研系统 Adapter，而不让智能体知道底层 ERP 的 API 差异。

`SubmitOperation` 必须结合幂等键、操作状态记录、预期版本和回执查询。发生网络超时不能直接重复提交，更不能假设远端操作一定没有发生。

## 七、Harness 的最小执行框架

Harness 是整个平台的执行中枢，不等于一个 Prompt 模板，也不应直接成为一个无限循环调用大模型的函数。

建议将执行拆分成四个部分：

1. `ContextBuilder`：根据用户权限、本体版本、业务对象和获准证据构建上下文。
2. `Planner`：生成受约束的执行计划。
3. `ToolRuntime`：验证和执行计划中的工具动作。
4. `CheckpointStore`：持久化运行状态、步骤结果及恢复位置。

### 7.1 执行器接口

```
package harness

import (
    "context"

    "odap/pkg/contracts"
)

type RunRequest struct {
    RunID contracts.RunID
}

type RunResult struct {
    RunID  contracts.RunID
    Status contracts.RunStatus
    Output map[string]any
}

type Executor interface {
    Execute(
        ctx context.Context,
        req RunRequest,
    ) (RunResult, error)

    Resume(
        ctx context.Context,
        runID contracts.RunID,
    ) (RunResult, error)

    Cancel(
        ctx context.Context,
        runID contracts.RunID,
    ) error
}
```

这个接口只规定外部能力，实际执行逻辑由内部的状态机驱动。

### 7.2 状态机原则

```
CREATED
   ↓
CONTEXT_BUILDING
   ↓
READY（排队语义由 available_at + 执行队列表达，不设 QUEUED 状态）
   ↓
PLANNING → PLAN_VALIDATING
   ↓
RUNNING
   ├──→ WAITING_INPUT ─────────→ RUNNING
   ├──→ WAITING_APPROVAL ──────→ RUNNING
   ├──→ PAUSED ────────────────→ RECOVERING → RUNNING
   ├──→ CANCELLING ────────────→ CANCELLED（取消收敛队列：等待在途外部操作收敛后落终态）
   ├──→ REQUIRES_RECONCILIATION → RUNNING / MANUAL_REVIEW（对账队列：结果未知的外部操作）
   ├──→ MANUAL_REVIEW ─────────→ RUNNING / FAILED
   ├──→ FAILED
   └──→ COMPLETED
（超过允许生命周期 → EXPIRED）
```

完整 17 态与 state×event 转换矩阵以 `docs/contracts/01-全局状态注册表.md` 与第六篇 §14.2 为权威，本图只展示主干；取消与对账两条队列的领取、租约与优先级见 §9.4 与第六篇 §6.2。真实实现还应为工具调用、ERP 操作和审批分别建立独立状态机。

特别是 ERP 操作，需要区分 `EXECUTING`、`SUCCEEDED`、`FAILED`、`UNKNOWN` 和 `RECONCILING`。智能体运行完成不代表 ERP 操作成功；反过来，智能体进程失败也不代表 ERP 操作没有成功。

### 7.3 工具调用的强制执行顺序

每次工具调用必须经过以下步骤：

1. 校验工具 ID、版本、输入 Schema。
2. 校验调用者、租户、数据范围和工具能力。
3. 检查业务规则、本体约束与操作前置条件。
4. 判断是否需要人工审批。
5. 将调用意图及幂等键持久化。
6. 执行工具，并保存返回值、错误或未知状态。
7. 保存证据、审计记录与后续恢复信息。

不允许模型自行跳过任何一个环节。

## 八、插件系统的工程骨架

平台的智能体、本体、工具和业务策略都采用插件化管理，但插件化不等于允许插件直接运行任意代码。

MVP 首先实现声明式插件包、注册、校验、版本管理和受控调用；不必立即支持任意语言插件热加载。

### 8.1 统一插件清单

每个插件都有 `manifest.yaml`。例如，一个差旅报销审核智能体：

```

apiVersion: odap.io/v1
kind: AgentPlugin

metadata:
  id: expense-review
  name: Expense Review Agent
  version: 1.0.0
  domain: finance

spec:
  entrypoint:
    type: declarative
    file: agent.yaml

  ontologyDependencies:
    - id: expense
      version: "1.0.0"

  toolDependencies:
    - id: erp-expense-read
      version: "1.0.0"

  capabilities:
    - ontology.read
    - expense.read
    - expense.validate

  execution:
    maxSteps: 20
    timeoutSeconds: 300

  security:
    networkAccess: false
    filesystemAccess: false
    requireAuthorization: true

```

以上只是插件元数据，不是安全策略本身。运行时还必须检查清单、签名或可信来源、依赖版本、能力授权和实际执行环境。

`capabilities` 表示插件请求的能力，不代表它已经获得这些权限。

### 8.2 插件注册生命周期

CREATED · 已创建

VALIDATING · 校验中

TESTING · 测试中

STAGED · 待发布

APPROVED · 已审批

PUBLISHED · 已发布

发布后可以进入 DEPRECATED（弃用）、DISABLED（禁用）或回滚流程。

对于本体插件，还必须完成语义校验和 SHACL 约束验证；对于工具插件，还必须完成权限声明与执行环境检查；对于智能体插件，还必须校验其本体、工具依赖是否兼容。

### 8.3 插件协议版本

统一的插件协议至少应包含：

- `apiVersion`：协议版本。
- `kind`：AgentPlugin、OntologyPlugin、ToolPlugin、PolicyPlugin 或 ModelProviderPlugin（共五类，与总书 §6.2、第四篇 §2.1 一致；`model_provider` 统一对接大语言模型、嵌入模型及企业私有模型服务）。
- `metadata`：插件 ID、名称、版本、业务域。
- `dependencies`：依赖 ID 与版本范围。
- `capabilities`：请求的能力。
- `inputSchema`、`outputSchema`：输入输出契约。
- `security`：网络、文件、数据和执行限制。
- `integrity`：内容摘要、签名或可信来源信息。

协议要支持向前兼容策略，但不能让新版本插件绕过旧版本的权限约束。升级协议时应进行契约测试，并明确不兼容版本的迁移方案。

## 九、Go 服务入口与启动装配

### 9.1 Server 入口

`apps/server/main.go` 只负责启动应用，不应在这里直接创建数据库连接、写权限规则或实现业务逻辑。

```
package main

import (
    "context"
    "log"
    "os"
    "os/signal"
    "syscall"

    "odap/internal/bootstrap"
)

func main() {
    ctx, stop := signal.NotifyContext(
        context.Background(),
        os.Interrupt,
        syscall.SIGTERM,
    )
    defer stop()

    app, err := bootstrap.NewServer(ctx)
    if err != nil {
        log.Printf("server initialization failed: %v", err)
        os.Exit(1)
    }

    if err := app.Run(ctx); err != nil {
        log.Printf("server stopped with error: %v", err)
        os.Exit(1)
    }
}
```

### 9.2 Bootstrap 装配

```
package bootstrap

import (
    "context"
    "fmt"
)

type ServerApp struct {
    // HTTP server、数据库连接池、业务服务等。
}

func NewServer(ctx context.Context) (*ServerApp, error) {
    // 1. 加载并校验配置。
    // 2. 初始化日志和可观测性。
    // 3. 建立 PostgreSQL 连接池并检查健康状态。
    // 4. 初始化 Repository。
    // 5. 创建授权、注册表、本体、Harness 等服务。
    // 6. 注册 HTTP 路由与中间件。
    // 7. 返回装配完成的应用。
    if err := ctx.Err(); err != nil {
        return nil, fmt.Errorf("initialize server: %w", err)
    }

    return &ServerApp{}, nil
}

func (a *ServerApp) Run(ctx context.Context) error {
    // 正式实现应启动 HTTP 服务并监听退出信号。
    // 退出时停止接收新请求，等待必要任务结束，
    // 最后关闭连接池与其他资源。
    return ctx.Err()

```

这里的空实现仅用于展示文件结构。实际开发时，应为启动过程定义明确的依赖结构、健康检查和优雅关闭流程。

### 9.3 Worker 入口

`apps/worker/main.go` 的职责不同于 API Server：

- 领取可执行任务。
- 检查任务租约与并发限制。
- 调用 Harness。
- 持久化检查点。
- 对中断任务进行恢复。
- 处理任务取消、超时与关闭信号。

任务领取应使用数据库事务或等价的可靠机制，确保同一任务不会被多个 Worker 同时执行。对于外部副作用，还需要独立的幂等和对账机制，因为仅仅保证任务不被重复领取，并不能保证远端操作只发生一次。

### 9.4 taskqueue 租约设计摘要

`internal/taskqueue`（§四目录）负责负责任务领取、租约与重试，最小设计如下：

- **租约字段**：任务记录携带 `lease_owner`（Worker 实例 ID）、`lease_expires_at`（租约截止时间）、`lease_epoch`（单调递增的租约代数，每次领取/续租 +1，用于识别“旧 Worker 迟到的结果”）、`attempt_count` 与 `max_attempts`；调度字段 `priority`、`available_at`、`cancel_requested_at` 与第六篇 §6.2 一致。
- **领取 SQL**：领取采用原子条件更新（`FOR UPDATE SKIP LOCKED`），按队列类型分治——执行、规划、取消收敛、对账四个队列独立领取；优先级为"到期恢复/对账 > 重试到账 > 正常可执行 > 低优先级后台"。完整 SQL 以第六篇 §6.2 为准，本篇不重复定义。
- **过期回收**：Worker 通过心跳续租（长任务定期延长 `lease_expires_at` 并递增 `lease_epoch`）；租约过期且无心跳的任务由恢复流程重新入队，新 Worker 以更高 `lease_epoch` 领取；旧 Worker 若迟到提交结果，按 `lease_epoch` 比对拒绝并转入对账，而不是覆盖新结果。
- **重试与退避**：`attempt_count` 达到 `max_attempts` 前按退避策略重投；涉及外部副作用的重试必须结合幂等键与对账（§2.3），不能因任务被重新领取就重复执行。

```
export interface ApiError {
  code: string;
  message: string;
  requestId?: string;
}

export async function apiRequest<T>(
  path: string,
  init?: RequestInit,
): Promise<T> {
  const response = await fetch(`/api/v1${path}`, {
    ...init,
    credentials: "include",
    headers: {
      "Content-Type": "application/json",
      ...init?.headers,
    },
```

统一前缀使用 `/api/v1`，采用 REST 风格管理资源。接口按模块分组，但权限规则统一由授权服务执行。

## 十二、数据库与迁移工程骨架

第一篇只规定数据库工程的组织方式，完整表结构、索引、约束与事务设计将在第二篇详细展开。

### 12.1 第一阶段需要的实体

组织与身份

tenants、organizations、users、memberships、roles、permissions

授权与策略

policy_versions、role_bindings、approval_rules

插件与智能体

ontologies、ontology_versions、ontology_artifacts、ontology_dependencies、validation_runs

审计与证据

audit_events、evidence_records

### 12.2 数据库设计规则

- 所有租户范围内的业务数据必须具有明确的租户归属。
- 外键、唯一约束和事务要在数据库层落实，而不只依赖 Go 代码。
- 版本化实体发布后原则上不可原地修改；修改应创建新版本。
- 长时间任务不能一直持有数据库事务，应使用短事务、租约与检查点。
- 审批决定、执行回执和关键审计记录需要持久化。
- 大型本体文件、插件包和证据附件可以放在对象存储中，数据库保存内容摘要、版本和访问元数据。
- 对于多租户隔离，除应用层过滤外，还应评估 PostgreSQL Row-Level Security（RLS），并确保连接池中的租户上下文不会串用。

## 十三、私有化部署骨架

MVP 推荐 Docker Compose。先确保一个普通 Linux 服务器能够完成安装、初始化、升级、备份和恢复，再考虑 Kubernetes。

### 13.1 部署拓扑

```
企业内网
   │
   ▼
反向代理 / TLS
   ├── Web 前端
   └── Go API Server
           │
           ├── PostgreSQL
           ├── 本体引擎
           ├── 对象存储
           └── Worker
                  ├── 模型服务
                  └── ERP Port
                        └── Mock ERP
```

模型服务和真实 ERP 的网络出口应按部署模式限制。默认情况下，智能体不能任意访问公网，也不能自行决定把企业数据发送到外部模型。

### 13.2 Compose 文件骨架

以下只展示服务组织方式，镜像名称、健康检查、密钥和存储配置应在实际仓库中补齐。

```

services:
  postgres:
    image: postgres:16
    environment:
      POSTGRES_DB: odap
      POSTGRES_USER: odap
      POSTGRES_PASSWORD: ${ODAP_DB_PASSWORD}
    volumes:
      - postgres_data:/var/lib/postgresql/data
    networks:
      - backend
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U odap -d odap"]
      interval: 10s
      timeout: 5s
      retries: 5
    deploy:
      resources:
        limits:
          cpus: "2"
          memory: 2G

  minio:
    image: minio/minio:latest
    command: server /data --console-address ":9001"
    environment:
      MINIO_ROOT_USER: ${ODAP_MINIO_ROOT_USER}
      MINIO_ROOT_PASSWORD: ${ODAP_MINIO_ROOT_PASSWORD}
    volumes:
      - minio_data:/data
    networks:
      - backend
    healthcheck:
      test: ["CMD", "mc", "ready", "local"]
      interval: 10s
      timeout: 5s
      retries: 5
    deploy:
      resources:
        limits:
          cpus: "1"
          memory: 1G

  server:
    build:
      context: ../..
      dockerfile: deploy/docker/server.Dockerfile
    environment:
      ODAP_DATABASE_URL: ${ODAP_DATABASE_URL}
      ODAP_OBJECT_STORE_ENDPOINT: http://minio:9000
    depends_on:
      postgres:
        condition: service_healthy
      minio:
        condition: service_healthy
    ports:
      - "127.0.0.1:8080:8080"
    networks:
      - backend
    healthcheck:
      test: ["CMD", "wget", "-qO-", "http://127.0.0.1:8080/health/live"]
      interval: 15s
      timeout: 5s
      retries: 3
    deploy:
      resources:
        limits:
          cpus: "1"
          memory: 1G

  worker:
    build:
      context: ../..
      dockerfile: deploy/docker/worker.Dockerfile
    environment:
      ODAP_DATABASE_URL: ${ODAP_DATABASE_URL}
      ODAP_OBJECT_STORE_ENDPOINT: http://minio:9000
    depends_on:
      postgres:
        condition: service_healthy
    networks:
      - backend
    healthcheck:
      test: ["CMD", "wget", "-qO-", "http://127.0.0.1:8081/health/live"]
      interval: 15s
      timeout: 5s
      retries: 3
    deploy:
      resources:
        limits:
          cpus: "2"
          memory: 2G

  pluginruntime:
    build:
      context: ../..
      dockerfile: deploy/docker/pluginruntime.Dockerfile
    environment:
      ODAP_DATABASE_URL: ${ODAP_DATABASE_URL}
    depends_on:
      postgres:
        condition: service_healthy
    networks:
      - backend
    healthcheck:
      test: ["CMD", "wget", "-qO-", "http://127.0.0.1:8082/health/live"]
      interval: 15s
      timeout: 5s
      retries: 3
    deploy:

        limits:
          cpus: "1"
          memory: 1G

  minio_data:

```

`pluginruntime` 是插件进程 Supervisor（第四篇 §8.1）：MVP 以独立受控进程托管插件（非 root + seccomp + cgroup + 只读文件系统 + 网络默认拒绝），容器 Runner 为可选能力（dockerd 受控接入，不直挂 docker.sock）。`minio` 提供 S3 兼容对象存储，保存本体包、插件制品、证据附件与大型查询结果。`deploy.resources.limits` 为各服务资源上限（非 Swarm 单机模式用等价的 `mem_limit`/`cpus` 字段）。server/worker/pluginruntime 的健康检查分别暴露 `/health/live` 与 `/health/ready`（§十一 路由）。

这个骨架不是可直接用于生产环境的完整 Compose 文件。正式部署还需要补充日志驱动与轮转、备份恢复、密钥管理、迁移步骤与回滚方案，最低要求见 §13.3。

另外，`internal: true` 会限制该网络的外部连通性。如果模型服务或 ERP 位于其他网络，需要显式设计受控出口或独立集成网络，而不是简单开放全部容器的互联网访问。

### 13.3 生产 Compose 检查清单

骨架不是生产配置。上线前至少完成以下四类检查（每类给出最低要求）：

| 类别 | 最低要求 |
| --- | --- |
| 资源限制 | 所有服务声明 CPU/内存上限（`deploy.resources.limits` 或等价字段）；postgres 单独限流并保留足够 shared_buffers；插件进程由 pluginruntime 以 cgroup 限额托管，超限终止并记录事件（第四篇 §8.1） |
| 日志驱动 | 统一日志驱动与轮转（`logging.driver` + `max-size`/`max-file`），禁止落盘无限增长；日志不得包含密钥、完整查询参数与提示词内容 |
| 备份 | postgres 定时基础备份 + WAL 归档；minio 对象存储版本化与跨介质备份；恢复演练纳入第十六篇 P7 交付门禁，未演练不视为可交付 |
| 密钥管理 | 数据库口令、MinIO 根凭据、模型与 ERP 密钥全部经环境变量或密钥服务注入，禁止写入 Compose 文件与镜像；插件密钥由平台 SecretProvider 按租户/版本/任务绑定（第四篇 §12.2） |

## 十四、工程质量与自动化测试

### 14.1 测试分层

| 测试层   | 主要验证对象                        |
| ----- | ----------------------------- |
| 单元测试  | 状态转换、权限决策、校验规则、业务服务           |
| 契约测试  | API Schema、插件协议、ERP Port、模型接口 |
| 集成测试  | PostgreSQL、任务队列、本体引擎、审批流程     |
| 恢复测试  | Worker 崩溃、租约过期、重复消息、未知操作结果    |
| 安全测试  | 越权访问、租户穿透、提示词注入、恶意插件          |
| 端到端测试 | 从用户请求到 Mock ERP 回执的完整流程       |

### 14.2 第一批必须通过的端到端场景

1. 无权限用户不能创建或执行指定智能体任务。
2. 用户只能读取其有权访问的业务对象。
3. 本体不符合 SHACL 约束时不能发布为可用版本。
4. 智能体不能调用未授权工具。
5. 高风险操作未审批前不能提交 ERP。
6. 审批完成后，如果操作参数或关键版本发生变化，原审批不能直接复用。
7. ERP 超时但实际执行成功时，不产生虚假的失败结论，也不重复执行副作用。
8. 同一幂等键的重复请求不会导致重复业务操作。
9. 任务运行期间权限被撤销后，后续敏感操作会重新鉴权。
10. 不同租户之间无法读取任务、对象、证据和审批记录。
11. 恶意输入不能诱导智能体绕过工具授权。
12. 发布新本体后，旧任务仍使用原先固定的版本。

### 14.3 CI 流程

每次提交至少执行：

```
代码格式检查
    ↓
静态分析与依赖检查
    ↓
Go 单元测试
    ↓
前端类型检查与构建
    ↓
契约测试
    ↓
数据库迁移测试
    ↓
集成测试
    ↓
安全测试与镜像扫描
    ↓
构建可部署制品
```

生产发布还应校验制品摘要、依赖来源、配置完整性和数据库迁移计划。高风险变更需要单独审批。

## 十五、从空仓库到可运行系统的实施顺序

工程落地建议分成七个里程碑。每个里程碑都应有一个可以启动、测试或演示的交付物，而不是只完成一批孤立代码。

## 01

工程底座

建立 Go Modules、React 工程、配置系统、日志、数据库连接、迁移工具、CI 和 Compose。

验收：开发者可以一键启动 API、Worker、前端和 PostgreSQL。

## 02

企业身份与权限

实现租户、组织、用户、角色、数据范围和统一授权服务。

验收：用户只能访问授权范围内的数据，越权测试全部通过。

## 03

插件与本体注册表

实现插件清单解析、版本管理、本体文件存储、校验流程和发布状态。

验收：能够注册一个本体包，验证 OWL/RDF/SHACL 结果并管理版本。

## 04

Harness 与任务运行时

实现任务队列、执行状态机、工具运行时、检查点、暂停、恢复和取消。

验收：模拟智能体可以运行多步任务，Worker 重启后可以恢复任务。

## 05

ERP Port 与 Mock ERP

实现只读查询、受控写操作、幂等、审批门禁、回执、超时和对账。

验收：无需真实 ERP，就能验证完整的业务操作生命周期。

## 06

管理控制台与制度驱动本体生成

实现智能体、本体、审批、执行监控、审计等页面，并接入制度解析到候选本体的生成流程。

验收：管理人员可以在界面完成注册、校验、发布和审批。

## 07

私有化交付与恢复验证

完善部署文档、备份恢复、权限审计、镜像安全和故障注入测试。

验收：新环境可以按文档安装，恢复演练和关键安全测试通过。

实际工期取决于人员配置、本体引擎的选型和权限体系的复杂程度。建议先完成一个可工作的端到端垂直切片，再并行扩展各业务模块，不宜仅按模块数量估算工期。

## 十六、第一阶段的最小可运行验收标准

我建议将第一个版本的目标定义为：

不接真实 ERP，也能完整演示一个受企业制度约束的智能体如何理解业务、执行任务、申请审批并通过标准接口完成模拟业务操作。

具体演示场景：

1. 管理员上传差旅报销制度。
2. 本体设计智能体解析制度，生成候选业务概念、规则与 SHACL 约束。
3. 系统完成语法、语义、结构约束和业务规则校验。
4. 管理员审核并发布本体版本。
5. 员工启动报销审核智能体。
6. Harness 根据员工权限、报销本体和获准工具构建执行上下文。
7. 智能体查询 Mock ERP 中的报销单，并给出带证据的审核意见。
8. 如果需要执行敏感操作，系统创建审批单并等待授权。
9. 审批通过后，ERP Adapter 执行模拟操作，返回正式回执。
10. 系统保存执行记录、审批记录、证据和审计日志。

这条链路一旦打通，就证明了平台的核心架构成立。后续接入合同管理、采购、财务分析、供应商管理等智能体，主要是增加本体包、业务插件、工具和相应策略，而不是重新开发一套智能体框架。
