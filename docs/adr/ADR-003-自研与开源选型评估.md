# ADR-003：自研与开源选型评估

- **状态**：已接受
- **日期**：2026-10-12
- **决策域**：工作流编排、消息可靠性原语、LLM 网关基础能力、RDF 存储与推理（跨第八篇、第九篇、第十篇、第十三篇）

## 背景

四个重叠领域目前均为全自研设计，与成熟开源方案存在功能重叠（评审报告 §4.1）。本 ADR 不是最终采购决定，而是把"哪些能力允许开源承载、哪些必须自研"固化为设计约束，避免实现期逐模块重复造轮子，也避免把差异化能力外包给不满足私有化与合规要求的组件。

## 决策

### 领域一：工作流编排（DAG + Saga + 重试，第八篇/第十篇）

- **候选**：Temporal、Cadence。
- **评估维度**：功能覆盖（DAG/Saga/重试/可见性）、运维成本（自建 server 集群 + 数据库 + 升级）、私有化许可（MIT/Apache 均可私有部署，Temporal 需自管 Cassandra/PostgreSQL）、团队学习曲线（workflow-as-code 心智 + 确定性重放约束）、退出成本（工作流定义与内置存储耦合，迁移需重放历史）。
- **结论倾向**：**自研保留 ERP 对账与治理层，通用编排评估后引入**。ERP 对账、操作账本、审批绑定、证据链是 ODAP 差异化层，必须自研；通用 DAG 调度/重试/可见性允许在评估后引入开源承载，但引入前提是通过私有化许可核验与故障注入对等测试。
- **触发重新评估**：① 开源方案完成私有化部署 PoC 且对账语义可无损映射；② 自研编排的故障注入回归连续两个迭代出现非业务缺陷；③ 出现第三十个独立工作流模板（维护成本信号）。

### 领域二：Outbox / Inbox / 租约 / 延迟队列（第十篇）

- **候选**：river（Go 原生，PostgreSQL）、pgmq。
- **评估维度**：功能覆盖（outbox/inbox/租约/延迟/重试/死信）、运维成本（river 仅依赖 PG，零额外组件）、私有化许可（river 为 SLAEL-1.1/proprietary 双许可，**私有化商用需取得商业许可或改用 pgmq/MIT 方案**）、团队学习曲线（river 与 Go worker 模型贴近）、退出成本（队列即 PG 表，退出时数据可平移）。
- **结论倾向**：**P1-P3 可用 river 覆盖**（MVP 阶段的事件总线、任务队列、延迟与重试），前提是商业许可落地；若许可受阻，回退 pgmq 或保留第十篇自研内核并冻结功能范围。
- **触发重新评估**：① 商业许可未获批；② 单租户事件吞吐超过 PG 单表可承载阈值（以第十六篇压测为准）；③ 需要跨区域多活队列。

### 领域三：LLM 协议转换 / 路由 / 限流 / 熔断（第九篇）

- **候选**：LiteLLM、Higress、Kong AI Gateway。
- **评估维度**：功能覆盖（多供应商协议统一/路由/限流/熔断/缓存）、运维成本（LiteLLM 需自建 proxy + Redis；Higress 需 Ingress 运维）、私有化许可（三者均可私有化），团队学习曲线（代理层配置化 vs 自研 Go 内嵌）、退出成本（数据分级与审计策略若外包，需评估迁移完整性）。
- **结论倾向**：**基础能力（协议转换、路由、限流、熔断、基础缓存）开源承载；自研聚焦数据分级、预算、审计、语义缓存三层与结构化输出校验回路**（P0-7/§4.4 的治理闭环不外包）。
- **触发重新评估**：① 数据分级策略无法在开源组件外沿可靠生效（数据出境风险）；② 开源组件限流粒度达不到端点×租户令牌桶要求；③ 供应商计费对账（账单 vs usage_ledger）无法通过插件化接入。

### 领域四：RDF 存储与推理（第十三篇）

- **候选**：成熟 RDF Store + reasoner（具体名单在 Spike 报告中确定）vs 自研 PG 三元组引擎。
- **评估维度**：功能覆盖（SPARQL 合规度、推理能力、增量物化）、运维成本（独立存储组件 vs PG 扩展）、私有化许可（逐一核验），团队学习曲线（RDF 生态 vs PG SQL）、退出成本（三元组可导出，执行器与物理索引耦合度决定迁移成本）。
- **结论倾向**：**Spike 门禁后决策**。P2 启动前用 1000 万三元组 Medium 集实测 PG 索引方案 vs 1-2 个成熟 RDF Store，输出选型报告作为进入 P2 的门禁（P0-9①）；无论选哪条路，V1.0 的 CBO 降为规则式优化（选择性排序 + 下推 PG SQL）。
- **触发重新评估**：① Spike 报告结论；② PG 五索引在 1 亿三元组目标下写放大无法通过分区与索引精简缓解；③ 推理能力需求超出 RDFS+SHACL 范围。

## 理由

- 四个领域的共同点：通用能力同质化高、差异化在治理层（对账、审计、数据分级、证据）。把通用能力外包、把治理层自研，是单位工程投入回报最高的切分。
- 私有化部署是 ODAP 的硬约束（企业内网、数据不出境），任何开源选型必须通过许可与数据流双重核验，本 ADR 的"触发重新评估"条件即为此设置回退路径。
- river 的许可风险必须显式登记：双许可组件的私有化商用条款未落实前，不得写入 MVP 关键路径的默认实现。

## 后果

- 正面：通用能力不重复造轮子；治理层保持自研可控；每个领域都有明确的回退触发条件，选型失败不会阻塞主链路。
- 负面：引入开源组件带来许可审查、版本升级与安全补丁的持续义务；river 商业许可是 MVP 关键路径上的未决项。
- 约束：任何开源组件进入 MVP 默认实现前，必须在第十六篇 `docs/decisions/` 记录对应 ADR（许可结论 + 对等测试结果）；RDF Spike 报告是第十三篇 P2 的门禁产物，未产出不得进入 P2。
