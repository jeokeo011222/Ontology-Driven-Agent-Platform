# ODAP 第十篇：任务事件总线、异步消息与分布式可靠执行详细设计

版本：V1.0 · 技术基线：Go + React/TypeScript + PostgreSQL · 部署模式：企业私有化部署

> 范围标签：[MVP-V1.0] §5/§6/§8 Outbox·Inbox·租约 · [V1.5] §11.5 Saga·§17 死信高级处置 · [V2] §4 消息代理引入

## 1. 设计目标

前九篇已经为 ODAP 建立了企业本体、Agent Registry、权限引擎、插件注册中心、Ontology Runtime、Harness、ERP Gateway、多智能体运行时和 LLM Gateway。

当这些模块从单机开发环境走向企业级运行环境时，会遇到一个新的核心问题：

当任务需要跨多个服务、多个 Worker、多个 Agent 和多个外部系统协作时，如何保证任务不会丢失、不会被重复执行造成业务副作用，并且能够在进程崩溃、网络中断和节点故障后恢复？

这不是简单地接入一个消息队列就能解决的问题。ODAP 必须同时设计：

- 任务持久化与事件发布的一致性。
- 异步消息的投递、确认、重试和死信处理。
- 多 Worker 并发抢占任务的协调机制。
- Harness 检查点、任务租约与崩溃恢复。
- 消费幂等、业务幂等和外部 ERP 操作幂等。
- 任务取消、超时、暂停、人工审批和恢复。
- 事件顺序、版本兼容和重复消息处理。
- 多租户隔离、权限检查、预算控制和审计。
- 分布式任务的监控、故障注入与恢复演练。

本篇的目标不是把 ODAP 一开始就建设成复杂的微服务集群，而是设计一套从 Docker Compose 开发环境到多节点生产环境都能沿用的可靠执行架构。

### 1.1 本篇的核心原则

1. 数据库中的任务状态是权威状态，消息队列是唤醒与传递机制。
2. 业务状态变更与待发布事件必须通过同一数据库事务提交。
3. 消息允许重复投递，消费者必须具备幂等处理能力。
4. Worker 的租约只能控制平台内任务所有权，不能自动阻止已发出的外部请求。
5. 外部 ERP 操作必须继续经过第七篇定义的 ERP Operation Gateway。
6. Harness 检查点、执行步骤和事件账本共同支持恢复，不以消息是否仍在队列中作为唯一依据。
7. 不能将“消息已投递”“Worker 已接收”“任务已完成”和“ERP 已提交”混为一谈。
8. 所有任务都必须有明确的截止时间、预算、取消策略和失败终态。
9. 对无法确认结果的外部操作，进入对账流程，而不是盲目重试。
10. 在保证安全和业务正确的前提下，再优化吞吐量与延迟。

## 2. 总体架构

建议将 ODAP 的分布式执行体系划分为七个主要组件。

API Server / Control Plane

创建任务、鉴权、版本锁定、取消与管理

Task Store + Transactional Outbox

任务状态、执行步骤、检查点、待发布事件

Event Bus

事件传递、消费确认、重试与死信

Orchestrator

任务编排与分支调度

Worker Pool

Agent、工具和后台执行

Agent Runtime

Ontology Runtime

ERP Gateway

各组件的职责如下：

| 组件                  | 主要职责              | 不负责的事情             |
| ------------------- | ----------------- | ------------------ |
| API Server          | 接受请求、鉴权、创建任务      | 长时间占用 HTTP 连接执行任务  |
| Task Store          | 保存权威任务状态          | 直接承担所有异步通知         |
| Outbox Publisher    | 发布数据库中已提交的事件      | 决定业务任务是否成功         |
| Event Bus           | 传递事件、提供背压与消费确认    | 替代数据库任务状态          |
| Orchestrator        | 计算依赖、调度步骤、处理分支    | 直接绕过 Gateway 写 ERP |
| Worker              | 执行领取到的工作单元        | 任意覆盖任务状态           |
| Recovery Controller | 检查过期租约、未完成步骤和异常操作 | 在结果未知时盲目重发外部操作     |

### 2.1 推荐的部署演进路径

ODAP V1.0 不需要立即依赖独立部署的 Kafka 集群。

建议分为三个阶段：

- 阶段 A：模块化单体 + PostgreSQL。 采用 PostgreSQL 持久化任务与 Outbox，使用数据库轮询实现事件分发。
- 阶段 B：PostgreSQL + 独立消息代理。 当 Worker 数量、事件吞吐量或多个服务独立扩缩容的需求明确后，引入 NATS JetStream、RabbitMQ 或 Kafka 等消息基础设施。
- 阶段 C：多节点生产集群。 引入独立 Worker Pool、分区消费、容量管理、故障恢复演练和完整的运行监控。

无论采用哪种部署方式，任务状态机、事件 Schema、幂等规则和恢复协议应保持一致。

## 3. 事件模型：把业务状态变化变成可追踪事件

ODAP 的事件总线不应该只传递“执行这个函数”的命令，还应当明确区分命令、事件、查询和执行结果。

### 3.1 四种消息语义

| 类型      | 含义          | 示例                   |
| ------- | ----------- | -------------------- |
| Command | 请求某个组件执行动作  | `ExecuteAgentStep`   |
| Event   | 已发生且已提交的事实  | `AgentStepCompleted` |
| Query   | 查询当前状态或业务数据 | `GetRunStatus`       |
| Result  | 某次处理的结果载荷   | `AgentStepResult`    |

建议遵循以下原则：

- Command 可以失败，也可以因条件不满足而拒绝。
- Event 表示已发生的事实，不能因为下游处理失败就把历史事实改写为未发生。
- Query 应读取权威状态，而不是假定某个事件消费者已处理到最新位置。
- Result 应关联原始任务和步骤，并通过 Schema 与摘要验证。

例如，`ExecuteAgentStep` 是执行请求，而 `AgentStepCompleted` 只有在步骤输出已持久化、步骤状态已成功提交后才可以发布。

### 3.2 ODAP 标准事件 Envelope

所有内部事件建议采用统一 Envelope。事件业务载荷独立版本化，Envelope 负责通用元数据。

```

package odapevents

import "time"

type EventEnvelope struct {
    EventID         string    `json:"event_id"`
    EventType       string    `json:"event_type"`
    SchemaVersion   string    `json:"schema_version"`

    TenantID        string    `json:"tenant_id"`
    AggregateType   string    `json:"aggregate_type"`
    AggregateID     string    `json:"aggregate_id"`
    AggregateSeq    int64     `json:"aggregate_seq"`

    RunID           string    `json:"run_id,omitempty"`
    StepID          string    `json:"step_id,omitempty"`
    CorrelationID   string    `json:"correlation_id"`
    CausationID     string    `json:"causation_id,omitempty"`

    OccurredAt      time.Time `json:"occurred_at"`
    PublishedAt     time.Time `json:"published_at,omitempty"`

    Producer        string    `json:"producer"`
    PayloadDigest   string    `json:"payload_digest"`
    Payload         []byte    `json:"payload"`
}

```

字段说明：

- `event_id`：事件的稳定唯一标识，用于去重。
- `event_type`：事件类型，建议采用 `DomainObject.Action` 风格或统一的点分隔命名。
- `schema_version`：载荷 Schema 版本。
- `tenant_id`：租户归属，由可信服务写入。
- `aggregate_id`：事件所属的权威业务实体，如 Run 或 Step。
- `aggregate_seq`：同一聚合内的逻辑序号，用于检测乱序和缺口。
- `correlation_id`：关联同一个业务流程。
- `causation_id`：标识触发当前事件的上游命令或事件。
- `payload_digest`：对规范化载荷计算的摘要，用于完整性校验。
- `occurred_at`：业务事实发生的时间。
- `published_at`：实际发布的时间。

`occurred_at` 与 `published_at` 不应混用，因为 Outbox 事件可能在事务提交后延迟发布。

### 3.3 标准事件类型

建议先定义以下事件目录。

| 领域       | 事件                                                                                                                    |
| -------- | --------------------------------------------------------------------------------------------------------------------- |
| Run      | `RunCreated`、`RunStarted`、`RunPaused`、`RunResumed`、`RunCompleted`、`RunFailed`、`RunCancelled`                          |
| Step     | `StepScheduled`、`StepClaimed`、`StepStarted`、`StepCompleted`、`StepFailed`、`StepRetryScheduled`                         |
| Agent    | `AgentInvocationRequested`、`AgentInvocationCompleted`、`AgentInvocationFailed`                                         |
| Approval | `ApprovalRequested`、`ApprovalGranted`、`ApprovalRejected`、`ApprovalExpired`                                            |
| ERP      | `ERPOperationRequested`、`ERPOperationAccepted`、`ERPOperationSucceeded`、`ERPOperationUnknown`、`ERPOperationReconciled` |
| Policy   | `AuthorizationGranted`、`AuthorizationDenied`、`PolicyVersionChanged`                                                   |
| Budget   | `BudgetReserved`、`BudgetConsumed`、`BudgetReleased`、`BudgetExceeded`                                                   |
| Recovery | `LeaseExpired`、`RecoveryStarted`、`RecoveryCompleted`、`ManualReviewRequired`                                           |

事件名称应表达已经发生的事实。比如 `ERPOperationSucceeded` 必须由操作账本和回执验证逻辑确认，不能仅因为 Adapter 收到了 HTTP 200 就发布。

### 3.4 事件与状态的关系

推荐将数据库中的状态变更视为权威事实，事件作为这些事实的传播载体。

以步骤完成为例：

1. Worker 执行 Agent 或工具。
2. Worker 验证输出。
3. 在一个 PostgreSQL 事务中写入输出引用、证据索引、步骤成功状态和 Outbox 事件。
4. 事务提交。
5. Outbox Publisher 发布 `StepCompleted`。
6. Orchestrator 收到事件后重新读取任务状态，调度符合依赖条件的后续步骤。

如果第 4 步成功、第 5 步失败，任务仍然是已完成状态。Publisher 恢复后可以重新发布事件；下游依靠事件 ID 和权威状态实现幂等处理。

这正是后续 Outbox 机制的基础。

## 4. Event Bus 选型与抽象接口

事件总线应与 ODAP 的业务代码解耦，避免让 Harness 直接依赖某个消息代理的 SDK。

### 4.1 选型比较

| 方案             | 优势             | 适用场景         | 注意事项             |
| -------------- | -------------- | ------------ | ---------------- |
| PostgreSQL 轮询  | 部署简单、事务语义清楚    | MVP、低到中等吞吐   | 需要优化轮询与锁竞争       |
| NATS JetStream | 轻量、支持持久化流与消费确认 | 任务事件、低延迟内部通信 | 需要设计流、消费者和重放策略   |
| RabbitMQ       | 路由、队列、确认机制成熟   | 工作队列、复杂路由    | 需要管理队列积压、死信和集群运维 |
| Kafka          | 高吞吐、分区日志、重放能力强 | 大规模事件流与分析管道  | 运行和分区治理更复杂       |

这些系统的交付保证、排序、保留和故障语义并不完全相同，不能因为它们都叫消息系统，就假定可以无差别替换。

### 4.2 ODAP 的推荐选择

对当前私有化部署、Go 应用层、PostgreSQL 持久化的 ODAP：

- MVP：使用 PostgreSQL Task Store + Transactional Outbox + 轮询 Publisher。
- 第一阶段扩展：如果重点是分布式 Worker 和任务事件，可优先评估 NATS JetStream 或 RabbitMQ。
- 大规模事件分析、长时间保留和高吞吐事件重放成为明确需求时，再评估 Kafka。

不要为了“架构先进”过早引入消息代理。 真正需要优先稳定的是任务状态机、幂等执行、Outbox 和恢复流程；这些机制无论使用什么消息代理都不能省略。

### 4.3 统一事件总线接口

```

package eventbus

import (
    "context"
    "time"
)

type Message struct {
    EventID       string
    Topic         string
    PartitionKey  string
    SchemaVersion string
    Headers       map[string]string
    Payload       []byte
}

type PublishResult struct {
    AcceptedAt time.Time
    MessageID  string
}

type Handler func(
    ctx context.Context,
    msg Message,
) error

type ConsumerConfig struct {
    ConsumerGroup string
    MaxInFlight   int
    MaxAttempts   int
}

type Bus interface {
    Publish(
        ctx context.Context,
        msg Message,
    ) (PublishResult, error)

    Subscribe(
        ctx context.Context,
        topic string,
        config ConsumerConfig,
        handler Handler,
    ) error

    Health(ctx context.Context) error
}

```

这里的 `PublishResult` 仅表示代理按其协议接受了消息，不代表消费者已经完成业务处理。

正式实现还应根据所选代理补充确认模式、消费取消、关闭流程、死信转移、重放权限和可观测性接口。不同代理的确认语义应封装在 Adapter 内，不能泄漏到业务逻辑中。

## 5. Transactional Outbox：解决数据库与消息队列之间的一致性

这是 ODAP 分布式可靠执行体系中最重要的机制之一。

### 5.1 为什么需要 Outbox

考虑如下代码：

```
1. 更新 run_steps 状态为 SUCCEEDED
2. 向消息队列发布 StepCompleted
```

如果数据库提交成功后，消息队列发布失败，就会出现：

- 数据库认为步骤已经完成。
- Orchestrator 没有收到完成事件。
- 下游步骤可能永远无法调度。

如果先发消息、再提交数据库事务，则可能出现相反的问题：消费者收到事件，但对应状态更新最终回滚。

Transactional Outbox 的核心思想是：把业务状态变更和待发布事件写入同一个数据库事务。

事务提交后，独立 Publisher 再把 Outbox 中的事件发送到消息代理。

### 5.2 Outbox 工作流程

Worker / Orchestrator 执行业务变更

PostgreSQL 单事务

更新业务状态 + 插入 Outbox Event

Outbox Publisher 扫描未发布事件

Event Bus 接受消息

标记 Outbox 已发布

注意最后两步之间仍然可能发生故障：消息代理已经接受事件，但 Publisher 在标记已发布之前崩溃。恢复后事件可能再次发送。

这是预期行为。Outbox 解决的是“业务状态与待发布事件不会只提交一边”的问题，它不保证消息只发布一次。下游仍然必须去重。

### 5.3 Outbox 表设计

```

CREATE TABLE outbox_events (
    event_id          UUID PRIMARY KEY,
    tenant_id         UUID NOT NULL,

    aggregate_type    TEXT NOT NULL,
    aggregate_id      UUID NOT NULL,
    aggregate_seq     BIGINT NOT NULL,

    event_type        TEXT NOT NULL,
    schema_version    TEXT NOT NULL,
    payload           JSONB NOT NULL,
    payload_digest    TEXT NOT NULL,

    occurred_at       TIMESTAMPTZ NOT NULL DEFAULT now(),
    available_at      TIMESTAMPTZ NOT NULL DEFAULT now(),

    status            TEXT NOT NULL DEFAULT 'PENDING',
    attempt_count     INT NOT NULL DEFAULT 0,
    published_at      TIMESTAMPTZ,

    claimed_by        TEXT,
    claim_until       TIMESTAMPTZ,
    last_error_code   TEXT,
    last_error_at     TIMESTAMPTZ,

    created_at        TIMESTAMPTZ NOT NULL DEFAULT now(),

    UNIQUE (
        tenant_id,
        aggregate_type,
        aggregate_id,
        aggregate_seq
    ),

    CHECK (status IN (
        'PENDING',
        'DISPATCHING',
        'SENT',
        'FAILED',
        'DEAD'
    ))
);

CREATE INDEX idx_outbox_pending
    ON outbox_events (available_at, created_at)
    WHERE status = 'PENDING';

CREATE INDEX idx_outbox_expired_claim
    ON outbox_events (claim_until)
    WHERE status = 'DISPATCHING';

```

生产实现中，`aggregate_seq` 的分配必须与聚合状态更新保持一致。不同聚合之间不要求全局连续序号；如果某个事件类型不需要严格排序，也不必强行实现全局排序。

**aggregate_seq 分配机制：每聚合一行计数器。** 每个聚合（`aggregate_type`，`aggregate_id`）在计数表中独占一行，领取序号即对该行执行行锁更新，且与聚合状态更新处于同一数据库事务：

```
CREATE TABLE aggregate_seq_counters (
    aggregate_type TEXT NOT NULL,
    aggregate_id   UUID NOT NULL,
    next_seq       BIGINT NOT NULL DEFAULT 1,
    updated_at     TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (aggregate_type, aggregate_id)
);
```

```
BEGIN;

-- 1. 领取序号：行锁分配，与状态更新同事务
UPDATE aggregate_seq_counters
SET next_seq = next_seq + 1,
    updated_at = now()
WHERE aggregate_type = $1
  AND aggregate_id = $2
RETURNING next_seq - 1 AS aggregate_seq;

-- 2. 用领取到的 aggregate_seq 写入 Outbox 事件行
-- 3. 同一事务内完成聚合状态更新
COMMIT;
```

行锁在事务提交前持续持有，因此同一聚合内不可能出现两个并发事务领到相同序号；状态更新回滚时计数器同步回滚，不会留下空洞。

明确不采用两种方案：

- 数据库序列（`SEQUENCE`）：事务回滚不归还已取出的值，必然留下永久空洞，与 §12.3 的缺口检测冲突，会把正常回滚误报为乱序。
- `SELECT max(aggregate_seq) + 1`：并发领取会读到相同最大值，产生唯一约束冲突后只能重试，高并发下成为热点，且无法与状态更新保持同一事务的一致性。

由于序号由行锁在同一事务内分配，正常情况下不存在序号空洞；§12.3 的缺口检测相应放宽——发现缺口时优先按"发布延迟或在途"处理（进入缺口等待窗口，见 §12.3），只有超出等待窗口才触发恢复重读，不得把每个暂时缺口都当作数据损坏。

### 5.4 Publisher 并发领取

多个 Publisher 可以使用 PostgreSQL 行锁和 `SKIP LOCKED` 领取不同的事件。发布采用两段式：先在短事务内领取并置为 `DISPATCHING`，再在事务之外调用消息代理，最后用短事务标记 `SENT` 或 `FAILED`。不能把"领取 + 发布"放进同一个事务——那会让数据库事务覆盖消息代理的往返时间，行锁与连接被长时间持有。

第一段：短事务领取（PENDING → DISPATCHING）

```
BEGIN;

WITH picked AS (
    SELECT event_id
    FROM outbox_events
    WHERE status = 'PENDING'
      AND available_at <= now()
    ORDER BY created_at, event_id
    FOR UPDATE SKIP LOCKED
    LIMIT 100
)
UPDATE outbox_events AS o
SET status = 'DISPATCHING',
    claimed_by = $1,
    claim_until = now() + interval '30 seconds',
    attempt_count = attempt_count + 1
FROM picked
WHERE o.event_id = picked.event_id
RETURNING o.*;

COMMIT;
```

第二段：事务外发布。Publisher 对领取出的批量事件（批量上限 100 条/批）在数据库事务之外调用消息代理。代理按其协议接受消息后，用第三个短事务标记 `SENT` 并写入 `published_at`：

```
BEGIN;

UPDATE outbox_events
SET status = 'SENT',
    published_at = now()
WHERE event_id = ANY($1)
  AND status = 'DISPATCHING';

COMMIT;
```

发布失败则在同一模式的事务中标记 `FAILED`，记录 `last_error_code`、`last_error_at`，并按退避策略写回 `available_at`；超过最大尝试次数的事件置为 `DEAD`，转入死信处理（§17）。

过期的 `DISPATCHING` 事件（`claim_until < now()`，即领取后进程崩溃）由恢复任务重新置为 `PENDING` 后重新领取。若进程崩溃导致重复发布，不应把重复发布视为数据损坏：Outbox 解决的是"业务状态与待发布事件不会只提交一边"，不保证只发布一次，下游按事件 ID 去重（§6）。

空转指数退避：扫描未领取到任何事件时，Publisher 进入指数退避而不是忙轮询——初始间隔 100ms，每轮空转翻倍，上限 5s；一旦领取到事件或收到唤醒信号，退避立即复位。退避应加入随机抖动（§10.2），避免多 Publisher 形成同步脉冲式扫描。

### 5.5 Outbox 的运行治理

建议监控：

- 最老未发布事件的年龄。
- 待发布事件数量。
- Publisher 每秒处理量。
- 事件发布失败率。
- 过期领取数量。
- 死信事件数量。
- 数据库锁等待时间。

Outbox 不是无限期的事件档案。已经发布的事件应按照保留策略归档或清理，但清理前必须确认审计、排障和恢复所需的事件记录已安全保留。

## 6. 消费者幂等：把重复投递变成安全的重复处理

消息代理可能重复投递消息，Publisher 可能重复发布事件，消费者也可能在业务处理完成后、确认消息前崩溃。

因此，ODAP 应把至少一次投递 + 幂等消费作为默认可靠性模型，而不是依赖消息代理提供“恰好一次”语义来保证整个业务流程没有重复副作用。

### 6.1 为什么重复消息不可避免

假设消费者收到 `StepCompleted`：

1. 消费者读取消息。
2. 更新 Orchestrator 状态。
3. 数据库提交成功。
4. 消费者尚未确认消息就崩溃。
5. 消息代理重新投递同一事件。

如果没有幂等机制，消费者可能重复创建后续步骤、重复扣减预算或重复发送命令。

因此，需要区分三种幂等：

- 消息幂等：同一事件不会被重复应用到本地消费状态。
- 业务幂等：同一逻辑业务动作不会重复产生不应重复的状态变更。
- 外部操作幂等：同一逻辑操作到达 ERP 或其他外部系统时，不会产生重复副作用。

三者相关，但不能互相替代。

### 6.2 Inbox 表设计

建议为每个有持久化副作用的消费者使用 Inbox 表，或者使用统一消费账本并以消费者组区分处理进度。

```
CREATE TABLE consumer_inbox (
    consumer_name  TEXT NOT NULL,
    event_id       UUID NOT NULL,
    tenant_id      UUID NOT NULL,

    payload_digest TEXT NOT NULL,
    status         TEXT NOT NULL DEFAULT 'RECEIVED',

    received_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    processed_at   TIMESTAMPTZ,
    last_error     TEXT,

    PRIMARY KEY (consumer_name, event_id),

    CHECK (status IN (
        'RECEIVED',
        'PROCESSED',
        'FAILED'
    ))
);
```

这里使用 `(consumer_name, event_id)` 作为唯一键，因为同一个事件可以被多个不同消费者合法处理一次。

**Inbox 增长治理。** `consumer_inbox` 随事件量持续增长，而去重语义不能被分区破坏，采用"去重键表 + 按时间分区的处理记录表"两张表：

1. `consumer_inbox_dedup(consumer_name, event_id)`：不分区，主键即全局唯一约束，插入冲突即判重（§6.3 的 `insertInboxIfAbsent` 落在该表）。表体积小（每消费者每事件一行），按事件保留策略整体清理。
2. `consumer_inbox`：按 `received_at` 做范围分区（按周或月），保存处理记录与诊断，不再承载全局唯一约束；`PROCESSED` 行按保留期（默认 30 天，审计要求更长时按租户配置）整分区清理（DROP 或 DETACH 分区），避免逐行 DELETE 造成表膨胀。

原因：PostgreSQL 要求分区表的唯一约束必须包含全部分区键。若直接对 `consumer_inbox` 按 `received_at` 分区并把唯一约束改为 `(consumer_name, event_id, received_at)`，同一事件在不同时间到达即可插入两行，去重被静默破坏。把唯一约束留给不分区的小表、把增长留给可整片清理的大表，两者兼顾。清理前必须确认审计、排障与恢复所需记录已安全归档（§15.3、§16.4）。

### 6.3 正确的消费事务

对于能够在同一 PostgreSQL 数据库事务中完成的业务处理，推荐采用以下模式：

```
BEGIN

1. 插入 Inbox 记录
2. 如果已存在已处理记录，则直接结束
3. 验证事件 Schema 与 Payload Digest
4. 更新权威业务状态
5. 创建后续步骤或命令
6. 写入新的 Outbox 事件
7. 标记 Inbox 为 PROCESSED

COMMIT

8. 按消息代理协议确认消息
```

核心 Go 伪代码：

```

func HandleEvent(
    ctx context.Context,
    msg Message,
) error {
    tx, err := db.BeginTx(ctx, nil)
    if err != nil {
        return err
    }
    defer tx.Rollback()

    inserted, err := insertInboxIfAbsent(
        ctx, tx, msg,
    )
    if err != nil {
        return err
    }

    if !inserted {
        state, err := getInboxState(
            ctx, tx, msg,
        )
        if err != nil {
            return err
        }

        if state == "PROCESSED" {
            return tx.Commit()
        }

        // 生产实现应对 FAILED/RECEIVED
        // 使用受控的恢复或重试策略。
    }

    if err := validateMessage(msg); err != nil {
        return err
    }

    if err := applyBusinessTransition(
        ctx, tx, msg,
    ); err != nil {
        return err
    }

    if err := insertOutboxEvents(
        ctx, tx, msg,
    ); err != nil {
        return err
    }

    if err := markInboxProcessed(
        ctx, tx, msg,
    ); err != nil {
        return err
    }

    return tx.Commit()
}

```

这段代码强调事务边界，并非可直接复制的完整消费者实现。正式代码需要处理并发插入冲突、失败记录、租约、事务重试和消息确认接口。

特别要注意：如果业务处理涉及外部 API 调用，不能把外部调用放在上述数据库事务里并假设两者能够原子提交。应先持久化命令，再由独立 Worker 调用外部服务，并依靠幂等键和操作账本管理结果。

### 6.4 事件 ID 冲突与摘要不一致

如果相同 `event_id` 再次到达，系统还应比较 `payload_digest`。

- ID 相同、摘要相同：视为重复投递。
- ID 相同、摘要不同：视为完整性或生产者缺陷，进入隔离队列并报警。

不能简单地把所有唯一键冲突都当作正常重复消息，否则可能掩盖事件 ID 被错误复用或数据被篡改的问题。

## 7. Worker Pool：分布式任务执行器

Worker 是实际执行 Agent、工具、模型调用和后台作业的运行单元。它必须是可替换、可扩容、可恢复的进程，而不能把任务状态保存在某个 Worker 的内存里作为唯一依据。

### 7.1 Worker 的职责边界

一个 Worker 应具备：

- 注册自身能力与健康状态。
- 从受控队列或任务存储中领取工作。
- 检查任务是否仍然有效。
- 获取或续约任务租约。
- 执行被分配的步骤。
- 持久化输出、证据和状态。
- 处理取消、截止时间与预算限制。
- 释放执行资源并上报指标。

Worker 不应该：

- 自行决定跳过前置步骤。
- 自行修改正式本体或授权策略。
- 将内存中的结果当作持久化成功。
- 在租约失效后继续提交普通业务状态。
- 绕过 ERP Gateway 直接写入 ERP。
- 因为消息重复就重新发起不具备幂等保障的外部操作。

### 7.2 工作队列与能力路由

ODAP 中的工作类型并不完全相同。建议将任务按能力分类，而不是把所有工作放入一个无差别的队列。

例如：

| 队列类别                  | 任务                  |
| --------------------- | ------------------- |
| `agent.execution`     | Agent 推理与结构化输出      |
| `tool.execution`      | 受控工具执行              |
| `ontology.validation` | 本体验证和规则检查           |
| `erp.operation`       | 通过 ERP Gateway 执行操作 |
| `reconciliation`      | 外部操作状态查询与对账         |
| `maintenance`         | 清理、归档、健康检查          |

队列分类是调度提示，不是授权机制。即使某个 Worker 被分配到 `erp.operation` 队列，它仍然只能通过 ERP Gateway 和权限引擎执行已授权的操作。

### 7.3 Worker 能力声明

建议 Worker 在注册时声明：

```
{
  "worker_id": "worker-agent-03",
  "version": "1.0.0",
  "capabilities": [
    "agent.execution",
    "structured-output-validation"
  ],
  "max_concurrency": 8,
  "status": "READY"
}
```

生产系统中应进一步限制声明的可信来源，并将能力与 Worker 镜像摘要、插件允许范围、资源配置及安全策略关联。Worker 自行声明某项能力，不代表系统自动授予它相应的业务权限。

### 7.4 执行资源隔离

建议至少将以下资源分开控制：

- Go Worker 进程并发。
- 每个任务的 Goroutine 与连接数。
- LLM Gateway 并发与 Token 预算。
- 工具插件 CPU、内存和执行时间。
- 数据库连接池。
- ERP Adapter 的外部请求并发。
- 长任务与短任务的调度优先级。

高延迟的模型调用不能无限占用所有 Worker，低成本的后台任务也不能耗尽 ERP 操作所需的数据库连接。

## 8. 任务租约、心跳与执行所有权

在多节点环境中，可能出现两个 Worker 同时认为自己有权执行同一任务的情况。任务租约可以降低这种风险，但必须正确处理过期、续约与旧 Worker 复活的问题。

### 8.1 Lease 数据模型

建议在 `run_steps` 或独立的工作领取表中保存：

- `lease_owner`
- `lease_until`
- `lease_epoch`
- `heartbeat_at`
- `attempt_count`
- `worker_id`
- `execution_started_at`

其中 `lease_epoch` 是单调递增的所有权代次，也可称为 fencing token（栅栏令牌）。

当新 Worker 取得租约时，系统递增 `lease_epoch`。旧 Worker 即使因为网络分区或进程暂停而恢复，也必须证明自己仍持有当前代次，才能提交允许受此机制保护的状态变更。

### 8.2 领取任务

下面给出 PostgreSQL 领取任务的简化示例：

```

WITH candidate AS (
    SELECT step_id
    FROM run_steps
    WHERE status IN ('READY', 'RETRY_WAIT')
      AND scheduled_at <= now()
      AND (
          lease_until IS NULL
          OR lease_until < now()
      )
    ORDER BY priority DESC, scheduled_at, step_id
    FOR UPDATE SKIP LOCKED
    LIMIT 1
)
UPDATE run_steps AS s
SET status = 'RUNNING',
    lease_owner = $1,
    lease_until = now() + interval '45 seconds',
    lease_epoch = s.lease_epoch + 1,
    heartbeat_at = now(),
    attempt_count = s.attempt_count + 1
FROM candidate
WHERE s.step_id = candidate.step_id
RETURNING s.*;

```

领取语义说明：Step 领取后直接进入 `RUNNING`（词汇对齐 contracts/01 §2，不再单设 `CLAIMED` 状态）；"已领取但尚未开始执行"的中间态由 `lease_owner`/`lease_epoch`/`heartbeat_at` 表达，避免状态膨胀与两层词表漂移。`run_steps` 的权威 DDL 以第二篇 §6.2 为准（含 `READY`/`RETRY_WAIT`/`RECONCILING` 等 12 态）。

注意，正式 Schema 必须先定义 `scheduled_at`、`priority`、`lease_epoch` 等字段。该示例展示的是领取语义，不是前文所有字段的完整迁移脚本。

### 8.3 续约

Worker 应定期续约。续约时必须检查当前所有权和代次：

```
UPDATE run_steps
SET lease_until = now() + interval '45 seconds',
    heartbeat_at = now()
WHERE step_id = $1
  AND lease_owner = $2
  AND lease_epoch = $3
  AND status IN ('RUNNING');
```

如果影响行数为零，说明 Worker 已失去当前执行权，或者步骤状态已经变化。Worker 应停止发起新的副作用，并向协调器报告失去租约。

### 8.4 租约过期不等于执行失败

假设一个 Worker 正在调用耗时较长的模型服务。由于网络延迟，心跳没有及时写入数据库，租约过期，另一个 Worker 领取了该任务。

此时可能出现两个进程同时运行。因此，ODAP 不能仅依赖租约防止重复执行，还必须结合：

- 数据库中的状态条件更新。
- `lease_epoch` 代次校验。
- 步骤幂等键。
- 外部操作的独立幂等机制。
- 对不确定结果的恢复与对账。

对 LLM 纯推理步骤，重复调用通常主要带来成本和结果不一致风险；对 ERP 写入步骤，重复调用可能产生真实业务副作用。二者应采用不同的恢复策略。

### 8.5 租约时间设计

租约时长应结合 Worker 心跳间隔、数据库写入延迟、网络抖动和任务类型设定。不能对所有任务统一使用过短的租约，也不宜设置过长的租约导致故障恢复缓慢。

对于需要长时间等待外部响应的任务，Worker 可以使用短周期心跳续约，但不得将租约机制当作外部操作取消机制。

## 9. Harness 与分布式状态机的整合

前六篇和第八篇已经设计了 Harness 的执行状态机。本篇不是另建一套状态机，而是补充多 Worker 环境下的持久化调度和恢复规则。

### 9.1 Run 与 Step 状态分离

Run 表示整个业务任务的状态，Step 表示一个具体工作单元的状态。两者不能简单共用一套状态枚举。

**Run 与 Step 的权威状态词表以 `docs/contracts/01-全局状态注册表.md` 为准**（Run 17 态、Step 12 态），本篇不得另行定义。本篇早期版本的自有词表按如下映射收编：

| 本篇旧值 | 收编到（contracts/01） | 说明 |
|---|---|---|
| Run `QUEUED` | Run `READY` | 排队语义由 `available_at` 与执行队列表达 |
| Run `WAITING_EXTERNAL` | Run `REQUIRES_RECONCILIATION` | 外部结果未知，进入对账 |
| Run `SUCCEEDED` | Run `COMPLETED` | 同义 |
| Step `QUEUED` | Step `READY` | 依赖已满足、可被领取 |
| Step `CLAIMED` | Step `RUNNING` | 领取与开始执行不拆两个状态；所有权代次由 `lease_epoch` 记录（见 §8.2） |
| Step `WAITING_EXTERNAL` | Step `UNKNOWN` | 外部副作用结果未知；对账中为 `RECONCILING` |

Run 状态全景（17 态，含转换矩阵）见 contracts/01 §1 与第六篇 §14.2；Step 状态全景见 contracts/01 §2。本篇 §9.2 的转换表是 Step 层的调度视角，与第六篇 Run 层矩阵通过 `StepStarted/StepSucceeded/StepFailed` 事件衔接，两层不得互相推断（第六篇 §3 四层状态机）。

### 9.2 状态转换规则（Step 层，词汇对齐 contracts/01）

| 当前状态               | 事件或条件       | 新状态                | 执行要求          |
| ------------------ | ----------- | ------------------ | ------------- |
| `PENDING`          | 前置条件满足      | `READY`            | 持久化调度事件       |
| `READY`            | Worker 成功领取 | `RUNNING`          | 创建租约，递增 `lease_epoch` |
| `RUNNING`          | 结果持久化成功     | `SUCCEEDED`        | 原子写状态与 Outbox |
| `RUNNING`          | 可重试错误       | `RETRY_WAIT`       | 记录退避时间        |
| `RUNNING`          | 等待人工审批      | `WAITING_APPROVAL` | 持久化暂停点        |
| `RUNNING`          | 外部操作结果未知    | `UNKNOWN`          | 进入对账流程（Run 层同步转 `REQUIRES_RECONCILIATION`） |
| `RETRY_WAIT`       | 达到调度时间      | `READY`            | 再次进入工作队列      |
| `WAITING_APPROVAL` | 审批完成        | `READY`            | 重新检查权限和前置条件   |
| `UNKNOWN`          | 对账确认成功      | `SUCCEEDED`        | 记录外部回执        |
| `UNKNOWN`          | 对账确认未执行     | `RETRY_WAIT` 或 `FAILED` | 按操作能力与策略处理    |

状态转换必须由服务端校验，不允许 Worker 通过任意写入状态字段跳过合法路径。

### 9.3 Step 完成与后续调度的事务边界

一个常见错误是先把 Step 标记为成功，然后异步通知 Orchestrator 创建下一步。如果通知丢失，流程会停滞。

建议把以下动作放在同一个 PostgreSQL 事务中：

1. 检查当前 `lease_epoch`。
2. 将 Step 状态改为 `SUCCEEDED`。
3. 保存输出引用、摘要和证据索引。
4. 更新 Run 的版本号或状态摘要。
5. 写入 `StepCompleted` Outbox 事件。

后续步骤可以由 Orchestrator 消费事件后创建，也可以由恢复控制器重新扫描并计算依赖。无论哪种方式，都必须能够在事件丢失或重复的情况下恢复。

如果选择让 Orchestrator 在同一事务中创建后续步骤，则需要避免把 DAG 的全部业务计算塞进数据库事务。推荐只将必要的状态更新、唯一键保护和待发布事件放在事务中，复杂的计划计算放在事务外。

### 9.4 检查点设计

Harness 检查点至少应记录：

- 当前 Run 与 Step。
- 已完成的前置步骤。
- 计划版本和 DAG 摘要。
- 当前执行位置。
- 已持久化的输入输出引用。
- 已完成的工具调用和外部操作 ID。
- 已使用的模型、本体、规则与映射版本。
- 已建立的审批记录。
- 当前预算状态和截止时间。
- 恢复策略与最近的状态版本。

检查点应引用持久化制品，而不是只保存进程内存中的对象。对于较大的 Prompt、模型响应或文件附件，建议保存对象存储引用、摘要、内容类型与访问策略，不应将全部原始内容塞进 PostgreSQL JSONB 字段。

## 10. 重试、退避与失败分类

可靠执行不等于无限重试。ODAP 必须区分可重试错误、永久错误、需要人工处理的错误和结果未知的错误。

### 10.1 错误类别

| 类别                  | 示例              | 默认策略        |
| ------------------- | --------------- | ----------- |
| `TRANSIENT`         | 短暂网络故障、临时限流     | 有限重试        |
| `PERMANENT`         | Schema 不合法、参数缺失 | 失败并返回诊断     |
| `POLICY_DENIED`     | 授权失败、数据策略拒绝     | 不自动重试       |
| `CAPACITY_EXCEEDED` | 队列或预算已满         | 排队、限流或失败    |
| `CONFLICT`          | 对象版本冲突          | 重新读取并重新决策   |
| `UNKNOWN_OUTCOME`   | 外部请求超时且结果不明     | 对账或人工复核     |
| `CANCELLED`         | 任务取消            | 停止新增工作      |
| `DEADLINE_EXCEEDED` | 超过业务截止时间        | 终止或走明确的补偿流程 |

上表是内部重试分类，不是对外错误码。对外错误码以 docs/contracts/02-统一错误码注册表.md 为准：`CAPACITY_EXCEEDED` → `BUS_CAPACITY_EXCEEDED`（基础码 `RESOURCE_EXHAUSTED`），`CONFLICT` → `CONFLICT` 或 `BUS_SEQUENCE_GAP`，`UNKNOWN_OUTCOME` → `EXECUTION_UNKNOWN`（结果未知走对账，不盲目重发），`POLICY_DENIED` → `AUTHZ_*` 域码，`DEADLINE_EXCEEDED` → 同名基础码。Inbox 去重命中返回 `BUS_DUPLICATE_EVENT`（幂等成功路径，非错误场景记 INFO）。

### 10.2 指数退避

对于适合自动重试的暂时性错误，可以使用指数退避并加入随机抖动：

\\[ d_n=\min(d\_{\max},d_0\cdot 2^n)+J_n \\]

其中：

- \\(d_0\\) 为基础延迟。
- \\(d\_{\max}\\) 为最大退避上限。
- \\(J_n\\) 为随机抖动，用于降低大量 Worker 同时重试造成的峰值。
- \\(n\\) 为重试次数。

实际调度时还必须遵守任务截止时间、供应商 `Retry-After` 提示、预算限制和租户配额。

### 10.3 重试预算

每个步骤应定义：

- 最大尝试次数。
- 最大累计执行时间。
- 最大累计推理费用。
- 最大退避时间。
- 允许的错误类别。
- 是否允许跨模型切换。
- 是否允许转人工处理。

达到任一硬性上限后，应停止自动重试并生成可追踪的失败状态。

### 10.4 消息重试与业务重试的区别

消息处理失败时，消费者可能需要重新接收同一事件；业务步骤失败时，Harness 可能需要重新执行某个逻辑步骤。

两者不能混为一谈。例如：

- 消费 `StepScheduled` 时数据库暂时不可用：重试消费。
- Agent 返回非法 JSON：通常需要修正输入、受控重新生成或终止步骤。
- ERP 写操作超时且结果未知：不能直接重新执行，必须先对账。

不能因为消息队列支持重试，就把所有业务错误都映射为消息重试。

## 11. 外部副作用、ERP 操作与可靠执行

这是整个分布式执行设计中风险最高的部分。

ODAP 无法通过 PostgreSQL 事务和普通消息队列，自动获得对任意 ERP 的端到端“恰好一次”执行保证。ERP 可能已提交操作，但响应在网络中丢失；本地系统无法单凭超时判断远端是否执行成功。

因此，必须延续第七篇的 ERP Gateway、幂等键和操作账本设计。

### 11.1 外部操作的独立账本

一次外部操作应具有稳定的业务操作 ID：

```
run_id
  └── step_id
       └── erp_operation_id
            ├── idempotency_key
            ├── payload_digest
            ├── authorization_decision_id
            ├── approval_id
            ├── remote_operation_id
            └── reconciliation_status
```

Worker 重启、消息重投或租约变更，都不能为同一逻辑操作重新生成一个完全无关的操作 ID。

如果请求内容发生变化，应创建新的、经过业务规则允许的操作版本或操作记录，而不是沿用原幂等键发送不同载荷。

### 11.2 外部操作状态机

```
CREATED
   ↓
VALIDATED
   ↓
AUTHORIZED
   ↓
DISPATCH_PENDING
   ↓
DISPATCHED
   ├── SUCCEEDED
   ├── FAILED
   └── UNKNOWN
          ↓
     RECONCILING
          ├── CONFIRMED_SUCCEEDED
          ├── CONFIRMED_NOT_EXECUTED
          └── MANUAL_REVIEW
```

关键点：

- `DISPATCHED` 表示已尝试发送请求，不代表 ERP 已经提交。
- `UNKNOWN` 表示目前不能可靠确定结果。
- `CONFIRMED_NOT_EXECUTED` 必须有足够证据支持，不能因为查询不到就随意认定没有执行。
- `MANUAL_REVIEW` 是明确的受控状态，不是系统异常后丢弃任务。

### 11.3 事务发件箱与外部操作

建议将 ERP 操作的本地准备与发送命令写入同一事务：

1. 检查当前步骤状态。
2. 创建或确认唯一的 ERP Operation 记录。
3. 固化 Payload Digest 和幂等键。
4. 记录授权与审批引用。
5. 写入 `ERPOperationDispatchRequested` Outbox 事件。
6. 提交事务。

独立的 ERP Dispatch Worker 再消费事件并调用 ERP Gateway。

如果 Dispatcher 崩溃后重新消费事件，必须先检查操作账本：

- 操作尚未发出：按策略发出请求。
- 已发出且结果未知：查询远端状态或启动对账。
- 已确认成功：不再执行。
- 请求摘要不一致：拒绝继续执行并报警。

具体能否安全重发，还取决于第七篇所定义的 ERP 能力等级、远端幂等支持和结果查询能力。

### 11.4 租约失效后的副作用处理

假设 Worker A 已经发起 ERP 操作，随后租约过期；Worker B 领取任务并发现操作记录存在。

Worker B 不能仅因自己拥有新租约就再次发送请求。它必须先查询操作账本并依据状态决定下一步。

这也是为什么任务租约与 ERP 幂等键必须并存：租约控制本地执行所有权，幂等键和操作账本控制外部副作用。

### 11.5 补偿与 Saga

对于由多个外部业务步骤组成的流程，可以使用 Saga 思路管理补偿动作，但不能假设每个操作都有可逆的补偿。

例如，报销流程中已经成功创建报销单，后续步骤失败，并不意味着可以直接删除报销单。可能需要撤回申请、取消单据或进入人工处理，具体取决于 ERP 工作流与企业制度。

每个 Saga 步骤应声明：

- 正向操作。
- 是否存在补偿操作。
- 补偿的前置条件。
- 补偿的权限与审批要求。
- 补偿失败时的处置。
- 是否允许人工接管。

补偿动作本身也是外部操作，同样需要操作账本、幂等键、授权、审计和结果确认。

**补偿编排归属。** 补偿不建第三套编排引擎：每个补偿动作定义为 Harness 计划中的特殊 Step 类型（`COMPENSATION`），复用第六篇 Harness 状态机与第八篇 Plan Compiler 的编译、授权、审批、租约与对账机制。Saga 只描述"哪个步骤失败时应触发哪些补偿 Step"的依赖关系，不定义独立的状态机或调度器；补偿 Step 与正向 Step 共用同一套 Outbox 发布、Inbox 去重与 Recovery Controller 恢复链路（§5、§6、§14）。

## 12. 事件顺序、分区与并发控制

分布式消息系统通常不能为所有事件提供全局有序保证。ODAP 不应假定跨队列、跨分区和跨消费者的事件天然按业务顺序到达。

### 12.1 哪些事件需要有序

建议按业务聚合划分顺序范围：

- 同一个 Run 的关键状态事件。
- 同一个 Step 的状态转换。
- 同一个 ERP Operation 的派发与回执事件。
- 同一个审批请求的状态事件。
- 同一个预算账户的扣减与结算事件。

不同 Run 之间通常不需要全局排序，否则会严重限制扩展性。

### 12.2 分区键

推荐使用稳定的业务聚合标识作为分区键：

| 事件类别      | 建议分区键                |
| --------- | -------------------- |
| Run 生命周期  | `run_id`             |
| Step 生命周期 | `step_id` 或 `run_id` |
| ERP 操作    | `erp_operation_id`   |
| 审批流程      | `approval_id`        |
| 租户级预算     | `tenant_id` 或预算账户 ID |

选择 `tenant_id` 可以集中同一租户事件，但可能导致大租户形成热点。选择 `run_id` 通常能提升并行度，但同一租户的预算事件仍需要通过预算服务的原子操作保障正确性。

### 12.3 聚合序号与乱序检测

每个需要顺序保证的聚合可以维护 `aggregate_seq`。

消费者收到事件时：

- 序号等于预期值：正常处理。
- 序号小于或等于已处理值：可能是重复或过期事件，应验证 Inbox 与业务状态。
- 序号大于预期值：发现缺口，应延迟处理、重新读取权威状态或触发恢复机制。

但并非所有业务都必须强制等待连续序号。例如，非关键遥测事件可以允许跳过中间序号；关键状态转换则应使用更严格的校验。

**缺口等待窗口。** 发现序号缺口（序号大于预期值）时不立即判定乱序，而是进入缺口等待窗口：

1. 窗口时长默认 30 秒，或按该聚合剩余 deadline 的 10% 取值（取较小者）；窗口内缺口被后续事件补齐，则按序正常处理。
2. 窗口超限仍未补齐：消费者触发 Recovery Controller 重读权威状态（Run / Step / ERP Operation 的当前状态与已处理序号，§14.2），以权威状态为准校准消费位点。
3. 权威状态也无法解释缺口时，按 `BUS_SEQUENCE_GAP`（基础码 `CONFLICT`，见 docs/contracts/02-统一错误码注册表.md §3.5）告警并进入隔离或人工诊断，不得静默跳过。
4. 联动路径：缺口等待窗口计时 → 超限 → Recovery Controller 重读权威状态并复位消费位点 → 仍异常则升级死信或人工处置（§17）。关键状态转换采用严格校验；非关键遥测事件可配置为跳过缺口并记 INFO。

### 12.4 乐观并发控制

对 Run、Step 和 ERP Operation 的状态更新，建议结合版本号进行乐观并发控制：

```
UPDATE runs
SET status = $1,
    version = version + 1,
    updated_at = now()
WHERE run_id = $2
  AND tenant_id = $3
  AND version = $4;
```

如果影响行数为零，说明当前状态已经变化或调用方使用了过期版本。系统应重新读取权威状态，再决定是否重试，而不是直接覆盖新状态。

## 13. 任务取消、暂停与人工审批

企业级智能体平台中的任务经常需要等待人工审批、外部系统或数据补充。因此，取消和暂停必须是持久化的业务状态，而不能仅仅取消一个 Go `context.Context`。

### 13.1 取消语义

建议定义三种取消相关状态：

- `CANCEL_REQUESTED`：已接受取消请求，但正在协调执行中的工作。
- `CANCELLED`：平台已确认任务进入取消终态。
- `CANCELLED_WITH_PENDING_EFFECTS`：任务停止继续执行，但仍有未确认的外部操作，需要对账或人工处理。

第三种状态是否直接作为 Run 状态，应根据 ODAP 的统一状态枚举决定；也可以保留 `CANCELLED` 并附加 `pending_effects=true`。无论采用哪种模型，都不能在仍有未知外部副作用时展示为“所有业务影响均已撤销”。

### 13.2 取消流程

1. API Server 检查取消权限。
2. 在事务中写入取消请求和 Outbox 事件。
3. Run 协调器停止调度新的普通步骤。
4. 向当前 Worker 发送取消信号。
5. Worker 取消可取消的模型调用或工具任务。
6. 已发出的外部操作继续被追踪和对账。
7. 汇总各步骤状态。
8. 持久化最终取消状态与审计事件。

对于尚未执行的步骤，可以直接转为 `CANCELLED`；对于已经发出的 ERP 操作，则应继续追踪其最终结果。

### 13.3 取消与租约的关系

取消请求不应直接删除 Worker 的租约记录。系统需要先协调当前执行者并确认任务状态。

如果 Worker 失联，恢复控制器可以收回平台内的任务所有权，但不能因此假定外部请求已经停止。

### 13.4 人工审批与恢复

人工审批是一种长期暂停点：

```
RUNNING
   ↓
WAITING_APPROVAL
   ↓
Approval Service 产生决定
   ↓
审批事件写入 Outbox
   ↓
Harness 恢复调度
   ↓
重新检查权限、版本和业务前置条件
   ↓
QUEUED
```

恢复时应重新验证：

- 当前用户和服务的权限是否仍然有效。
- 审批绑定的请求摘要是否与待执行载荷一致。
- 相关本体、规则和映射版本是否仍可使用。
- 目标 ERP 对象是否发生变化。
- 任务是否已超过截止时间。
- 预算是否仍然足够。

不能因为审批已经通过，就跳过这些检查。

## 14. 延迟任务、定时调度与恢复控制器

不是所有任务都应立即进入消息队列。重试、定时触发、审批等待、外部系统等待和周期性维护都需要延迟调度能力。

### 14.1 不要把延迟任务仅存在消息代理中

建议将 `scheduled_at`、截止时间和当前状态持久化在 PostgreSQL 中，消息代理仅负责通知 Worker 有可执行任务。

这样，即使消息代理清空了某个队列或发生数据迁移，ODAP 仍然可以从权威任务表中恢复尚未执行的工作。

### 14.2 Recovery Controller 的职责

建议将恢复控制器设计为独立的逻辑模块，可以先与 Orchestrator 部署在同一个进程中，后续再独立扩展。

其职责包括：

- 扫描过期租约。
- 查找长期停留在 `QUEUED` 的任务。
- 检查 Outbox 的发布积压。
- 恢复未完成的步骤与依赖调度。
- 检查超时审批和外部等待任务。
- 扫描 `UNKNOWN` 状态的 ERP 操作。
- 处理死信事件与可恢复失败。
- 检测任务截止时间和预算超限。
- 产生恢复审计事件。

### 14.3 恢复扫描规则

| 异常情况                     | 处理建议               |
| ------------------------ | ------------------ |
| Outbox 长期未发布             | 重新领取并发布，超过阈值报警     |
| Worker 租约过期              | 检查步骤与副作用状态，再决定重新排队 |
| Run 长期无进展                | 读取状态、检查依赖与队列积压     |
| Step 处于 `RETRY_WAIT` 且到期 | 重新调度               |
| 审批长期未处理                  | 通知、升级或按策略终止        |
| ERP 操作结果未知               | 查询远端状态并对账          |
| 事件进入死信队列                 | 诊断、修复或人工重放         |
| Run 已取消但仍有运行中步骤          | 协调 Worker，追踪外部副作用  |
| 预算已耗尽                    | 停止新增调用，保存可恢复状态     |

恢复控制器不能简单地把所有超时步骤重新置为 `QUEUED`。它必须根据步骤类型判断：纯计算、模型调用、工具执行和 ERP 写操作的安全重试条件并不相同。

## 15. 数据库 Schema 补充设计

ODAP 前两篇已经定义了 Run、Step、Checkpoint、Approval、ERP Operation、Receipt 和审计相关表。本篇建议在原有 Schema 上扩展，而不是重复创建同义数据表。

### 15.1 推荐的表清单

| 表                               | 作用             |
| ------------------------------- | -------------- |
| `outbox_events`                 | 保存待发布事件        |
| `consumer_inbox`                | 记录消费者已接收或处理的事件 |
| `event_subscriptions`           | 管理订阅配置与版本      |
| `event_dead_letters`            | 保存无法自动处理的事件    |
| `worker_instances`              | Worker 实例与健康状态 |
| `worker_leases` 或扩展 `run_steps` | 管理任务租约与执行代次    |
| `task_attempts`                 | 保存每次步骤执行尝试     |
| `recovery_jobs`                 | 记录恢复任务及其处理结果   |
| `event_archive`                 | 按策略保存历史事件归档    |

如果使用消息代理提供的持久化队列，`event_subscriptions` 不一定要保存全部消费位点；但 ODAP 仍应保留足以排查业务处理、关联任务和管理重放的元数据。

### 15.2 Task Attempt 数据模型

建议将步骤定义与每次执行尝试分离。

一个 `run_step` 代表逻辑工作单元，而 `task_attempts` 记录它被执行了多少次。

建议字段包括：

- `attempt_id`
- `tenant_id`
- `run_id`
- `step_id`
- `attempt_no`
- `worker_id`
- `lease_epoch`
- `started_at`
- `finished_at`
- `status`
- `error_code`
- `input_digest`
- `output_digest`
- `model_request_id`
- `erp_operation_id`
- `cost_estimate`
- `trace_id`

这样可以清楚区分“一个步骤最终成功”和“该步骤之前经历过三次失败与重试”。

### 15.3 数据保留与分区

事件账本、任务尝试和遥测数据可能持续增长，建议按数据用途设定不同保留策略：

- 当前任务状态：按业务生命周期长期保留。
- 执行尝试与审计记录：按企业治理和审计要求保留。
- Outbox 已发布记录：在安全归档后按策略清理。
- 高基数遥测：使用独立的指标与追踪后端。
- 大型输入输出：保存在对象存储，数据库保存摘要与受控引用。

对于高吞吐事件表，可评估按时间分区；对于需要高效去重的 Inbox 表，必须确认所选 PostgreSQL 分区策略不会削弱全局唯一性约束。不能只因为表增长就盲目分区。

Inbox 与死信的保留细节：

- `consumer_inbox`：唯一约束由不分区的 `consumer_inbox_dedup` 表承载，处理记录表按 `received_at` 范围分区，`PROCESSED` 行按保留期整分区清理（§6.2）。
- `event_dead_letters`：`payload_ref` 指向的载荷必须落入加密对象存储——使用租户级 KMS 数据密钥做信封加密，密钥引用与访问策略独立管理；数据库只保存不可逆的 `payload_digest` 与 `payload_ref`，不保存明文载荷。载荷 TTL 默认 90 天，到期删除并保留摘要与处置记录；`OPEN` / `INVESTIGATING` 状态的死信在 TTL 到期前 7 天提醒责任人，避免"加密了但没人处理"变成变相长期堆积。
- `outbox_events`：`SENT` 行在安全归档后（§16.4）按策略清理，保留期与审计要求取较长者。

### 15.4 RLS 与租户隔离

所有业务任务、Inbox、Outbox 和操作账本都应采用与 ODAP 既有架构一致的租户隔离方案。

注意：

- `tenant_id` 必须由可信服务上下文确定。
- 消息中的租户 ID 不能被直接当作授权证明。
- 消费者必须验证事件租户与目标业务对象租户一致。
- 重放工具必须执行与正常消费相同的租户与对象权限检查。
- 平台级维护 Worker 的跨租户访问应采用明确的服务身份与审计策略。

## 16. 事件版本兼容与重放治理

消息一旦进入持久化队列或历史归档，就可能在数小时、数天甚至数月后被重新消费。因此，事件 Schema 的演进必须成为平台工程的一部分。

### 16.1 版本管理

每个事件载荷应有独立的 `schema_version`。

例如：

```
{
  "event_type": "StepCompleted",
  "schema_version": "1.0.0",
  "event_id": "evt_123",
  "tenant_id": "tenant_01",
  "aggregate_id": "run_step_123",
  "aggregate_seq": 7,
  "payload": {
    "step_id": "run_step_123",
    "result_ref": "artifact_456"
  }
}
```

生产环境中的标识格式、UUID 类型和引用规则应与实际 API Schema 一致。示例中的引用值不代表可直接访问的资源地址。

### 16.2 兼容性原则

- 增加可选字段通常更容易兼容，但仍需考虑旧消费者的严格解析行为。
- 删除字段或改变字段语义属于高风险变更。
- 枚举新增值可能破坏只认识旧枚举的消费者。
- 时间、金额、状态和标识字段的语义变更必须特别谨慎。
- 不兼容变更应使用新 Schema 版本，并为消费者提供迁移或适配策略。

不能仅通过字符串版本号判断兼容性。应使用 Schema 契约测试，并验证旧生产者、新消费者和必要的反向组合。

### 16.3 事件重放

建议支持三种不同的操作：

1. 重试失败消费：重新处理某个消费者尚未成功处理的事件。
2. 重新投递事件：将原事件再次交给消费者，并保留原始事件 ID。
3. 业务补偿或重新执行：创建新的业务命令或 Run，而不是伪装成原事件重新发生。

重放工具应具有专门的权限、审计、影响预览和速率限制。

如果消费者已经完成了 ERP 写入，重新播放历史的 `StepScheduled` 事件可能造成严重风险。因此，重放时必须检查当前权威状态、Inbox 记录和外部操作账本，不能只清空消息确认记录就重新执行。

### 16.4 事件归档

对需要长期保留的事件，可以将已发布记录按策略归档到对象存储或专用事件归档系统。

归档数据应保留：

- 原始事件 ID。
- Schema 版本。
- 原始载荷摘要。
- 事件发生时间和发布记录。
- 租户与业务关联标识。
- 归档时间、存储位置与完整性验证信息。

归档事件可以用于审计和诊断，但不能自动等同于当前业务状态。恢复时仍应读取权威状态并评估事件是否仍然适用。

## 17. 死信队列与人工修复机制

死信不是一个用来存放“没人想管的消息”的垃圾桶，而是可靠执行系统的受控异常处理区。

### 17.1 进入死信的条件

建议以下情况进入死信或隔离状态：

- 消息 Schema 无法解析。
- 相同事件 ID 对应不同载荷摘要。
- 事件版本不被当前消费者支持。
- 超过最大处理尝试次数。
- 业务状态与事件内容出现不可自动修复的矛盾。
- 消费者持续产生确定性的处理错误。
- 事件涉及已撤销版本或违反安全策略。
- 自动重试可能造成重复外部副作用。

并非所有失败都应进入死信。例如，普通限流和短暂网络故障可以先使用有限退避重试。

### 17.2 Dead Letter 数据结构

```
CREATE TABLE event_dead_letters (
    dead_letter_id UUID PRIMARY KEY,
    tenant_id      UUID NOT NULL,

    consumer_name  TEXT NOT NULL,
    original_event_id UUID NOT NULL,
    event_type     TEXT NOT NULL,
    schema_version TEXT NOT NULL,

    payload_digest TEXT NOT NULL,
    payload_ref    TEXT,
    failure_code   TEXT NOT NULL,
    failure_detail TEXT,

    attempt_count  INT NOT NULL,
    first_failed_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    last_failed_at  TIMESTAMPTZ NOT NULL DEFAULT now(),

    status         TEXT NOT NULL DEFAULT 'OPEN',
    resolution     TEXT,
    resolved_by    TEXT,
    resolved_at    TIMESTAMPTZ,

    CHECK (status IN (
        'OPEN',
        'INVESTIGATING',
        'REPLAY_APPROVED',
        'RESOLVED',
        'DISCARDED'
    ))
);
```

这里的 `payload_ref` 可以指向受控保存的消息载荷。对含敏感数据的消息，应采用加密、访问控制和保留期限，避免死信系统变成敏感信息的长期堆积区。

### 17.3 人工处理流程

建议设计为：

```
OPEN
 ↓
INVESTIGATING
 ↓
分析错误与业务影响
 ↓
选择处置方案
 ├── 修复消费者后重试
 ├── 重新生成业务命令
 ├── 执行补偿操作
 ├── 转业务负责人处理
 └── 经授权后丢弃
```

每次处置都应记录操作者、理由、关联事件和最终结果。

丢弃消息不能自动等于撤销业务动作。 如果消息对应的外部操作已经发生，必须先确认其实际状态，再决定如何修复。

### 17.4 重放前检查

重放工具至少要检查：

- 原始事件是否完整。
- 当前消费者是否支持该 Schema 版本。
- 原事件是否已经被成功处理。
- 当前 Run、Step 和 ERP Operation 的状态。
- 当前权限与策略是否允许重放。
- 重放是否会创建重复业务操作。
- 是否需要人工批准。
- 预估影响和执行范围。

建议将重放分为“只读预览”和“执行重放”两个阶段。生产环境中不应提供绕过权限和业务状态检查的通用重放按钮。

## 18. 多租户、公平调度与容量治理

在企业私有化部署中，一个租户可能只有少量任务，另一个租户可能同时运行大量 Agent。如果使用简单的全局先进先出队列，大租户容易占满 Worker 和数据库连接，影响其他租户。

### 18.1 多租户调度目标

ODAP 应兼顾：

- 租户之间的资源公平性。
- 高优先级业务的合理响应时间。
- 单个租户的最大并发限制。
- 不同任务类型的资源隔离。
- 系统维护与恢复任务的最低资源保障。
- 高风险任务的安全优先级。

优先级不能被普通用户任意设置为最高级，否则会形成资源争抢和拒绝服务风险。

### 18.2 建议的调度层级

可以采用分层调度：

1. 按租户计算可用并发额度。
2. 在租户内部按任务优先级和等待时间排序。
3. 按工作类型分配 Worker 资源池。
4. 根据模型、数据库和 ERP 限流动态控制并发。
5. 为恢复、对账和安全维护任务保留最低执行能力。

例如，ERP 对账任务不能完全被普通文本分析任务挤出资源，否则外部操作结果未知的记录会持续积压。

### 18.3 背压机制

当下游处理能力不足时，系统必须主动减速，而不是继续无上限地接收任务。

建议设置：

- 队列最大长度或待执行任务上限。
- 租户级待处理任务上限。
- Worker 最大并发数。
- 数据库连接池上限。
- 模型调用并发与 Token 预算。
- ERP 端点并发与速率限制。
- 队列等待时间阈值。
- 超过截止时间的任务拒绝或过期策略。

当达到容量上限时，API Server 应返回明确的过载结果，例如 `BUS_CAPACITY_EXCEEDED`（基础码 `RESOURCE_EXHAUSTED`，见 docs/contracts/02-统一错误码注册表.md §3.5），或在业务允许时将任务持久化为等待状态。不能返回"任务已完成"或让调用方误以为后台一定会执行。

### 18.4 自动扩容原则

可以根据队列积压、等待时间和 Worker 利用率扩容，但自动扩容仍需遵守外部系统容量限制。

增加 Worker 并不一定能提高端到端吞吐量：如果瓶颈是模型供应商的速率限制、数据库连接池或 ERP 端点，继续扩容只会增加竞争和错误率。

## 19. 安全设计与威胁模型

分布式消息系统扩大了 ODAP 的攻击面。消息可能被伪造、重放、跨租户误投，Worker 也可能因缺陷而重复执行高风险操作。

### 19.1 核心安全风险

| 风险            | 防护机制                    |
| ------------- | ----------------------- |
| 伪造事件          | 服务身份认证、消息完整性校验、生产者白名单   |
| 跨租户消息混淆       | 租户上下文验证、RLS、对象级授权       |
| 重放攻击          | 事件 ID、Inbox、操作幂等键和状态校验  |
| 旧 Worker 继续执行 | 租约代次、条件更新、外部操作账本        |
| 恶意死信重放        | 专门权限、预览、影响评估和审计         |
| 事件载荷注入        | Schema 校验、来源可信度标记、上下文隔离 |
| 敏感数据泄露        | 载荷最小化、加密、访问控制与保留策略      |
| 队列耗尽          | 速率限制、容量上限、租户配额和背压       |
| 插件无限重试        | 平台级尝试次数、预算与截止时间限制       |
| 事件版本降级攻击      | 允许的 Schema 版本范围与签名/摘要校验 |

### 19.2 消息信任边界

即使消息来自内部消息代理，也不能直接信任消息中的所有字段。

消费者至少应验证：

- 生产者身份是否允许发布该事件类型。
- 租户是否与目标业务对象匹配。
- 事件载荷是否符合已登记的 Schema。
- 事件 ID 和摘要是否一致。
- 目标对象是否存在且状态允许该转换。
- 当前操作是否仍在授权范围内。

消息中的 `AuthorizationDecisionID`、`ApprovalID` 等引用只是关联信息。执行高风险操作时仍需检查其有效性、作用范围、绑定摘要和撤销状态。

### 19.3 内网并不等于可信

在企业私有化部署中，消息代理、数据库、Worker 和插件虽然都在内网，但仍然应建立明确的服务身份与最小权限边界。

建议：

- 每类服务使用独立身份。
- 限制每个服务能够订阅和发布的事件类型。
- 为消息代理配置访问控制与传输加密。
- 限制 Worker 对数据库表的直接写权限。
- 对插件采用进程或容器隔离。
- 对管理操作和事件重放进行审计。
- 生产环境中禁止未经批准的 Worker 任意连接外部网络。

## 20. 可观测性与运行监控

分布式系统最难排查的问题之一，是任务表面上停滞，却没有明显报错。因此，ODAP 必须将任务状态、消息传递、Worker 执行和外部操作统一关联起来。

### 20.1 全链路关联模型

```
Business Request
  └── Run
       ├── Event: RunCreated
       ├── Step A
       │    ├── Lease / Worker
       │    ├── LLM Request
       │    └── StepCompleted
       ├── Step B
       │    ├── Ontology Validation
       │    └── StepCompleted
       └── ERP Operation
            ├── Dispatch Event
            ├── Remote Request
            ├── Receipt
            └── Reconciliation
```

每个环节应携带统一的 `trace_id`、`run_id`、`step_id`、`event_id` 和 `operation_id`，使运维人员能够从业务任务一路追踪到消息、Worker 和 ERP 回执。

### 20.2 核心监控指标

| 指标                                | 含义             |
| --------------------------------- | -------------- |
| `outbox_pending_count`            | 待发布事件数量        |
| `outbox_oldest_age_seconds`       | 最老待发布事件的等待时间   |
| `event_publish_failure_total`     | 事件发布失败次数       |
| `consumer_processing_lag_seconds` | 消费处理滞后时间       |
| `consumer_duplicate_total`        | 重复消息数量         |
| `consumer_dead_letter_total`      | 死信数量           |
| `worker_active_count`             | 当前活动 Worker 数量 |
| `worker_lease_expired_total`      | 租约过期次数         |
| `task_queue_wait_seconds`         | 任务等待时间         |
| `task_retry_total`                | 步骤重试次数         |
| `task_stuck_count`                | 长期无进展任务数量      |
| `erp_unknown_operation_count`     | 外部结果未知的操作数量    |
| `reconciliation_backlog`          | 待对账操作积压量       |
| `task_cancel_latency_seconds`     | 取消请求到停止调度的耗时   |

指标标签应控制基数。不要直接将 `run_id`、`event_id` 或用户 ID 作为所有指标的标签，否则监控系统可能产生巨大的时间序列数量。这类高基数信息应保留在日志和 Trace 中。

### 20.3 任务健康判定

建议为每个 Run 计算一个可解释的健康状态：

- `HEALTHY`：执行正常，近期有进展。
- `WAITING`：等待审批、外部事件或预定时间，属于正常等待。
- `DEGRADED`：发生重试、延迟或部分依赖异常。
- `STALLED`：超过预期时间没有进展，需调查。
- `RECOVERING`：正在恢复执行。
- `NEEDS_ATTENTION`：存在结果未知、死信或需要人工介入的问题。

“长时间未更新”不能单独作为任务故障依据。等待人工审批的任务可能数小时没有变化，但仍属于正常等待；一个持续输出心跳却永远无法推进的 Worker，也可能实际上已经卡死。

因此，健康判定应结合状态、截止时间、步骤进展、队列延迟和业务等待条件。

## 21. API 设计：任务调度与事件治理

建议在现有 `/api/v1` 下增加任务调度、运行管理和事件运维接口。

### 21.1 任务接口

| 方法     | 接口                           | 功能         |
| ------ | ---------------------------- | ---------- |
| `POST` | `/api/v1/runs`               | 创建异步 Run   |
| `GET`  | `/api/v1/runs/{id}`          | 查询 Run 状态  |
| `GET`  | `/api/v1/runs/{id}/steps`    | 查询步骤状态     |
| `POST` | `/api/v1/runs/{id}/cancel`   | 请求取消       |
| `POST` | `/api/v1/runs/{id}/resume`   | 请求恢复       |
| `GET`  | `/api/v1/runs/{id}/events`   | 查询可访问的事件记录 |
| `GET`  | `/api/v1/runs/{id}/attempts` | 查询执行尝试     |
| `GET`  | `/api/v1/runs/{id}/recovery` | 查询恢复记录     |

### 21.2 运维接口

| 方法     | 接口                                                    | 功能              |
| ------ | ----------------------------------------------------- | --------------- |
| `GET`  | `/api/v1/operations/queue-stats`                      | 查询队列积压          |
| `GET`  | `/api/v1/operations/workers`                          | 查询 Worker 状态    |
| `GET`  | `/api/v1/operations/outbox`                           | 查询 Outbox 积压    |
| `GET`  | `/api/v1/operations/dead-letters`                     | 查询死信            |
| `GET`  | `/api/v1/operations/recovery-jobs`                    | 查询恢复任务          |
| `POST` | `/api/v1/operations/dead-letters/{id}/replay-preview` | 预览重放影响          |
| `POST` | `/api/v1/operations/dead-letters/{id}/replay`         | 经授权后执行重放        |
| `POST` | `/api/v1/operations/workers/{id}/drain`               | 将 Worker 置为排空状态 |

所有运维接口都必须经过管理员权限、租户范围和审计检查。重放、取消、恢复与 Worker 排空属于会影响系统运行状态的操作，应提供操作理由和明确的执行反馈。

### 21.3 创建任务的接口示例

```
POST /api/v1/runs
Content-Type: application/json
Idempotency-Key: expense-review-request-001
```

```
{
  "agent_ref": "finance.expense-processor",
  "input": {
    "expense_claim_id": "expense_123"
  },
  "execution_mode": "propose",
  "deadline": "2026-10-13T12:00:00Z"
}
```

服务端应在创建 Run 时：

1. 验证调用者身份和业务权限。
2. 验证输入 Schema。
3. 锁定 Agent、本体、规则、工具和必要模型策略版本。
4. 检查任务截止时间与预算。
5. 在同一事务中创建 Run、初始步骤和 Outbox 事件。
6. 返回 Run 标识与初始状态。

重复提交相同的幂等请求时，应返回原有逻辑请求对应的结果，而不是重复创建 Run。如果相同幂等键被用于不同请求载荷，服务端应拒绝并返回明确的冲突错误。

## 22. Go 工程实现建议

推荐继续采用 Go 实现 API Server、Orchestrator、Worker、Outbox Publisher 和 Recovery Controller。

### 22.1 模块边界

建议定义以下核心接口：

```

package execution

import (
    "context"
    "time"
)

type RunID string
type StepID string
type WorkerID string

type Lease struct {
    StepID    StepID
    WorkerID  WorkerID
    Epoch     int64
    ExpiresAt time.Time
}

type StepRepository interface {
    ClaimNext(
        ctx context.Context,
        workerID WorkerID,
    ) (Lease, error)

    RenewLease(
        ctx context.Context,
        lease Lease,
    ) (Lease, error)

    CompleteStep(
        ctx context.Context,
        lease Lease,
        result StepResult,
    ) error

    FailStep(
        ctx context.Context,
        lease Lease,
        failure StepFailure,
    ) error
}

type StepExecutor interface {
    Execute(
        ctx context.Context,
        lease Lease,
    ) (StepResult, error)
}

type RecoveryController interface {
    RecoverExpiredLeases(
        ctx context.Context,
    ) error

    RecoverPendingDispatches(
        ctx context.Context,
    ) error

    ReconcileUnknownOperations(
        ctx context.Context,
    ) error
}

```

这是接口边界草案。正式实现应明确 `CompleteStep` 与 `FailStep` 的条件更新、事务和 Outbox 语义，不能让接口调用只更新状态却遗漏事件。

### 22.2 Worker 主循环

建议采用以下处理流程：

```
启动 Worker
   ↓
加载配置并验证身份
   ↓
检查依赖服务健康状态
   ↓
领取任务与租约
   ↓
加载持久化上下文
   ↓
检查取消、截止时间和预算
   ↓
执行 Step
   ↓
验证输出与副作用状态
   ↓
持久化结果、状态和 Outbox
   ↓
释放资源
   ↓
继续领取下一任务
```

Worker 退出时应支持优雅关闭：

1. 停止领取新任务。
2. 尽可能完成允许在关闭宽限期内完成的工作。
3. 持久化可以安全保存的结果。
4. 对尚未完成的步骤按策略释放或让租约到期。
5. 对已发出的外部操作保留账本与恢复信息。
6. 关闭数据库连接和消息消费者。

强制终止进程仍然可能发生，因此恢复能力必须依赖持久化状态，而不是依赖优雅关闭一定执行成功。

### 22.3 Context 与取消传播

Go 的 `context.Context` 适合传递请求截止时间和取消信号，但不适合替代持久化状态。

例如，用户点击取消后，API Server 可以通过持久化的 `CANCEL_REQUESTED` 状态和消息通知 Worker；Worker 再把取消信号传播给本地执行链路。

如果 Worker 重启，新的 Worker 必须从数据库读取任务是否已取消，而不能依赖旧进程中的 Context。

## 23. Docker Compose 与生产部署

### 23.1 MVP 部署结构

建议先采用如下部署：

```
docker-compose
├── odap-api
├── odap-worker
├── odap-scheduler
├── odap-mock-erp
├── postgres
├── object-storage
└── observability
```

其中：

- `odap-api`：任务创建、查询与管理 API。
- `odap-worker`：执行 Agent、工具与后台步骤。
- `odap-scheduler`：调度与恢复，可在 MVP 中与 API 或 Worker 合并。
- `odap-mock-erp`：独立模拟 ERP 服务与数据存储。
- `postgres`：任务、Outbox、Inbox、操作账本与元数据。
- `object-storage`：保存大型制品、证据和归档。
- `observability`：日志、指标和追踪采集。

在第一阶段，可以不部署独立消息代理，直接由 Publisher 从 PostgreSQL Outbox 读取事件并交给内部调度器或数据库任务队列。

### 23.2 多节点部署

当需要多节点时，可以拆分为：

- 多实例 API Server。
- 多实例 Orchestrator。
- 按能力分组的 Worker Pool。
- 独立 Outbox Publisher。
- 独立 Recovery Controller。
- 高可用 PostgreSQL。
- 可选的持久化消息代理。
- 独立的遥测与归档系统。

同一个调度服务可以运行多个实例，但必须依赖数据库行锁、唯一约束和租约协议避免重复领取，而不是依赖“通常只会有一个实例运行”的假设。

### 23.3 部署升级策略

升级 Worker 或事件 Schema 时，建议采用兼容优先的滚动升级：

1. 发布能够兼容旧事件的消费者版本。
2. 验证新消费者对旧事件的处理。
3. 更新事件生产者。
4. 观察错误率、死信与任务延迟。
5. 在必要时回滚生产者或切回已验证的消费者版本。

对不兼容的事件变更，应使用新版本事件类型或 Schema，并规划旧消费者退役时间。

## 24. 测试与故障注入

分布式可靠执行的正确性，必须通过故障测试验证。仅仅在正常环境中跑通一次业务流程是不够的。

### 24.1 测试分层

| 测试类型        | 重点                          |
| ----------- | --------------------------- |
| 单元测试        | 状态转换、退避、幂等键、错误分类            |
| 数据库集成测试     | Outbox 原子性、租约、并发抢占、Inbox 去重 |
| 消息代理契约测试    | 确认、重投、持久化、死信和重放             |
| Worker 故障测试 | 进程终止、租约失效、重复领取              |
| ERP 故障测试    | 请求超时、提交后丢失响应、回执延迟           |
| 并发压力测试      | 多租户、公平调度、队列积压和资源竞争          |
| 安全测试        | 跨租户事件、伪造载荷、越权重放             |
| 恢复演练        | 数据库重启、代理不可用、Worker 批量退出     |

### 24.2 必须验证的故障场景

1. 数据库提交成功，但 Publisher 在发送事件前崩溃。
2. 消息代理已接受事件，但 Publisher 在标记发布成功前崩溃。
3. 消费者处理成功，但在确认消息前崩溃。
4. 相同事件被并发投递给两个消费者。
5. Worker 领取任务后立即退出。
6. Worker 执行期间租约过期，另一个 Worker 接管。
7. 旧 Worker 恢复后尝试提交结果。
8. Run 被取消，但消息仍然留在队列中。
9. 事件载荷合法，但业务状态已经不允许该转换。
10. Outbox 大量积压，数据库出现锁等待。
11. 供应商限流导致任务持续退避。
12. 消息代理不可用，但任务创建事务仍已提交。
13. ERP 操作成功，但远端响应丢失。
14. ERP 对账结果返回延迟或暂时未知。
15. 死信重放导致重复业务命令的风险被识别并阻止。
16. 两个租户竞争 Worker 资源时，调度器仍满足配置的资源边界。

### 24.3 MVP 验收标准

建议以以下标准作为首个版本的验收门槛：

- Run、Step 与 Outbox 事件在事务边界上保持一致。
- Publisher 故障恢复后，已提交的待发布事件能够继续发布。
- 重复事件不会重复创建同一逻辑步骤。
- Worker 崩溃后，任务能够通过租约与恢复机制重新评估。
- 旧 Worker 不能覆盖新执行者已提交的步骤状态。
- 取消、审批与恢复状态可以在服务重启后保留。
- 结果未知的 ERP 操作不会被自动盲目重发。
- 事件 Schema 不兼容会被识别并隔离。
- 死信重放具有权限、影响检查和审计记录。
- 多租户事件和数据访问经过隔离验证。
- 队列积压、租约过期和对账积压均可被监控。
- 数据库和消息代理恢复后，系统能从持久化状态继续工作。

这里不建议在尚未明确硬件、模型和业务吞吐量的情况下，承诺固定的每秒事件数或恢复时间。性能指标应通过目标部署环境中的压测确定。

## 25. MVP 实施路线与优先级

建议按照“先保证正确性，再扩展吞吐量”的顺序开发。尤其不建议先搭建复杂消息集群，再回头补充状态机和幂等机制。

P1：持久化任务状态与 Outbox

扩展 Run、Step、Task Attempt、Outbox 数据模型，统一状态转换事务。

验收：任务状态更新与事件记录不会出现只提交一边的情况。

P2：Inbox 与幂等消费者

实现事件去重、事务消费、失败重试和载荷摘要校验。

验收：重复消息不会重复创建步骤或重复应用同一状态变更。

P3：Worker Pool 与任务租约

实现并发领取、心跳、租约代次、优雅关闭和失效恢复。

验收：多个 Worker 能并行执行不同任务，旧 Worker 无法覆盖新执行者的状态。

P4：Harness 分布式状态机

联调步骤依赖、暂停恢复、取消、截止时间和预算控制。

验收：Worker 重启后，Run 可以从持久化状态继续，而不依赖原进程内存。

P5：ERP 操作账本与恢复控制器

实现外部操作状态查询、未知结果对账、死信与受控重放。

验收：模拟 ERP 提交成功但响应丢失时，不会因 Worker 重启而盲目重复提交。

P6：事件总线与运行监控

完善队列统计、消费者延迟、故障注入、死信处理与端到端 Trace。

验收：运维人员能够定位任务停滞原因，并安全地恢复或转交人工处理。

### 25.1 第一阶段应该做多复杂？

对于当前 ODAP，我建议第一阶段只部署：

- Go API Server。
- Go Worker。
- Go Orchestrator / Recovery Controller。
- PostgreSQL。
- Mock ERP。
- 对象存储。

事件总线先用 PostgreSQL Outbox 与轮询 Publisher 实现。等端到端可靠性测试通过后，再根据实测的队列延迟、数据库负载和并发需求决定是否接入独立消息代理。

这样可以避免同时引入消息代理、分布式状态机、复杂部署和业务逻辑等多个变量，让故障定位更加困难。

## 27. 本篇最终架构决策

综合 ODAP 前十篇，建议将以下内容作为 V1.0 分布式可靠执行基线。

1. 数据库任务状态是权威状态，事件总线负责传递和唤醒。
2. 业务状态更新和 Outbox 事件必须在同一数据库事务中提交。
3. 默认采用至少一次消息投递与幂等消费，不假设端到端恰好一次。
4. Inbox、Outbox、Task Attempt 和业务操作账本分别解决不同问题，不能互相替代。
5. Worker 使用租约、心跳和执行代次协调任务所有权。
6. 租约失效不能自动证明外部操作未发生。
7. Harness 的状态转换、暂停、取消和恢复必须持久化。
8. 所有重试都要受错误分类、最大尝试次数、截止时间和预算限制。
9. ERP 写操作必须经过 ERP Gateway，并具有稳定的操作 ID、幂等键和对账能力。
10. 未知外部操作结果应进入对账或人工复核，不能盲目重发。
11. 事件必须有版本、摘要、租户归属和业务关联标识。
12. 死信重放、任务恢复和人工修复必须经过授权与审计。
13. 多租户公平调度、背压和容量上限属于基础能力，不应等到过载后再补。
14. 所有可靠性承诺必须通过故障注入、并发测试和恢复演练验证。

第十篇完成后，ODAP 的架构就从“多个智能体能够协作”进一步发展到“多个服务和 Worker 能够在故障环境中可靠地协作”。

这两者的区别非常重要：前者证明系统能够完成业务流程，后者才使系统有机会在企业生产环境中持续、安全地完成业务流程。
