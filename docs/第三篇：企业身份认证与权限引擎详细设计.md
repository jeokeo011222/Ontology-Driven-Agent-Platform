# 第三篇：企业身份认证与权限引擎详细设计

版本：V1.0 · 技术栈：Go + PostgreSQL + React/TypeScript · 部署模式：企业私有化 · 承接第二篇核心数据模型设计

> **本篇 scope 标签**：`[MVP-V1.0]` 身份认证与可信上下文（§四）、RBAC 与数据范围（§五）、统一 PDP 与 JSON DSL 策略（§六/§七）、决策流水线与错误码收敛（§八）、Harness/ERP 三层强制（§九/§十四）、会话撤销传播（§4.6）；`[V1.5]` Obligations 附加义务、撤销传播 SLA 度量看板、OPA/Rego 适配器；`[V2]` explain API 高级分析、可视化策略编辑器。状态词表与错误码以 `contracts/01`、`contracts/02` 为唯一真源，本篇只引用不重定义；授权决策类型以 §7.1 为篇内唯一权威定义。

## 一、设计目标与安全边界

企业本体驱动智能体平台不是普通的聊天机器人系统。智能体需要查询企业数据、解释业务制度、调用工具、生成操作计划，并在获得授权后向 ERP 提交业务操作。

因此，权限引擎必须解决一个核心问题：

如何确保智能体只能代表经过认证的主体，在当前组织、当前业务范围、当前策略和当前授权条件下，执行被允许的操作？

本篇将身份认证、企业组织、角色权限、属性授权、业务策略、审批控制与执行时复核整合为一套统一机制。

### 1.1 设计目标

- 支持企业本地账号与 OIDC/SSO 身份提供方。
- 支持集团、法人、部门、项目组和跨组织成员关系。
- 同时支持 RBAC、ABAC 和业务策略。
- 将用户权限、智能体权限、工具能力和业务对象权限分开管理。
- 让每一次敏感操作都能解释授权依据。
- 支持权限撤销、审批、临时授权和紧急禁用。
- 与 Harness、插件运行时、本体运行时和 ERP Adapter 统一集成。
- 支持私有化部署，敏感企业数据默认不发送到未批准的外部服务。

### 1.2 权限系统不负责什么？

权限引擎不负责判断某份合同在商业上是否合理，也不负责判断一个本体的数学语义是否正确。这些问题分别由业务规则、本体校验和领域服务处理。

权限引擎负责判断：谁可以对什么资源执行什么动作，在什么条件下可以执行，以及是否需要额外审批。

例如，智能体判断一张报销单符合制度，不等于它有权批准该报销单；用户有权查看报销单，也不等于其有权修改报销金额；管理员可以注册插件，也不应因此自动获得读取全部业务数据的权限。

## 二、总体授权架构

建议采用经典的 PAP + PDP + PEP + PIP 模型，并将其与 Harness 的执行流程结合。

主体与身份认证

员工、管理员、服务账号、智能体执行身份

PEP · 策略执行点

API 中间件、Harness、Tool Runtime、ERP Adapter

在受保护操作入口拦截并执行授权决定

PDP · 策略决策点

统一计算 Allow / Deny / RequireApproval

PIP · 属性信息点

用户、组织、资源属性、业务状态、风险等级

PAP · 策略管理点

角色、策略版本、审批规则、发布与撤销

受保护业务能力

本体查询、文件访问、工具调用、审批操作、ERP 写入

### 2.1 四个核心组件

| 组件  | 职责              | 示例                   |
| --- | --------------- | -------------------- |
| PAP | 管理、编辑、审核和发布策略   | 发布“超过 1 万元需审批”的策略    |
| PDP | 根据请求、属性和策略计算决策  | 判断员工是否能读取某部门报销单      |
| PEP | 在操作执行前强制执行决策    | 阻止智能体直接调用未授权的 ERP 工具 |
| PIP | 获取可信的身份、资源和环境属性 | 查询组织归属、报销金额和对象密级     |

这些组件是逻辑职责，不必一开始部署为四个独立微服务。MVP 可以在一个 Go 模块中实现统一的授权服务接口，再由不同模块调用。

### 2.2 最重要的执行原则

所有受保护的操作都必须经过 PEP。仅在前端隐藏按钮，或者只在创建智能体任务时检查一次权限，都不足以构成安全边界。

即使模型提出“读取所有员工的工资数据”，Harness 也必须在工具调用入口重新鉴权；即使智能体之前获得过授权，审批人离职、用户权限被撤销或业务对象状态发生变化，也必须在关键操作提交前重新验证。

## 三、身份主体模型：人、服务与智能体

企业智能体平台不能把所有执行行为都记录为同一个“用户”。至少要区分发起请求的人、代表业务执行的智能体、实际调用工具的服务身份，以及最终执行外部操作的适配器身份。

### 3.1 四类主体

| 主体类型    | 示例                      | 典型权限             |
| ------- | ----------------------- | ---------------- |
| Human   | 员工、部门经理、财务主管            | 按组织、岗位和业务范围授权    |
| Service | Worker、ERP Adapter、后台任务 | 只授予完成指定服务职责所需的权限 |
| Agent   | 报销审核智能体、合同分析智能体         | 仅在授权任务范围内使用获准工具  |
| System  | 迁移程序、系统初始化任务            | 受控运维权限，不参与普通业务授权 |

建议使用统一的 `Subject` 抽象，但保留主体类型与具体身份之间的差异。

```
package authz

type SubjectType string

const (
    SubjectHuman   SubjectType = "HUMAN"
    SubjectService SubjectType = "SERVICE"
    SubjectAgent   SubjectType = "AGENT"
    SubjectSystem  SubjectType = "SYSTEM"
)

type Subject struct {
    ID          string
    Type        SubjectType
    TenantID    string
    OrgIDs      []string
    MembershipID string
    ClientID    string
    AuthMethod  string
}
```

这里的 `OrgIDs` 只是请求上下文中的组织范围信息，不能作为未经验证的授权依据。真正的组织关系应从可信的身份与组织服务获取，或使用经过验证的短期授权上下文。

本篇类型定义收敛规则：本节定义请求侧的主体抽象（`Subject`/`SubjectType`），它是 §7.2 `AuthorizationRequest` 的输入组成部分；**授权决策侧类型（`DecisionEffect`、`Decision`、`Obligation`）以 §7.1 为唯一权威定义**，本篇不在其他章节重复声明（§11.2 应用层代码同样只引用该定义，包名统一为 `authz`）。

### 3.2 采用双主体与委托链

建议将用户请求和智能体执行身份分开记录：

- `initiator`：谁发起了任务。
- `effective_subject`：当前操作以哪个主体身份执行。
- `agent_id`：由哪个智能体版本产生该操作。
- `service_identity`：哪个服务组件实际提交了请求。
- `delegation_chain`：从用户授权到智能体执行的委托关系。

例如：

```
员工 Alice
  │ 发起报销审核任务
  ▼
ExpenseReview Agent v1.2.0
  │ 请求调用 read_expense 工具
  ▼
Harness / Tool Runtime
  │ 验证 Alice 的业务访问权限
  │ 验证 Agent 的工具调用范围
  ▼
ERP Adapter
  │ 使用受控服务凭证访问 ERP
  ▼
ERP
```

这并不意味着 ERP 必须使用 Alice 的个人账号。ERP Adapter 可以使用专用服务账号，但它必须同时保留发起人、委托关系、业务对象和授权决策的可追溯信息。

### 3.3 委托不能扩大原始权限

设用户 \\(u\\) 对资源 \\(r\\) 的有效权限为 \\(P_u(r)\\)，智能体自身被允许使用的权限为 \\(P_a(r)\\)，委托范围为 \\(P_d(r)\\)，则智能体的有效权限应满足：

\\[ P\_{\mathrm{effective}}(r) \subseteq P_u(r)\cap P_a(r)\cap P_d(r) \\]

对于由平台系统账号发起的合法后台任务，可以采用独立的服务授权路径，但必须明确其业务所有者、资源范围、操作类型和有效期限，不能借助服务账号绕过普通业务规则。

## 四、企业身份认证设计

身份认证解决“你是谁”，授权解决“你能做什么”。两者应独立实现，不能把登录成功直接视为拥有业务权限。

### 4.1 认证方式

建议优先支持以下认证模式：

1. OIDC / SSO：企业已有身份提供方时，使用标准 OIDC Authorization Code Flow，配合 PKCE。
2. 本地管理员引导：仅用于首次初始化、故障恢复或明确批准的场景。
3. 服务身份认证：服务之间采用独立身份，优先使用短期凭证、mTLS 或受控的客户端凭证机制。
4. 智能体执行身份：由 Harness 根据已认证的请求人、智能体版本和委托策略构建，不接受模型自行声明身份。

如果企业已有统一身份平台，应优先集成它，而不是在 ODAP 内重新实现一套完整的密码管理和账号生命周期系统。

### 4.2 OIDC 登录流程

1\. 用户访问 Web

前端跳转到后端发起登录

2\. 身份提供方认证

企业 SSO 完成身份验证与 MFA（如配置）

3\. 后端验证 OIDC 响应

校验签名、issuer、audience、nonce、state 与有效期

4\. 身份映射与状态检查

映射内部用户、租户、成员关系及账号状态

5\. 创建应用会话

签发安全会话 Cookie，或使用受控的访问令牌机制

后端必须验证 OIDC 响应中的 `iss`、`aud`、`exp`、签名和流程关联参数；不能只解析 JWT 的 Payload 就相信其中的用户 ID。

### 4.3 建议的认证接口

| 接口                                     | 方法   | 说明            |
| -------------------------------------- | ---- | ------------- |
| `/api/v1/auth/login`                   | GET  | 发起 OIDC 登录    |
| `/api/v1/auth/callback`                | GET  | 接收并验证登录回调     |
| `/api/v1/auth/logout`                  | POST | 注销本地会话        |
| `/api/v1/auth/session`                 | GET  | 查询当前会话        |
| `/api/v1/identity/me`                  | GET  | 返回当前用户和有效组织范围 |
| `/api/v1/identity/switch-organization` | POST | 切换当前组织上下文     |

切换组织只改变当前请求的上下文，不会自动授予新组织的权限。后端必须检查用户是否为该组织的有效成员。

### 4.4 Web 会话安全

对于 React Web 管理控制台，优先考虑由后端管理的会话 Cookie：

- 设置 `HttpOnly`、`Secure` 和适当的 `SameSite` 属性。
- 对状态变更请求实施 CSRF 防护。
- 会话 ID 在登录后重新生成，避免会话固定攻击。
- 注销时使服务端会话失效。
- 对高风险操作支持重新认证或 MFA 强化验证。
- 对管理端登录、失败尝试和异常访问实施限速与告警。

不要把长期访问令牌或刷新令牌存放在 `localStorage` 中作为默认方案。具体会话机制需要与部署环境、跨域要求和企业 SSO 方式相匹配。

### 4.5 身份映射与生命周期

建议新增身份映射表，避免仅依赖邮箱进行身份关联。

```
CREATE TABLE iam.external_identities (
    id UUID PRIMARY KEY,
    user_id UUID NOT NULL REFERENCES iam.users(id),
    issuer TEXT NOT NULL,
    subject TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),

    UNIQUE (issuer, subject)
);
```

OIDC 的稳定身份标识通常应使用经过验证的 `issuer + subject` 组合。邮箱可能发生变更，不能在没有额外验证的情况下用邮箱自动合并两个账号。

账号停用、员工离职、组织变更和外部身份解绑，都应触发相应的会话失效、权限重新计算和必要的运行中任务检查。

### 4.6 会话存储、撤销传播与失效 SLA

Web 会话不能只保存在进程内存或浏览器存储中：私有化多实例部署、Worker 重启、停用与权限撤销都要求会话状态可被服务端权威查询并立即失效。建议增加 PostgreSQL 会话表（DDL 风格对齐第二篇）：

```
CREATE TABLE iam.sessions (
    id UUID PRIMARY KEY,
    tenant_id UUID NOT NULL,
    subject_id UUID NOT NULL,
    subject_type TEXT NOT NULL CHECK (
        subject_type IN ('HUMAN', 'SERVICE', 'AGENT', 'SYSTEM')
    ),
    subject_version BIGINT NOT NULL DEFAULT 1,
    auth_method TEXT NOT NULL,
    issued_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    last_active_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    expires_at TIMESTAMPTZ NOT NULL,
    revoked_at TIMESTAMPTZ,
    revoke_reason TEXT,
    refresh_token_hash TEXT NOT NULL,
    refresh_expires_at TIMESTAMPTZ NOT NULL,
    refresh_rotated_at TIMESTAMPTZ,

    CHECK (expires_at > issued_at),
    CHECK (revoked_at IS NULL OR revoked_at >= issued_at)
);

CREATE INDEX idx_sessions_subject_active
    ON iam.sessions(tenant_id, subject_id, subject_version)
    WHERE revoked_at IS NULL;
```

设计与撤销传播路径：

- **`subject_version` 是撤销传播的核心机制**。停用账号、撤销角色绑定、委托终止或外部身份解绑时，服务端递增对应主体的 `subject_version`，旧会话令牌中携带的版本号全部失配；会话校验时同时比对令牌版本与当前值，失配即拒绝，不需要逐会话定位删除。
- **短期 TTL + 刷新令牌轮换**：访问令牌 TTL 建议 15 分钟；每次刷新签发新刷新令牌并将旧令牌标记 `refresh_rotated_at`；已轮换令牌被再次使用视为泄露信号，立即撤销该会话全部令牌并告警。刷新令牌只存哈希，禁止明文。
- **撤销生效时延 SLA**：版本号失配为同步生效；缓存与事件传播决定尾延迟。目标为普通停用与权限变更的会话失效 P95 ≤ 30 秒、P99 ≤ 60 秒。高影响操作（§9.2 的 R4）不依赖该 SLA，仍在执行前实时复核（§12.3）。
- 注销、超时、管理员强制下线都写入 `revoked_at` 与原因，供审计查询；会话记录本身按保留策略归档，不长期保存刷新令牌明文派生值以外的敏感数据。

## 五、RBAC：角色访问控制

RBAC 用于表达组织中的岗位和职责。例如：

- 普通员工：查看和提交自己的报销单。
- 部门经理：审核授权范围内的部门报销。
- 财务审核员：审核满足额度和职责分离条件的报销。
- 本体管理员：设计、验证和发布业务本体。
- 平台管理员：管理平台配置和插件注册，但不自动拥有全部业务数据权限。

### 5.1 权限命名规范

建议统一采用：

```
<domain>.<resource>.<action>
```

示例：

```
identity.user.read
identity.role.manage

ontology.package.read
ontology.package.create
ontology.version.validate
ontology.version.publish

agent.run.create
agent.run.read
agent.run.cancel

expense.read
expense.submit
expense.review
expense.approve

erp.operation.request
erp.operation.execute

audit.event.read
plugin.version.publish
```

命名需要保持稳定。不要将某个具体部门、某个员工或某个金额写进权限名称；这些应通过属性和业务策略表达。

### 5.2 角色不是权限的唯一来源

有效授权应结合：

1. 用户在当前租户和组织中的有效成员关系。
2. 当前生效的角色绑定。
3. 资源的数据范围。
4. 当前业务操作的属性条件。
5. 智能体和工具的能力限制。
6. 当前生效的策略与安全约束。

例如，“财务审核员”角色可能允许 `expense.review`，但不能由此推导出其能审核任何租户、任何部门、任何金额的报销单。

### 5.3 数据范围模型

建议至少支持以下范围：

| 范围            | 含义           |
| ------------- | ------------ |
| `SELF`        | 仅本人创建或负责的数据  |
| `ORG`         | 指定组织的数据      |
| `ORG_SUBTREE` | 指定组织及其下级组织   |
| `ASSIGNED`    | 显式分配给当前用户的数据 |
| `TENANT`      | 当前租户范围内的数据   |
| `EXPLICIT`    | 由明确资源列表定义的范围 |

数据范围应在查询和操作入口实际执行。不能只把 `scope_type` 返回给前端，再期待前端自行过滤。

对于跨组织角色、矩阵式汇报关系和临时项目组，应明确范围的合并规则，并为数据范围变更提供审计记录。

#### 5.3.1 数据范围的存储承载（scope 结构设计）

上表六种范围需要落到第二篇 `governance.role_bindings`，但该表当前只有 `TENANT`/`ORG` 两种 `scope_type`，无法表达 `SELF`、`ORG_SUBTREE`、`ASSIGNED`、`EXPLICIT`。本节给出 scope 结构的权威设计（DDL 风格对齐第二篇）；`governance.role_bindings` 的 `scope_type` CHECK 按本节扩展，`ORG_SUBTREE` 依赖组织闭包表。

**scope_type 枚举扩展与字段映射**：

| scope_type | 语义 | 承载字段 |
| --- | --- | --- |
| `TENANT` | 当前租户全部数据 | 无（`scope_org_id IS NULL`） |
| `ORG` | 指定组织的数据 | `scope_org_id` 指向该组织 |
| `ORG_SUBTREE` | 指定组织及其下级组织 | `scope_org_id` 指向子树根组织，展开依赖 `iam.org_closure` |
| `SELF` | 仅本人创建或负责的数据 | 无（运行时按 `subject_id` 过滤，不存组织引用） |
| `ASSIGNED` | 显式分配给当前用户的数据 | 无（运行时按分配关系过滤，绑定本身不存组织） |
| `EXPLICIT` | 由明确资源列表定义的范围 | `scope_resource_refs`（JSONB 资源引用列表，受控格式） |

**组织闭包表**（支持 `ORG_SUBTREE` 的传递展开，避免逐次递归 CTE）：

```
CREATE TABLE iam.org_closure (
    tenant_id UUID NOT NULL,
    ancestor_id UUID NOT NULL,
    descendant_id UUID NOT NULL,
    depth INTEGER NOT NULL CHECK (depth >= 0),
    PRIMARY KEY (tenant_id, ancestor_id, descendant_id),

    FOREIGN KEY (tenant_id, ancestor_id)
        REFERENCES iam.organizations(tenant_id, id),
    FOREIGN KEY (tenant_id, descendant_id)
        REFERENCES iam.organizations(tenant_id, id)
);

CREATE INDEX idx_org_closure_descendant
    ON iam.org_closure(tenant_id, descendant_id);
```

约定：每个组织对自身存在 `depth = 0` 的一行；组织新增、移动、撤销时以事务维护闭包表，并递增 §4.6 的 `subject_version`，使依赖组织关系的授权缓存同步失效。组织规模较大时 `org_closure` 可按租户分区；`ltree` path 物化方案可作为等价替代，但必须保证深度语义一致，二者选其一后回填第二篇迁移。

**role_bindings 的 scope 约束**（对齐第二篇 CHECK 风格扩展）：

```
scope_type TEXT NOT NULL DEFAULT 'ORG'
    CHECK (scope_type IN (
        'TENANT', 'ORG', 'ORG_SUBTREE',
        'SELF', 'ASSIGNED', 'EXPLICIT'
    )),

CHECK (
    (scope_type = 'TENANT' AND scope_org_id IS NULL)
    OR (scope_type IN ('ORG', 'ORG_SUBTREE') AND scope_org_id IS NOT NULL)
    OR (scope_type IN ('SELF', 'ASSIGNED') AND scope_org_id IS NULL)
    OR (scope_type = 'EXPLICIT' AND scope_resource_refs IS NOT NULL)
)
```

**求值规则**：PDP 解析角色绑定时，`ORG_SUBTREE` 经 `org_closure` 展开为组织集合；`SELF`/`ASSIGNED` 在查询入口转换为行级过滤条件；`EXPLICIT` 的资源列表在发布时校验格式与存在性。同一主体命中多个范围时取并集，但并集结果仍受 §7.3 显式禁止规则约束——范围只放大"可访问集合"，不能覆盖安全禁止。数据范围变更（绑定新增/撤销、组织移动）必须写审计，并触发 §12.4 的权限变更事件。

## 六、ABAC：属性访问控制

RBAC 解决岗位职责，ABAC 解决上下文条件。企业业务操作通常需要两者配合。

例如，用户具有 `expense.approve` 权限，但只有在报销金额不超过其审批额度、申请人与审批人不是同一人、报销单属于其管理范围且状态正确时，才允许批准。

### 6.1 属性分类

| 属性类别 | 示例                    | 可信来源        |
| ---- | --------------------- | ----------- |
| 主体属性 | 用户 ID、角色、组织、职级        | 身份与组织服务     |
| 资源属性 | 报销单所属部门、金额、密级         | 业务数据源       |
| 操作属性 | 查询、修改、审批、提交 ERP       | 服务端请求       |
| 环境属性 | 时间、网络区域、认证强度          | 服务端环境与认证上下文 |
| 任务属性 | Agent 版本、Run ID、任务发起人 | Harness 运行时 |
| 证据属性 | 本体版本、制度版本、验证状态        | 本体与证据服务     |

属性不能全部由调用方传入。例如，浏览器请求中声明 `"department": "Finance"` 并不证明用户属于财务部；`amount`、`owner_org_id` 和业务对象状态也应由受信任的数据源读取或验证。

### 6.2 ABAC 决策示例

假设存在以下业务规则：

- 申请人可以读取自己的报销单。
- 部门经理可以读取管理范围内的报销单。
- 只有指定角色才能审批。
- 申请人不能审批自己的报销单。
- 超过审批额度必须转交更高级别审批人。

可以用概念表达式描述：

\\[ \operatorname{Allow}(s,a,r)= \operatorname{RoleAllowed}(s,a) \land \operatorname{ScopeAllowed}(s,r) \land \operatorname{BusinessCondition}(s,a,r) \\]

这里的 `BusinessCondition` 需要由受控策略计算，不能由智能体自行给出一个布尔值作为授权证明。

### 6.3 策略语言选择（已锁定：V1.0 使用 JSON DSL 子集）

授权策略语言选型经评审确认，结论如下：

| 版本 | 决策 | 说明 |
| ---- | ---- | ---- |
| V1.0 | **自定义受限 JSON DSL 子集** | 策略种类较少的第一版，用字段白名单 + 比较算子 + 逻辑组合表达，严格限制可表达能力 |
| V1.5 | OPA/Rego 作为**可选适配器** | 不改变 §7.4 的 `AuthorizationService` 接口，经 `PolicyEvaluator` 适配器接入；面向复杂 ABAC、策略测试与企业治理需求的企业可选启用 |

无论哪种方案，策略表达式都禁止任意代码执行、任意 SQL 执行和未经授权的网络访问；底层策略计算实现始终是可替换组件，ODAP 自身稳定的授权接口（§7.4）不变。

JSON DSL 的约束（V1.0）：

- **字段白名单**：每条策略只能引用在属性注册表中登记过的字段（§6.1 六类属性），未登记字段在发布校验期直接拒绝，不留到运行期。
- **算子白名单**：逻辑 `AND`/`OR`/`NOT`；比较 `EQ`/`NE`/`GT`/`GTE`/`LT`/`LTE`/`IN`/`NOT_IN`/`CONTAINS`；存在性 `EXISTS`/`NOT_EXISTS`。不提供算术、函数调用与自定义表达式。
- **逻辑组合仅限树形求值**：不允许循环引用与自引用；单条策略的节点数与深度在发布校验时有上限。
- 策略文档整体为 JSON，随 `governance.policy_versions.policy_document`（第二篇）不可变版本化存储。

`policy_versions.policy_language` 增加 CHECK 约束锁定取值（与第二篇 DDL 对齐扩展）：

```
policy_language TEXT NOT NULL DEFAULT 'JSON_DSL_V1'
    CHECK (policy_language IN ('JSON_DSL_V1', 'OPA_REGO_V1_5'))
```

`OPA_REGO_V1_5` 在 V1.0 允许登记但**不允许发布**，提前占位避免 V1.5 迁移时破坏历史数据。

最小示例（字段名与 §7.2 `AuthorizationRequest` 结构对齐，直接取请求中的 `Attributes`/`Environment` 键）：

```
{
  "policy_id": "expense.approve.amount_limit",
  "version": "1.0.0",
  "effect": "REQUIRE_APPROVAL",
  "reason_code": "REQUIRE_APPROVAL_AMOUNT",
  "target": {
    "resource_type": "ExpenseClaim",
    "action": "expense.approve"
  },
  "condition": {
    "all": [
      { "field": "attributes.claimAmount", "op": "GT", "value": 10000 },
      { "field": "attributes.currencyCode", "op": "IN", "value": ["CNY", "USD"] }
    ]
  },
  "approval_rule": "finance.approval.amount_gt_10k"
}
```

同一请求命中多条策略时，按 §7.3 决策优先级合成最终 `ALLOW`/`DENY`/`REQUIRE_APPROVAL`；JSON DSL 只描述单条可判定规则，不承载优先级逻辑本身。

## 七、统一授权决策模型

所有受保护模块都应调用统一的授权服务，不允许各模块自行拼接角色、组织和业务条件。

### 7.1 决策结果

```
package authz

type DecisionEffect string

const (
    EffectAllow           DecisionEffect = "ALLOW"
    EffectDeny            DecisionEffect = "DENY"
    EffectRequireApproval DecisionEffect = "REQUIRE_APPROVAL"
)

type Decision struct {
    Effect          DecisionEffect
    ReasonCode      string
    PolicyVersionIDs []string
    ApprovalRuleID  string
    Obligations     []Obligation
    DecisionID      string
}

type Obligation struct {
    Type   string
    Params map[string]any
}
```

`Obligations` 表示执行时必须满足的附加要求，例如字段脱敏、只读访问、记录额外审计或要求双人复核。

需要注意，`REQUIRE_APPROVAL` 不是一种普通的允许。它表示操作暂时不能执行，必须创建审批流程，等审批通过并重新校验后才能继续。

### 7.2 授权请求

```
type AuthorizationRequest struct {
    RequestID string
    TenantID  string

    Subject    Subject
    AgentID    string
    AgentVersionID string

    ResourceType string
    ResourceID   string
    Action       string

    Environment map[string]any
    Attributes   map[string]any

    RunID       string
    ToolCallID  string
    PayloadDigest string
}
```

请求中的主体身份、租户 ID、智能体版本和业务对象属性必须由可信服务端上下文构建或重新验证。对于敏感操作，`PayloadDigest` 应绑定实际准备执行的规范化操作内容，而不是绑定一段模型描述。

### 7.3 决策优先级

建议采用以下统一规则：

1. 认证无效、账号禁用或租户不匹配：拒绝。
2. 命中不可覆盖的安全禁止规则：拒绝。
3. 不满足角色、资源范围或智能体能力约束：拒绝。
4. 满足基础授权，但命中审批规则：要求审批。
5. 满足全部必要条件且没有禁止规则：允许。
6. 策略服务异常、关键属性无法验证或版本不确定：敏感操作默认拒绝。

这套规则的重点是：不能让某条普通 `ALLOW` 规则覆盖显式的安全禁止规则，也不能将缺失属性自动解释成“符合条件”。

### 7.4 Go 服务接口

```
package authz

import "context"

type AuthorizationService interface {
    Authorize(
        ctx context.Context,
        req AuthorizationRequest,
    ) (Decision, error)

    Recheck(
        ctx context.Context,
        req AuthorizationRequest,
        previousDecisionID string,
    ) (Decision, error)
}
```

`Authorize` 负责计算新决策，`Recheck` 负责在关键操作前重新验证授权条件。二者应保存可追溯的决策记录。

`Recheck` 不能简单地返回之前缓存的 `ALLOW`。它需要重新检查当前用户状态、策略有效性、资源状态、审批状态和操作摘要。

## 八、权限计算流水线

建议将授权计算拆成可测试的阶段，每个阶段都返回明确结果和可解释的拒绝原因。

01

认证与主体解析

验证当前会话、服务身份、租户与委托链

02

主体状态检查

检查用户、成员关系、服务账号与智能体状态

03

基础权限匹配

查找角色、权限及其有效时间

04

资源范围判断

确认资源属于正确租户并位于授权范围

05

ABAC 与业务策略

读取可信属性并评估条件

06

智能体与工具约束

确认 Agent 版本、工具版本及调用能力获准

07

审批与附加义务

决定是否需要审批、脱敏或加强审计

08

记录并返回决策

生成决策 ID、策略版本引用和理由代码

### 8.1 推荐的理由代码

```
ALLOW_ROLE_SCOPE
ALLOW_POLICY_MATCH

DENY_UNAUTHENTICATED
DENY_SUBJECT_DISABLED
DENY_TENANT_MISMATCH
DENY_PERMISSION_MISSING
DENY_RESOURCE_SCOPE
DENY_AGENT_CAPABILITY
DENY_TOOL_NOT_REGISTERED
DENY_POLICY_EXPLICIT
DENY_ATTRIBUTE_UNTRUSTED
DENY_POLICY_UNAVAILABLE
DENY_APPROVAL_INVALID
DENY_PAYLOAD_CHANGED

REQUIRE_APPROVAL_AMOUNT
REQUIRE_APPROVAL_SENSITIVE_ACTION
REQUIRE_APPROVAL_SEPARATION_OF_DUTIES
```

这些代码用于机器处理和审计。对用户展示时，应转换成清晰但不过度泄露安全配置的提示。例如，可以提示“当前用户无权执行此操作”，但不必向普通用户暴露所有内部规则细节。

### 8.2 错误与拒绝必须区分

- `DENY`：系统已完成判断，结论是不允许。
- `REQUIRE_APPROVAL`：基础条件可能满足，但需要审批。
- `ERROR`：系统无法完成可信判断，例如策略服务不可用、属性源故障或数据库异常。

需要强调两点边界：

1. **决策效果严格三态**。§7.1 的 `DecisionEffect` 只有 `ALLOW`/`DENY`/`REQUIRE_APPROVAL`；`ERROR` 不是第四种效果，评估器故障统一以错误码 `AUTHZ_POLICY_EVALUATION_ERROR` 上抛（基础码 `INTERNAL`，见 `contracts/02` §3.2）。故障不使用 §8.1 的理由代码——理由代码只服务于已完成的判断，把故障记成 `DENY_*` 会误导排障。
2. **失败关闭**。PEP 收到 `AUTHZ_POLICY_EVALUATION_ERROR` 时：敏感写操作默认拒绝；对只读操作是否允许有限降级，应由明确的风险策略决定，而不是在代码中默认放行；两种路径都必须记录审计。

对敏感写操作，`ERROR` 不得被降级为 `ALLOW`，也不得把故障信息伪装成普通 `DENY`。

## 九、智能体 Harness 中的权限执行机制

权限引擎必须深度集成 Harness。否则，即使 API 接口有鉴权，模型仍可能通过工具运行时触发未授权的业务操作。

### 9.1 每次工具调用的标准流程

```
模型生成工具调用意图
        ↓
Harness 校验工具是否在当前 Agent 版本的允许清单中
        ↓
Tool Runtime 校验输入 Schema 与参数完整性
        ↓
AuthorizationService 执行权限与业务策略检查
        ↓
 ┌──────────┬──────────────┬───────────┐
 │ DENY     │ REQUIRE_APPROVAL │ ALLOW  │
 └──────────┴──────────────┴───────────┘
      ↓              ↓             ↓
   记录拒绝       创建审批单      执行工具
                     ↓             ↓
                  等待审批       保存结果
                     ↓             ↓
             审批通过后重新鉴权   写入证据
                                   ↓
                              记录审计事件
```

模型只能提出工具调用意图，不能直接决定授权结果，也不能自行把操作状态改成 `APPROVED`、`EXECUTING` 或 `SUCCEEDED`。

### 9.2 只读工具与写工具分级

建议对工具声明风险级别，但不能只依靠模型或插件清单里的风险标签。服务端还需要根据真实动作、资源类型和操作内容确定风险。

| 风险级别 | 示例             | 控制要求                  |
| ---- | -------------- | --------------------- |
| R0   | 读取公开的系统元数据     | 基础认证与权限检查             |
| R1   | 查询授权范围内的业务数据   | 数据范围过滤、必要的字段脱敏        |
| R2   | 创建草稿、生成建议      | 输入校验、审计与可撤销控制         |
| R3   | 修改业务记录、提交审批    | 强制重新鉴权、版本检查、幂等        |
| R4   | 付款、过账、签署或高影响操作 | 人工审批、职责分离、强审计；必要时多重审批 |

R0–R4 只是平台建议的风险分级，不是所有企业都适用的固定标准。企业应按业务影响、可逆性、财务额度和合规要求调整。

### 9.3 授权上下文必须绑定版本

创建任务时，Harness 应固定：

- 智能体版本 ID。
- 工具版本 ID。
- 本体版本 ID。
- 相关策略版本 ID。
- 请求人的有效身份与委托关系。
- 业务对象版本或操作摘要。

运行过程中不能只依赖创建任务时的授权结论。策略更新、用户离职、权限撤销或对象状态变化，都可能使原有授权不再适用。

### 9.4 最小化授权上下文

不要把所有员工资料、全部角色列表和完整权限配置发送给模型。Harness 应仅向当前任务提供必要的业务上下文。

模型不需要知道全部权限引擎内部实现；它只需要知道当前获准调用哪些工具、哪些操作不可执行，以及遇到权限不足时应停止、解释或请求人工介入。

## 十、审批与职责分离

审批是授权系统的一部分，不应作为 Harness 中的普通聊天步骤实现。

### 10.1 审批规则

建议将审批规则设计为可版本化的策略，包含：

- 适用的租户、组织与业务域。
- 目标资源类型与操作类型。
- 触发条件，例如金额、密级或不可逆性。
- 审批人选择规则。
- 最低审批人数。
- 是否禁止发起人审批自己的请求。
- 是否需要不同部门或不同角色联合审批。
- 审批有效期与失效条件。

### 10.2 审批流程状态

```
PENDING
   ├──→ APPROVED
   ├──→ REJECTED
   ├──→ EXPIRED
   ├──→ CANCELLED
   └──→ INVALIDATED
```

只有 `APPROVED` 可以进入后续授权复核，但这也不代表外部操作已经成功。

审批通过后，平台还应检查：

1. 审批是否仍然有效。
2. 审批人当时是否具有审批权限。
3. 操作摘要是否与审批时一致。
4. 业务对象版本是否发生变化。
5. 相关策略和审批规则是否仍然有效。
6. 执行人当前是否仍具备执行权限。

### 10.3 审批与执行之间的竞态

例如，财务主管批准了某张金额为 8,000 元的报销单，但在操作提交前，业务数据被改成 80,000 元。

如果系统只检查审批单状态，就会产生严重漏洞。

正确做法是将审批与操作摘要、业务对象版本绑定；在提交前重新读取并核验。如果关键内容发生变化，应将原审批标记为 `INVALIDATED`，重新申请审批。

### 10.4 紧急授权与紧急撤销

企业可能需要临时授权或紧急停用某个智能体。建议区分：

- 临时授权：有明确范围、授权人、原因、开始时间和到期时间。
- 紧急禁用：立即阻止指定工具、智能体版本或外部写操作继续执行。
- 恢复运行：由具备权限的人员确认风险已解除，并重新验证挂起任务。

紧急授权不能默认绕过所有禁止规则。尤其是不可逆的财务操作，应保留企业规定的职责分离和审批要求。

### 11.1 领域层与适配器分离

领域层定义授权请求、决策结果和业务规则，不直接依赖 PostgreSQL、OIDC SDK 或具体策略引擎。

适配器负责：

- 从数据库加载角色、权限和策略。
- 从可信业务服务获取资源属性。
- 调用具体策略引擎。
- 将授权决策写入持久化存储。
- 将统一授权接口集成到 API、Harness 和 ERP Adapter。

这种设计允许以后更换 OIDC 提供方、策略引擎或数据库实现，而不必重写业务模块。

### 11.2 授权服务主流程

以下代码展示服务层的基本组织方式。授权决策领域类型（`DecisionEffect`/`Decision`/`Obligation`）与请求类型（`AuthorizationRequest`）分别以 §7.1、§7.2 为唯一权威定义，本服务层**只引用、不重定义**；包名统一为 `authz`（领域层）/`authorization`（应用层）。它是结构示例，正式版本还需补齐策略快照、审计事务、缓存与超时控制。

```

package authorization

import (
    "context"
    "errors"

    authz "odap/internal/authorization/domain" // 即 §7.1 定义的 authz 领域类型
)

var ErrAuthorizationUnavailable =
    errors.New("authorization service unavailable")

type SubjectProvider interface {
    LoadAndValidate(
        ctx context.Context,
        req authz.AuthorizationRequest,
    ) error
}

type PolicyEvaluator interface {
    Evaluate(
        ctx context.Context,
        req authz.AuthorizationRequest,
    ) (authz.Decision, error)
}

type DecisionRepository interface {
    Save(
        ctx context.Context,
        req authz.AuthorizationRequest,
        decision authz.Decision,
    ) error
}

type Service struct {
    subjects  SubjectProvider
    evaluator PolicyEvaluator
    decisions DecisionRepository
}

func (s *Service) Authorize(
    ctx context.Context,
    req authz.AuthorizationRequest,
) (authz.Decision, error) {
    if req.TenantID == "" ||
        req.Subject.ID == "" ||
        req.Action == "" {
        return authz.Decision{}, errors.New(
            "invalid authorization request",
        )
    }

    if err := s.subjects.LoadAndValidate(ctx, req); err != nil {
        return authz.Decision{
            Effect:     authz.EffectDeny,
            ReasonCode: "DENY_SUBJECT_INVALID",
        }, err
    }

    decision, err := s.evaluator.Evaluate(ctx, req)
    if err != nil {
        // 评估器故障：上抛 AUTHZ_POLICY_EVALUATION_ERROR
        // （contracts/02），不得降级为 ALLOW，也不得伪装成
        // 普通 DENY。
        return authz.Decision{}, ErrAuthorizationUnavailable
    }

    if decision.Effect != authz.EffectAllow &&
        decision.Effect != authz.EffectDeny &&
        decision.Effect != authz.EffectRequireApproval {
        return authz.Decision{}, ErrAuthorizationUnavailable
    }

    if err := s.decisions.Save(
        ctx, req, decision,
    ); err != nil {
        // 决策无法可靠记录时，不允许敏感写操作继续。
        return authz.Decision{}, ErrAuthorizationUnavailable
    }

    return decision, nil
}

```

此示例特意把决策持久化作为执行前的重要步骤。正式实现还应区分“明确拒绝”和“基础设施故障”，避免把故障信息伪装成普通拒绝，导致排障困难。

另外，`LoadAndValidate` 必须从可信来源确认身份状态、租户关系与委托信息，不能仅根据请求体中的 `SubjectID` 进行判断。

## 十二、缓存、权限撤销与一致性

权限系统可以使用缓存提高性能，但不能为了降低数据库访问量而让已经撤销的权限长期有效。

### 12.1 可以缓存什么？

| 数据         | 缓存策略建议           |
| ---------- | ---------------- |
| 权限目录       | 可长时间缓存，变更时主动失效   |
| 已发布策略版本    | 按不可变版本 ID 缓存     |
| 组织树        | 使用版本号或变更事件失效     |
| 用户和成员关系    | 短期缓存，禁用和撤销时主动失效  |
| 角色绑定       | 短期缓存，角色变更时主动失效   |
| 资源业务属性     | 按资源版本或业务更新时间校验   |
| `ALLOW` 决策 | 仅对明确可缓存的操作使用短期缓存 |
| 审批状态       | 敏感操作提交前必须重新检查    |

### 12.2 缓存键

如果需要缓存授权结果，缓存键必须覆盖所有影响决策的关键维度，例如：

```
tenant_id
+ subject_id
+ membership_id
+ agent_version_id
+ resource_type
+ resource_id
+ action
+ resource_version
+ policy_version_set
+ authorization_context_digest
```

漏掉其中某个关键维度，可能导致将一个用户、一个资源或一个策略下的授权错误地复用到另一个场景。

### 12.3 权限撤销策略

建议分成三个等级：

- 普通读取：可以使用短期缓存，但必须接受明确规定的最大撤销传播延迟。
- 敏感业务修改：提交前重新鉴权，并验证业务对象版本。
- 高影响操作：执行前实时检查主体状态、审批状态、策略版本和操作摘要；关键依赖不可用时停止执行。

如果企业要求权限撤销近乎实时生效，就需要定义并验证撤销传播 SLA，而不是仅仅缩短一个缓存 TTL。可以通过版本号、事件通知和提交前复核共同实现。

### 12.4 权限变更事件

可以建立统一的权限变更事件，例如：

```
USER_DISABLED
MEMBERSHIP_REVOKED
ROLE_BINDING_CHANGED
ROLE_PERMISSION_CHANGED
POLICY_PUBLISHED
POLICY_DISABLED
AGENT_VERSION_DISABLED
TOOL_VERSION_DISABLED
```

事件处理器负责失效相关缓存、更新授权版本、通知运行时，并对正在执行的任务进行必要的复核。

对于高影响操作，不能只依赖异步事件。事件可能延迟或丢失，因此执行入口仍然要查询可信的当前状态。

## 十三、与本体驱动授权的结合

ODAP 的独特之处在于，本体不只是用于描述业务数据，也可以帮助授权引擎理解资源之间的语义关系。但需要明确：本体推理可以提供关系事实，不能自行赋予访问权限。

### 13.1 本体可以提供什么？

例如，某个企业本体可以描述：

```
Employee
  └── belongsTo → Organization

Expense
  ├── submittedBy → Employee
  ├── ownedBy → Organization
  ├── hasAmount → Money
  └── hasStatus → ExpenseStatus

Approval
  ├── approves → Expense
  └── approvedBy → Employee
```

这些关系可以帮助系统识别：

- 报销单属于哪个组织。
- 某个员工是否为申请人。
- 当前审批人与申请人是否为同一人。
- 业务对象处于哪个流程状态。
- 某项操作涉及哪些关联对象。

但最终是否允许访问，仍由权限策略决定。

### 13.2 本体推理结果的信任边界

本体运行时应向授权服务提供结构化、可追溯的事实，例如：

```
{
  "resourceType": "Expense",
  "resourceId": "EXP-10001",
  "ownerOrganization": "ORG-FINANCE",
  "submittedBy": "USER-123",
  "status": "PENDING_REVIEW",
  "ontologyVersionId": "ontology-version-id",
  "factDigest": "sha256:example"
}
```

以上仅为数据结构示例。

授权引擎应验证事实来源、对象版本和本体版本。若事实来自未经验证的模型输出，不能直接用来授予权限；如果推理结果缺失或不确定，敏感操作应拒绝或转人工处理。

### 13.3 本体变更影响授权

假设旧本体将“部门经理”定义为对本部门报销单具有审核关系，新版本修改了组织继承关系。即使角色表未变化，资源范围的语义也可能改变。

因此，本体版本应进入授权决策的依赖清单。对于涉及本体推理的策略，应：

1. 固定本体版本。
2. 记录推理所使用的事实与规则版本。
3. 在发布新本体时运行权限回归测试。
4. 对语义变更进行影响分析。
5. 在敏感操作前验证本体版本与事实是否仍然有效。

这使本体成为权限系统可追溯的语义依赖，而不是一条隐蔽的权限旁路。

## 十四、API、中间件与执行入口

建议统一实现以下服务接口，并在不同模块中复用。

| 接口                                         | 用途             |
| ------------------------------------------ | -------------- |
| `GET /api/v1/identity/me`                  | 当前用户及组织上下文     |
| `GET /api/v1/identity/permissions`         | 当前用户可见的权限摘要    |
| `GET /api/v1/authorization/decisions/{id}` | 查询授权决策详情       |
| `POST /api/v1/authorization/explain`       | 对某个资源和动作解释授权结果 |
| `GET /api/v1/admin/roles`                  | 管理角色           |
| `POST /api/v1/admin/role-bindings`         | 创建角色绑定         |
| `DELETE /api/v1/admin/role-bindings/{id}`  | 撤销角色绑定         |
| `POST /api/v1/admin/policies/{id}/publish` | 发布授权策略         |
| `POST /api/v1/admin/subjects/{id}/disable` | 禁用主体或账号        |

`authorization/explain` 只能用于受控的策略解释与排障，不能让用户提交一个虚构身份，就获得任意资源的真实授权判断。查询决策详情本身也需要权限检查。

### 14.1 Go HTTP 中间件

HTTP 中间件主要负责认证、建立可信上下文和执行基础资源权限检查。

```
func RequirePermission(
    authzService AuthorizationService,
    resourceType string,
    action string,
) func(http.Handler) http.Handler {
    return func(next http.Handler) http.Handler {
        return http.HandlerFunc(
            func(w http.ResponseWriter, r *http.Request) {
                subject, ok := SubjectFromContext(r.Context())
                if !ok {
                    http.Error(
                        w, "unauthorized",
                        http.StatusUnauthorized,
                    )
                    return
                }

                req := BuildAuthorizationRequest(
                    r, subject, resourceType, action,
                )

                decision, err := authzService.Authorize(
                    r.Context(), req,
                )
                if err != nil {
                    http.Error(
                        w, "authorization unavailable",
                        http.StatusServiceUnavailable,
                    )
                    return
                }

                switch decision.Effect {
                case Allow:
                    next.ServeHTTP(w, r)
                case RequireApproval:
                    http.Error(
                        w, "approval required",
                        http.StatusForbidden,
                    )
                default:
                    http.Error(
                        w, "forbidden",
                        http.StatusForbidden,
                    )
                }
            },
        )
    }
}
```

这是说明控制流的骨架，不是完整生产实现。正式版本需要统一错误响应、审计、请求关联 ID、超时控制和审批工作流入口。

尤其要注意：`RequireApproval` 不能只返回 HTTP 403 就结束。对于支持审批的业务接口，应由应用服务创建审批单、持久化操作摘要并返回审批资源 ID。审批流程完成后，仍需在执行入口重新授权。

### 14.2 三个强制执行位置

1. API 层：控制用户能否访问管理和业务接口。
2. Harness / Tool Runtime 层：控制智能体能否读取对象、调用工具或启动写操作。
3. ERP Adapter 层：控制外部写操作是否真正被提交。

只保护第一层是不够的，因为内部服务调用可能绕过 HTTP 中间件。对写操作，ERP Adapter 必须验证调用方服务身份、操作授权、审批绑定、操作摘要和幂等信息。

## 十五、权限引擎的测试体系

权限引擎不能只靠几个成功案例证明安全。测试必须覆盖允许、拒绝、异常、并发和撤销。

### 15.1 单元测试

- 用户有角色但没有对应资源范围时，必须拒绝。
- 用户属于正确组织，但成员关系已停用时，必须拒绝。
- 缺失关键属性时，不得默认放行。
- `DENY` 不能被普通 `ALLOW` 覆盖。
- 高风险操作命中审批规则时，必须返回 `REQUIRE_APPROVAL`。
- Agent 版本不在授权范围内时，必须拒绝调用工具。
- 策略计算失败时，敏感写操作必须失败关闭。
- 过期的临时授权不能继续生效。

### 15.2 集成测试

- OIDC 登录成功后，能够正确映射内部用户和组织。
- 外部身份被解绑或用户被禁用后，现有会话和敏感操作受到限制。
- 角色绑定撤销后，缓存不会继续长期授予旧权限。
- RLS 与应用层数据范围共同生效。
- 本体版本变化后，依赖该本体的授权策略能够识别版本变更。
- 审批摘要与执行摘要不一致时，写操作不能提交。
- Worker 重启后，恢复的任务仍然使用原来的版本清单并重新鉴权。

### 15.3 对抗性测试

建议把以下情况列为发布阻断项：

| 测试场景              | 预期结果            |
| ----------------- | --------------- |
| 浏览器伪造 `tenant_id` | 不得跨租户访问         |
| 模型要求调用未注册工具       | 拒绝              |
| 工具输入伪造资源所属部门      | 从可信来源校验，不信任输入声明 |
| 普通管理员尝试读取全部工资数据   | 根据数据权限拒绝        |
| 审批人试图批准自己的敏感操作    | 按职责分离规则拒绝       |
| 审批后修改金额再执行        | 审批失效，重新申请       |
| 用户权限在任务运行中被撤销     | 后续敏感操作被阻断       |
| 策略服务不可用           | 敏感写操作失败关闭       |
| 恶意插件伪造 Agent 身份   | 身份与签名校验失败       |
| RLS 连接池复用到另一租户    | 不得读取上一租户数据      |
| 工具返回提示词注入内容       | 不得改变服务端授权决定     |
| 智能体请求扩大委托范围       | 拒绝超出原始授权的请求     |

### 15.4 权限回归测试

每次发布新角色、策略、本体或智能体版本，都应执行权限回归测试。

例如，某个本体版本变更了“所属部门”的推理规则，系统需要验证相关员工是否因此获得了额外的数据范围。如果权限集合出现意外扩大，发布流程应阻止上线，除非经过明确的安全审核。

建议为关键场景维护一组固定的授权测试样例，记录期望结果、使用的策略版本和测试依据。策略修改后自动重放，避免后续变更无意中放宽权限。

## 十六、实施路线与验收标准

建议分五个阶段实施权限系统，先建立不可绕过的授权边界，再增加复杂的企业治理功能。

P1

身份认证与可信上下文

实现 OIDC、会话管理、内部身份映射、租户上下文与服务身份。

验收：未认证请求不能访问受保护 API，伪造租户信息不能改变授权范围。

P2

RBAC 与组织范围

实现角色、权限、成员关系、组织继承和数据范围过滤。

验收：能够验证本人、部门、组织树和租户级权限的边界。

P3

统一 PDP 与 ABAC

建立统一决策接口、可信属性提供方、策略版本和授权审计。

验收：缺失属性、策略异常和明确禁止规则均不能导致错误放行。

P4

Harness、审批与 ERP 门禁

为工具调用和 ERP 写入接入强制鉴权、审批摘要、执行前复核。

验收：智能体无法绕过权限服务直接触发未授权写操作。

P5

缓存撤销、对抗测试与运维治理

完善缓存失效、紧急禁用、权限回归测试和安全监控。

验收：权限撤销延迟有明确指标，关键安全测试全部通过。

具体工期应由团队规模和企业现有 SSO、组织数据与审批系统的成熟度决定。对于第一版，建议优先保证身份可信、拒绝策略可靠、工具入口不可绕过，而不是先追求复杂的可视化策略编辑器。

### 16.1 第一版必须达到的验收标准

- 所有受保护的 API、工具调用和 ERP 写操作都有服务端授权检查。
- 未认证、越租户、缺失关键属性和策略故障不会导致敏感操作被放行。
- 授权决策可以追溯到请求主体、资源、动作和策略版本。
- 高风险审批绑定确定的操作摘要，并在提交前重新验证。
- 权限撤销能够影响运行中的任务，而不只影响新建任务。
- 本体和智能体版本固定，版本变更可以触发权限回归测试。
- 管理员权限和业务数据访问权限相互独立。
- 所有关键授权失败和高风险放行都有审计记录。

### 16.2 能力裁剪：哪些进 MVP，哪些延后

按首版价值与安全边界依赖关系，对本篇部分能力做显式裁剪：

| 能力 | 处置 | 理由 |
| --- | --- | --- |
| `Obligations`（决策附加义务：字段脱敏、只读、双人复核） | **延后至 P4** | MVP 阶段脱敏由字段级访问控制与 §9.2 风险分级覆盖；义务框架需与 §6.3 JSON DSL 同步演进，提前引入只会得到空壳 |
| `POST /api/v1/authorization/explain` | **延后至 P5** | 排障价值高但不构成安全边界；MVP 先用 `GET /api/v1/authorization/decisions/{id}` 查询决策记录满足追溯 |
| 服务间 mTLS | **延后至 P5** | 私有化单网络平面内先以短期服务凭证 + 网络隔离兜底；多节点与跨机房部署前再上 mTLS，避免证书运维拖慢 MVP 交付 |
| §8.1 理由代码（17 个） | **MVP 保留 10 个**：`ALLOW_ROLE_SCOPE`、`DENY_UNAUTHENTICATED`、`DENY_SUBJECT_DISABLED`、`DENY_TENANT_MISMATCH`、`DENY_PERMISSION_MISSING`、`DENY_RESOURCE_SCOPE`、`DENY_POLICY_EXPLICIT` 及三个 `REQUIRE_APPROVAL_*`；其余 7 个（`ALLOW_POLICY_MATCH`、`DENY_AGENT_CAPABILITY`、`DENY_TOOL_NOT_REGISTERED`、`DENY_ATTRIBUTE_UNTRUSTED`、`DENY_POLICY_UNAVAILABLE`、`DENY_APPROVAL_INVALID`、`DENY_PAYLOAD_CHANGED`）**延后至 P4** | 语义已定义、随时可补；首期调用方少，逐个接入的边际价值低，随 Harness 工具链完善后补齐 |
| 会话撤销传播 SLA 度量看板 | **延后至 V1.5** | §4.6 的 `subject_version` 机制 MVP 即实现（安全正确性不依赖度量）；SLA 看板与告警属于运营增强 |

裁剪不改变安全边界：所有延后项都不允许把"未实现"变成"默认放行"——对应路径在 MVP 必须显式拒绝或转人工（§15.3 对抗性测试覆盖）。

## 十七、本篇最终架构决策

建议将以下决策作为 ODAP 权限系统的工程基线。

| 设计事项  | 推荐决策                                        |
| ----- | ------------------------------------------- |
| 身份认证  | 优先 OIDC/SSO，本地管理员仅用于受控初始化和恢复                |
| 授权模型  | RBAC + ABAC + 业务策略                          |
| 决策架构  | 统一 PDP，多个 PEP                               |
| 主体模型  | 人、服务、智能体、系统身份分离                             |
| 智能体授权 | 用户权限、Agent 能力、工具权限与委托范围取交集                  |
| 敏感操作  | 执行前重新鉴权，必要时人工审批                             |
| 本体与权限 | 本体提供可追溯语义事实，策略引擎决定是否授权                      |
| 缓存    | 可缓存不可变策略与低风险数据，敏感操作实时复核                     |
| 故障策略  | 关键授权条件无法验证时，敏感操作默认拒绝                        |
| 审计    | 记录主体、资源、动作、决策、策略版本与执行关联                     |
| 执行门禁  | API、Harness/Tool Runtime、ERP Adapter 三层强制执行 |

这套权限系统最重要的价值，是把智能体从“能够调用工具的模型”，变成“在企业授权边界内承担业务任务的执行主体”。

它不仅要限制模型做什么，还要能够解释为什么允许、为什么拒绝、需要谁审批，以及权限发生变化后如何停止或恢复任务。
